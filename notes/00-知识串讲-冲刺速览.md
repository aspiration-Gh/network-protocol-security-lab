## 0.1 全课骨架：五章其实是一条因果链

「实体（entity）」是每一层上的活动元素，包括实现该层功能的全部硬件（网卡）与软件（进程）。「对等实体（peer entity）」指源节点与目标节点上处于同一层次、完成相同功能的实体——只有对等实体之间才谈得上"协议"。这条定义是分层安全分析的起点：**攻击总是发生在某一对等实体之间的通信语义上，防御也必须在同一层或其上层补齐该语义**。

协议三要素决定了攻击面：语法（syntax）规定数据与控制信息的结构格式，语义（semantics）规定发什么控制信息、做什么动作、回什么响应，同步（timing）规定事件顺序。用信封类比：信封外是控制信息、信封内是数据；**格式由语法定义，格式的含义由语义规定，投递先后由同步规定**。于是三类典型攻击正好一一对应：改格式（伪造/畸形报文）、改含义（重定向、欺骗）、改顺序（重放、乱序插入）。

### 0.1.1 安全目标与协议的三条原罪

计算机网络安全是用计算机、密码学、信息安全与通信网络管理技术，保护信息的**保密性、完整性、可用性、可控性、不可否认性**。狭义上指信息资源与网络系统资源不受有害因素威胁危害；广义上还包括与之相关的技术、管理和过程控制。

课程把"协议为什么不安全"归结为三条，这是全课的总纲，任何一道"分析某攻击成因"的题都可以往这三条上靠：

| 原罪 | 具体表现 | 直接导致的攻击 |
|---|---|---|
| 设计初衷是异构网互联，未考虑安全 | 各层协议开放、报文格式公开、默认信任 | 嗅探、伪造、畸形报文、分片滥用 |
| 缺乏验证通信双方真实性的有效认证机制 | 源地址不校验、ARP 无状态、DNS 无签名 | IP 欺骗、ARP 欺骗、DNS 欺骗、会话劫持 |
| 缺乏保密机制 | 载荷明文、凭据明文 | 口令窃取、数据泄露、中间人 |

### 0.1.2 分层安全速览（背这张表就够）

| 层 | 对应 OSI | 主要风险 | 主要防护 |
|---|---|---|---|
| 网络接口层 | 物理层 + 数据链路层 | 设备损坏与老化、意外故障、信息探测与窃听 | 物理隔离、VLAN、VPN、加密、流量监控与过滤 |
| 网络层 | 网络层 | IP 地址欺骗、ICMP 攻击、IP 分片威胁、数据报篡改与重放 | IPv6 简化首部并内建安全设计、IPsec 提供加密与认证 |
| 传输层 | 传输层 | TCP 泛洪、TCP 重置、TCP 会话劫持；UDP 泛洪、UDP 反射放大 | SSL 起源、TLS 提供身份验证、完整性检验、保密性 |
| 应用层 | 应用层 | 缓冲区溢出、SQL 注入、XSS、数据泄露 | 身份认证、加密、应用层防火墙、数据脱敏备份、零信任、新增安全协议 |

网络接口层的监听之所以可行，是因为「分组嗅探器（Packet Sniffer）」把网卡置为**混杂方式（promiscuous mode）**：网卡不再按目的 MAC 过滤，而是接收所有进入本接口的 MAC 帧。正常网卡只收"目的地址是我/广播/组播"的帧，混杂模式取消了这个过滤器——这是"设计上默认共享介质、默认互信"的直接后果，也是后面 ARP 欺骗、会话劫持能够落地的前提。

安全防范有四个支柱：法律（许多情况下作用大于技术）、教育（提升安全意识与技能）、管理（保护信息资产免受威胁）、技术（策略 + 工具）。答题时若问"如何治理"，四者要齐；只答技术会被扣分。

## 0.2 网络接口层：从封装到 MAC 泛洪

### 0.2.1 链路层的三项基本功

| 功能 | 做法 | 安全含义 |
|---|---|---|
| 封装成帧 | 在一段数据前后加首部和尾部，构成帧 | 首尾标志可被伪造，产生帧边界混淆 |
| 透明传输 | 无论何种比特组合都能在链路上传，用字节填充或字符填充实现 | 填充/转义处理不当可构造绕过检测的载荷 |
| 差错控制 | 提供比特差错检测（FCS） | 只有检错、没有纠错与认证，改内容后重算校验即可通过 |

关键结论：链路层的帧校验和只解决"传输是否出错"，**不解决"是不是你发的"**。所以任何在链路层做完整性校验来防篡改的想法都是错的，必须靠上层密码学手段。

### 0.2.2 PPP 家族：一个协议字段值就是一张身份证

PPP 把不同网络层协议的数据统一装进自己的信息字段，靠 PPP 首部中的**协议字段**区分内部载荷是谁。这个字段是全章最好的记忆锚点：

| 内部协议 | PPP 协议字段值 | 作用 | 关键代码/取值 |
|---|---|---|---|
| LCP | 0xC021 | 链路的配置、维护与终止 | 链路建立阶段协商参数 |
| PAP | 0xC023 | 口令认证 | 1 认证请求、2 认证确认、3 认证未确认 |
| CHAP | 0xC223 | 挑战—应答认证 | 1 挑战、2 应答、3 成功、4 失败 |
| IPCP | 0x8021 | 协商网络层参数（IP 地址等） | 只使用代码 1–7，其余代码不被承认并触发 Code-Rejects |

> 补充：PPP 帧的固定骨架为 标志 0x7E、地址 0xFF、控制 0x03、协议 2 字节、信息、FCS、标志，其中 0xFF/0x03 是"所有站点均为目的、无编号帧"的历史默认值。

PPP 的工作流程共 5 个阶段，顺序不可乱：

1. **链路不可用阶段**——物理层未就绪，无任何 PPP 帧。
2. **链路建立阶段**——LCP 协商最大接收单元、认证协议、压缩等参数。
3. **认证阶段**——按协商结果执行 PAP 或 CHAP；认证失败直接进入终止。
4. **网络层协议阶段**——由 IPCP 分配/协商 IP 地址，开始承载网络层报文。
5. **链路终止阶段**——LCP 终止请求，释放链路。

PAP 与 CHAP 的差别是必考点，本质是"口令是否在链路上出现、是否可被重放"：

| 对比项 | PAP | CHAP |
|---|---|---|
| 握手次数 | 两次（请求—确认） | 三次（挑战—应答—成功/失败） |
| 传输内容 | 用户名 + 口令 | 用户名 + 对"挑战值+口令"的散列结果 |
| 口令是否明文过线 | 是 | 否 |
| 抗重放 | 无（抓到口令即可复用） | 有（挑战值每次随机，散列结果一次性） |
| 抗穷举 | 无 | 有限（靠挑战值变化） |

### 0.2.3 L2TP：在不可靠的 UDP 上跑"可靠的控制"

L2TP 的两个组件是接入集中器（L2TP Access Concentrator, LAC）与网络服务器（L2TP Network Server, LNS），二者是隧道的两个端点，互为对等体，在不同网络中协商建立隧道以转发 PPP 报文。它是**端口号为 1701 的应用层协议**，却承担着"搬运二层帧"的职责——这个错位本身就是理解它的关键。

它把消息分成两类，走两个逻辑通道：

| 通道 | 承载 | 可靠性 |
|---|---|---|
| 数据通道 | 数据消息（PPP 载荷） | 不保证可靠传输 |
| 控制通道 | 隧道与会话的协商、维护、终止消息 | 保证可靠传输（序号 + 确认 + 重传） |

工作流程 5 步：建立控制连接（Start Control Connection, SCC）→ 建立会话 → 数据通信 → 终止会话 → 终止控制连接。SCC 阶段 LAC 与 LNS 协商控制连接参数，并**利用 CHAP 的"三次握手"互相验证对方身份**——这是 L2TP 唯一的认证环节，也是它被攻击的主要缺口（CHAP 只验身份不加密载荷）。

封装是层层加壳，顺序不能记反：

```
+---------------------------+
|  新的 IP 首部             |  为了在 IP 网上路由这个 UDP 包
+---------------------------+
|  UDP 首部（目的 1701）    |
+---------------------------+
|  L2TP 首部                |
+---------------------------+
|  PPP 报文（首部+载荷）    |
+---------------------------+
```

即：LAC 收到 PPP 报文后，**先封 L2TP 头，再封 UDP 头，最后加一个新 IP 头**。

### 0.2.4 以太网：地址、帧长与那两个"为什么"

MAC 地址 = 硬件地址 = 物理地址，6 字节 48 位。前 3 字节由 IEEE 的注册管理机构 RA 分配给厂家（如 00-00-0C 为 CISCO、00-18-82 为 Huawei），后 3 字节由厂家自行指派，称扩展标识符，必须保证出厂适配器不重复。48 位空间远未耗尽，至今不存在地址枯竭问题——这与 IPv4 的 32 位形成鲜明对照，是常考对比。

以太网 V2 的 MAC 帧由六个字段构成（前导码 + 五个实际字段）：

| 字段 | 长度 | 作用 | 安全相关性 |
|---|---|---|---|
| 前导码 | 8 字节 | 收发同步 | 可被用于物理层干扰 |
| 目的地址 | 6 字节 | 目的主机 MAC | 可伪造，是 MAC 泛洪/欺骗的入口 |
| 源地址 | 6 字节 | 源主机 MAC | 不校验真实性，可任意填写 |
| 类型 | 2 字节 | 指明上层协议（0x0800 IP、0x0806 ARP、0x8863/0x8864 PPPoE） | 决定解封装路径，是"类型混淆"攻击点 |
| 数据 | 46–1500 字节 | 上层数据 | 载荷明文 |
| FCS | 4 字节 | 帧检验序列 | 仅检错，不防篡改 |

两个"为什么"必须会推：

- **为什么有效帧 ≥ 64 字节**：CSMA/CD 要求最短帧的发送时间 ≥ 争用时隙 2τ，否则发送方在帧发完后冲突才回来，无法判定是谁冲突。10 Mbps 以太网规定 2τ = 51.2 μs，故最短帧长 = 10 Mbps × 51.2 μs ÷ 8 = 64 字节。**结论：64 字节是冲突检测的时间约束，不是安全约束。**
- **为什么有效帧 ≤ 1518 字节**：1518 = 14（头）+ 1500（数据）+ 4（FCS）。上限来自上世纪七八十年代接收缓存内存昂贵，属于成本约束。**结论：1500 字节的 MTU 是历史成本决定的，它直接决定了 IP 分片的存在，从而派生出 0.3 节的分片攻击。**

### 0.2.5 PPPoE 与交换机自学习

PPPoE 分两阶段：

1. **发现阶段**——客户端在广播网络上发发现报文寻找可用的 PPPoE 服务器，建立唯一的 PPPoE 会话 ID，随后与服务器初始化通信。
2. **会话阶段**——建立点对点连接，交换认证信息与会话参数，之后传输数据。

阶段靠以太网帧类型字段区分：**0x8863 = 发现阶段，0x8864 = 会话阶段**。PPPoE 数据包封装在以太网帧的数据字段中。

交换机自学习算法三步：初始化（地址表为空）→ 自学习（收到帧就把"源 MAC—入端口"写入表）→ 自动更新（表项老化刷新）。它成立的前提是"**源 MAC 一定可信**"，这正是 MAC 泛洪攻击的着力点。

MAC 泛洪（MAC flooding）的机制链条：

| 步骤 | 动作 | 交换机状态 |
|---|---|---|
| 1 | 攻击者持续发送大量**源 MAC 随机**的帧 | 逐个学习，表项迅速填满 |
| 2 | 地址表超出容量 | 无法再学习新地址 |
| 3 | 未知目的 MAC 的帧无表项可查 | 退化为集线器模式，向所有端口广播 |
| 4 | 所有端口都能收到他人流量 | 攻击者嗅探成功、网络效率下降、敏感数据泄露 |

注意它和 ARP 欺骗的分工：泛洪让交换机"变傻"（被迫广播），欺骗让主机"变瞎"（缓存被污染）。二者常配合使用。

防御三件套：**端口安全**（限制每端口可学习的 MAC 数量，超限则告警/关闭端口）、**动态 ARP 检测（DAI）**（校验 ARP 报文的 IP-MAC 绑定，防伪造 ARP）、**静态 MAC 地址绑定**（端口与特定 MAC 强关联，阻断未授权设备）。

## 0.3 网络层：欺骗、分片与隧道

### 0.3.1 IP 的职责与两代首部

IP 基于**无连接的"尽力而为"**传输，主要功能六项：寻址和转发、数据报格式定义、分片和重组、错误处理、最佳路径选择、数据报路由。

| 对比项 | IPv4 | IPv6 |
|---|---|---|
| 地址长度 | 32 位 | 128 位 |
| 地址数量 | 约 43 亿，接近耗尽 | 大于 3.4×10^38 |
| 首部字段数 | 14 个（固定部分 20 字节 + 可变选项） | 8 个 |
| 安全设计 | 无内建安全 | 简化首部、增加安全性设计，配合 IPsec |

IPv4 首部由固定部分（20 字节，必有）与可变部分（选项，长度可变）组成。安全相关的字段只有几个，其余是转发用：**源 IP 地址**（可伪造，一切欺骗的根）、**标识/标志/片偏移**（分片三件套，分片攻击的根）、**协议字段**（1 ICMP、6 TCP、17 UDP、50 ESP、51 AH）、**首部校验和**（只覆盖首部，不覆盖数据）。

分片计算是必考计算题，套路固定：

> 例题：总长 3820 字节、20 字节固定首部，链路要求每片不超过 1420 字节。

| 步骤 | 计算 | 结果 |
|---|---|---|
| 数据部分 | 3820 − 20 | 3800 字节 |
| 每片可载数据 | 1420 − 20 = 1400，且必须是 8 的整数倍 | 1400 字节 |
| 片数 | 3800 ÷ 1400 上取整 | 3 片 |
| 各片数据长 | 1400 / 1400 / 1000 | — |
| 各片总长 | 1420 / 1420 / 1020 | — |
| 片偏移（单位 8 字节） | 0 / 1400÷8=175 / 2800÷8=350 | 0、175、350 |
| MF 标志 | 1 / 1 / 0 | 最后一片 MF=0 |

### 0.3.2 源地址欺骗与分片攻击

互联网设计之初**对分组的源 IP 地址不做合法性验证**，因此伪造源地址的成本近乎为零。攻击者构造带伪造源 IP 的报文发往目标，目标按信任关系或正常流程处理，并把响应发给被伪造的地址。它的定位是"基础能力"：后续的数据注入、连接劫持（TCP 会话劫持）、DNS 污染都要以它为前置条件。

防御现状：真实地址、真实身份等技术标准出现后有所缓解，但彻底解决仍需持续投入。答题要点是"**入口过滤 + 源地址验证**"这一方向，而不是指望端到端修补。

分片攻击的成因是"**先分片、再重组**"的机制：分片发生在源主机或中间路由器，重组往往在目的端发生，中间节点不保存分片状态。据此产生两类效果：

| 类型 | 机理 | 后果 |
|---|---|---|
| 拒绝服务 | 大量不完整分片涌入，接收端为重组预分配缓存并启动定时器 | 重组缓存/CPU 耗尽，正常分片无法重组 |
| 污染攻击 | 利用**重叠分片**，后到的分片覆盖先到分片中的同一段偏移 | 篡改重组后的内容，绕过只检查单片的安全设备 |

防御：TCP 有 MSS（Maximum Segment Size）选项，可通过调整 MSS 适配路径 MTU 以避免分片；UDP 没有 MSS，只能在应用层限制报文大小、在中间设备做分片归一化/丢弃异常分片。核心思想是**能不分片就不分片**。

### 0.3.3 ARP：无状态、无认证的地址翻译

ARP 的作用是把网络层 IP 地址解析为链路层硬件地址。关键字段：

| 字段 | 长度 | 作用 | 安全相关性 |
|---|---|---|---|
| 目的地址 / 源地址 | 6 字节 | 以太网目的/源 MAC；目的为全 1 即广播地址，电缆上所有接口都要接收 | 广播使请求可被全网监听 |
| 帧类型 | 2 字节 | ARP 请求或应答取 0x0806 | — |
| 硬件类型 | 2 字节 | 网络接口类型，以太网为 1 | — |
| 协议地址长度 / 硬件地址长度 | 各 1 字节 | 指明地址字段字节数 | 可构造畸形长度 |
| 操作码 | 2 字节 | 1 请求、2 应答 | 应答可被主动伪造 |

工作流程（四步）：

1. 主机 A 要解析的 IP 若在同一子网，先查本机 **ARP 高速缓存**。
2. 命中则直接取出硬件地址写入 MAC 帧发送。
3. 未命中则 ARP 进程在本局域网**广播**发送 ARP 请求分组。
4. 收到 ARP 响应后，把"IP—硬件地址"映射写入 ARP 高速缓存。

ARP 欺骗（ARP spoofing，又称 ARP 污染 ARP poisoning）的成因有三条：**无状态**（收到应答就更新缓存，不校验是否请求过）、**无认证**（不验证应答方身份）、**可主动应答**（不必等请求）。效果是让攻击者成为中间人（Man-in-the-Middle, MITM），获取甚至篡改局域网数据包，同时可迫使受害主机无法正常接收报文（把网关 MAC 指向不存在的地址即断网）。

### 0.3.4 ICMP：辅助协议被做成三种武器

ICMP 用于更有效地转发 IP 数据报、提高交付成功机会，允许主机或路由器报告差错与异常，也常用于测试网络。它**不直接交给链路层，而是先封装成 IP 数据报**，IP 首部协议字段值为 1。ICMP 是 IP 的组成部分、起辅助作用，但报文作为载荷携带在 IP 数据报中，从这个角度它"看起来像上层协议"——这个双重身份是 ICMP 隧道能绕过检测的根源。

ICMP 首部前 4 字节格式统一（类型、代码、校验和），接着 4 字节内容与类型有关（如 Echo 的标识符与序号、重定向的网关地址），数据字段长度取决于类型。

| 攻击 | 原理 | 关键条件 | 防御 |
|---|---|---|---|
| ICMP 重定向攻击 | 伪装成路由器发送虚假 ICMP 重定向报文，迫使受害主机修改路由表中默认网关或特定主机路由，把流量导向攻击者控制的节点以嗅探或假冒 | 主机信任重定向报文 | 主机拒绝接受重定向（关闭 accept_redirects）、使用静态路由、边界过滤 ICMP 重定向 |
| ICMP 隧道攻击 | 把数据封装在 ICMP 消息中传输，利用"数据部分本无意义"这一点替换为需要的数据并修正校验和 | 防火墙放行 ICMP | 限制 ICMP 出网、检测载荷长度与内容异常、只允许必要类型 |
| ICMP Flood | 用 Echo 请求/响应及其他类型（Destination Unreachable、Time Exceeded）大量发送伪造消息，耗尽带宽、CPU 或内存 | 无速率限制 | 限速/流量清洗、关闭对外 ICMP 响应、Anycast 分散 |

ICMP 隧道值得多记一句：正常 Ping 的数据部分是系统默认生成的、无实际含义的内容；攻击者把它换成指令或文件分片，再重算校验和，于是"看起来完全正常的 Ping"就成了双向信道。IDS 若只按协议类型放行，形同虚设。

### 0.3.5 IPsec：网络层唯一成体系的答案

IPsec 是一套协议包，含三个主要协议：

| 协议 | 提供的能力 | 不提供 |
|---|---|---|
| AH（IP Authentication Header，认证包头） | 信息源验证 + 完整性保证 | 不提供保密性 |
| ESP（IP Encapsulating Security Payload，封装安全负载） | 加密保证（亦可附带认证） | 单独使用时对 IP 首部无认证 |
| IKE（Internet Key Exchange） | 双方交流时的共享安全信息（密钥协商） | 不承载业务数据 |

两种工作方式，区别只在"保护范围"：

```
传输模式（Transport）:
[ 原 IP 首部 ][ IPsec 首部 ][   传输层报文   ][ IPsec 尾部 ]
               保护范围：传输层报文

隧道模式（Tunnel）:
[ 新 IP 首部 ][ IPsec 首部 ][ 原 IP 首部 ][ 传输层报文 ][ IPsec 尾部 ]
               保护范围：整个原始 IP 数据报
```

| 对比项 | 传输模式 | 隧道模式 |
|---|---|---|
| 是否新增 IP 首部 | 否 | 是 |
| 保护对象 | 传输层报文（载荷） | 整个原始 IP 数据报，含原源/目的地址 |
| 典型场景 | 主机到主机 | 网关到网关（VPN） |
| 是否隐藏真实地址 | 不隐藏 | 隐藏 |

AH 首部字段：下一首部、载荷长度、保留、安全参数索引（SPI）、序列号、认证数据（ICV）。ESP 字段：SPI、序列号、载荷数据、填充、填充长度、下一首部、认证数据。二者共有 SPI（标识安全关联）与序列号（防重放）。

IPsec 能同时挡三类攻击，这段是标准答案模板：

1. 攻击者截获安全数据报，只要不知密钥，**只能看到首部的源/目的 IP，看不懂载荷含义**——保密性。
2. 攻击者删除载荷中若干字节，**接收端完整性验证不通过，直接丢弃**——完整性。
3. 攻击者尝试重放，**由于使用了有效序号，重放不成功**——抗重放。

## 0.4 传输层：连接状态机如何被滥用

### 0.4.1 端口与两种传输服务

端口号 0–65535，由 IANA 分配管理以保证全网统一识别。

| 类别 | 范围 | 分配方式 | 特点 |
|---|---|---|---|
| 熟知端口（系统端口） | 0–1023 | IANA 分配给常用应用层协议 | 固定不变，扫描首选目标 |
| 登记端口 | 1024–49151 | IANA 分配给相对知名的应用/服务 | 需注册，如 3306、3389 |
| 临时端口 | 49152–65535 | 操作系统动态分配 | 客户端发起连接时临时使用，通信结束释放 |

必背端口：FTP 21/20、SMTP 25、DNS 53、DHCP 67/68、HTTP 80、HTTPS 443；MySQL 3306、SQL Server 1433、RDP 3389、Redis 6379、Oracle 1521。

三条容易漏的端口性质：**端口号只具有本地意义**（只用于标识本机协议栈中的应用进程）；**不同计算机上的相同端口号互不相关**；**TCP 与 UDP 的端口号空间相互独立**。因此"TCP 53 和 UDP 53 是两个不同的监听"。

| 对比项 | TCP | UDP |
|---|---|---|
| 连接 | 面向连接，先建立、后传输、再释放 | 无连接，直接发 |
| 可靠性 | 可靠（确认、重传、排序、流量控制） | 不可靠，尽力而为 |
| 实现复杂度 | 高，首部大，占用处理机资源多 | 低，首部小 |
| 典型攻击 | SYN 泛洪、RST 攻击、会话劫持 | UDP 泛洪、反射放大 |

### 0.4.2 TCP 首部与六个标志位

TCP 报文段分首部与数据两部分，**TCP 的全部功能都体现在首部各字段中**。首部固定 20 字节：源端口 2、目的端口 2、序号 4、确认号 4、数据偏移 4 位、保留 6 位、六个标志位、窗口 2、校验和 2、紧急指针 2，其后为选项。

| 标志位 | 置 1 的含义 |
|---|---|
| URG 紧急 | 紧急指针字段有效，报文段含紧急数据应尽快传送，位置由紧急指针给出 |
| ACK 确认 | 确认号字段有效 |
| PSH 推送 | 发送方置 1 则不受发送窗口限制立即发送；接收方置 1 则不在接收缓冲区排队，尽快交付应用进程 |
| RST 复位 | 连接出现严重差错（主机崩溃等），必须释放连接后重建 |
| SYN 同步 | 这是一个连接请求或连接接收报文 |
| FIN 终止 | 发送方数据已发完，要求释放连接 |

TCP 连接的端点叫套接字（socket，又称插口）：socket = (IP 地址 : 端口号)；一条 TCP 连接由两个端点唯一确定，即 TCP 连接 ::= {socket1, socket2} = {(IP1:Port1), (IP2:Port2)}。**这个四元组就是所有"劫持/伪造"类攻击必须凑齐的四个值**，记住这一点，后面三种攻击的防御逻辑自然通。

> 补充：三次握手为 SYN → SYN+ACK → ACK；四次挥手为 FIN → ACK → FIN → ACK，等待 2MSL 后关闭。连接未完成握手时处于半连接（Half-Open）状态。

### 0.4.3 三种 TCP 攻击：一条主线，三种用法

**（1）TCP SYN 泛洪（SYN flooding）**

```
伪造源IP的Client            Server
    SYN  ----------------->  分配 TCB，置 SYN_RCVD（半连接）
    <--------------- SYN+ACK  等待 ACK
    （不回 ACK）              超时重传，占用 backlog 直至 SYN Timeout
```

| 步骤 | 动作 | 目的 |
|---|---|---|
| 1 | 伪造大量不同 IP 地址，以这些地址发大量 TCP 连接请求 | 让每个半连接看起来来自不同客户 |
| 2 | 服务器为每个 SYN 分配缓存等资源并回 SYN+ACK | 消耗内存与表项 |
| 3 | 攻击者不响应 ACK | 连接停留半连接，超时重传进一步放大消耗 |
| 4 | 半连接数超过系统上限 | 服务器拒绝所有新连接请求，正常客户无法接入 |

成因：TCP 在**收到 SYN 后、验证对方可达之前就分配资源**（状态机把"未验证的对等实体"当成合法请求）。防御：SYN Cookie（不预分配，把状态编码进序列号）、缩短 SYN Timeout、增大 backlog、SYN 代理/清洗设备、源地址验证。

**（2）TCP RST 攻击**

RST 置 1 可强制关闭一条连接。C 伪造 RST 发给 B 时，必须保证**端口一致**且**RST 的序列号落在 B 的接收窗口之内**；B 收到后认为来自 A 的连接有错误，丢弃该连接缓冲区上所有数据并强制关闭。

| 攻击者位置 | 获知信息的方式 |
|---|---|
| 与受害者同一内网 | 嗅探或欺骗，直接拿到 A 的 IP、端口与 A-B 的序列号 |
| 处于不同网络 | 伪造大量 RST，随机猜测端口与序列号（盲攻击，靠带宽撞概率） |

成因：TCP 只在建链时校验一次身份，之后仅凭四元组 + 序列号识别连接；序列号空间若可预测，窗口校验就等于没有。防御：加密（TLS/IPsec）使攻击者无法获知序列号、ISN 强随机化、缩小接收窗口、入口过滤防伪造源。

**（3）TCP 会话劫持（TCP session hijacking）**

攻击流程：

1. 攻击者截获客户端与服务器之间的 TCP 报文，取得四元组与当前序列号。
2. 据此伪造 TCP 报文发给服务器。
3. 若服务器**先收到伪造报文**且序列号在接收窗口内，就把它当作合法数据接受（认证"成功"）。
4. 服务器将 TCP 会话连接至攻击者主机，此后数据经由第三方攻击者中转。
5. 攻击者反向利用从服务器获得的连接信息与被攻击客户端建立连接，完成双向劫持，而通信双方毫无察觉。

与 RST 攻击的区别一句话：**RST 是"拆台"，劫持是"顶替"**。防御：全链路加密、序列号随机化、交换机端口隔离 + DAI 抑制嗅探、应用层二次认证（如重认证、绑定会话指纹）。

### 0.4.4 UDP、QUIC 与放大攻击

UDP 首部仅 8 字节：源端口 2、目的端口 2、长度 2、校验和 2。计算校验和时要在前面临时加 12 字节**伪首部**（源 IP 4、目的 IP 4、第三个字段全 0、第四个字段 17 表示封装它的 IP 数据报协议字段为 17、UDP 长度 2）。伪首部不是真正的首部，只是校验和计算用的临时结构——它把 IP 层信息纳入校验范围，但仍不含任何认证能力。

QUIC（Quick UDP Internet Connection）是 Google 于 2013 年推出的传输协议，整合了 TCP 的可靠性与 UDP 的速度效率，四个卖点：

| 特性 | 含义 |
|---|---|
| 建立连接低时延 | 减少握手往返（0-RTT/1-RTT 恢复） |
| 改进的拥塞控制 | 可插拔拥塞控制，避免队头阻塞 |
| 加密认证 | 传输层默认加密，抵御明文注入 |
| 连接迁移 | 换网络不断连（TCP 换网必须重连） |

两种 UDP 攻击要分清"直接"与"借刀"：

| 攻击 | 机制 | 特征 |
|---|---|---|
| UDP 泛洪 | 僵尸网络向目标发大量伪造 UDP 报文，一般是大包且速率极高（通常以 DDoS 形式） | 直接耗尽目标链路带宽，造成链路拥塞甚至网络瘫痪 |
| UDP 反射放大 | 以 Memcached 为例：向服务器 UDP 11211 端口发**伪造源 IP 的小字节请求**，服务器产生数万倍大小的响应，全部发回被伪造的源地址（即攻击目标） | 间接放大，攻击者带宽消耗极小 |

反射放大的两个必要条件必须能背出来：**协议无需握手即可用伪造源发起请求**（UDP 天然满足）、**响应远大于请求**（放大倍数 = 响应字节 / 请求字节）。防御：关闭不必要的 UDP 服务与开放解析器、BCP38 入口过滤、响应速率限制。

### 0.4.5 SSL/TLS：夹在两层之间的安全子层

SSL 位于应用层与传输层之间。应用层数据在传输前**先封装进 SSL 报文，再把 SSL 报文封装进 TCP 报文**。它在传输层之上补齐了三项服务：身份验证、完整性检验、保密性。

SSL 记录协议是所有数据的唯一出口，五步固定：

1. 把来自上层协议的数据进行分组；
2. 对每个分组进行压缩；
3. 计算压缩数据的 MAC 值，放置在尾部；
4. 加密"压缩数据 + MAC 值"；
5. 在密文上增加 SSL 头。

注意第 3、4 步的顺序：**先 MAC 后加密**（MAC-then-Encrypt），这也是后来 TLS 1.3 改为 AEAD 的原因——先加密再认证的构造在实现上更容易出错。

## 0.5 应用层：五组协议的认证与明文缺陷

### 0.5.1 协议—端口总表

| 中文名 | 协议 | 端口 | 用途 |
|---|---|---|---|
| 域名系统 | DNS | 53 | 域名转 IP，互联网域名解析的基础服务 |
| 超文本传输协议 | HTTP | 80 | 从服务器传输超文本到本地浏览器 |
| 简单邮件传输协议 | SMTP | 25 | 发送电子邮件 |
| 邮局协议 | POP3 | 110 | 从邮件服务器接收邮件 |
| 因特网邮件访问协议 | IMAP | 143 | 接收、读取和管理电子邮件 |
| 动态主机配置协议 | DHCP | 67（服务器）/ 68（客户端） | 自动分配 IP 地址 |
| 文件传输协议 | FTP | 20（数据）/ 21（控制） | 网络文件传输 |

### 0.5.2 DNS：四类服务器、两种查询、五类攻击

域名服务器按功能分四类：**根域名服务器、顶级域名服务器、权限域名服务器、本地域名服务器**（前三者构成层次树，本地服务器是递归入口）。

查询模式的分工是考点：

```
主机 --递归--> 本地域名服务器 --迭代--> 根 --> 顶级 --> 权限
        (一次问到底)              (每次只给下一个该问谁)
```

| 查询方式 | 责任 | 负担 |
|---|---|---|
| 递归查询 | 被查询服务器负责给出最终答案 | 负担大 |
| 迭代查询 | 被查询服务器只返回"下一步去问谁" | 负担小 |

因此实际部署取折中：**从请求主机到本地域名服务器的查询是递归查询，其余查询是迭代查询**。

DNS 报文含查询报文与响应报文，**前六个字段长度相同**：标识、标志、问题数、回答数、授权数、附加数（首部共 12 字节）；靠"标志"字段第一位区分，取值 0 为查询报文，否则为响应报文。

| 攻击方式 | 攻击原理 | 攻击后果 |
|---|---|---|
| DNS 欺骗 | 修改 DNS 缓存、劫持 DNS 请求 | 网络钓鱼、信息窃取 |
| DNS 隐蔽信道 | 利用 DNS 数据包封装信息 | 发送恶意指令、窃取隐私信息 |
| DNS DDoS 攻击 | 直接耗尽服务器带宽资源 | 丧失网络服务能力 |
| DNS 反射放大攻击 | 间接耗尽服务器带宽资源 | 丧失网络服务能力 |
| 恶意 DGA 域名 | 使用域名生成算法批量生成恶意域名 | 大量恶意域名存在，破坏安全性 |

防护两条线：

- **加密认证**：传统开放式解析缺乏数据真实性与完整性保护，易受欺骗；DNSSEC、DoT、DoH 可增强安全性与可靠性。
- **解析限制**：① 设置开放服务器查询权限，只允许合法可信来源发请求；② 设置权威服务器响应速率阈值，限制同一来源的查询频率，抵御 DDoS 与反射放大。

DNSSEC 用非对称加密验证身份，机制是一对"算摘要—加解密—比对"：

| 过程 | 步骤 |
|---|---|
| 签名 | 域名服务器用散列函数计算回复报文内容的散列值（内容摘要）→ 用**私钥**加密该摘要 → 把加密结果附加到 DNS 报文 |
| 验证 | 本地 DNS 服务器收到 DNSSEC 报文 → 自行计算报文的内容摘要 → 用**公钥**解密收到的加密摘要 → 比对两者是否一致 |

要点：DNSSEC 只做**来源认证与完整性**，不提供保密性（报文内容仍可被看到）；DoT/DoH 才提供传输加密，三者是互补而非替代。

### 0.5.3 HTTP：从明文到 QUIC

HTTP/3.0 于 2022 年发布，采用 QUIC（基于 UDP 的新型协议），减少连接建立延迟与丢包率影响，从而提升性能；并支持连接迁移，客户端可在不同网络间无缝切换，而 TCP 换网必须反复重连。

HTTP 请求报文与响应报文都由三部分组成（开始行、首部行、实体主体），**区别主要体现在开始行**：请求报文是请求行（方法 URI 版本），响应报文是状态行（版本 状态码 短语）。

HTTP 默认不加密且无状态。为识别客户端身份、维持用户状态，服务器用 Cookie 与 Session 跟踪会话：

| 机制 | 存放位置 | 工作方式 |
|---|---|---|
| Cookie | 客户端 | 随请求一并发送 |
| Session | 服务器端 | 通过唯一 Session ID 与客户端 Cookie 关联，存储会话状态与信息 |

这两类信息一旦泄露，产生两种典型攻击：

| 攻击 | 前提 | 做法 | 后果 |
|---|---|---|---|
| 会话劫持 | 拿到有效 Session ID | 直接冒用该 ID 接管已登录会话 | 以受害者身份操作 |
| 会话固定 | 能预先设定 ID 并让受害者使用 | 攻击者先获得一个 Session ID，诱导受害者用该 ID 登录，之后自己复用 | 免密登录受害者账户 |

防御：全站 HTTPS、Cookie 加 HttpOnly/Secure、登录后重新生成 Session ID（治会话固定）、会话绑定指纹与超时失效。

### 0.5.4 邮件三协议与 MIME

邮件是"推 + 拉"两段式：**用 SMTP 发送邮件，用 POP3 读取邮件**。

SMTP 定义了 14 条命令和 21 种应答信息；每条命令由 4 个字母组成；每种应答一般只有一行，以一个 3 位数字代码开始，后面可附简单文字说明。POP3 与 IMAP4 都采用基于 TCP 的客户/服务器方式，端口分别为 110 与 143。

MIME（多用途互联网邮件扩展）解决的是 SMTP 的编码能力缺陷：SMTP 只能传送 ASCII 码文本，不能传送可执行文件或其他二进制对象，也无法满足带图片、音频、视频的多媒体邮件需求，中文、俄文乃至带重音符号的法文德文同样无法传送。MIME 定义一套编码规则处理非 ASCII 数据，扩展邮件功能——它不只用于邮件，也广泛用于 HTTP，这是常被忽略的一点。

POP3 的加固三招：使用 TLS/SSL 或 STARTTLS 加密会话；改进客户端设计（本地加密存储邮件、支持多设备安全同步）；以支持多端同步的 IMAP 替代 POP3。

### 0.5.5 DHCP：四步交互与三种攻击

```
Client                                  Server
Discover（广播，找服务器） --------->
              <--------- Offer（单播，IP 提议）
Request（选择该提议）   --------->
              <--------- Ack（可用） / Nak（不可用，回到发现阶段）
```

| 阶段 | 报文 | 方向/方式 | 内容 |
|---|---|---|---|
| 发现 | DHCP Discover | 客户端广播 | 查找 DHCP 服务器，表达获取 IP 需求 |
| 提供 | DHCP Offer | 服务器单播 | 准备一个 IP 地址提议 |
| 请求 | DHCP Request | 客户端 | 从多个 Offer 中选一个，接受该提议 |
| 确认 | DHCP Ack / Nak | 服务器 | 确认分配成功 / 无法分配，客户端重新进入发现阶段 |

DHCP 报文中有"经过的中继数目"字段（hops），用于跨网段中继时防环与限跳。

三种攻击与对应防御，全部围绕 DHCP Snooping 展开：

| 攻击 | 做法 | 防御 |
|---|---|---|
| DHCP 饥饿 | 频繁更改请求中的客户端硬件地址（Chaddr）字段值，耗尽地址池，使合法用户拿不到 IP | 交换机启用 DHCP Snooping，比对报文的**源 MAC 与 Chaddr**：一致放行，不一致丢弃 |
| DHCP Server 仿冒 | 私自架设 DHCP 服务器，下发错误网关/DNS，把流量引向自己 | Snooping 把端口分为**信任端口**与**非信任端口**：连合法服务器的端口设为信任并正常转发，非信任端口收到的 DHCP 报文一律丢弃 |
| DHCP 中间人 | 仿冒服务器把自己设为网关，形成 MITM | 启用 ARP 与 DHCP Snooping **联动**：由 Chaddr 确定客户端 MAC、由分配记录确定其 IP，建立动态绑定表；检测 ARP 报文时校验源 IP 与源 MAC 是否与绑定表匹配，不一致即拒绝 |

记忆口诀：饥饿看 Chaddr、仿冒看端口信任、中间人看绑定表。

### 0.5.6 FTP：两组连接与两种模式

FTP 基于客户/服务器模式，用 TCP 建立稳定会话传输文件，需要**两组连接**：

| 连接 | 生命周期 | 用途 | 默认端口 |
|---|---|---|---|
| 控制连接 | 持续存在 | 传输 FTP 命令与响应 | TCP 21 |
| 数据连接 | 临时，传完即关 | 实际文件数据传输 | TCP 20（主动模式） |

两种工作模式的区别在于"谁发起数据连接"：

| 模式 | 客户端命令 | 谁发起数据连接 | 适用场景 |
|---|---|---|---|
| 主动模式（PORT） | PORT | 服务器从 TCP 20 主动连客户端指定端口 | 客户端无防火墙阻挡 |
| 被动模式（PASV） | PASV | 服务器打开临时端口，客户端主动连该端口 | 客户端在防火墙内，避免外部连接被拦 |

PORT 命令的地址编码是常考小计算：`PORT 192,168,1,2,19,137` 前 4 个参数是客户端 IP（逗号分隔），后两个参数计算监听端口：**256 × 19 + 137 = 5001**。

FTP 的安全风险三条：**用户名和密码明文传输**（不做任何加密处理，易被拦截窃取）；**传输数据不加密**（任何人可窥视内容，且存在中间人篡改窃取风险）；**权限管理不完善**（多级权限之间可能重叠或冲突，导致数据泄露或误操作）。

防御五条：以 SFTP 代替 FTP（基于 SSH，防截取与解密）；使用加密与强身份验证（仅接受加密连接，凭据可用口令/证书/令牌）；限制用户权限（ACL 与强制访问控制 MAC）；监控服务器活动（登录与文件操作记录、异常检测）；使用防火墙限制未授权访问。

## 0.6 跨层攻击族对比：把二十种攻击压缩成七类

复习课最值钱的一张表。任何"某攻击的原理"题，先归族，再套该族的通用因果与通用防御，最后补该协议的字段细节。

| 攻击族 | 本质 | 依赖的协议缺陷 | 各层实例 | 通用防御 |
|---|---|---|---|---|
| 窃听嗅探 | 被动读取 | 介质共享、载荷明文 | 混杂模式嗅探、ARP 欺骗后嗅探、FTP/SMTP 明文抓取 | 加密（IPsec/TLS/SSH）、VLAN 隔离、端口安全 |
| 身份伪造/欺骗 | 冒充他方 | 无源地址校验、无报文认证 | IP 源地址欺骗、ARP 欺骗、DHCP 仿冒、DNS 欺骗、ICMP 重定向 | 入口过滤、DAI/DHCP Snooping、DNSSEC、证书体系 |
| 泛洪型拒绝服务 | 耗尽资源 | 无状态预分配、无速率限制 | SYN 泛洪、ICMP Flood、UDP 泛洪、MAC 泛洪、DHCP 饥饿 | 限速/清洗、SYN Cookie、端口安全、Anycast |
| 反射放大 | 借第三方打目标 | 无需握手即可伪造源 + 响应大于请求 | UDP 反射放大（Memcached 11211）、DNS 反射放大 | 关闭开放服务、BCP38、响应速率限制 |
| 会话劫持/中间人 | 顶替或插手中转 | 连接仅凭四元组+序列号识别 | TCP 会话劫持、TCP RST 攻击、HTTP 会话劫持 | 加密、序列号随机化、会话重生成与绑定 |
| 隧道/隐蔽信道 | 把非法数据装进合法外壳 | 协议字段语义未被强制、检测只看类型 | ICMP 隧道、DNS 隐蔽信道、L2TP（合法用途） | 载荷内容检测、限制出网协议、长度/频率异常告警 |
| 分片/重组滥用 | 利用重组歧义 | 分片无状态、重叠分片处理不一致 | IP 分片 DoS、重叠分片污染 | 避免分片（MSS/PMTU）、分片归一化、丢弃重叠分片 |

再补两类不属于"协议机制"但同样常考：**配置与管理缺陷**（默认口令、开放递归解析、开放 Memcached、权限重叠）与**代码实现缺陷**（缓冲区溢出、SQL 注入、XSS）——后者属应用层，PPT 明确归入应用层风险。

## 考点提示

1. **协议三要素与攻击的对应**：语法对格式伪造、语义对含义篡改、同步对重放乱序；依据是三者分别定义结构、动作含义与事件顺序。
2. **协议不安全的三条根因**（设计未考虑安全、缺认证、缺保密）是全课总纲，任何"成因分析"题都先写这三条再落到具体字段。
3. **网络安全五要素**是保密性、完整性、可用性、可控性、不可否认性；只答 CIA 三要素会失分。
4. **PAP 与 CHAP 的判据是"口令是否过线 + 有无随机挑战值"**：PAP 两握手明文，CHAP 三握手散列且抗重放。
5. **四个 PPP 协议字段值**（0xC021/0xC023/0xC223/0x8021）必须与协议名一一对应，混一个就全错。
6. **L2TP 的双通道可靠性相反**：数据通道不可靠、控制通道可靠；SCC 阶段用 CHAP 三次握手互验身份。
7. **64 字节来自 CSMA/CD 时间约束，1518 字节来自内存成本约束**；后者导致 1500 的 MTU，进而产生分片攻击面。
8. **MAC 泛洪的后果是交换机退化为集线器**（未知单播泛洪），不是"地址表被清空"。
9. **分片计算三件套**：数据部分减首部、每片数据取 8 的整数倍、片偏移以 8 字节为单位。
10. **IP 分片攻击分两类**：拒绝服务（重组资源耗尽）与污染（重叠分片覆盖），防御核心是"避免分片"。
11. **ARP 欺骗成立的三条件**：无状态、无认证、可主动应答；结果是 MITM + 可致断网。
12. **ICMP 重定向改的是路由表，不是 ARP 表**；ICMP 隧道利用的是"数据字段本无意义"。 
13. **IPsec 三协议分工**：AH 认证不加密、ESP 加密（可认证）、IKE 协商密钥；传输模式保护载荷、隧道模式保护整个原数据报。
14. **SYN 泛洪的根因是"收到 SYN 即分配资源"**；防御标志性手段是 SYN Cookie。
15. **RST 攻击需端口一致 + 序列号落在接收窗口内**；RST 是拆连接，会话劫持是顶替连接。
16. **反射放大的两个必要条件**：可伪造源且无需握手、响应远大于请求（Memcached 可达数万倍）。
17. **SSL/TLS 位于应用层与传输层之间**，记录协议五步顺序为分组→压缩→算 MAC→加密→加 SSL 头。
18. **DNS 查询折中方案**：主机到本地递归，其余迭代；原因是递归对被查询服务器负担过大。
19. **DNSSEC 只做认证与完整性、不做保密**；保密要靠 DoT/DoH。
20. **DHCP 攻击防御全部落在 Snooping**：饥饿比对源 MAC 与 Chaddr、仿冒靠信任/非信任端口、中间人靠绑定表与 ARP 联动。
21. **FTP 主动/被动判据是"谁发起数据连接"**：PORT 由服务器 20 端口主动连，PASV 由客户端连服务器临时端口。
22. **HTTP 会话劫持与固定的区别在"ID 是偷来的还是预先埋下的"**；治固定要在登录后重生成 Session ID。

## 易错点与自测

### 易错点对比表

**（1）TCP RST 攻击 vs TCP 会话劫持**

| 对比项 | RST 攻击 | 会话劫持 |
|---|---|---|
| 目标 | 强制关闭连接 | 接管连接继续通信 |
| 报文 | RST=1 的伪造报文 | 带合法序列号的正常数据报文 |
| 必要条件 | 端口一致 + 序列号在接收窗口内 | 四元组 + 序列号在窗口内 + 抢在真报文之前到达 |
| 后果 | 拒绝服务（连接中断） | 数据被窃取/篡改，双方无察觉 |

**（2）会话劫持 vs 会话固定**

| 对比项 | 会话劫持 | 会话固定 |
|---|---|---|
| Session ID 来源 | 从受害者处窃取 | 攻击者自己预先生成并"送"给受害者 |
| 是否需要受害者先登录 | 是（劫持已认证会话） | 否（受害者登录后 ID 才生效） |
| 关键防御 | HTTPS、HttpOnly、绑定指纹 | 登录成功后重生成 Session ID |

**（3）递归查询 vs 迭代查询**

| 对比项 | 递归 | 迭代 |
|---|---|---|
| 被查询方责任 | 必须给出最终结果 | 只告诉下一步该问谁 |
| 负担 | 重 | 轻 |
| 实际使用位置 | 主机 → 本地域名服务器 | 本地 → 根 → 顶级 → 权限 |

**（4）IPsec 传输模式 vs 隧道模式**

| 对比项 | 传输模式 | 隧道模式 |
|---|---|---|
| 新增 IP 首部 | 无 | 有 |
| 保护范围 | 传输层报文 | 整个原 IP 数据报 |
| 真实地址可见性 | 可见 | 被封装隐藏 |
| 典型场景 | 主机到主机 | 网关到网关 VPN |

**（5）MAC 泛洪 vs DHCP 饥饿**

| 对比项 | MAC 泛洪 | DHCP 饥饿 |
|---|---|---|
| 耗尽的资源 | 交换机 MAC 地址表 | DHCP 地址池 |
| 关键字段 | 帧的源 MAC | DHCP 请求的 Chaddr |
| 直接后果 | 交换机退化为集线器，全端口泛洪 | 合法客户端拿不到 IP |
| 防御 | 端口安全、静态绑定 | DHCP Snooping 比对源 MAC 与 Chaddr |

### 自测题

**1. 为什么以太网最小帧长是 64 字节，而最大帧长是 1518 字节？两者的约束性质有何不同？**

**答**：64 字节源于 CSMA/CD 的冲突检测要求——最短帧发送时间必须不小于争用时隙 2τ，10 Mbps 下 2τ=51.2 μs，故 10 Mbps×51.2 μs÷8=64 字节，属**时间/正确性约束**。1518 字节 = 14 字节头 + 1500 字节数据 + 4 字节 FCS，源于早期接收缓存内存昂贵，属**成本约束**。前者不能改，后者随技术发展已可通过巨帧放宽。

**2. SYN 泛洪为何能拖垮服务器？给出两种有效防御并说明原理。**

**答**：服务器收到 SYN 后立即分配 TCB 等资源并置半连接，在收到 ACK 前一直占用；攻击者用伪造源 IP 发大量 SYN 且不回 ACK，半连接数超过上限后服务器拒绝一切新连接。防御：① SYN Cookie——不预分配状态，把连接参数编码进 SYN+ACK 的序列号，收到合法 ACK 再建 TCB；② 缩短 SYN Timeout / 增大 backlog / 部署 SYN 代理与清洗，降低单位时间资源占用。

**3. 某 IDS 只按协议类型放行，攻击者如何用 Ping 建立双向信道？如何检测？**

**答**：利用 ICMP Echo 的**数据字段本无意义**这一点，把指令或文件分片填入数据字段并重算校验和，接收端按约定提取，形成 ICMP 隧道，从而绕过防火墙、IDS 与其他安全设备。检测：统计 ICMP 载荷长度分布与请求/响应频率异常、检查数据字段是否为非结构化随机内容、限制 ICMP 出网并只允许必要类型。

**4. 一个总长 3820 字节、20 字节首部的 IPv4 数据报，在 MTU 为 1420 的链路上如何分片？**

**答**：数据部分 3800 字节，每片最多载 1400 字节（1420−20，且为 8 的倍数），分为 3 片，数据长 1400/1400/1000，总长 1420/1420/1020，片偏移 0/175/350，MF 为 1/1/0。

**5. DNSSEC、DoT、DoH 分别解决什么问题？能否互相替代？**

**答**：DNSSEC 用非对称加密对 DNS 报文内容做签名与验证，解决**数据真实性与完整性**（防欺骗、防篡改），但不加密内容，不解决保密性；DoT/DoH 把 DNS 查询封装进 TLS/HTTPS，解决**传输保密性与抗窃听**，但不证明记录本身真伪。三者互补，部署上常 DNSSEC + DoH 并用。
