# 第一章 计算机网络协议安全概述

本章是全课程的地基，要解决三件事：把「网络是什么、怎么分层」讲清楚；把「网络安全要保护什么」讲清楚；最后把「协议为什么不安全」这件事从体系结构层面讲清楚。后四章（网络接口层、网络层、传输层、应用层）都是本章 1.4.3 那张四层安全性框架的逐层展开，因此本章的每一个概念都会在后面反复出现。

学习本章的正确姿势不是背定义，而是始终带着一个追问往前走：**这一层本来负责什么功能，它为了完成这个功能做了哪些"信任假设"，而这些假设在开放网络里恰好都不成立**。协议安全的所有漏洞，本质都是这句话的实例。

## 1.1 计算机网络基础

### 1.1.1 计算机网络的定义

先分清两个词。「网络」是一个极宽泛的概念：为了达到某种目的而以某种方式联系或组合在一起的对象或物体的集合——交通网、人际网、电网都符合。加上「计算机」这个限定词之后，它才成为一个技术概念。

**计算机网络**：将分布在不同地理位置的**多台计算机及其外部设备**通过**通信线路**连接起来，实现**资源共享**的计算机系统。

这个定义包含四个可判定的要素，缺一不可，考试常在这里做偷换：

| 要素 | 含义 | 缺失后的反例 |
|---|---|---|
| 多台计算机及外部设备 | 至少两个具备独立处理能力的节点 | 一台主机连若干哑终端，属多用户系统而非网络 |
| 分布在不同地理位置 | 存在距离，因而必须依赖通信线路 | 机箱内部总线互联不叫网络 |
| 通信线路 | 网线、电话线、光纤、无线等传输介质 | 两台机器各自离线存放数据不构成网络 |
| 资源共享 | 目的与结果，包括硬件、软件、数据 | 仅通电相连而不能互访资源，只是物理连接 |

定义里没有出现"安全"二字，这一点很关键：计算机网络的原始设计目标是**连通与共享**，安全是后来追加的需求，而不是内建属性。本章 1.4.2 讲的所有协议缺陷，根子都在这里——**协议是"先通后安"的产物**，任何安全机制都只能是补丁式的叠加。

### 1.1.2 计算机网络的发展历程

互联网（即采用 TCP/IP 协议构建的计算机网络）的发展可划分为四个阶段。这四个阶段用几何形态来记最省力：**点 → 线 → 面 → 体**。

| 阶段 | 形态 | 时间与标志事件 | 技术特征 | 安全问题的新增面 |
|---|---|---|---|---|
| 第一阶：雏形前夜（点） | 单机孤立 | 1946 年，为解决弹道计算问题，世界上第一台电子数字计算机诞生；通信技术尚处模拟通信世界，是电报与电话的时代 | 计算与通信彼此独立，计算机之间不互联 | 风险以物理与内部管理为主，尚无网络攻击 |
| 第二阶：雏形期（点→线） | 两点/多点连线 | 1969 年，ARPANET 诞生 | 分组交换，主机之间以租用线路互联 | 出现"线路被搭线窃听"的物理风险，通信双方默认互信 |
| 第三阶：商业化期（线→面） | 网状铺开 | PC 普及、视窗操作系统推出、Mosaic 浏览器诞生；商业资本介入，催生大量互联网企业与商业模式 | 用户规模爆炸，应用形态从科研工具变为大众服务 | 用户身份不可信、利益驱动攻击、Web 应用漏洞（注入、XSS）成为主流 |
| 第四阶：融合期（面→体） | 立体泛在 | 移动互联网、物联网、云计算与人工智能融合，人—机—物一体 | 连接对象从"计算机"扩展到"任何设备"，物理世界可被远程操控 | 攻击后果从"信息损失"升级为"物理世界破坏"，工控与物联网成为高危区 |

第一阶段与第二阶段之间还夹着一个常被忽略的**标准化期**，它的意义远超时间顺序上的位置。此前的网络体系结构是各家私有、互不兼容的：

- IBM 的 SNA（System Network Architecture，系统网络结构），1974 年；
- DEC 的 DNA（Digital Network Architecture，数字网络体系），1975 年。

私有体系导致"谁的设备多谁定规则"，跨厂商互通只能靠网关硬翻译，成本极高。于是出现两条标准化路线：国际标准 **ISO 的 OSI/RM**（开放系统互连参考模型），以及事实标准 **TCP/IP**。**1983 年，TCP/IP 成为 ARPANET 上的标准协议**，同年通常被视为互联网的诞生时间。

这里的因果值得琢磨：标准化解决了"互通"，同时也把**同一套协议的缺陷复制到了全球每一个节点**。一个协议漏洞（如 IP 源地址可伪造）在私有网络时代只影响一家企业，标准化之后则成为互联网级别的系统性风险。这是"标准化"与"安全性"之间第一处结构性矛盾。

第四阶段"融合期"的形态变化（面→体）用一句话概括：网络从"传输信息的通道"变成了"控制物理世界的神经系统"。当网络连着电厂的阀门、汽车的刹车、医院的输液泵时，可用性（Availability）的权重会急剧上升，而机密性的优先级会被工程实践压低——这正是 1.5 节工控协议风险的根源。

> 补充：融合期的典型技术标志包括移动互联网、物联网、云计算、大数据与人工智能的交叉渗透；PPT 在此处以图示呈现，文字层未保留具体条目。

### 1.1.3 计算机网络的体系结构

#### 为什么必须分层

设想不做任何抽象，直接让两个人协作完成"从太原寄信到北京"这件事，需要同时解决：写信的格式、信封的写法、邮局的分拣规则、航空公司的货运规则、取件的凭证。若把这些规则混成一坨，任何一处改动都会牵连全部。

PPT 用一个寄信的类比把这套分工讲得很清楚：用户遵守"用户规则"（信的格式与内容），邮局遵守"邮规则"（邮包封装、地址、挂号），航空公司遵守"机场规则"（货运箱装载）。三方各自只关心自己那一层的规定，**相邻层之间通过明确的接口交付，对等层之间通过相同的规则对话**。

```
   太原                                    北京
  You  ──── 用户规则(信) ────────────────  Your friend
   |                                          |
  Post office A ── 邮规则(邮包) ── Post office B
   |                                          |
  Airport ─────── 机场规则(货运箱) ────── Airport
   |                                          |
   +=========== 实际运输通道(航线) ===========+
```

于是引出**网络体系结构**的正式定义：计算机网络体系结构是为简化网络的研究、设计与实现而抽象出来的**结构模型**，是对计算机网络及其部件**所应完成的功能的精确定义**。

必须把「体系结构」与「实现」严格分开：

| 概念 | 回答的问题 | 是否涉及具体软硬件 |
|---|---|---|
| 体系结构 | 各层应该完成哪些功能、层间如何交互 | 不涉及，纯抽象 |
| 实现 | 遵循该体系结构的前提下，用何种硬件或软件完成这些功能 | 涉及，具体到芯片、驱动、进程 |

这条区分是本章最容易被考到的辨析点：**同一体系结构可以有无数种实现**（Windows 的 TCP/IP 栈与 Linux 的 TCP/IP 栈实现不同，但体系结构一致）。反过来，实现不同就意味着**同一协议在不同平台上的行为可能有细微差异，而这些差异本身就是漏洞来源**（如分片重组策略不一致导致规避检测）。

#### 分层的基本方法

分层的做法是：将整体要实现的诸多功能**从逻辑上划分为不同层次**，利用不同层次上的**实体**去实现。

```
     +---------------+          +---------------+
     |   Layer N+1   |<--协议-->|   Layer N+1   |
     +---------------+          +---------------+
            | 接口                    | 接口
     +---------------+          +---------------+
     |    Layer N    |<--协议-->|    Layer N    |
     +---------------+          +---------------+
            | 接口                    | 接口
     +---------------+          +---------------+
     |   Layer N-1   |<--协议-->|   Layer N-1   |
     +---------------+          +---------------+
        源节点系统                 目标节点系统
```

图中有两种箭头，含义完全不同：**水平箭头是协议**（对等实体之间的规则），**垂直箭头是接口**（同一系统内相邻层之间的服务调用）。混淆二者是初学者的高频错误。

分层带来的直接收益就是五大功能的分离实现，PPT 明确列出这五项，它们也正好是各层安全机制的作用点：

| 编号 | 功能 | 内容 | 安全相关性 |
|---|---|---|---|
| ① | 差错控制 | 使相应层次对等方的通信更加可靠 | 校验和/CRC 被攻击者可重算，故差错控制不等于完整性保护 |
| ② | 流量控制 | 发送端速率必须让接收端来得及接收 | 速率相关的状态机可被耗尽（如 SYN 泛洪打半连接队列） |
| ③ | 分段和重装 | 发送端把数据块划分为更小单位，接收端还原 | 分片重叠、重组策略差异是经典绕过手法 |
| ④ | 复用和分用 | 多个高层会话复用一条低层连接，接收端再分用 | 复用标识（端口、连接 ID）可被猜测或劫持 |
| ⑤ | 连接建立和释放 | 交换数据前建立逻辑连接，结束后释放 | 三次握手的状态与序列号是 TCP 攻击的全部抓手 |

#### 六个必须分清的概念

| 概念 | 定义 | 关键限定 |
|---|---|---|
| 源 | 通信过程中数据的发送方 | 通信是双向的，故一个节点**同时**是源和目标 |
| 目标 | 通信过程中数据的接收方 | 同上；"客户端/服务器"是角色，不是固定身份 |
| 实体 | 每一层上的活动元素，包括实现该层功能的**所有硬件与软件** | 网卡是实体，进程也是实体 |
| 对等实体 | 相互通信的两个不同节点上**位于同一层次、完成相同功能**的实体 | 跨系统、同层次，二者缺一不可 |
| (n) 层 / (n+1) 层 / (n-1) 层 | 某特定层 / 其相邻上层 / 其相邻下层 | 每层实体与**同系统相邻层**交互，与**不同系统对等实体**交互 |
| 服务 | 每一层为其相邻上层所提供的功能 | N 层使用 N−1 层的服务，向 N+1 层提供更高一级的服务 |

服务的定义里藏着一个方向性结论：**服务是"下层给予上层"的，协议是"对等层之间"的**。服务是垂直的、单向的、有 provider 与 user 之分；协议是水平的、对称的。用这个标准去判断题目里"XX 是服务还是协议"，基本不会错。

**协议**的定义：对等实体之间为实现有效的数据交换或通信，所必须遵守的**规则或标准的集合**。

#### 协议三要素

协议须具备三大要素，这是本章最高频的考点：

| 要素 | 定义 | 类比（信封） | 缺失后的后果 |
|---|---|---|---|
| 语法（Syntax） | 数据与控制信息的**结构或格式** | 信封的尺寸、地址栏位置、邮票贴法 | 对方无法解析，报文被丢弃 |
| 语义（Semantics） | 需要发出**何种控制信息**、完成**何种动作**、做出**何种响应** | 地址栏写的内容表示"寄往何处" | 报文可解析但意义被曲解，如把"删除"理解为"查询" |
| 同步（Synchronization） | **事件实现顺序**的详细说明 | 先封口再投递，不能颠倒 | 状态机错乱，出现重放、乱序、竞态 |

PPT 用信封作比方的原话很值得记住：**信封里面是数据，信封外部是数据传输所需的控制信息；信封的格式由语法来定义，而格式的含义由语义来规定。**

从这个类比可以直接推出攻击面：语法决定了攻击者能否构造出"合法格式、恶意内容"的报文；语义决定了同一个字段能否被赋予第二种解释（协议歧义攻击）；同步决定了攻击者能否把旧报文在错误的时间点重放。**协议三要素既是设计的三根柱子，也是攻击的三个人口。**

#### 协议数据单元（PDU）与封装

每层实体所采用的数据格式由该层协议决定，称为**协议数据单元**（Protocol Data Unit, PDU）。它是协议的载体，是网络中所传送数据的逻辑组成单元。

PDU 的通用格式：

```
        +-------------------+---------------------------+
        |       PCI         |        用户数据 (SDU)      |
        +-------------------+---------------------------+
        <-- 本层控制信息 -->  <-- 来自上层的载荷 -------->
```

| 成分 | 全称 | 作用 | 典型内容 | 安全相关性 |
|---|---|---|---|---|
| PCI | 协议控制信息（Protocol Control Information） | 为实现协议而在数据首部或尾部添加的控制信息 | 地址、端口、序号、标志位、校验和 | 多数攻击直接伪造或篡改 PCI（源 IP、源 MAC、序列号） |
| 用户数据 | 上层交付的 SDU | 为提供服务而传送的信息 | 上层 PDU | 机密性保护的对象，通常明文裸露 |

PCI（协议控制信息）是为实现协议而在传送数据的首部或尾部加的控制信息，如地址信息；用户数据是为了提供服务而传送的信息。考虑到协议的要求（如时延、效率等），PDU 的大小一般都有**一定的长度要求**——这就是 MTU 与分片机制的由来，也是"分片攻击"的存在前提。

封装与拆封的方向必须记牢：

```
 源端（自上而下，逐层加头 = 封装）        目的端（自下而上，逐层去头 = 拆封）

 应用层   [ 数据 ]                       应用层   [ 数据 ]
            | 加应用首部                          ^ 去应用首部
 传输层   [TH| 数据 ]                     传输层   [TH| 数据 ]
            | 加传输首部                          ^ 去传输首部
 网络层   [NH|TH| 数据 ]                  网络层   [NH|TH| 数据 ]
            | 加网络首部                          ^ 去网络首部
 链路层   [DH|NH|TH| 数据 |DT]            链路层   [DH|NH|TH| 数据 |DT]
            |                                        ^
            +========== 物理介质上的比特流 ==========+
```

这张图解释了两件安全上的事：其一，**每一层只能看见自己的首部**，下层对上层载荷一无所知，因此下层无法校验上层内容的语义，加密必须由知道语义的那一层来做（这解释了为什么 TLS 在传输层之上、应用层之下）；其二，**任何中间节点都能看到自己那一层的首部**，链路上每个交换机都能看到 MAC、每个路由器都能看到 IP，所以"链路上无隐私"是结构性的，不是实现疏忽。

#### 三种经典体系结构与 OSI/RM 的成败

网络层次结构模型与各层协议的集合称为网络体系结构。体系结构是抽象的，仅对网络应该实现的功能进行定义，不涉及具体硬件与软件实现。经典体系结构分三类：

| 类别 | 代表 | 性质 |
|---|---|---|
| 厂商标准 | IBM-SNA、DEC-DNA | 私有，绑定单一厂商，互通性差 |
| 国际标准 | ISO-OSI/RM | 法律意义上的正统，但市场失败 |
| 事实标准 | TCP/IP | 实际运行的标准（de facto） |

OSI/RM 的评价要能两面作答。

**核心贡献**：提出分层模型，明确区分**服务、接口、协议**三个概念，规范了网络体系结构的研究方法。也就是说，OSI 的最大遗产不是它的七层，而是"分层+三概念"这套**方法论**——TCP/IP 的教科书叙述至今仍借用 OSI 的术语。

**缺点**（PPT 归纳为三个"糟糕"）：

| 缺点 | 具体表现 | 后果 |
|---|---|---|
| 糟糕的提出时机（"双峰论"，太晚） | OSI 标准成型时，TCP/IP 已在 ARPANET 与 UNIX 世界里跑通并被免费分发 | 标准赶不上实现，市场已被占领 |
| 糟糕的技术（模型和协议都有缺陷） | 模型层次划分与实际协议不匹配，会话层、表示层近乎空壳 | 按模型实现的产品功能冗余、效率低 |
| 糟糕的实现（庞大，笨拙，缓慢） | 标准文本冗长，实现门槛高，早期产品性能差 | 用户用脚投票，转向 TCP/IP |

这段历史给出一条通用的工程判断：**在网络安全与网络协议领域，"事实标准"往往击败"法定标准"，因为先跑起来的实现会形成生态，而生态比标准更难替换**。这也是为什么至今所有安全加固都发生在 TCP/IP 之上，而不是等一个"安全的 OSI"。

#### TCP/IP 的兴起与"两个 Everything"

TCP/IP 的胜利有清晰的时间线，四个节点连起来就是"根红苗正"的过程：

| 时间 | 事件 | 意义 |
|---|---|---|
| 20 世纪 70 年代中期 | ARPA 实现异种网互连，TCP/IP 出现；1974 年定义 TCP/IP | 解决"异构网络如何互通"，诞生即刚需 |
| 1980 年前后 | ARPA 将 ARPANET 上所有机器转向该协议，并资助开发用于 UNIX 的 TCP/IP | 从实验协议变为可部署产品 |
| 1983 年 | TCP/IP 成为 ARPANET 上的标准协议，同年视为互联网诞生 | 事实标准的地位确立 |
| 1985 年 | 美国国家科学基金会 NSF 涉足 TCP/IP 的研究与开发，其所资助的网络机构均采用该协议 | 学术与资金双重背书，生态锁定 |

TCP/IP 的设计哲学浓缩为两个口号，这两个口号同时也是它的安全软肋：

- **Everything Over IP**：IP 可应用到各式各样的网络上；
- **IP Over Everything**：IP 可在各式各样的网络构成的互联网上运行。

为什么坚持"单一的互联网协议"？PPT 给出的两条理由是：**最大化互操作性**、**最小化服务接口的数量**。接口越少，需要标准化和维护的东西越少，任意两种网络只要各自实现 IP 就能互通——这是工程上的极大成功。

但从安全角度看，代价同样明确：

| 设计选择 | 工程收益 | 安全代价 |
|---|---|---|
| 单一 IP 层、最小接口 | 互操作性最大化，异构网无缝互联 | 所有上层安全都只能压在 IP 之上，IP 本身一旦被绕过（源地址伪造）全线失守 |
| 端到端原则 | 网络简单，智能在端系统 | 网络中间不校验身份，端系统被攻陷即等于身份被冒用 |
| 无状态网络 | 路由器无需保存连接状态，易扩展 | 无法在网络层识别"异常会话"，扫描与泛洪难以在途中拦截 |
| 尽力而为（best effort） | 无需资源预留，鲁棒 | 无服务质量保证，无带宽/连接数上限，天然利于 DoS |

#### 五层协议体系结构

教材采用折中方案——OSI 的七层框架 + TCP/IP 的四层内容，合成**五层**：

```
   OSI 七层              TCP/IP 四层            五层（本课程）
 +-------------+                              +-------------+
 |  应用层      |                              |  应用层      |  HTTP/DNS/SMTP
 +-------------+          +-------------+     +-------------+
 |  表示层      |          |  应用层      |     |  运输层      |  TCP/UDP
 +-------------+          +-------------+     +-------------+
 |  会话层      |          +-------------+     |  网际层      |  IP/ICMP/ARP
 +-------------+          |  运输层      |     +-------------+
 |  运输层      |          +-------------+     |  网络接口层  |  以太网/802.11
 +-------------+          |  网际层      |     +-------------+
 |  网络层      |          +-------------+            |
 +-------------+          |  网络接口层  |            |
 | 数据链路层    |          +-------------+            |
 +-------------+                                     |
 |  物理层      |                                     |
 +-------------+                                     +
```

对应关系可以压缩成一句话：**OSI 的高三层（应用、表示、会话）合并为应用层；OSI 的低两层（数据链路、物理）合并为网络接口层；中间的运输层与网络层一一对应。**

| 层 | 核心职责 | 数据单元 | 典型协议 | 典型设备 | 主要安全风险（本章后文展开） |
|---|---|---|---|---|---|
| 应用层 | 面向具体业务提供通信服务 | 报文 | HTTP、DNS、SMTP、FTP | 主机上的应用进程 | 缓冲区溢出、SQL 注入、XSS、数据泄露 |
| 运输层 | 端到端（进程到进程）的数据传送 | 报文段（TCP）/ 用户数据报（UDP） | TCP、UDP | 主机协议栈 | SYN 泛洪、RST 攻击、会话劫持、UDP 反射放大 |
| 网际层 | 编址与路由转发，异构网互联 | IP 数据报 | IP、ICMP、ARP | 路由器 | IP 地址欺骗、ICMP 攻击、IP 分片、篡改与重放 |
| 网络接口层 | 相邻节点间的帧传输与介质访问 | 帧 | 以太网、802.11 | 交换机、AP、网卡 | 设备损坏与老化、意外故障、信息探测与窃听 |

TCP/IP 的优缺点归纳：

| 维度 | 优点 | 缺点 |
|---|---|---|
| 设计 | 简洁、开放、免费、实现高效，事实标准，生态庞大 | **设计之初缺乏对安全和信任的考虑**，无认证、无保密的内建机制 |
| 扩展 | 支持十亿级规模扩展，完全开放，对所有新协议新技术新应用提供开放服务 | 完全开放同时意味着攻击面完全开放 |
| 服务 | 尽力而为，适配各种链路 | 无 QoS 保证，无连接数限制，利于拒绝服务 |
| 地址 | IPv4 编址简单，路由聚合高效 | 地址空间有限，且源地址不受验证 |

## 1.2 计算机网络安全概述

### 1.2.1 计算机网络安全的定义

**计算机网络安全**：基于计算机、密码学、信息安全以及通信网络管理等技术，保护信息的**保密性、完整性、可用性、可控性和不可否认性**。

这个定义有三个层次需要拆开：

| 层次 | 内容 | 说明 |
|---|---|---|
| 狭义 | 信息资源和网络系统资源**不受有害因素的威胁和危害** | 强调"状态"：没被破坏就是安全的 |
| 广义 | 凡是涉及与网络安全目标相关的**技术、管理和过程控制**，都属于网络安全领域的范畴 | 强调"体系"：安全是持续的过程，不是一次配置 |
| 支撑技术 | 计算机技术、密码学、信息安全技术、通信网络管理技术 | 强调"多学科"：纯技术手段不足 |

从定义本身能读出两个应试要点：

1. **安全 = 五性的保持**，不是"加密"的同义词。只做加密而不做备份，可用性为零；只做备份而不做校验，完整性为零。
2. **安全 = 技术 + 管理 + 过程**。定义里"管理和过程控制"与"技术"并列，这正是 1.3.3 节"法律、教育、管理、技术"四类措施的理论依据。

### 1.2.2 计算机网络安全的发展历程

威胁形态的演变与 1.1.2 的网络形态演变严格同步：网络每扩大一层连接范围，攻击者的可达面就扩大一层，攻击动机也从"炫技"转为"获利"再转为"破坏与勒索"。

| 时期 | 代表性威胁 | 攻击者的能力假设 | 主要受害面 |
|---|---|---|---|
| 早期（主机/局域网时代） | 病毒、非授权访问 | 需要物理接近或内部账号 | 单机数据与主机系统 |
| 互联网普及期 | 蠕虫、拒绝服务、扫描探测 | 可从远端发起，利用协议栈缺陷 | 网络服务可用性 |
| 21 世纪初：新世纪新威胁 | **网络钓鱼、勒索病毒、零日漏洞** | 利用人的疏忽 + 利用未修补漏洞 | 用户凭据、数据资产（勒索加密） |
| 智能化时代 | 大模型滥用、数据隐私泄露、智能体失控 | 仅需语言描述意图即可生成攻击物料 | 企业核心数据、模型与训练数据 |

PPT 在"21 世纪初"这一节点上点了三种典型的新型攻击手段，值得逐一说明它们的"新"在哪里：

- **网络钓鱼（Phishing）**：攻击点从技术转向**人**。它不破解任何密码学机制，只是伪造一个可信的界面或邮件，让合法用户自己交出凭据。防护因此无法只靠协议，必须叠加身份认证强度（多因素）与安全意识。
- **勒索病毒（Ransomware）**：把"破坏数据"变成"变现数据"。它同时打击**可用性**（加密文件）与**机密性**（窃取后威胁公开），使传统"备份即可恢复"的防御不再充分。
- **零日漏洞（Zero-day）**：在补丁存在之前被利用的漏洞。它证明了一件事——**基于已知特征的检测天然滞后**，这条结论直接催生了 1.3.4 中的入侵容忍、拟态防御等"不依赖先验知识"的机制。

与之对应，防御技术也在演进，PPT 归纳为三条主线：

| 防御主线 | 应对的威胁变化 | 技术要点 |
|---|---|---|
| 智能终端防护 | 攻击目标从服务器扩展到手机、IoT 终端 | 终端侧沙箱、权限最小化、应用签名校验 |
| 云端安全治理 | 数据与服务集中到云上，边界消失 | 身份为中心、云原生安全策略、租户隔离 |
| 前沿密码技术 | 传统加密面临算力与算法风险 | 新型密码算法与密码协议的应用 |

#### 大模型带来的新安全风险

这一部分是本课程的时代背景，也是近年命题的热点。核心判断是：大模型**延续**了传统 AI 的安全风险，同时因其**低使用门槛**和**高通用性**而带来大量衍生风险。

**风险一：攻击门槛被彻底拉低。** 仅需用语言描述意图，生成式人工智能即可遵循意图完成钓鱼邮件内容的编写和恶意脚本代码的生成，极大降低了网络犯罪的门槛。过去需要专业训练才能完成的社工文案与免杀脚本，现在成了"会说话就能做"的事。这改变的不是攻击的种类，而是**攻击者的数量与迭代速度**。

**风险二：数据隐私泄露。** 生成式 AI 对训练和推理数据具有强大的记忆能力，容易泄露敏感数据；已有研究针对 GPT 系列模型实现**推理数据重构**——即从模型输出中反推出训练数据片段。这意味着"把数据喂给模型"约等于"把数据发布出去"。

PPT 用三星的案例把这个风险讲得很具体：

| 项目 | 内容 |
|---|---|
| 时间与背景 | 2023 年 3 月，三星半导体部门为提升效率，放开员工使用 ChatGPT |
| 后果 | 由于缺乏有效的管控机制，短短 20 天内连续发生三起严重的核心机密泄露事件 |
| 事件一 | **源代码泄露**：将半导体核心测试源代码直接粘贴至 ChatGPT 对话框，导致核心代码外溢 |
| 事件二 | **工艺数据泄露**：将包含芯片良率、关键工艺参数的代码上传至 ChatGPT，致使核心工艺数据泄露 |
| 事件三 | **内部文档泄露**：上传涉密的内部会议纪要至 ChatGPT，导致公司战略与内部决议信息外流 |
| 核心根源 | **协议层校验机制的全面缺失** |

这里的"核心根源"是本课程视角的关键：企业出口网络**协议层未做输入校验**，且 AI 接口**协议无内容过滤机制**，导致涉密数据以明文形式被上传至境外服务器，全程无任何拦截与告警。请注意这个分析框架——**问题不在员工，而在协议层缺少"出口校验"这一环**。这是把"数据泄露"翻译成"协议缺陷"的典型示范，也是本课程反复使用的方法论：任何安全事件都要能落到某一层的某个机制缺失上。

**风险三：模型幻觉。** 模型会以高度自信的语气输出与事实不符的内容。在安全语境下，它的危害不只是"答案错了"，而是当模型被用于漏洞分析、日志研判、代码生成时，错误结论会被当作依据采纳，形成**自动化放大的错误**。

**风险四：生成内容滥用。** 深度合成（换脸、拟声）使"眼见为实"失效，直接冲击身份认证与社会信任体系；结合 1.3.5 的执法案例可以看到，这类服务若不做安全评估与显著标识，就是明确的违法行为。

**风险五：开源智能体的系统性风险。** 以 OpenClaw 这类开源 AI 智能体为例，它标志着 AI 技术从"对话辅助"向"自主执行"转型——真正拥有"动手干活"的能力，成为"数字员工"。能力越强，一旦被利用后果越重。PPT 指出其三大风险：

| 风险 | 表现 | 安全属性受损 |
|---|---|---|
| 权限过高 | 默认配置拥有过高系统权限，易被恶意指令利用删除数据 | 完整性、可用性 |
| 漏洞可被远程利用 | 已披露多个漏洞，攻击者可远程接管设备 | 保密性、可控性 |
| 供应链污染 | 超 10% 的第三方插件含恶意代码，可窃取密钥、植入后门 | 保密性、不可否认性 |

注意第三条的份量：**插件生态的污染率超过 10%**，意味着"安装即中招"是概率事件而非个案。这为第 1.4.1 节"开源协议/开源软件的缺陷易被发现但生态风险更高"提供了一个现实注脚。

### 1.2.3 网络安全的目标：五性

这是本章最需要背准、也最容易混淆的一组概念。五个目标各有明确边界，且各有对应的技术手段。

#### 保密性（Confidentiality）

**定义**：不把国家机密、企业和社会团体的商业机密和个人信息等网络信息泄露给非授权实体。

**实现手段**：通常利用信息加密、身份认证、访问控制、安全通信协议和审计等方法实现；其中**信息加密是防止信息非法泄露的最基本手段**。

要点辨析：加密解决的是"传输与存储过程中被看到"的问题，访问控制解决的是"被合法读取到但无权读取"的问题。二者不可互相替代——文件权限设得再严，线路被嗅探照样泄露；加密做得再强，授权用户滥用权限照样泄露。

#### 完整性（Integrity）

**定义**：信息在存储或传输过程中，如果未经授权，需保持不被修改、破坏或丢失的完整状态。此外，信息的完整性还要求**信息的来源具有正确性和可信性**。

**影响因素与防护**：影响信息完整性的因素包括设备故障、自然灾害和人为蓄意破坏等；通过**数据备份、校验和、访问控制**等方式确保信息的完整性。

这里有个高频陷阱：定义的后半句"来源正确可信"把完整性扩展成了**数据完整性 + 来源真实性**两件事。因此校验和（如 IP 首部校验和、CRC）只能证明"没被随机噪声改坏"，**不能证明"没被人故意改过"**——因为攻击者改完数据可以顺手把校验和重算一遍。真正抗敌手的完整性必须依赖密码学手段（MAC、数字签名），这一点在后四章会反复出现。

#### 可用性（Availability）

**定义**：在正常情况下，网络信息被授权实体按要求访问使用，或在非正常情况下能恢复使用的特性。即系统运行时可以正确存取所需信息，当系统遭受意外攻击或破坏时，可以迅速恢复并能投入使用。

**要点**：可用性是衡量网络信息系统**面向用户**的一种安全性能，以保障为用户提供稳定的服务；需要防范**拒绝服务攻击**、破坏系统正常运行等攻击，确保系统的高可用性。

可用性是唯一一个**站在用户视角**定义的目标：前两个目标关心"数据对不对、看不看得到"，可用性关心"我现在能不能用"。这也是它与 DoS/DDoS 直接对立的原因。

#### 可控性（Controllability）

**定义**：网络信息系统**责任主体**对网络系统和信息传输具有管理、支配能力的特性。能够根据授权规则对系统行为、信息的传播路径、范围及其内容进行有效掌握和控制。

**举例**：不允许不良内容通过公共网络进行传输，使信息在合法用户的有效掌控之中，确保网络空间的健康和有序；通过技术手段和管理措施实现对网络信息的可控性，防止非法信息的传播和滥用。

可控性带有明显的**治理色彩**，它不是针对外部攻击者的，而是针对**系统所有者/监管者对系统本身的支配力**。这也解释了为什么它是我国网络安全定义中区别于经典 CIA 三要素的两个补充项之一。

#### 不可否认性（No-repudiation）

**定义**：所有参与者不可否认或抵赖本人的真实身份，以及提供信息的**原样性**和完成的操作与承诺。

**实现手段**：**数字签名技术**是解决不可否认性的重要手段。

不可否认性解决的是"事后追责"问题，其技术前提是**签名私钥的唯一持有性**。因此它天然与身份认证、密钥管理绑定，也天然脆弱——私钥一旦泄露或被共享，不可否认性即刻失效（这一点在后续章节的证书与 PKI 部分会展开）。

#### 五性的整体关系

| 目标 | 保护对象 | 主要破坏手段 | 主要保障技术 | 一句话记忆 |
|---|---|---|---|---|
| 保密性 | 信息内容 | 窃听、嗅探、越权访问、明文传输 | 加密（最基本）、身份认证、访问控制、安全协议、审计 | 不让看的人看不到 |
| 完整性 | 信息内容与来源 | 篡改、伪造、重放、设备故障、灾害 | 备份、校验和、访问控制、MAC/数字签名 | 看到的就是原来那样，且确实来自那里 |
| 可用性 | 服务能力 | DoS/DDoS、破坏系统运行 | 冗余、限速、抗 DoS 架构、快速恢复 | 该用的时候用得上 |
| 可控性 | 系统行为与信息传播 | 内容非法传播、系统失控 | 授权规则、内容治理、审计与管控 | 主体说了算 |
| 不可否认性 | 行为与承诺 | 抵赖、事后否认 | 数字签名、可信时间戳、审计日志 | 做过就得认 |

五性之间存在**内在张力**，这是分析题的得分点：加密越强，密钥管理越复杂，可用性与易用性越差；审计日志越完整，不可否认性越强，但日志本身成为新的机密性风险点；可控性要求深度检测（如内容过滤），而深度检测与端到端加密直接冲突。**安全设计从来是权衡，不是叠加。**

## 1.3 计算机网络安全威胁与防范

### 1.3.1 威胁的类型

PPT 在本小节以图示呈现威胁分类，文字层未保留具体条目；课堂小结明确点出"**6 种常见威胁类型**"。虽然图示缺失，但本章后文（以及第 1.4 节各层风险）已经把所有需要掌握的威胁逐一点名，可以按"受损的安全属性"重新组织如下——这张表覆盖了本章出现的全部威胁名称，考试按属性定位即可：

| 威胁 | 典型手法 | 受损属性 | 出现位置 |
|---|---|---|---|
| 窃听/嗅探 | 被动接收链路上的数据帧 | 保密性 | 1.4.3 网络接口层 |
| 流量分析 | 不改内容，只分析通信模式（频率、长度、对端） | 保密性 | 1.3.3 被动攻击 |
| 篡改 | 修改传输中的数据或存储中的数据 | 完整性 | 1.3.3 主动攻击 |
| 伪造 | 假冒源地址、源 MAC、身份或整个报文 | 完整性、不可否认性 | 1.4.2、1.4.4 |
| 重放 | 截获合法报文后原样重发 | 完整性、不可否认性 | 1.4.4 IP 数据报重播 |
| 拒绝服务 | 耗尽带宽、连接或计算资源 | 可用性 | 1.4.5 TCP/UDP 泛洪 |
| 非授权访问 | 绕过认证读取或修改资源 | 保密性、完整性 | 1.4.6 SQL 注入 |
| 恶意代码 | 病毒、蠕虫、木马、勒索软件 | 全部 | 1.2.2 |
| 社会工程/钓鱼 | 欺骗人而非欺骗机器 | 保密性、完整性 | 1.2.2 |

需要建立一个稳定的判断习惯：**任何威胁都能落到至少一个安全属性上**。做题时先问"它损害了哪一性"，再问"它利用了哪一层的哪个机制缺陷"，答案自然成形。

### 1.3.2 安全风险的因素

风险不是单一原因造成的。工程上通用的表述是：**风险 = 资产价值 × 威胁 × 脆弱性**，三者同时具备才构成实际风险——没有资产则无损失，没有威胁则无人利用，没有脆弱性则攻击不成立。PPT 在此处以图示给出因素分类，文字层缺失，按通用框架可归为四类（此处为归纳，非 PPT 原文条目）：

| 因素类别 | 具体表现 | 对应本章内容 |
|---|---|---|
| 技术脆弱性 | 协议设计缺陷（无认证、无加密）、软件漏洞（溢出、注入）、配置错误（默认口令、开放端口） | 1.4 全节 |
| 人为因素 | 安全意识不足（点击钓鱼链接、粘贴源码给大模型）、内部人员越权、误操作 | 1.2.2 三星案例 |
| 环境与意外 | 设备故障、老化、自然灾害、供电中断 | 1.4.3 网络接口层风险 |
| 管理缺陷 | 无安全制度、无审计、无应急响应、供应链失控 | 1.3.3 管理措施、智能体插件污染 |

这个框架的实用价值在于**定位责任**：同一个"数据泄露"事件，若归因为技术脆弱性，解法是加密与校验；若归因为管理缺陷，解法是制度与审计。真实事件往往多因叠加——三星案例就是"人为因素（员工操作）+ 管理缺陷（缺乏管控）+ 技术脆弱性（协议层无输入校验）"三者齐备。

> 补充：风险三要素（资产、威胁、脆弱性）的乘法表述源自风险管理通用模型；PPT 本小节为图示，未给出文字定义，此处用于建立分析框架。

### 1.3.3 防范措施：被动攻击与主动攻击的分野

这是本章最重要的分类，也是后续所有攻击章节的总纲。

**被动攻击（Passive Attack）**：攻击者通过窃听手段**仅观察和分析**网络中传输数据流中的敏感信息，而**不对其进行干扰**。
**主动攻击（Active Attack）**：攻击者对网络中传输着的数据流进行**各种处理**，典型如**篡改**与**伪造**。

```
                 +------------------+
                 |    安全威胁      |
                 +------------------+
                    /            \
        +----------------+   +----------------+
        |   被动攻击      |   |   主动攻击      |
        | 窃听、流量分析  |   | 篡改、伪造、重放 |
        | (只看，不改)    |   | 拒绝服务等      |
        +----------------+   +----------------+
               |                    |
     不涉及数据更改，很难被发现   容易检测
               |                    |
       以加密技术预防为主      预防 + 检测 + 溯源 + 法律
```

两者的**防御逻辑完全不同**，这是必考对比：

| 维度 | 被动攻击 | 主动攻击 |
|---|---|---|
| 是否改动数据 | 不涉及对数据的更改 | 对数据流进行处理、改动或阻断 |
| 可检测性 | **很难被发现**（无异常流量特征，受害者无感知） | **容易检测**（会产生异常报文、错误响应、服务中断） |
| 防御重心 | **预防** | **预防 + 检测 + 响应** |
| 主要手段 | 各种**数据加密技术** | 数据加密、访问控制等预防措施；各种**检测技术**及时发现并阻止攻击；对**攻击源进行追踪**；利用**法律手段**打击 |

理解这条分野的关键在于：被动攻击**不留下"事件"**，只留下"泄露"，而泄露往往在很久之后才以其他形式暴露（如撞库、勒索、商业机密外流）。因此对被动攻击唯一有效的策略是**让数据即使被拿走也读不懂**——加密。这就是为什么"信息加密是防止信息非法泄露的最基本手段"。

主动攻击则相反：它必然造成可观测的偏离（连接异常中断、响应内容不对、服务不可达），因此**检测**才有意义。但同时要意识到主动攻击的成本极低——伪造一个源 IP 只需改一个字段，所以单纯"检测到"并不够，还要能**阻断**与**溯源**。

#### 四类防范措施

PPT 把防范体系划为四条腿，并特别强调第一条的分量：

| 措施 | 内容 | 特点与局限 |
|---|---|---|
| 法律 | 在许多情况下，**法律法规的作用大于技术** | 提供事后惩戒与威慑，界定行为边界；但滞后于技术，跨境执法困难 |
| 教育 | 教育是提升安全意识、知识技能的重要环节 | 成本最低、覆盖面最广；但效果难以度量，无法对抗技术漏洞 |
| 管理 | 管理可以提高网络的安全性，保护信息资产免受威胁 | 制度、流程、审计、权限；依赖执行力度 |
| 技术 | 技术措施包括策略和技术工具，旨在保护网络免受攻击 | 直接有效；但永远存在未修补漏洞与配置错误 |

"法律法规的作用大于技术"这句话常被误解。它的准确含义是：**技术只能解决"能不能"，法律才能解决"敢不敢"**。当攻击者的收益远高于风险时，再强的技术也只是提高成本；反之，明确的法律责任与执法能力可以从动机端压制大量攻击（尤其是内部人员与黑产从业者）。

### 1.3.4 网络空间安全基本机制的发展

PPT 以发展概况、安全目标、基本思想和原理三个维度，梳理了一条从"边界防护"到"内生安全"的演进线索，涉及七种机制：沙箱、入侵容忍、可信计算、类免疫防御、移动目标防御、拟态防御、零信任网络。以下释义为通用定义（PPT 仅列名称与框架）：

| 机制 | 安全目标 | 基本思想 | 解决的传统防御痛点 |
|---|---|---|---|
| 沙箱（Sandbox） | 限制恶意代码的影响范围 | 在隔离环境中运行不可信代码，监视其行为，越界即阻断 | 特征检测无法识别未知恶意代码 |
| 入侵容忍（Intrusion Tolerance） | 在系统已被部分攻陷时仍能提供可接受的服务 | 承认"无法完全阻止入侵"，通过冗余、多样、门限密码等使系统带伤运行 | 单点失守即全线崩溃 |
| 可信计算（Trusted Computing） | 建立从硬件根出发的信任链 | 以 TPM 等可信根度量启动过程，逐级验证，确保运行环境可信 | 主机可能已被植入 rootkit，其上的一切软件判断都不可信 |
| 类免疫防御 | 对未知攻击产生"抗体" | 借鉴生物免疫：对"非我"成分识别与清除，而非匹配已知特征 | 依赖先验特征库 |
| 移动目标防御（Moving Target Defense, MTD） | 增加攻击者的探测与利用成本 | 动态改变攻击面（地址、端口、指令集随机化），使攻击者掌握的信息快速失效 | 静态配置使攻击者可长期踩点 |
| 拟态防御 | 用异构冗余消除未知漏洞后门 | 多套异构等价执行体并行处理同一请求，由裁决器按多数/一致性输出，异常执行体被清洗 | 单一实现的同源漏洞无法被发现 |
| 零信任网络（Zero Trust） | 消除"内网即可信"的假设 | 永不信任、始终验证；以身份为中心，逐次访问逐次授权，最小权限 | 边界被突破后横向移动畅通无阻 |

这条演进线索可以用一句话串起来：**防御的假设从"我能挡住"逐步转向"我可能已经被攻破"**。沙箱与可信计算仍在强化"挡"；入侵容忍、类免疫、移动目标防御、拟态防御则在承认"挡不住"的前提下追求"打得动、活得下"；零信任则干脆取消了"内网"这个可信区域本身。

### 1.3.5 我国网络安全政策法规

#### 战略层面

我国已经是拥有约 **11 亿网民**的网络大国。**2014 年 2 月 27 日，中央成立网络安全和信息化领导小组**，习近平总书记任组长，强调：网络安全和信息化是事关国家安全和国家发展、事关广大人民群众工作生活的重大战略问题，要从国际国内大势出发，总体布局，统筹各方，创新发展，努力把我国建设成为网络强国。

战略布局可归纳为五个方面：

| 方面 | 核心表述 | 落点 |
|---|---|---|
| 总体安全 | 网络安全纳入**国家总体安全观** | 安全不再是部门事务，而是国家安全组成部分 |
| 技术保障 | 要有自己的、过硬的信息技术 | 自主可控，摆脱对单一供应链的依赖 |
| 法治建设 | 出台完善网络安全法律法规 | 立法先行，见下方法律清单 |
| 领导体制 | 加快完善互联网管理领导体制 | 统一统筹，避免多头管理 |
| 国际合作 | 建立多边、民主、透明的国际互联网治理体系 | 反对单边主义，参与规则制定 |

#### 法规体系层次

我国网络安全治理文本呈金字塔结构，考试常要求"把某个文件名放到正确的层级"：

| 层级 | 制定主体 | 代表文件（本章出现） | 效力 |
|---|---|---|---|
| 法律 | 全国人大及其常委会 | 《国家安全法》《网络安全法》《数据安全法》《个人信息保护法》 | 最高 |
| 部门规章/规范性文件 | 国家网信办等部门 | 《网络安全审查办法》《互联网信息服务深度合成管理规定》《生成式人工智能服务管理暂行办法》《互联网信息服务算法推荐管理规定》《具有舆论属性或社会动员能力的互联网信息服务安全评估规定》 | 具体可执行 |

其中《网络安全审查办法》的两条是高频考点，必须能背出适用条件：

- **第二条**：关键信息基础设施运营者采购网络产品和服务，网络平台运营者开展数据处理活动，**影响或者可能影响国家安全**的，应当按照本办法进行网络安全审查。前款规定的关键信息基础设施运营者、网络平台运营者统称为**当事人**。
- **第七条**：掌握**超过 100 万用户个人信息**的网络平台运营者**赴国外上市**，必须向网络安全审查办公室申报网络安全审查。

把这两条放在一起看，逻辑非常清晰：审查的触发条件不是"数据量大小"本身，而是**数据处理活动与国家安全的关联**；而"100 万用户 + 赴国外上市"之所以被单列，是因为境外上市会导致数据与审计底稿的跨境流动，形成**控制权转移**的风险。

#### 两个执法案例

**案例一：生成式人工智能——深度合成服务未做安全评估**

| 项目 | 内容 |
|---|---|
| 主体与行为 | 浙江某科技有限责任公司运营的 App 提供 AI 换脸服务（视频换脸、图片换脸、照片舞动配音），用户可对上传图片、视频中的人物进行换脸 |
| 违法点 | ① 未按规定落实**安全评估**要求；② 相关深度合成内容**未作显著标识** |
| 违反规定 | 《互联网信息服务深度合成管理规定》《生成式人工智能服务管理暂行办法》《互联网信息服务算法推荐管理规定》《具有舆论属性或社会动员能力的互联网信息服务安全评估规定》 |
| 处理结果 | 网信部门依法责令移动应用程序分发平台依规依约对该 App 予以下架处置 |
| 风险实质 | 深度合成内容不标识 → 公众无法分辨真伪 → 直接冲击**不可否认性**与信息真实性 |

这个案例把 1.2.2 的"生成内容滥用"从技术风险落到了法律责任：**技术能力不等于合规资格，提供深度合成服务必须先过安全评估，输出必须可辨识。**

**案例二：数据跨境流动——滴滴网络安全审查**

| 项目 | 内容 |
|---|---|
| 时间 | 2021 年 7 月 |
| 依据 | 《国家安全法》《网络安全法》《数据安全法》，由网络安全审查办公室按《网络安全审查办法》实施审查 |
| 后续 | 根据审查结论及发现的问题和线索，国家互联网信息办公室依法对滴滴公司涉嫌违法行为进行立案调查；期间进行调查询问、技术取证，责令提交证据材料，深入核查分析，并充分听取企业意见以保障其合法权利 |
| 认定 | 违反《网络安全法》《数据安全法》《个人信息保护法》，事实清楚、证据确凿、情节严重、性质恶劣，应当**从严从重**予以处罚 |
| 加重情节 | 存在严重影响国家安全的**数据处理活动**；拒不履行监管部门的明确要求，阳奉阴违、恶意逃避监管 |
| 处理特点 | 因涉及国家安全，依法**不公开** |

两个案例对照起来看，可以得到一条方法论：**网络安全执法并不针对"技术"，而针对"未履行义务"**。前者是"该评估没评估、该标识没标识"，后者是"该申报没申报、该整改不整改"。这也呼应了 1.3.3 的判断——法律的作用在于设定行为边界，而边界一旦明确，技术选择就必须服从合规约束。

## 1.4 计算机网络协议安全威胁

### 1.4.1 计算机网络协议基本概念

**计算机网络协议**是网络通信和数据交换的**规则集合**，是**特殊软件**。三要素为语法、语义和同步：

| 要素 | 定义（本节表述） | 具体所指 |
|---|---|---|
| 语法 | 数据与控制信息的**结构或格式** | 字段布局、长度、编码方式 |
| 语义 | 控制信息的**动作与响应** | 收到某字段后应执行什么、回什么 |
| 同步 | 说明**事件顺序** | 谁先发、何时发、何时算超时 |

"协议是特殊软件"这句话值得单独立一段。它的含义是：**协议规范是文本，但协议必须由代码实现**。因此存在两类完全不同的缺陷：

| 缺陷类型 | 来源 | 特点 | 典型例子 |
|---|---|---|---|
| 设计缺陷 | 规范本身没考虑安全 | 影响所有实现，无法靠打补丁根治，只能加安全协议或改版本 | IP 源地址可伪造、TCP 无认证 |
| 实现缺陷 | 代码写错（边界、类型、状态机） | 只影响特定实现，可通过补丁修复 | 缓冲区溢出、整数溢出、解析逻辑错误 |

这个二分是后续四章的骨架：第三章讲 IP 的设计缺陷，第五章讲应用实现缺陷（注入、XSS、溢出）。答题时先说清属于哪一类，再谈防御——**设计缺陷要靠协议扩展（IPSec/TLS）或架构改造（零信任），实现缺陷要靠补丁与安全编码**，二者不可混用。

**协议分类与安全关系**（PPT 给出的判断很直接）：

| 分类维度 | 类别 | 安全含义 |
|---|---|---|
| 开放程度 | 开源协议 | **健壮性好，安全缺陷易被发现**（多人审阅，缺陷暴露快） |
| 开放程度 | 专利协议 | **安全缺陷不易被发现**（细节不公开，审计受限；但攻击者仍可通过逆向发现） |
| 规范表述 | 英语描述的自然语言文本 | 不同提供商可能有**不同解释**，产生互操作歧义，歧义即攻击面 |
| 协作要求 | 必须相互协作才能工作 | 任何一方的实现偏差都会影响全局，攻击者可利用"合法但异常"的行为 |

这里要特别注意开源与安全的**非对称关系**：开源使缺陷**更容易被防御方发现**，但也同样**更容易被攻击方发现**；而且开源带来生态与供应链风险（参见 1.2.2 中"超 10% 第三方插件含恶意代码"）。因此"开源更安全"是一个需要限定条件的结论，不能作为普遍命题。

### 1.4.2 协议安全风险的根源

#### 历史与标准化

上世纪 70 年代，**罗伯特·卡恩（Robert Kahn）和文顿·瑟夫（Vinton Cerf）**开发了 TCP/IP 协议。TCP/IP 是互联网的核心，其标准化过程由 **IETF**（Internet Engineering Task Force，互联网工程任务组）主导，形成的标准系列名为 **RFC**（Request for Comments，请求评论）。

#### 互联网体系结构的设计原则

David Clark 在 **1988 年**提出的互联网设计目标仍然适用于当前及未来互联网体系结构。无连接的**分组交换**技术及**端到端原则**是互联网发展壮大的技术精髓，研究和创新安全可信互联网体系结构仍需继承和发扬这些设计原则。

PPT 列出的原则可整理为两组：

| 设计目标 | 具体设计选择 | 安全后果 |
|---|---|---|
| 支持多种类型的通信服务 | 分层、协议族并行 | 层间信任假设被攻击者利用 |
| 面临故障时的通信生存能力 | 无状态网络体系结构、动态路由 | 无法识别异常会话，路由可被劫持 |
| 支持不同类型网络的接入 | IP over everything | 异构链路的安全能力参差， weakest link 效应 |
| 端到端通信原则 | 网络中间只转发不检查 | 网络层不验证身份，源地址可任意填写 |
| 降低网络复杂度 | 分离 TCP 和 IP 协议 | 职责分离清晰，但 IP 单独使用时毫无可靠性保障 |
| 提供多样化传输服务 | 传输层增加 UDP 协议 | 无连接、无握手、无速率控制，天然适合反射放大 |
| 对网络提供的功能做出最低限度的假设 | 尽力而为、最小假设 | 无法对安全性做任何保证 |

结论一句话：**开放分层的互联网体系结构成为互联网的基础和核心，然而设计之初缺乏对安全和信任的考虑。**

#### 体系结构设计的三个目标与安全代价

| 设计目标 | 内容 | 对应的安全风险 |
|---|---|---|
| 支持大规模扩展 | 支持十亿级规模扩展 | 无法维护全局身份目录，身份与地址解耦缺失，**地址可被伪造** |
| 完全开放 | 对所有新协议、新技术、新应用提供开放服务 | 攻击面随生态无限扩张，任何新协议都可被滥用（如把 DNS 当隧道） |
| （缺失项）安全与信任 | 设计之初缺乏对安全和信任的考虑 | 面临**地址被伪造、隐私信息泄露、数据转发受攻击**等诸多安全风险 |

#### 三方面风险的正式归纳

PPT 把计算机网络协议的安全风险归结为以下三方面，这是本章最标准的一段结论，建议原文背下：

| 编号 | 风险 | 表述 | 对应的设计缺失 |
|---|---|---|---|
| ① | 设计初衷问题 | 设计初衷为**异构网互联**，未充分考虑安全性；各层协议的**开放性及设计缺陷**使其易受攻击 | 目标函数里没有"安全"这一项 |
| ② | 认证缺失 | 缺乏用于验证**通信双方真实性**的有效认证机制 | 地址即身份（源 IP、源 MAC 都可任意填写） |
| ③ | 保密缺失 | 缺乏**保密机制**，无法实现数据机密性的功能 | 全栈明文，机密性靠上层应用自行解决 |

这三条是后面四章的"总病根"，请把它们与四层结构对应起来：

```
        ①设计缺陷            ②无认证             ③无保密
           |                    |                   |
  应用层  注入/XSS/溢出    —— 无应用级身份绑定 ——  明文 HTTP
           |                    |                   |
  运输层  SYN泛洪/RST劫持   —— 端口即信任边界   ——  明文 TCP
           |                    |                   |
  网际层  分片/ICMP攻击     —— 源IP可伪造       ——  明文 IP
           |                    |                   |
  接口层  嗅探/弱鉴别       —— MAC可伪造/SSID   ——  明文帧
```

### 1.4.3 TCP/IP 协议安全体系结构：网络接口层

网络接口层对应 OSI/RM 模型的**物理层和数据链路层**。

| 项目 | 内容 |
|---|---|
| 安全风险 | 设备损坏与老化、意外故障、信息探测与窃听 |
| 防护措施 | 物理隔离、VLAN、VPN、加密技术、流量监控和过滤 |

注意这一层风险的特殊性：**前两项（损坏、故障）属于可靠性问题，而非攻击**。它们之所以被列入安全风险，是因为它们直接损害**可用性**——这也是"安全不等于防黑客"的最好例证。真正的攻击性风险只有一项：**信息探测与窃听**。

#### 网络监听与嗅探的原理

**网络嗅探（Sniffers）**是一种网络流量数据分析的手段，常见于网络安全攻防技术使用，也有用于业务分析领域。其所使用的工具称为"嗅探工具"，也称"数据包分析器"，还有"嗅探器""抓包工具"等别称。常见的开源嗅探工具包括 **TCPDUMP**、**WIRESHARK**。

嗅探具有**两面性**：

| 使用者 | 目的 | 性质 |
|---|---|---|
| 网络管理员 | 通过捕获分析网络流量，进行高效的网络管理（排障、性能分析、入侵取证） | 合法、必要 |
| 恶意攻击者 | 攫取网络中的大量敏感信息，进行网络攻击 | 违法 |

**恶意的网络嗅探取决于攻击者的位置和攻击能力**，PPT 给出两种典型场景：

| 场景 | 攻击者条件 | 手段 |
|---|---|---|
| 共享网络传输链路 | 与受害者处于同一冲突域/广播域 | 把网卡置为混杂模式，被动接收链路上所有帧 |
| 控制网络设备 | 已攻陷交换机、路由器或 AP | 对流经的流量进行拦截嗅探（端口镜像、流量牵引） |

现实中的规模化监听印证了这一判断：**"棱镜"计划**监视范围很广，情报人员通过"后门"进入 9 家主要科技公司的服务器，包括微软、雅虎、谷歌、Facebook、PalTalk、美国在线、Skype、YouTube 和苹果。这个案例说明，当攻击者的位置从"链路旁"上升到"服务端"时，链路加密也无法保护数据——**端点失守，传输层的一切保护归零**。

#### 混杂模式：嗅探的技术前提

**分组嗅探器（Packet Sniffer）**是一种网络监听工具软件，运行在网络中的某台主机上，**被动接收所有出入该主机的网卡的数据链路层协议数据单元（即帧）**。

正常情况下，网卡只接收目的 MAC 地址指向自己的帧（以及广播/组播帧），其余帧在硬件层就被丢弃。若**将网络适配器配置为混杂方式（Promiscuous Mode）**，网络适配器就会接收所有进入自己接口的 MAC 帧，**而不管这些帧的目的 MAC 地址是否指向该网络适配器**。

```
   正常模式                                混杂模式
   +--------+                              +--------+
   |  网卡  |  只收 目的MAC=自己/广播/组播   |  网卡  |  全部收下，交给嗅探器
   +--------+                              +--------+
       |                                       |
   驱动丢弃他人帧                          全部上交协议栈 + 抓包库
       |                                       |
   只有自己的帧进入系统                    pcap 落盘 → Wireshark 分析
```

> 补充：混杂模式只能收到"本网卡物理上能看到的帧"。在共享式以太网（集线器）中，所有帧广播到每个端口，因此混杂模式可看到全网流量；在交换式以太网中，交换机按 MAC 表定向转发，混杂模式默认只能看到本端口流量，攻击者需配合 MAC 泛洪（塞满 CAM 表使交换机退化为广播）或 ARP 欺骗（把流量引到自己端口）才能看到他人流量。这是"嗅探取决于位置"的技术原因。

**防御与加固**（PPT 给出的措施 + 直接推论）：

| 措施 | 作用点 | 阻断的攻击 |
|---|---|---|
| 物理隔离 | 根本不让流量经过不可控介质 | 外部搭线窃听 |
| VLAN 划分 | 缩小广播域，隔离部门流量 | 同网段混杂嗅探 |
| VPN | 在不可信链路上建立加密隧道 | 链路嗅探、运营商侧截取 |
| 加密技术（TLS/IPSec/802.11i） | 即使被抓包也读不懂 | 内容窃取（最根本的一条） |
| 流量监控和过滤 | 发现异常抓包行为与异常流量 | 探测、横向扫描 |

要建立一个判断：**嗅探无法被"阻止"，只能被"废掉价值"**。只要攻击者能接触到链路，他就能复制比特流；因此链路层的正确目标不是"防嗅探"，而是"让嗅探到的东西没有价值"——这就是加密在被动攻击防御中居于首位的原因。

#### 数据链路层安全实例：802.11i

随着 802.11 无线局域网（Wi-Fi）的广泛应用，其安全问题越来越受关注。在无线通信方式下，**电磁波在自由空间辐射传播**，任何无线终端都可在无线接入点的信号覆盖范围内接收其无线信号。若不采取相应安全措施，任何无线终端都可以接入网络，进而窃听网络通信或非法使用网络资源。

这段描述点出了无线与有线的**本质差异**：有线网络的边界是物理的（拔掉网线就断开），无线的边界是**信号强度**，而信号不认墙。因此"物理隔离"这条有线网络最有效的手段，在无线场景下直接失效。

802.11 无线局域网主要在**数据链路层**为用户提供安全服务。早期采取的安全机制比较简单，共三种：

**机制一：SSID 匹配**

服务集标识符 SSID（Service Set Identifier）即无线网络的名称。

```
        终端 SSID 与 AP 相同  ──→  可以加入 AP 形成的网络
        终端 SSID 与 AP 不同  ──→  不能加入 AP 形成的网络
```

这种 SSID 匹配机制**仅是一种简单的不加密的口令鉴别**，**不能防止窃听和冒充**，它仅仅提供了一种**非常弱的访问控制**功能。原因很直白：SSID 由 AP 周期性广播，用任何扫描工具都能看到，"知道名字"不等于"有权限"。

**机制二：MAC 地址过滤**

AP 配置允许接入的 MAC 地址白名单，不在名单内的终端无法接入。攻击手法是：**将自己的无线局域网网卡的 MAC 地址也设置为截获的有效的 MAC 地址**，这样攻击者就可以接入网络，其所发送的帧会被 AP 接收和转发。

这种 MAC 地址过滤机制与 SSID 匹配机制一样，**也只能提供非常弱的访问控制**功能。根本原因是 **MAC 地址是终端自己声明的，不是被验证的**——这正是 1.4.2 中"缺乏验证通信双方真实性的有效认证机制"在链路层的具体体现。

**机制三：有线等效保密 WEP**

工作方式：网络管理员在 AP 上配置一个由 **AP 和用户的无线终端共享**的 WEP 密钥，然后告知用户，由用户在自己的无线终端上设置该密钥。

```
   管理员手工配置 WEP 密钥
        |                  \
   配置到 AP            口头/书面告知用户 → 用户手工配置到终端
        |                  /
        +---- 同一把共享密钥 ----+
                    |
       鉴别阶段与数据通信阶段全部使用这把密钥
```

WEP 的两个致命问题：

| 问题 | 具体表现 | 后果 |
|---|---|---|
| 无密钥分发机制 | 在鉴别过程和其后的数据通信过程中，所有通信都使用**同一个共享密钥**，且所有接入同一 802.11 无线局域网的无线终端**都使用这同一个密钥** | 一人泄露即全网泄露；无法逐用户撤销；无法追责 |
| 算法强度低 | 国内外众多研究人员已从理论上和实际上都证明了 WEP 加密存在**严重的安全隐患** | 密钥可被统计恢复，加密形同虚设 |

"有线等效保密"这个名字本身就是它的设计目标宣言——"做到和有线一样安全"。但它的实现把"共享密钥"当成了"身份认证"，且密钥手工分发、全网红共享、算法脆弱，三条加在一起，实际安全性远低于有线。

**机制四（替代方案）：WPA / WPA2**

**无线局域网受保护的接入（Wi-Fi Protected Access, WPA）**是作为无线局域网安全的**过渡标准**（替代 WEP）提出的，商业名称为 **WPA2**。它与早期机制的对比如下：

| 对比维度 | 早期机制（弱） | WPA/WPA2（强） |
|---|---|---|
| 鉴别 | SSID 匹配、MAC 地址过滤（明文口令式，可伪造） | **可扩展的鉴别机制的集合** |
| 加密 | WEP（算法强度低） | **更强的加密算法** |
| 密钥管理 | 无分发机制，全网共享一把密钥 | **密钥分发机制** |

目前大多数 802.11 无线局域网都支持 WPA 和 WPA2，建议用户尽量使用 **WPA2**。

#### 802.11i 的鉴别架构与四个阶段

802.11i 的关键设计是**把鉴别服务器（AS）从 AP 中分离出来**。目的在于可使**一台 AS 服务于多台 AP**，集中在一台 AS 中处理鉴别和接入，可以**降低 AP 的复杂性和成本**。

```
   +-----------+        +-----------+        +-----------+
   | 无线终端  |        |  接入点AP |        | 鉴别服务器 |
   |  (STA)    |<--无线->|           |<--有线->|    (AS)    |
   +-----------+        +-----------+        +-----------+
         \                   |                    /
          \              只转发EAP报文           /
           +-------- 真正的鉴别在 STA 与 AS 之间完成 --------+
```

这种"三方分离"的架构有一个重要的安全收益：**AP 只是通道，不持有鉴别凭据**。AP 被盗或固件被篡改，也不会泄露用户的主密钥。

鉴别过程使用**可扩展的鉴别协议（Extensible Authentication Protocol, EAP）**。要强调的是：**EAP 只是一个鉴别框架，并未指定具体的鉴别协议**。在 EAP 中，AS 可选择多种鉴别方式中的任何一种来执行鉴别，主要利用**公钥加密技术**（包括**不重数加密**和**报文摘要**）在某个无线终端和 AS 之间进行相互鉴别，并生成双方共享的一个**主密钥（Master Key, MK）**。

"框架而非协议"这个定性非常重要：它的好处是可扩展（新方法可插拔），坏处是**安全性取决于所选的具体方法**——选了一个弱方法，EAP 框架本身不背锅。

四个阶段的时序：

```
 STA                          AP                          AS
  |                            |                           |
  |  ① 发现/通告阶段            |                           |
  |<--- 通告所支持的鉴别与加密方式 ---|                           |
  |---  请求所期望的鉴别与加密方式 --->|                           |
  |    （此时已交换报文，但 STA 尚未被鉴别，也未获得加密密钥）      |
  |                            |                           |
  |  ② 鉴别阶段（802.1X + EAP）  |                           |
  |<=========== 仅转发 EAP 报文 ==============>|            |
  |<------------------ EAP 相互鉴别 ---------------------->|
  |<------------------ 生成共享主密钥 MK ------------------>|
  |                            |                           |
  |  ③ 密钥派生与分发阶段        |                           |
  |<--------------- 由 MK 派生出加密密钥并分发 ------------->|
  |                            |                           |
  |  ④ 数据传输阶段             |                           |
  |<=========== 使用 TK 加密的数据通信 ====================>|
```

各阶段的安全含义：

| 阶段 | 做了什么 | 关键安全点 |
|---|---|---|
| ① 发现/通告 | AP 通告所支持的鉴别和加密方式，STA 请求期望的方式 | 尽管该阶段无线终端已与 AP 交换了报文，但**此阶段无线终端还没有被鉴别，也没有获得用于数据通信的加密密钥**——所有报文均为明文 |
| ② 鉴别 | 使用 EAP，AP 仅在 STA 与 AS 之间转发报文；AS 与 STA 相互鉴别并生成 MK | 相互鉴别（双向），防止假冒 AP；MK 只在两端产生，不经空口传输 |
| ③ 密钥派生分发 | 由 MK 派生出会话密钥并分发 | 实现**逐会话、逐用户**的密钥隔离 |
| ④ 数据传输 | 使用 TK 加密 | 前向保密与密钥更新 |

> 补充：阶段③的具体链条为 MK → PMK（Pairwise Master Key）→ PTK（Pairwise Transient Key），PTK 的最终生成依赖"四次握手"（4-Way Handshake）交换随机数并校验双方持有同一 PMK；TK 即 PTK 中用于数据加密的部分。此外 802.1X 把 AP 端口分为"非受控端口"（只放行 EAP 报文）与"受控端口"（鉴别通过后才放行业务数据），这就是"阶段①能交换报文但拿不到密钥"的机制原因。这些细节 PPT 以时序图呈现，文字层未保留。

**加固要点**：优先 WPA2（或 WPA3）；禁用 WEP 与 WPS；企业场景用 802.1X/EAP 而非 PSK；终端侧校验服务器证书以防伪造 AP（邪恶双子）；关闭 SSID 隐藏作为辅助而非主要手段（隐藏 SSID 不影响被动嗅探）。

### 1.4.4 TCP/IP 协议安全体系结构：网络层

| 项目 | 内容 |
|---|---|
| 安全风险 | 网络层负责数据包路由和转发，**IPv4 因设计未考虑安全性**，IP 数据报易遭 IP 地址欺骗、ICMP 攻击、IP 分片威胁、数据报篡改和重播等攻击 |
| 防护措施 | **IPv6** 简化 IP 头结构，增加安全性设计；IETF 制定 **IPsec** 协议体系，提供数据包加密和认证，确保数据传输安全 |

四类风险的成因逐条对照（成因是答题得分点）：

| 攻击 | 手法 | 成因（协议设计缺陷） |
|---|---|---|
| IP 地址欺骗 | 伪造源 IP，冒充他人或隐藏真实来源 | 首部无源地址验证机制，接收方**只能相信报文自称的来源** |
| ICMP 攻击 | 利用 ICMP 做探测（ping 扫描）、重定向、不可达伪造，或借大包/广播做放大 | ICMP 是网络层"控制信道"，其报文被默认可信且无认证 |
| IP 分片威胁 | 构造重叠分片、微小分片（teardrop、tiny fragment）绕过检测或造成重组崩溃 | 分片与重组规则存在解释空间，不同实现处理不一致 |
| 篡改与重播 | 修改数据报内容或原样重发 | 首部校验和只覆盖首部、且可被重算；**无完整性认证、无序号/时间戳** |

#### IPSec 协议

**IPSec（Internet Protocol Security）**，即 Internet 协议安全性，是一种**开放标准的框架结构**，通过对 IP 协议的分组进行**加密和认证**，来保护基于 IP 协议的网络传输。

部署地位：在 **IPv4 中，IPSec 的使用是一个可选项**；在 **IPv6（RFC 6434）中，初始设为必选项**。未来随着 IPv6 的进一步流行，IPSec 可以得到更为广泛的使用。

**两种工作方式**：

传输方式（Transport Mode）——保护**传输层报文**，原始 IP 首部保留：

```
  +--------+-------------+----------------+-------------+
  | IP首部 | IPSec首部   |  传输层报文     | IPSec尾部   |
  +--------+-------------+----------------+-------------+
     ^            ^                                ^
   原首部      新增认证/加密信息              新增完整性校验
```

隧道方式（Tunnel Mode）——把**整个原始 IP 数据报**当作载荷，外面套一个新的 IP 首部：

```
  +--------+-------------+-----------------------------+-------------+
  | 新IP首部| IPSec首部  |      原始 IP 数据报          | IPSec尾部   |
  +--------+-------------+-----------------------------+-------------+
     ^           ^          ^                                  ^
  网关地址    安全关联信息  含原始IP首部+传输层报文            完整性校验
```

| 对比 | 传输方式 | 隧道方式 |
|---|---|---|
| 保护范围 | 传输层报文（TCP/UDP 及其载荷） | 整个原始 IP 数据报（含原 IP 首部） |
| 原 IP 首部 | 保留，可路由 | 被封在内部，外部不可见 |
| 典型部署 | 主机到主机（端系统之间） | 网关到网关（路由器之间） |
| 地址隐藏 | 不隐藏真实源/目的地址 | **隐藏内部地址拓扑**，外部只看到网关地址 |
| 开销 | 较小 | 较大（多一层 IP 首部） |

隧道方式的实际形态，PPT 用"总部—分公司"的场景说明：

```
   公司总部                                                分公司
  主机A(源A)                                          主机B(目的B)
     |                                                       |
     +---- 原始IP数据报 [源A → 目的B] ----+                  |
                                          |                  |
                                   [R1]===== 因特网 =====[R2]
                                     \___ 安全关联SA ___/
                                        （安全隧道）
   在 R1 处封装：新首部 [源R1 → 目的R2] + IPSec首部 + 原始数据报[源A→目的B]
   在 R2 处解封：取出原始数据报，按原目的地址 B 转发
```

关键点：**在路由器之间建立安全关联（Security Association, SA）**，形成一条"安全隧道"。隧道两端的地址是 R1、R2，而原始报文的地址 A、B 被加密保护，中间网络（因特网）只能看到 R1→R2 的流量。这同时带来两个收益：机密性（看不到内部地址与内容）与拓扑隐藏（外部无法推断内网结构）。

> 补充：IPSec 由三个协议组成——**AH**（Authentication Header，认证头）提供完整性与数据源认证但不加密；**ESP**（Encapsulating Security Payload，封装安全载荷）提供加密，也可提供认证；**IKE**（Internet Key Exchange，密钥交换）负责协商 SA 与密钥。SA 是单向的，因此双向通信需要两条 SA。PPT 仅给出框架与两种封装方式，未展开协议组成。

**评价**：IPSec 是"在不可信网络上重建可信通道"的典范，它把 1.4.2 中"无认证、无保密"两大缺失一次性补上。但它也有明确边界：只能在 IP 层保护**站点之间**的流量，无法防止端点被攻陷后的数据外泄（对照 1.2.2 三星案例）；且密钥管理与策略配置复杂，NAT 环境需额外处理（NAT-T）。

### 1.4.5 TCP/IP 协议安全体系结构：传输层

| 项目 | 内容 |
|---|---|
| 安全风险 | 传输层包括 TCP 和 UDP。**TCP** 提供面向连接的可靠数据传输，易遭 **TCP 泛洪攻击、TCP 重置攻击和 TCP 会话劫持**；**UDP** 提供无连接快速数据传输，易遭 **UDP 泛洪攻击和 UDP 反射放大攻击** |
| 防护措施 | 为提高传输层安全性，**网景公司（Netscape）引入 SSL，后发展为 TLS**，提供身份验证、完整性检验和保密性服务，降低安全风险 |

成因分析（把攻击手法与协议机制对应）：

| 攻击 | 手法 | 成因（协议机制） |
|---|---|---|
| TCP 泛洪（SYN Flood） | 大量发送 SYN 不回 ACK，占满服务器半连接队列 | 三次握手中服务端在收到 SYN 后必须**先分配资源**（半连接），且无源地址验证，伪造源 IP 即可放大 |
| TCP 重置攻击 | 伪造 RST 报文强制断开连接 | RST 仅凭四元组 + 序列号即可被接受，**报文本身无认证** |
| TCP 会话劫持 | 猜测/嗅探序列号，冒充一方插入数据 | 序列号是唯一凭证，且**明文可嗅探**；无加密即无完整性 |
| UDP 泛洪 | 高速发送大量 UDP 包耗尽带宽 | 无连接、无握手、无速率控制、无状态跟踪 |
| UDP 反射放大 | 伪造受害者源 IP 向开放服务（DNS/NTP/SSDP）发小请求，大响应打向受害者 | UDP **无握手验证源地址**，响应可被放大数十至数百倍 |

这五条攻击有一个共同的结构：**都建立在"源地址可伪造"与"报文无认证"之上**。因此传输层的加固必须包含网络层的配合——入口过滤（防止本网伪造源地址外出）是抑制反射放大的关键，这一点在第四章会展开。

#### SSL/TLS 的三项安全服务

SSL 提供以下三种安全服务：

| 服务 | 内容 | 是否必需 | 对应的安全目标 |
|---|---|---|---|
| SSL 服务器鉴别 | 支持 SSL 的客户端通过**验证来自服务器的证书**，来鉴别服务器的真实身份并**获得服务器的公钥** | 必需（实际部署中） | 身份真实性、不可否认性基础 |
| SSL 客户鉴别 | 用于**服务器证实客户的身份** | **可选**安全服务 | 身份真实性 |
| 加密的 SSL 会话 | 加密客户和服务器之间传送的**所有报文**，并**检测报文是否被篡改** | 必需 | 保密性 + 完整性 |

注意第三项同时包含两件事：**加密**（保密性）与**篡改检测**（完整性）。这正好对应 1.2.3 中"加密不等于完整性"的辨析——SSL 用加密算法 + MAC（AEAD 模式下合二为一）同时解决，而不是只加密。

"客户鉴别可选"这点常被考：因为绝大多数场景只需要用户相信服务器（如网购、网银），服务器不需要密码学意义上确认用户身份（用口令/令牌即可）。双向证书认证（mTLS）在零信任架构中才成为常态。

#### SSL/TLS 在协议栈中的位置

**SSL/TLS 作用于应用层与运输层之间**，在应用层中使用 SSL/TLS 最多的协议是 **HTTP**。

```
   +----------+   +----------+        +----------+
   |  应用层  |   |  应用层  |        |  应用层  |
   +----------+   +----------+        +----------+
        |              |                   |
        |         +----------+        +----------+
        |         | SSL/TLS  |<--安全通道-->| SSL/TLS  |   ← 插在两层之间
        |         +----------+        +----------+
        |              |                   |
   +----------+   +----------+        +----------+
   |  运输层  |   |  运输层  |        |  运输层  |
   +----------+   +----------+        +----------+
        |              |                   |
   +----------+   +----------+        +----------+
   |  网际层  |   |  网际层  |        |  网际层  |
   +----------+   +----------+        +----------+
        |              |                   |
   基于IP的无连接   基于TCP连接的      基于HTTP的
   不可靠传输       可靠传输           安全应用
        \______________ 因特网 ______________/
```

要点：SSL/TLS **依赖 TCP 的可靠传输**（它需要有序、不丢的字节流才能做记录层分帧与完整性校验），因此它不能直接架在 UDP 上（DTLS 是为 UDP 做的适配版本）。它在 TCP 连接上建立起一个**安全通道**，让上层应用无需修改就能获得机密性与完整性。

#### HTTPS 的连接建立过程

以 HTTPS 为例（**HTTPS 的 TCP 端口号为 443**，使用 **SSL 提供安全服务**）：

| 步骤 | 动作 | 安全作用 |
|---|---|---|
| 1 | 客户端发起 TCP 连接（目的端口 443） | 建立可靠传输通道 |
| 2 | 服务器出示证书（含公钥，由 CA 签发） | 把"身份"与"公钥"绑定 |
| 3 | 客户端**使用该证书的认证中心 CA 公开发布的公钥验证该证书** | 确认证书未被伪造/篡改，从而相信公钥属于该服务器 |
| 4 | 客户端**产生一个随机的秘密数** | 引入不可预测性，防止重放与预计算 |
| 5 | 客户端用服务器公钥加密该秘密数并发送 | 只有持有私钥的服务器能解出 |
| 6 | 双方**使用秘密数，按之前协商好的加密算法产生共享的对称会话密钥** | 用非对称解决密钥分发，用对称解决性能 |
| 7 | 后续通信使用对称会话密钥加密并校验完整性 | 机密性 + 完整性 |

这个过程体现了密码工程的核心套路：**非对称加密只用来"安全地协商一个对称密钥"，真正的数据用对称加密传**。原因很实际——非对称运算比对称慢几个数量级，无法承载业务流量。

同时它暴露了 TLS 的**信任根**：整个链条的起点是"客户端信任 CA 的公钥"。因此 CA 被攻陷、证书被误签发、客户端忽略证书告警，都会使 2~4 步全部失效——**中间人攻击不需要破密码，只需要让你相信一个假证书**。

**加固要点**：禁用 SSLv3/TLS1.0/1.1 与弱套件；启用 HSTS 防降级；证书固定（pinning）防误签发；正确处理证书校验错误（不提供"继续访问"选项）；服务端配置前向保密套件（ECDHE）。

### 1.4.6 TCP/IP 协议安全体系结构：应用层

| 项目 | 内容 |
|---|---|
| 安全风险 | 应用层协议是面向应用程序的通信协议，易遭**缓冲区溢出攻击、SQL 注入、跨站脚本攻击（XSS）、数据泄露**等攻击。例如，SQL 注入攻击可使攻击者**绕过正常的身份验证**，访问或修改数据库中的敏感信息 |
| 防护措施 | 通过**用户身份认证、加密技术、应用层防火墙、数据脱敏备份、零信任模型**，以及**添加新的安全协议**等措施，构建多层次、全方位的安全防护体系 |

应用层风险的特殊性在于：**它不来自协议规范的缺陷，而主要来自实现代码的缺陷**（对照 1.4.1 的两类缺陷）。因此它的修复方式也不同——不是加一个安全协议就能解决，而要靠安全编码、输入校验与运行时防护。

| 攻击 | 本质 | 成因 | 防御要点 |
|---|---|---|---|
| 缓冲区溢出 | 写入超出缓冲区边界，覆盖相邻内存（返回地址、函数指针） | 缺少边界检查；C/C++ 等语言不自动校验 | 安全函数、栈保护（Canary）、DEP/ASLR、内存安全语言 |
| SQL 注入 | 把用户输入拼进 SQL 语句，使输入被当作代码执行 | **数据与代码未分离**（字符串拼接） | 参数化查询/预编译、最小权限数据库账号、输入校验 |
| XSS | 把恶意脚本注入页面，在其他用户浏览器中执行 | **数据与代码未分离**（HTML 拼接）+ 浏览器信任同源脚本 | 输出转义、CSP、HttpOnly |
| 数据泄露 | 敏感数据明文存储/传输/过度返回 | 无分级、无脱敏、无最小化 | 加密存储、脱敏、最小必要原则、DLP |

SQL 注入为什么能"绕过正常的身份验证"，值得展开一句：典型登录逻辑把用户输入拼成 `SELECT * FROM users WHERE name='<输入>' AND pwd='<输入>'`，若输入 `' OR '1'='1`，条件恒真，查询返回第一条记录，认证即通过。**这里没有任何密码学被破解——被绕过的是"数据只能当数据"这个假设。**

#### 跨站脚本攻击（XSS）

**XSS（Cross-Site Scripting）**：跨站脚本攻击。为不和层叠样式表（Cascading Style Sheets, CSS）的缩写混淆，故将跨站脚本攻击缩写为 **XSS**。

**原理**：恶意攻击者往 Web 页面里**插入恶意 Script 代码**，当用户浏览该页之时，嵌入 Web 里面的 Script 代码会被执行，从而达到恶意攻击用户的目的。

关键在于**执行位置**：脚本不是攻击者自己执行的，而是在**受害者的浏览器里、以受害者的身份、在目标站点的源（Origin）下**执行的。因此浏览器把这段脚本当作"目标站点的合法代码"，赋予它读取该站点 Cookie、发起该站点请求的全部权限。这是 XSS 危害远大于"页面乱码"的根本原因。

**可能造成的影响**（PPT 列三条）：

| 影响 | 说明 |
|---|---|
| 骗取用户个人信息 | 伪造登录框、诱导填写敏感信息 |
| 利用脚本窃取用户的 Cookie 值，被害者在不知情的情况下，帮助攻击者**发送恶意请求** | 攻击者拿到会话凭据后可完全冒充身份；"帮攻击者发请求"即 CSRF 效果的达成方式 |
| 显示伪造的文章或图片 | 破坏内容可信度，可进一步用于诈骗、舆论操纵 |

**分类**：

| 类型 | 恶意脚本存放位置 | 触发方式 | 特点 |
|---|---|---|---|
| 非持久型 XSS（反射型） | 不落库，脚本藏在 URL 参数中，由服务端原样"反射"回页面 | 诱导受害者点击特制链接 | 一次性，需社工配合，隐蔽 |
| 持久型 XSS（存储型） | 存入数据库（评论、留言、昵称、富文本） | 任何访问该页面的用户都会被触发 | **无需社工诱导，影响面最大**，可蠕虫式传播 |

两者防御手段相同，差别只在"污点从哪里进来"，因此排查重点不同：反射型查所有**回显点**，持久型查所有**入库字段**。

**防御方法**——PPT 用一句话给出了最精确的分工：

> **转义负责"输入输出"检查，CSP 负责"加载执行"检查。**

| 手段 | 作用点 | 防住什么 | 失效场景 |
|---|---|---|---|
| 输出转义/编码 | 数据拼入 HTML/JS/URL 时按上下文编码 | 让 `<script>` 变成纯文本，不被解析为代码 | 转义上下文选错（HTML 转义后拼进 JS）；转义遗漏的富文本属性 |
| 输入校验（白名单） | 入口处限制字符与格式 | 减少可注入的载荷形态 | 业务需要富文本时无法全禁；绕过编码变形 |
| **CSP（内容安全策略）** | 浏览器加载与执行阶段 | 即使脚本被注入，也禁止执行内联脚本与外部域脚本 | 策略过宽（unsafe-inline）、依赖旧浏览器 |
| HttpOnly Cookie | 会话凭据读取 | 脚本读不到 Cookie，窃取会话失效 | 仍可发起同源请求（CSRF 类操作） |
| 框架自动转义 | 模板引擎默认转义 | 减少手写遗漏 | 使用"原始输出"API 时失效 |

这套分工的深层逻辑是**纵深防御**：转义是"第一道门"，它要求开发者每一处都写对，而人会漏；CSP 是"最后一道闸"，它在浏览器侧统一兜底，即使前一道门漏了，脚本也跑不起来。**只在输入侧过滤（黑名单替换 `script`）是最脆弱的做法**，因为编码变形、事件属性、SVG 等方式可以轻易绕过。

> 补充：XSS 还有第三种形态 **DOM 型**——恶意数据不经过服务端，直接由前端 JS 从 `location.hash`、`document.referrer` 等源写入 DOM（如 `innerHTML`），因此服务端日志与 WAF 都看不到；防御重点在前端避免危险 API。PPT 只列非持久型与持久型两类。

## 1.5 行业专用协议的安全风险：物联网与工业控制

这一节在 PPT 中位于课程导入部分，作用是**提前证明"协议安全"不是抽象理论**：只要协议在设计时把功能与效率放在安全之前，风险就必然出现。物联网与工控是这条规律最极端的两个样本。

### 1.5.1 常见物联网协议

物联网协议按通信距离分三档：

| 距离档 | 协议 | 适用场景 | 安全特征 |
|---|---|---|---|
| 近距离通信 | 射频识别（RFID）/ 低功耗蓝牙（BLE） | 门禁、支付 | 标签算力极低，难以承载强加密；配对与绑定过程是攻击重点 |
| 中距离通信 | ZigBee / Wi-Fi（IEEE 802.11） | 智能家居、工业控制 | ZigBee 有网络密钥全网共享问题；Wi-Fi 见 1.4.3 |
| 远距离通信 | LoRa / NB-IoT | 智慧城市、户外监测 | 广域覆盖、终端海量，密钥管理与固件升级困难 |

这三档的共同点是**终端资源受限**：算力、电量、带宽、存储都紧张。而密码学是要消耗资源的，于是"省电"与"安全"直接冲突——这就是物联网安全困境的技术根源。

### 1.5.2 物联网协议的安全风险

PPT 用一张"无线攻击—危害的安全属性"对照表来组织，这张表的价值在于**它示范了"攻击 → 属性"的映射方法**：

| 无线攻击 | 危害的安全属性 | 攻击机理 | 防御方向 |
|---|---|---|---|
| 窃听 | 消息机密性 | 无线信号在开放空间传播，任何覆盖范围内的终端都能接收 | 链路加密、应用层加密、密钥不硬编码 |
| 重放攻击 | 反重放能力、消息完整性 | 截获合法报文后原样重发，设备无法区分新旧 | 序号/时间戳/不重数（nonce） |
| 破解密钥 | 安全的认证过程、机密性 | 密钥硬编码、密钥过短、配对过程可被窃听推导 | 安全密钥存储、逐设备唯一密钥、安全配对 |
| 电池耗尽攻击 | 安全认证 | 反复触发认证/唤醒，使终端电量耗尽 | 认证节流、休眠策略、轻量认证 |
| 射频干扰 | 抗干扰能力 | 同频段大功率噪声压制正常通信 | 跳频、多信道冗余、干扰检测 |

两个值得注意的条目：

**"电池耗尽攻击"** 是物联网独有的威胁类型。它利用的不是协议漏洞，而是**"安全机制本身消耗资源"这一事实**：认证要算密码、要收发包、要唤醒 CPU，攻击者只要持续诱发认证，就能让一颗纽扣电池在几小时内耗尽。这直接说明：在资源受限环境下，**安全机制的设计必须把"被滥用为耗尽手段"作为威胁模型的一部分**。

**"重放"损害的是"反重放能力"** ——PPT 的这个表述很讲究。它不是简单地说"完整性受损"，而是指出协议需要**显式具备反重放机制**（序号、时间戳、挑战应答）。这解释了为什么后面 1.4.4 中"IP 数据报重播"被列为独立风险：IP 层没有序号，天然不能反重放。

### 1.5.3 常见工业控制协议

| 协议类别 | 核心特点 | 优势 | 典型应用 |
|---|---|---|---|
| 现场总线协议 | 工业网络协议总称，用于实时分布式控制，大幅缩减供电线路 | 简单可靠，能有效构建复杂控制系统 | 汽车制造、化工生产，连接传感器与控制器 |
| 工业以太网协议 | 基于以太网核心技术，针对**实时性、安全性、时间同步性**改进 | 方便构建大型复杂控制系统，提升系统性能和效率 | 制造业、电力系统，实现高速数据传输与精准控制 |
| 工业无线协议 | 无需布置供电线路，灵活配置传感器位置 | 灵活性高，适用于复杂环境和难以布线的场所 | 智能农业、工业自动化、环境监测、远程控制 |

### 1.5.4 工控协议的安全风险

PPT 只用一句话点出根源，但这一句是本课程最锋利的一句：

> **工控协议在设计之初，开发者优先考虑功能、效率、实时性。**

把它展开，就是一条完整的因果链：

```
设计优先级：功能 > 效率 > 实时性 >> 安全
        |
        v
协议无认证、无加密、无完整性校验，报文格式固定、字段可预测
        |
        v
攻击者可任意伪造控制指令（如"开阀""停机"），且无法追溯来源
        |
        v
后果不止数据泄露，而是物理世界破坏（爆炸、停产、污染）
```

IT 与 OT（Operational Technology，运营技术）的安全优先级差异，可以用一张表说清：

| 维度 | IT 系统 | OT/工控系统 |
|---|---|---|
| 首要目标 | 机密性（CIA 顺序） | **可用性优先**（AIC 顺序） |
| 补丁策略 | 尽快打补丁 | 不敢停机，补丁滞后数年 |
| 设备生命周期 | 3~5 年 | 15~30 年，协议无法替换 |
| 认证 | 账户口令、多因素 | 很多协议**原生无认证** |
| 攻击后果 | 数据泄露、业务中断 | 人身安全、环境灾难、供应链中断 |

这解释了为什么"给工控加加密"往往行不通：加密带来延迟（损害实时性）、密钥管理需要运维能力（现场没有）、设备算力不足（老 PLC 跑不动 TLS）。因此工控安全的主流思路是**在网络边界做隔离与深度解析（工业防火墙、单向网关）**，而不是改造协议本身——这又是"设计缺陷只能靠架构补偿"的一个实例。

## 1.6 课程定位与学习方法

这一节把 PPT 的课程导入内容收拢，目的是让复习有方向感。

### 1.6.1 学习重点与难点

**学习重点**（PPT 明确给出的两条主线）：

| 主线 | 学时 | 方法 |
|---|---|---|
| 基于 TCP/IP 的体系结构，通过学习各层协议的功能，**逐层思考**：该层负责什么？有什么安全缺陷？通常采用什么技术进行防范？ | 32 | 三层追问法（功能→缺陷→防御） |

"三层追问法"就是本笔记每一小节的组织方式（原理→攻击→防御）。复习时若能把任意一层用这三句话讲完，这一层就掌握了。

| 难点 | 具体表现 | 突破方法 |
|---|---|---|

| 安全协议的**数学基础与实现细节** | IPSec、SSL/TLS 涉及对称加密、非对称加密、数字签名、哈希函数等密码学概念，以及**证书链验证、密钥交换算法** | 先掌握"用非对称协商对称密钥"这一条主线，再看细节 |

## 考点提示

- 计算机网络的定义必须能说出四个要素：多台计算机及外设、地理分散、通信线路、资源共享。少一个即错。
- 四阶段用"点→线→面→体"记；**1969 年 ARPANET**、**1983 年 TCP/IP 成为标准协议（互联网诞生年）**是必考年份。
- **体系结构是功能定义，实现是软硬件方案**；同一体系结构可有多种实现，实现差异本身即漏洞来源。
- 服务是**下层给上层**的（垂直、单向），协议是**对等层之间**的（水平、对称）；接口是相邻层之间的约定。
- 协议三要素：**语法=格式、语义=动作与响应、同步=事件顺序**。判断题目给的是哪一要素，看它谈的是"长什么样""做什么""什么时候做"。
- PDU = **PCI + 用户数据**；PCI 是实现协议而加的首部/尾部控制信息，是攻击者伪造的主要目标。
- OSI/RM 的核心贡献是**分层模型 + 服务/接口/协议三概念**；失败原因是三个"糟糕"：时机太晚、技术有缺陷、实现庞大笨重。
- 五层模型 = OSI 高三层合并为应用层、低两层合并为网络接口层，中间两层一一对应。
- 网络安全五性：保密性、完整性、可用性、可控性、不可否认性；**加密是保密性最基本手段，数字签名是不可否认性的重要手段**。
- 完整性的两个层次：内容不被篡改 + **来源正确可信**；因此校验和不能替代密码学完整性保护（可被重算）。
- **被动攻击不涉及数据更改、很难被发现，以加密预防为主**；**主动攻击容易检测，需预防+检测+溯源+法律**。这条对比几乎必考。
- 防范四类措施：法律、教育、管理、技术；"法律的作用往往大于技术"指法律解决"敢不敢"，技术解决"能不能"。
- 协议安全风险的三方面归纳（必背）：①设计初衷为异构互联、开放性及设计缺陷使其易受攻击；②缺乏验证通信双方真实性的有效认证机制；③缺乏保密机制。
- **Everything Over IP / IP Over Everything** 的收益是最大化互操作性、最小化服务接口数量；代价是安全只能叠加在 IP 之上。
- 网络接口层风险有三：设备损坏与老化、意外故障、信息探测与窃听；**前两项损害可用性，不是攻击**。
- 嗅探的技术前提是网卡**混杂模式**；有效嗅探取决于**攻击者位置**（共享链路 / 控制设备）。
- 早期 802.11 三机制（SSID 匹配、MAC 过滤、WEP）都只提供**非常弱的访问控制**；WEP 的两大硬伤是**无密钥分发（全网共享一把密钥）**与**算法强度低**。
- WPA/WPA2 相对 WEP 的三点改进：可扩展的鉴别机制集合、更强的加密算法、**密钥分发机制**。
- 802.11i 的关键设计是**AS 从 AP 分离**（一台 AS 服务多台 AP，降低 AP 复杂度与成本）；**EAP 只是鉴别框架，不指定具体鉴别协议**。
- 802.11i 第一阶段虽已交换报文，但**终端尚未被鉴别、也未获得加密密钥**——这是常考细节。
- IP 数据报的四类风险：IP 地址欺骗、ICMP 攻击、IP 分片威胁、篡改与重播；IPSec 在 **IPv4 可选、IPv6（RFC 6434）初始为必选**。
- IPSec 传输方式保护传输层报文（保留原 IP 首部，主机到主机）；隧道方式封装整个原始 IP 数据报（新增 IP 首部，网关到网关，隐藏内网拓扑）。
- SSL 三项服务：服务器鉴别（必需）、客户鉴别（**可选**）、加密会话（加密+篡改检测）。
- SSL/TLS 位于**应用层与运输层之间**，依赖 TCP 可靠传输；HTTPS 端口 **443**。
- HTTPS 用**非对称加密协商对称会话密钥**；信任根是 CA 公钥，因此**中间人攻击只需伪造证书，不必破密码**。
- 应用层风险主要来自**实现缺陷**（溢出、注入、XSS），修复靠安全编码与运行时防护，不是加协议就能解决。
- XSS 命名是为了避免与 **CSS** 混淆；防御分工是**转义管"输入输出"检查，CSP 管"加载执行"检查**。
- 工控协议风险根源一句话：**设计之初优先考虑功能、效率、实时性**，安全被排在最后。

## 易错点与自测

### 易混淆概念对比

| 对比项 | 概念 A | 概念 B | 区分要点 |
|---|---|---|---|
| 体系结构 vs 实现 | 各层应完成的功能的精确定义 | 遵循该结构的硬件/软件方案 | A 抽象、与产品无关；B 具体、因厂商而异 |
| 协议 vs 服务 | 对等实体之间的规则集合 | 下层向上层提供的功能 | 协议水平对称，服务垂直单向 |
| 语法 vs 语义 | 数据与控制信息的结构或格式 | 发出何种控制信息、完成何种动作与响应 | 语法管"长什么样"，语义管"是什么意思、要做什么" |
| 被动攻击 vs 主动攻击 | 只观察分析，不干扰数据流 | 对数据流进行处理（篡改、伪造、阻断） | 关键判据是**是否改动数据**；由此决定"难发现→靠加密预防"与"易检测→靠检测+溯源" |
| 保密性 vs 完整性 | 不泄露给非授权实体 | 未经授权不被修改，且来源正确可信 | 加密保保密；校验和/签名保完整；**校验和可被重算，不能抗篡改** |
| 传输方式 vs 隧道方式 | 保留原 IP 首部，保护传输层报文 | 新增 IP 首部，封装整个原始 IP 数据报 | 看"原 IP 首部是否还在外层"；隧道方式可隐藏内网拓扑 |
| SSL 服务器鉴别 vs 客户鉴别 | 客户端验证服务器证书并取得公钥 | 服务器证实客户身份 | 前者必需，后者**可选** |
| SSID 匹配 vs MAC 过滤 | 靠"知道网络名"接入 | 靠"MAC 在白名单内"接入 | 两者都是**明文声明**，都可被伪造，仅提供很弱的访问控制 |
| WEP vs WPA2 | 全网共享一把手工配置的密钥，算法弱 | 可扩展鉴别 + 更强加密 + 密钥分发机制 | 差别不在"有没有加密"，而在**有没有密钥管理与逐会话密钥** |
| 反射型 XSS vs 存储型 XSS | 脚本藏在 URL，服务端反射回显 | 脚本入库，访问即触发 | 前者需诱导点击，后者**无需社工，影响面更大** |

### 自测题

**1. 判断：OSI/RM 是国际标准，因此它的市场地位优于 TCP/IP。**
**答**：错。OSI/RM 是法定（de jure）国际标准，TCP/IP 是事实（de facto）标准。OSI 因提出时机太晚、模型与协议有缺陷、实现庞大笨重而市场失败；TCP/IP 因先跑通、免费、随 UNIX 扩散而形成生态。**标准地位不等于市场地位**。

**2. 简答：为什么说"CRC/校验和通过"不能证明数据完整性未被攻击？**
**答**：校验和只能检出随机错误，其算法公开且无密钥，攻击者篡改数据后可**重新计算校验和**一并替换。抗敌手的完整性必须依赖带密钥或绑定身份的机制（MAC、数字签名），使攻击者无法在不知道密钥的情况下生成合法校验值。

**3. 分析：某公司内网被植入嗅探器，管理员发现核心数据库密码泄露。请问这属于被动攻击还是主动攻击？应采取什么措施？为什么单纯部署 IDS 无效？**
**答**：属于**被动攻击**（只观察不篡改，不产生异常流量，受害者无感知）。措施应以**预防**为主：全链路加密（TLS/IPSec）、VLAN 与端口隔离、禁止明文协议、凭据定期轮换与多因素认证。单纯部署 IDS 无效，因为被动攻击**不涉及数据更改、很难被发现**，没有可供匹配的异常特征；IDS 的价值在主动攻击的检测侧。

**4. 计算/分析：IPSec 隧道方式下，因特网上的中间路由器能看到哪些地址？原始报文的源/目的地址是否暴露？**
**答**：中间路由器只能看到**隧道两端网关的地址（如 R1、R2）**。原始报文（源 A、目的 B）被完整封装在 IPSec 载荷内并受加密保护，对外不可见。因此隧道方式同时提供机密性与**内网拓扑隐藏**；这也是它与传输方式的关键差别（传输方式保留原 IP 首部，真实地址仍然可见）。

**5. 分析：某网站对所有用户输入执行了"把 `<script>` 替换为空字符串"的过滤，是否足以防御 XSS？说明理由并给出正确方案。**
**答**：不足。黑名单替换可被多种方式绕过：大小写混写（`<ScRiPt>`）、嵌套构造（`<scr<script>ipt>`）、不使用 script 标签（`<img onerror=...>`、`<svg onload=...>`）、编码变形等。正确方案是**输出转义（按 HTML/JS/URL 上下文编码）+ CSP（禁止内联脚本与不可信域）+ HttpOnly Cookie**，即 PPT 的分工："转义负责输入输出检查，CSP 负责加载执行检查"。

**6. 简答：早期 802.11 的 SSID 匹配与 MAC 地址过滤为什么只能算"非常弱的访问控制"？**
**答**：两者的凭据都是**终端自己声明的明文信息**，而非被验证的秘密。SSID 由 AP 周期广播，扫描即可获得；MAC 地址可在网卡上任意修改，攻击者截获一个合法 MAC 后设置为自己的地址即可接入。二者都不提供加密，因而**不能防窃听，也不能防冒充**，只提高了接入的"操作门槛"，不构成真正的身份认证。
