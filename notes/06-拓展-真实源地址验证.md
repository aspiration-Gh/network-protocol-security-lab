# 拓展·真实源地址验证

本章是一个独立于主线章节的拓展专题：主线讲的是“某个协议出了什么漏洞、怎么打、怎么防”，本章往后退一层，问一个更根本的问题——**为什么网络层的攻击可以如此廉价地发起**。答案落在一个很不起眼的地方：IP 首部里的源地址是发送方自己填的，全程没有人核对。

把这个洞补上，需要一套跨越接入网、域内、域间的体系结构，这就是真实源地址验证体系结构（Source Address Validation Architecture, SAVA）。本章按“问题从哪来 → 传统办法为何不够 → 体系结构怎么分层 → 各层关键技术 → 落地与局限”的顺序展开。

## 6.1 问题的提出：一个没有信任基础的网络

### 6.1.1 从“彼此信任”到“必须设防”

互联网的设计年代有一个今天看来很奢侈的前提：使用者是彼此认识的一小群研究人员。PPT 引用的说法是——“我们并不都认识对方，但我们都多少信任对方，这种基本的信任感渗透了整个网络”（Danny Hillis）。那时网络是封闭的俱乐部，协议里不需要身份，也不需要防伪。

规模一旦爆炸，前提就崩了。同一个网络里既有银行也有僵尸网络，源地址仍然是“你说你是谁就是谁”。于是有了另一句更冷的描述——“在互联网上发送 IP 分组时，人只能祈祷它不要落到错误的人手里”（Adrian Perrig）。Vinton Cerf 的判断是：当前的互联网体系结构缺乏安全可信基础，很容易发生网络攻击，值得深入研究。

这不是“某个协议实现得不好”，而是**体系结构层面的缺省信任**。主线各章的攻击之所以能成立，很大一部分都站在这个缺省信任上。

### 6.1.2 三个层面的安全现状

PPT 把当前互联网体系结构的安全问题归成三条，并明确指出其中哪一条最根本：

| 层面 | 具体表现 | 缺的是什么 | 根因定位 |
|---|---|---|---|
| 地址 | 地址易被伪造 | 地址标识缺乏合法性验证 | **最根本**：IP 地址同时承担位置与身份双重角色 |
| 隐私 | 隐私信息易泄露 | 云端基础设施承担信任支撑，仿冒伪造与单点故障暴露用户隐私 | 信任被外包给少数中心 |
| 转发 | 数据转发过程易受攻击 | 传输通道不可信 | 路由体系只保证可达，不保证可信 |

为什么说地址这一条最根本？因为地址是“基本载体和核心”。上层协议（TCP、UDP、DNS、HTTP、应用层鉴权）统统把 IP 地址当作对端标识来用。地址一旦可以随便写，所有以地址为凭据的信任关系同时失效。PPT 的措辞是：IP 地址欺骗已经成为大量攻击成功的一个**先决条件**。

### 6.1.3 信件类比：信任转移断在哪一环

PPT 用寄信作类比。我们信任一封信，实际依赖三样东西，而这三样在 IP 通信里逐一对不上：

| 信件中的信任凭据 | IP 分组中是否有对应物 | 可靠性结论 |
|---|---|---|
| 信封上的发件人地址 | 首部中的源 IP 地址 | 两者都由发送方填写，邮递员/网关都不核验，**同样不可靠** |
| 信件字迹（个人书写习惯） | 数据包的比特序列 | 所有分组都是 01 序列，人人“字迹”相同，**没有区分度** |
| 信件上的签名 | 不存在 | IP 首部不携带签名，**信任无法落到人身上** |

三样凭据里，只有“地址”被继承下来了，而它恰好是最不可靠的那一样。

```
        信件通信                             IP 通信
  +---------------------+            +----------------------+
  | 发件人地址 --> 可伪造 |            | 源 IP 地址 --> 可任意填写 |
  | 字迹       --> 难伪造 |            | 比特序列   --> 全是 01，无区分 |
  | 签名       --> 难伪造 |            | （无）     --> 不存在        |
  +---------------------+            +----------------------+
        可信度：地址最弱                      可信度：只剩最弱的那一项
```

对照 PPT 的因果链，伪造之所以“非常简单”，就两条：

1. **构造首部时可以随意填一个源地址**——协议没有规定这个字段必须与发送者的实际接入位置一致，也没有任何字段能证明它。
2. **网关转发时不检查源地址是否来自其所在局域网**——中转设备只查目的地址做查表转发，源地址对它只是“回程信息”，不影响转发决策。

第一条是协议设计缺陷，第二条是转发设备的行为惯性。二者叠加，源地址就退化成了一个纯粹的“回信地址备注”，写什么都行。

## 6.2 成因与攻击形态

### 6.2.1 从首部字段看缺陷位置

IPv4 固定首部 20 字节，逐字段看哪一处能承担“证明身份”的职责：

| 字段 | 长度 | 作用 | 安全相关性 |
|---|---|---|---|
| 版本 | 4 位 | 标明 IP 版本 | 无 |
| 首部长度 | 4 位 | 首部长度，单位 4 字节 | 可用于构造畸形包 |
| 服务类型 ToS | 8 位 | 区分服务、优先级 | 少用字段，曾被用作夹带标签的载体 |
| 总长度 | 16 位 | 整个分组的长度 | 分片攻击相关 |
| 标识 | 16 位 | 分片重组时的同一分组标识 | 可预测，辅助分片攻击 |
| 标志 | 3 位 | DF/MF | 影响分片行为 |
| 片偏移 | 13 位 | 分片在原文中的位置 | 重叠分片攻击相关 |
| 生存时间 TTL | 8 位 | 跳数上限，防环 | 可被用于推断拓扑与路径长度 |
| 协议 | 8 位 | 上层协议号 | 无 |
| 首部校验和 | 16 位 | 仅校验首部完整性 | **只防误码，不防伪造**；改了源地址重算即可 |
| 源 IP 地址 | 32 位 | 发送方标识 + 回程地址 | **由发送方单方面填写，无任何验证机制** |
| 目的 IP 地址 | 32 位 | 转发依据 | 决定路由，受网络侧控制 |

结论很干净：整个首部里，唯一有可能承载“身份”的字段就是源 IP 地址，而它没有任何配套的证明机制；唯一带“校验”字样的字段只保证比特没传错，不保证写的人是谁。

> 补充：首部校验和是简单的反码求和，任何人都能重算，因此它对伪造毫无阻力；这也是为什么后文的方案都不约而同地把验证点放在“地址与接入位置的绑定”上，而不是放在报文内容的自校验上。

### 6.2.2 两类攻击：伪造随机地址与伪造特定地址

PPT 按“是否针对特定地址”把基于源地址伪造的攻击分成两支：

| 分支 | 伪造对象 | 目的 | 典型攻击 |
|---|---|---|---|
| 不伪造特定地址 | 大量随机源地址 | 用海量请求占满目的主机资源，使其无法响应正常请求甚至崩溃 | 分布式拒绝服务（Distributed Denial of Service, DDoS） |
| 不伪造特定地址 | 大量随机源地址 | 隐藏自身信息，使受害方即使被攻击也无法追溯攻击源，规避网络审查 | 反射/跳板式攻击的隐匿 |
| 伪造特定地址 | 某个受信任主机的地址 | 利用“特定 IP 与目的主机之间的信任关系”取得信任，执行恶意指令或窃取机密 | 远程访问注入攻击 |

**为什么随机伪造地址就能打瘫一台主机**：目的主机在收到 SYN 或查询请求时，必须为每个半开连接/待处理请求分配状态（内存、表项、定时器）。伪造源地址意味着“回包永远回不来”，三次握手永远完不成，状态却已经占住了。攻击者不需要看到回包，所以不需要真实地址；受害者想反查，反查到的地址是随机的，追溯链断掉。

**为什么伪造特定地址能骗过认证**：大量早期服务把“源 IP”当作身份凭据——rlogin/rsh 的主机信任、防火墙与路由器的管理白名单、基于 IP 的访问控制列表、甚至部分数据库与中间件的可信来源配置。伪造一个白名单内的地址，等于直接借用别人的身份。

### 6.2.3 远程访问注入的分步过程

PPT 描述的远程访问注入是“两步走”：先让被攻击主机暂时停止响应，再冒充它去和目的主机对话。

| 步骤 | 动作 | 目的 | 关键字段/条件 |
|---|---|---|---|
| 1 | 对“被冒充主机”发起 DDoS，使其暂时停止响应 | 制造沉默，让目的主机察觉不到真正的对端已经离线 | 攻击目标是被冒充者的可用性 |
| 2 | 猜测被冒充主机与目的主机之间连接的标识信息（连接标识、序列号一类） | 取得与目的主机“对得上话”的资格 | 需猜到当前连接的标识/序号 |
| 3 | 以被冒充者的源 IP 向目的主机发包 | 目的主机依据源地址认为这是老朋友 | 源 IP 设为被冒充者 |
| 4 | 注入恶意脚本/指令 | 破坏目的主机、窃取机密，甚至取得控制权 | 上层协议已认为会话可信 |

成因回到协议本身：TCP 用“四元组 + 序列号”识别连接，四元组里的源地址可以伪造，序列号在早期实现中可预测，于是“连接身份”整体可伪造。**上层把安全建立在 IP 地址这个不安全标识之上**，这就是 PPT 反复强调的那句话。

### 6.2.4 泛滥程度：CAIDA Spoofer 的测量

互联网数据分析合作协会（CAIDA）设立 Spoofer 项目，主动测量全球互联网对源地址欺骗的敏感程度。截至 2021 年 2 月 21 日的数据：

| 指标 | 数值 | 含义 |
|---|---|---|
| 可被假冒的 IPv4 地址块比例 | 21.1% | 超过五分之一的地址块允许伪造源地址出网 |
| 可被假冒的自治系统比例 | 24% | 约四分之一的 AS 未部署任何出口过滤 |

PPT 用红色表示最容易伪造、绿色表示最安全。这个数字的意义在于：源地址过滤是**部署激励极弱**的一类措施——你部署了，受益的是别人；别人不部署，受害的是你。所以二十多年过去，仍有近四分之一的路由域敞开。

### 6.2.5 危害为什么超出网络层

PPT 给了三层递进的论证：

1. **跨层污染**：IP 是核心底层协议，上层协议把 IP 地址当作对端标识。伪造源地址不只是骗了 IP，而是连带欺骗了所有以地址为凭据的上层协议，攻击能力因此溢出网络层，危害其他层。
2. **追责失效**：攻击者借伪造隐藏身份与位置，逃避法律制裁。安全事件的“事后追溯”这一环直接断掉。
3. **运维失能**：基于真实地址的网络计费、管理、监控、安全认证全部无法正常进行——你不知道流量是谁发的，就既不能计费也不能定责。

这三条合起来说明：源地址真实性不是“多加一个功能”，而是**其他安全机制能否成立的地基**。审计、溯源、计费、准入，全都预设了地址是真的。

## 6.3 传统防御手段及其局限

### 6.3.1 两条技术路线

针对“源地址可伪造”这一脆弱性，历史上出现过两类思路，PPT 归纳为四条脆弱性对应两类防御：

| 脆弱性 | 对应防御思路 |
|---|---|
| 数据包都是 01 序列、彼此同质 | 数据包签名：给包加上可验证的身份标签 |
| IP 首部源地址可随意填 | 数据包签名 / 出流量源地址检测 |
| 数据包中不存在签名 | 数据包签名 |
| 网关等设备不检测出流量源地址 | 出流量源地址检测 |

而“互联网根本设置，难以修正”这一条，是所有方案共同的天花板：任何要求全网同时升级的方案，在工程上都等于不可行。

### 6.3.2 具体方法与缺点对照

| 防御种类 | 方法 | 原理简介 | 缺点 |
|---|---|---|---|
| 数据包签名 | SPM、Passport、StackPi、Base | 在 IP 首部的 ToS 或其他较少使用的选项字段中加入用户身份鉴别标签 | 假冒者可以学习标签的添加方法，从而逃避验证 |
| 数据包签名 | HIP（Host Identity Protocol） | 修改终端主机协议栈，在 IP 层与传输层之间插入“主机标识层” | 需改端系统，实际部署困难 |
| 出流量源地址检测 | Ingress Filtering | 路由器检查出流量源 IP 是否属于该路由器所属网络，不属于则丢弃 | 配置过于复杂 |
| 出流量源地址检测 | uRPF（unicast Reverse Path Forwarding） | 用源地址反查路由表，判断该地址应走的出接口是否与报文入接口一致 | 无法防同方向的地址假冒；路由非对称会造成假阳性误判 |
| 出流量源地址检测 | SAVE | 为路由器提供拓扑、时钟等附加信息，设计整套数据包验证与路由机制 | 协议过于复杂，且需要修改用户主机协议栈 |

逐条看它们的失效点，逻辑其实很一致：

- **签名类**败在“标签可被学习”。标签是包头里的一段可写字段，攻击者只要知道格式就能照样写一个，验证方无法区分“原始签发”和“照着抄”。要真正不可伪造，标签必须与密钥绑定，而这又要求密钥分发基础设施。
- **HIP** 败在“要动终端”。它把身份从地址中剥离出来，方向正确，但要让全球几十亿台主机换协议栈，等于重做互联网。
- **Ingress Filtering** 败在“配置成本”。它要求每个边缘路由器精确掌握“本网络应出现的源前缀”，在多出口、客户自带地址、移动场景下规则迅速膨胀。
- **uRPF** 败在“假设对称”。它默认“回程路径 = 来程路径”，一旦路由非对称（多宿主、流量工程、Anycast），合法流量就被误杀；而“同方向假冒”——攻击者与被伪造者从同一接口进来——它根本看不见。
- **SAVE** 败在“复杂度与改主机”两点同时踩。

> 补充：uRPF 有严格与松散两种模式——严格模式要求反查出的出接口与入接口一致，松散模式只要求该源前缀在路由表中存在。前者更安全但误杀多，后者误杀少但基本挡不住伪造，这正是“配置折衷换不来安全”的典型例子。

### 6.3.3 共性缺陷：为什么需要体系结构而不是补丁

PPT 对这批技术的总评是四句话，值得背下来：

1. **互不相关**：现有源地址验证技术相互独立，只能部分地解决源地址验证的问题。
2. **没有整体结构**：没有人把它们串成一个覆盖整个网络的完整体系。
3. **算法复杂、协议开销大**：验证本身消耗转发资源，路由器是性能敏感的。
4. **缺乏部署激励**，且**完备性不足、可扩展性不足**。

“部署激励”是这里最关键的一句。源地址过滤是典型的正外部性行为：部署者付出性能与配置成本，收益由被保护者享有。没有强制、没有结算、没有可见收益时，理性的运营商都会观望——这就是 21.1% 这个数字背后的经济学。

因此 SAVA 的定位不是“再发明一个过滤算法”，而是**设计一套分层、可增量的体系结构**，让不同位置的部署者各自获得局部收益，且不部署的区域不会让已部署区域失效。

## 6.4 SAVA 的总体设计：三层结构与三条原则

### 6.4.1 由来与标准地位

2005 年，清华大学在国际上首次提出真实源地址验证体系结构 SAVA，从**接入网、域内、域间**三个层次设计关键技术，形成系列化 IETF 国际标准，并推动 IETF 成立了接入网真实源地址验证工作组 SAVI（Source Address Validation Improvements）。

三个标志性成果：

| 标准 | 内容 | 地位 |
|---|---|---|
| RFC 5210 | SAVA 体系结构与测试床、部署经验 | 我国获得的第一个试验类 RFC；国际上首次提出“基于真实 IPv6 源地址的网络寻址体系结构”；入选 2008 年中国高校十大科技进展 |
| RFC 7039 | 接入网内监听地址分配控制报文，动态绑定端设备 IP 与通信端口（SAVI） | 接入网层的核心标准 |
| SAVA-X | 自治域间建立信任联盟实现源地址验证 | 域间层方案 |

注意 RFC 5210 的性质：它是 **Testbed and Deployment Experience**（测试床与部署经验）类文档，不是纯协议规范。这说明该体系从一开始就是“边做边验”的路线，而不是纸面架构。

### 6.4.2 “真实”的三重含义

SAVA 的目标是“在网络层提供一种透明的服务，确保互联网中转发的每一个分组都使用真实 IP 源地址”。这里的“真实”有三个并列的判据，考试常考：

| 含义 | 判据 | 靠什么保证 |
|---|---|---|
| 经授权的 | 源地址必须是经互联网 IP 地址管理机构分配授权的，不能伪造 | 地址分配链条 + 分配信息监听 |
| 唯一的 | 源地址必须全局唯一 | 地址分配机制的排他性 + 冲突检测 |
| 可追溯的 | 可根据源地址找到其所有者与位置 | 地址与接入端口/设备的绑定关系 |

三者是递进关系：授权解决“能不能用”，唯一解决“是不是只有你在用”，可追溯解决“出了事找不找得到你”。少任何一条，验证都是残缺的——只做“唯一”不做“授权”，等于承认抢来的地址合法。

### 6.4.3 三层结构与粒度

```
+------------------------------------------------------------------+
|  域间层（自治域 / 地址域之间）                                    |
|  机制：信任联盟 + 可验证标签（SAVA-X）                            |
|  粒度：地址域前缀       目标：前缀不被冒用、跨域可验证            |
+------------------------------------------------------------------+
|  域内层（自治域 / 地址域内部）                                    |
|  机制：标签 + 分布式路由同步（SAVA-P）                            |
|  粒度：前缀             目标：保护核心设备不被伪造源攻击          |
+------------------------------------------------------------------+
|  接入层（接入网）                                                 |
|  机制：监听地址分配控制报文 + 绑定锚（SAVI）                      |
|  粒度：主机 / 单个地址  目标：地址使用可追溯                      |
+------------------------------------------------------------------+
        ^ 越靠下越接近主机：验证越精确、绑定越难欺骗、开销越集中
```

三个层次的组织特点，PPT 明确列为三条：

1. **不同层次实现不同粒度的验证**——越靠近主机，粒度越细（单个地址），越靠近骨干，粒度越粗（前缀、地址域）；这符合“越靠近源头的证据越可靠、越远离源头越只能做粗判”的物理规律。
2. **每一层次允许不同运营商采用不同方法**——不做全球唯一实现，避免“一刀切”导致无法部署。
3. **整体简单性与部分灵活性的平衡**——结构上只有三层（简单），每层内部实现自由（灵活）。

### 6.4.4 三条设计原则

PPT 第 2 节把设计原则归为三组，每组内部再分点。这是本章理论性最强的一块。

**（1）可扩展性**

- 层次化是满足可扩展性的常用手段：各层按约定协议简单交互，不必关心对方内部实现细节，效率因此提升。互联网本身就是这么做的——网络五层模型、多级 ISP、层次化路由、层次化 IP 寻址，全是同一招。
- 反例是**扁平结构**：如果源地址验证是扁平的，每一个验证实体都要具备“对所有对等实体验证”的能力，信息量与状态量随规模平方增长，必然崩。
- 但层次化不能过度耦合：需要建立合理的层次间关系，使各层能协作，同时避免层间过度依赖。
- 还要允许**粒度可变**：当前网络在可部署性上并不均匀，有些区域能做到主机粒度，很多区域连前缀都难控制。因此必须支持划分灵活可变的验证粒度。

**（2）可演进**

| 维度 | 要求 | 原因 |
|---|---|---|
| 与已有协议兼容 | 技术所依赖的协议必须与现有体系结构协议兼容 | 技术依附于现有体系实现，不能要求先换掉互联网 |
| 自身部署可演进 | 过渡阶段允许部分区域已部署、部分未部署，二者要能共存 | 部署是持续过程，不可能一次到位 |
| 运营商之间可演进 | 允许不同运营商各自实现，各部分相互独立、功能互不依赖 | 避免被单一厂商方案或单一运营商节奏绑架 |

**（3）安全性**

给现有体系“赋予安全性”的方案，自身必须安全，否则就是引入新的攻击面。PPT 列了三个风险：

| 风险 | 内容 | 设计要求 |
|---|---|---|
| 可信标识风险 | 标识本身可能被伪造或复用 | 标识应具备唯一性、可追溯性 |
| 数据转发风险 | 携带标签的数据包在转发中可能被篡改 | 保证标签不被篡改；即使被篡改也应被及时准确识别 |
| 单点信任风险 | 验证依赖某个中心设施，则该设施成为攻击目标 | 标签验证不应依赖中心化网络基础设施 |

“单点信任风险”这条是设计上的关键取舍：它直接否定了“全球统一的地址验证中心数据库”这类方案，也解释了为什么后文的域间方案要用**区块链 + 联盟**这种去中心结构——不是为了时髦，是为了消除单点。

### 6.4.5 部署收益

PPT 列的收益可以分成“安全”与“运维”两组：

| 类别 | 收益 | 机制解释 |
|---|---|---|
| 安全 | 安全责任明确 | 地址可归属到机构与人，责任边界清晰 |
| 安全 | 易于追踪攻击事件、定位攻击者 | 源地址可回溯到接入端口 |
| 安全 | 杜绝基于伪造源地址的攻击 | 伪造包在接入或边界即被丢弃 |
| 运维 | 网络管理简化 | 地址即身份，减少额外标识体系 |
| 运维 | 简化身份认证 | 网络层已提供可信标识，应用层可复用 |
| 运维 | 流量可审计、不可抵赖 | 源地址真实 → 记录可作证据 |
| 运维 | 支持基于 IP 地址的网络计费 | 计费前提“流量归属明确”被满足 |

这张表的价值在于回答“凭什么让运营商部署”：安全收益是社会性的，而**管理与计费收益是运营商自己的**。体系结构要落地，必须让部署者先赚到后一半。

## 6.5 地址结构与“地址域”：部署范围为何会失配

### 6.5.1 一个地址，两个角色

IPv4 地址 32 位，被切成网络 ID 与主机 ID 两段：

| 部分 | 标识什么 | 角色 |
|---|---|---|
| 网络 ID（network） | 主机所在的网络 | 位置信息 |
| 主机 ID（host） | 特定主机 | 身份信息 |

```
 0                    8                    16                   31
 +--------------------+--------------------+--------------------+
 |        网络 ID（位置信息）              |   主机 ID（身份信息） |
 +--------------------+--------------------+--------------------+
```

分类编址把这条切分线固定在字节边界上，历史分类如下：

| 类别 | 地址范围 | 用途 |
|---|---|---|
| A | 1.0.0.0 – 127.255.255.255 | 政府机构等超大规模网络 |
| B | 128.0.0.0 – 191.255.255.255 | 大中型企业 |
| C | 192.0.0.0 – 223.255.255.255 | 个人/小型网络使用 |
| D | 224.0.0.0 – 239.255.255.255 | 组播 |

这个“一个字段干两件事”的设计是整个问题的源头。位置本应随接入点变化（我换到另一个网络，位置就该变），身份本应终身不变（我还是我）。把二者压进同一个 32 位字段，结果是：**地址一变身份就断，地址不变位置就无法移动**。更要命的是，验证“这个地址是否合法”必须同时知道“它在哪”和“它是谁”，而网络层只诚实地记录了前者的一部分。

> 补充：这也是后来移动 IP、标识分离（Identifier/Locator Split）等研究方向共同的出发点——它们都想把位置与身份拆成两个命名空间，代价是要改动上层协议。

### 6.5.2 自治域：管理边界从哪来

出于管理便利性与扩展目的，全球互联网被划分成许多自治域（Autonomous System, AS）。一个 AS 可以是一个简单网络，也可以是一个或多个实体管理控制的网络群体。

| 属性 | 内容 |
|---|---|
| 域内路由 | 同一 AS 内使用相同的域内路由协议（Interior Gateway Protocol, IGP），如 OSPF、RIP |
| 域间路由 | AS 之间采用域间路由策略，即 BGP |
| 编号 | 运营商、机构、公司均可申请自治系统号（ASN），所分配 IP 地址清楚标记归属哪个 ASN |
| 规模（截至 2021 年 1 月） | 全球共分配 177776 个 ASN，中国占 2883 个 |

划分 AS 的两个好处，正好对应 SAVA 关注的“可扩展”与“可演进”：

1. **资源可控**：路由器只需保存本域内链路状态，存储、更新、查询的资源占用保持在合理区间，路由更快。
2. **策略独立**：域内策略修改不影响网络其他部分，各域可按自身需求采用不同策略。这正是 SAVA“每层允许不同运营商用不同方法”的现实基础。

### 6.5.3 早期的三粒度划分与失配

源地址在分配上天然分层：AS 从区域地址分配机构（RIR）获取多个前缀，前缀再被拆细分配给域内各子网，主机从所接入的子网获取地址。基于这个链条，早期 SAVA 很自然地把验证划成三个粒度：

```
   AS 粒度  ──>  前缀粒度  ──>  主机粒度
   （域间）      （域内）        （接入）
```

问题出在**增量部署**。随着技术推广，出现了一个 AS 内“部分子网已部署 SAVI、其余子网尚未部署”的中间状态。此时验证边界（部署到哪）与地址管理边界（谁管哪段前缀）不再重合，这就是**部署与地址管理范围的失配**。

PPT 举的例子极典型：**很多校园网并没有申请 AS 号，也不采用 BGP 协议**。它既不是一个标准意义上的 AS，又确实是一大片需要统一管理的地址空间。按“AS—前缀—主机”三粒度去套，这类网络无处安放；按 AS 边界去部署，它连边界都没有。

### 6.5.4 用“地址域”替代“自治域”

SAVA 的解法是引入一个新的管理单元——**地址域**：

> 地址域：同一机构所属的全部 IP 地址中的可部分管理范围。

这个定义有两个要点：归属同一机构，且**可以只取其中一部分**。于是地址域是可以嵌套、可以任意切分的：

```
 +------------------------------------------------------------+
 | 校园网（一个地址域）                                        |
 |  +----------------------+  +----------------------------+  |
 |  | 某院系（子地址域）    |  | 另一院系（未部署，留空）    |  |
 |  |  +----------------+  |  |                            |  |
 |  |  | 某所（子地址域）|  |  |                            |  |
 |  |  |  +-----------+ |  |  |                            |  |
 |  |  |  | 某组      | |  |  |                            |  |
 |  |  |  +-----------+ |  |  |                            |  |
 |  |  +----------------+  |  |                            |  |
 |  +----------------------+  +----------------------------+  |
 +------------------------------------------------------------+
   地址域边界 = 机构/管理边界，与 AS 边界解耦
```

地址域可以是某院系下的某个所某个组，也可以是某个所、某个院系，甚至整个校园网。它“显著提升了体系结构的灵活性”，使部署结构可以贴合真实的管理边界，而不是贴合 BGP 拓扑。

于是三层结构改写为“接入网—地址域内—地址域间”，其优点是**松耦合、多重防御、支持增量部署**。三层各自的职责被明确切成：

| 层次 | 提供的能力 | 目标 |
|---|---|---|
| 接入层面 | 主机粒度的源地址验证 | 保证地址使用的可追溯性 |
| 地址域内层面 | 前缀级别的保护 | 保护核心设备不被（伪造源的）攻击打垮 |
| 地址域间层面 | 地址域级别的联盟内可验证 + 保护自身不被伪造 | 前缀不被冒用，跨域流量可验证 |

这里有一个值得注意的设计思想：**每层的目标不是“完全验证”，而是“保护本层最值钱的东西”**。核心路由器最怕的是被伪造源的高速流量打瘫，那就只需要前缀级粗过滤；终端地址是否精确到主机，交给接入层。这就是“多重防御”——不追求一层解决全部，而是层层削减攻击面。

## 6.6 接入网：SAVI 的三步曲

### 6.6.1 基本思想：不听声明，只听分配过程

SAVI 的核心洞察很朴素：**源地址不可信，但“地址是怎么分配出去的”这个过程是可信的**。地址分配由网络侧的服务器/路由通告完成，这些控制报文是网络设备自己发的，攻击者伪造不了（或很难伪造）。

于是验证被拆成三步：

| 步骤 | 动作 | 说明 |
|---|---|---|
| 1 获取合法地址 | 监听控制类报文（ND、DHCPv6 等），即 CPS 分组，获取地址分配信息，识别主机合法 IP 源地址 | 不听主机“自称”，只听网络“分配” |
| 2 建立绑定关系 | 将合法 IP 地址与主机网络附属的**链路层属性**绑定，该属性称“绑定锚” | 绑定锚可验证，且比主机 IP 源地址本身更难欺骗 |
| 3 匹配验证 | 对数据包的 IP 源地址与其绑定锚进行匹配，不匹配则丢弃 | 逐包检查，就近执行 |

```
  主机                     接入交换机（SAVI）                 DHCPv6/ND
   |  ① 申请地址（ND/DHCPv6）  |                                 |
   |------------------------->|===== ② 旁路监听 CPS ===========>|
   |<-------------------------|======== 地址分配结果 ============|
   |                           |                                 |
   |                           | ③ 写入绑定表：                  |
   |                           |    IP  <-->  绑定锚(端口/MAC)   |
   |  ④ 发数据包(源IP=X)        |                                 |
   |------------------------->| ⑤ 查表：X 对应的锚 == 入端口?   |
   |                           |    是 -> 转发   否 -> 丢弃      |
```

两个关键判断，PPT 直接给出：

- **绑定锚“可验证，且比主机的 IP 源地址本身更难欺骗”**——因为链路层属性（端口、MAC、VLAN、隧道标识）由设备本地掌握，远端无法伪造。
- **部署位置越靠近主机，有效性越高**——越靠近，能看到的控制报文越完整，绑定越难绕过；越往上走，看到的地址已被聚合，只能做粗判。

### 6.6.2 接入网的三种异构性

SAVI 之所以要为不同场景设计不同方案，是因为接入网在三个维度上都不统一：

| 维度 | 表现 | 对验证的影响 |
|---|---|---|
| 终端多样性 | 手机、电脑、服务器、嵌入式设备；同一类设备系统还可能不同（安卓/iOS） | 终端能力与行为差异大，不能要求终端配合 |
| IP 分配方式多样性 | DHCP 分配、SLAAC 分配、静态配置 | 有无可监听的控制报文不同，绑定依据不同 |
| 接入方式多样性 | 有线、无线等 | 不同接入模式可用的绑定锚不同（端口/关联标识） |

```
                  +---------------------------+
                  |        接入网              |
   终端  -------->|  安卓 / iOS / PC / 服务器  |
                  |  嵌入式设备                |
   分配  -------->|  DHCP / SLAAC / 静态配置   |
                  |                           |
   接入  -------->|  有线(port) / 无线(?)      |
                  +---------------------------+
```

这也是 PPT 里那几个“?”的含义：无线接入没有“物理端口”这个锚，锚的候选变成了关联标识一类的东西，所以方案必须按接入技术分别定义。

### 6.6.3 三类标准方案

SAVI 针对上述异构性设计了对应的验证方式，其设计前提是：**所有相关网络设备在同一个网络管理机构的管理控制之下**（这也是接入网层能成立的根本前提——单域可控）。方案与两件事密切相关：接入子网的地址管理分配与控制策略，以及端系统的接入方式。

| 方案 | 标准 | 适用场景 | 解决的核心问题 |
|---|---|---|---|
| SAVI-DHCP | RFC 7513 | DHCP 分配地址（DHCPv4 / DHCPv6） | 有状态分配下的绑定建立与验证 |
| SEND SAVI | RFC 7219 | SEND 地址分配场景 | 基于加密地址的分配场景下的绑定 |
| FCFS SAVI | RFC 6620 | 无状态地址分配（SLAAC 一类） | 先来先服务式的绑定与验证 |

FCFS（First-Come First-Served）这个名字已经暴露了它的弱点：无状态分配下没有权威的“分配记录”可听，只能按“谁先声明谁拥有”来绑定，验证强度弱于 DHCP 场景。这是接入网层最实际的一块软肋——**静态配置地址的主机根本不发任何申请报文，SAVI 只能退化处理**。

### 6.6.4 SAVI-DHCP 的完整流程

PPT 用主机 A、攻击主机、DHCPv6 服务器、SAVI 交换机四个角色描述了一次正常接入。把二者合并成一条完整时序（IPv6 场景，同时含 RA 与 DHCPv6）：

| 步 | 报文/事件 | 方向 | SAVI 交换机动作 |
|---|---|---|---|
| 1 | 汇聚交换机发 RA 通告 | 网络 → 主机 A | 旁路监听，记录前缀信息 |
| 2 | 主机 A 依前缀自动生成 IPv6 地址 | 主机本地 | — |
| 3 | 主机 A 发 DHCPv6 request | 主机 → 服务器 | 记录请求的客户端标识与源链路层信息 |
| 4 | DHCPv6 服务器回 reply（含 IPv6 地址、DNS 等信息） | 服务器 → 主机 | 监听分配结果，暂不立即建绑定 |
| 5 | 主机 A 发 DAD（重复地址检测）报文 | 主机 → 链路 | 观察是否收到 NA（邻居通告） |
| 6 | 规定时间内未收到 NA | — | **建立 DHCP 绑定**：地址 ↔ 绑定锚 |
| 7 | 攻击主机以伪造源地址发包 | 攻击者 → 网络 | 源地址与绑定锚不匹配，丢弃 |

第 5、6 步的设计很讲究：**绑定不是在“分配完成”时建立，而是在“冲突检测通过”后建立**。因为地址分配出去不等于地址可用——如果链路上已有人用这个地址，DAD 会收到 NA，此时建立绑定就会把地址绑到错误的主机上。等到 DAD 静默期结束再建绑定，等于把“唯一性”这一重含义也纳入了验证。

部署位置：SAVI 功能部署在**接入设备**上，网络中包含 DHCP 服务器、接入交换机、无线接入点等。SAVI 交换机通过执行 DHCPv4/v6 监听（snooping）建立“DHCP 分配的地址”与“主机对应绑定锚”之间的绑定关系，用来验证报文中源地址的真实性。

### 6.6.5 SAVA-MIX：多方案共存时的绑定表

SAVI-DHCP、FCFS SAVI、SEND SAVI “通常被视为彼此独立的，每个方法处理自己的条目”。如果同一台设备上同时启用多种方法而不做协调，就会出现一个荒诞的结果：**每一种方法都会拒绝通过其他方式绑定的数据包**。一台主机用 DHCP 拿到地址，另一台用 SLAAC 自配置，两者的绑定分属不同的表，交叉验证必然误杀。

SAVA-MIX 就是解决这个问题的统一绑定表管理模块：

| 步 | 动作 |
|---|---|
| 1 | 某种 SAVI 方法生成 IP 地址与对应绑定锚后，向 SAVA-MIX 请求在绑定表中设置条目 |
| 2 | SAVA-MIX 检查绑定表中是否存在冲突（同一地址被不同锚绑定，或同一锚绑定不同地址） |
| 3 | 无冲突则生成新绑定条目 |
| 4 | 有冲突则按既定策略进行冲突解决 |

这套机制被称为“动态自适应的地址分配分组监听”。它的价值在 PPT 中被总结为两点：

- **对现有网络设备与主机协议栈透明**：不修改协议、不修改主机，能适应复杂、动态、大规模的实际网络环境。这是它能部署的前提。
- **实现地址级的无漏判源地址验证**：通过与合法 IP 地址关联设备标识，达到“端网协同”，同时保证接入网兼容性。

“无漏判”这个词需要理解准确：它的意思是**凡是经过绑定表覆盖的地址，都能被逐包核对**，而不是“任何伪造都能拦住”。绑定表本身覆盖不到的情况（如静态配置、未部署设备的下挂子网）不在其保证范围内。

## 6.7 域内与域间：从主机粒度到地址域粒度

### 6.7.1 域内层：标签 + 分布式路由同步

接入层解决了“终端到接入交换机”这一段，包进了汇聚/核心层之后就没有人管了：核心路由器收到的包，源地址可能属于本域内任何一个前缀，它需要一种**低成本**的方式判断“这个源地址是否可能从那个方向来”。

域内方案的基本形态是：**入口打标签，沿途按标签与路由同步信息校验**。

```
  接入区               汇聚/核心（域内）                 出口边界
  ------               ------------------                --------
  主机 --> SAVI 交换机 --> [核心路由器 A] --> [核心路由器 B] --> 边界
              打标签L        校验L与入端口/前缀一致      剥离/透传
                              （依赖分布式路由同步）
```

PPT 在域内层列出两项关键技术：**分布式路由同步**与**数据包防篡改**；产品化部分则说明域内验证“允许配置标签和实现路由同步功能”。也就是说，域内路由器必须知道“哪个前缀应该从哪个方向来”，这份信息靠路由协议同步获得，标签则用于在包上携带“我是从哪个域/哪个区进来的”。

它的定位是**保护核心设备**：核心路由器最怕的是被伪造源的高速流量打瘫（转发面与控制面同时受压），因此这一层只需要前缀级粗过滤——源地址不属于本域任何前缀、或不属于该入方向应出现的集合，直接丢。粒度粗，但开销小，能线速执行。

### 6.7.2 域间层：SAVA-X 的信任联盟

跨域这一段没有共同的管理者，接入层的“单域可控”前提彻底失效。SAVA-X 的思路是**在地址域之间建立信任联盟**，把验证能力做成“联盟内互认”：

| 要素 | 内容 |
|---|---|
| 部署位置 | 联盟成员的**边界路由器**上 |
| 出方向职责 | 为本域内发往其他联盟成员的报文做**地址域级别的源地址前缀检查**，保证源自本地址域的报文，其源地址确实属于本地址域 |
| 打标签 | 为“源自本地址域、宿于其他成员地址域”的报文添加用以标识本地址域身份的**标签**，该标签可验证，确保地址域前缀不被冒用 |
| 入方向职责 | 校验来包携带的标签与源前缀是否一致，不一致则丢弃 |

```
  地址域 A                                          地址域 B
  --------                                          --------
  主机 --+                                    +--> 主机
         |                                    |
    [边界路由器A]  === 标签(A) + 源前缀检查 ===>  [边界路由器B]
         ^                                    ^
         |  联盟内互认：标签可验证              |
         +------------------------------------+
              伪造者无合法标签，无法冒充 A 的前缀
```

PPT 图中标注了三类设备/角色：AER、REG 与 SMA（State Machine based Anti-spoofing，基于状态机的防伪造）。其中 SMA 是明确给出全称的：**用状态机来防伪造**。

状态机防伪造的逻辑可以这样理解：边界路由器为每条“前缀—标签”关系维护一个状态，报文必须落在当前状态允许的取值集合内才被接受。标签不是固定常量（固定常量会被照抄，这正是 SPM 一类方案失败的原因），而是随状态推进而变化的量，因此“抄一次”没有用，抄来的标签在下一个状态就失效。这正是 6.4.4 中“即使被篡改也应被及时准确识别”这条原则的落地方式。

> 说明：PPT 只给出 AER、REG 两个缩写，未给出全称与职责说明；此处仅按图注位置描述为边界侧设备与注册/记录类实体，不作展开，避免臆测。

### 6.7.3 用区块链组织域间联盟

联盟要解决的是“互认的信任从哪来”。传统做法是找一个中心机构签发与核验标签，但这违反 6.4.4 的“单点信任风险”原则。SAVA-X 的选择是**用区块链做信任基础**：

| 组成 | 作用 |
|---|---|
| 密钥/证书 | 每个地址域的身份凭据 |
| 分布式结构 | 不依赖单一中心节点 |
| 共识系统 | 对联盟状态达成一致 |
| 区块链协商状态机种子 | 用链上共识结果初始化状态机，使各域状态机同步 |

组织方式是**两层联盟**：

**子联盟内**——各地址域之间维护 1 对 1 的标签状态，通信过程**不涉及标签替换**；子联盟内选择一个**主地址域**。

**子联盟间**——由主地址域之间交互“子联盟级前缀”与状态机，联盟间状态机用主地址域号表示，形如 `<主地址域1, 主地址域2>`。

```
            子联盟 1                        子联盟 2
   +-------------------------+     +-------------------------+
   |  域A1 <--1对1标签--> 域A2 |     |  域B1 <--1对1标签--> 域B2 |
   |        \               /  |     |        \              /  |
   |         \  主地址域A*  /   |     |         \ 主地址域B* /   |
   +-------------|-----------+     +-------------|-----------+
                 |   <A*, B*> 状态机 + 子联盟级前缀
                 +-------------------------------+
                        虚拟 AS (AS_V) 代表“所有其他子联盟”
```

**虚拟 AS（AS_V）** 是关键技巧：它代表所有其他子联盟，并包含所有其他子联盟的前缀。有了它，边界地址域只需面向两个对象做标签处理——“联盟内成员”与“AS_V”，而不必为每一个远端联盟维护一套标签。边界地址域据此进行标签替换（虚拟地址域维护子联盟间标签）。

PPT 明确说明这么做的目的：**利用虚拟地址域避免多径传输带来的标签替换难题**。多径场景下同一对域之间的流量走不同路径，若逐路径维护标签，状态会爆炸；用 AS_V 把“外部”聚合成一个对象，替换规则就收敛了。

### 6.7.4 三层机制的对照

| 维度 | 接入层 SAVI | 域内层 | 域间层 SAVA-X |
|---|---|---|---|
| 验证粒度 | 主机/单个地址 | 前缀 | 地址域前缀 |
| 信任基础 | 本域地址分配过程 | 域内路由同步 | 联盟 + 区块链共识 |
| 部署位置 | 接入交换机、AC/AP | 汇聚/核心路由器 | 边界路由器 |
| 主要目标 | 地址使用可追溯 | 保护核心设备 | 前缀不被冒用、跨域可验证 |
| 对终端要求 | 透明，不改主机 | 透明 | 透明 |
| 失效条件 | 静态配置/未部署子网 | 路由不同步、标签伪造 | 联盟外流量、联盟未覆盖 |

## 6.8 增强机制：可信身份标识与数据包防篡改

源地址真实只解决“包从哪来”，不解决“包是谁发的”和“包有没有被改过”。PPT 在体系结构之上加了两个增强件。

### 6.8.1 基于 IPv6 的可信身份标识

**技术难点**：网络是分布式管理的，每个管理域有自己个性化的终端标识，跨域时有效性大幅降低。因此要求真实性标识必须基于**统一结构**，否则 A 域的标识到 B 域无法解读。

**研究思路**：用 IPv6 地址空间承载终端标识，保障跨域验证的有效性。具体做法是利用 IPv6 地址强大的语义表达能力，把**IPv6 地址后 64 位的设备标识符**（接口标识）替换为经过验证和哈希处理的可信设备标识符（AID）：

```
 |<------------------ 前 64 位 ------------------>|<--------- 后 64 位 --------->|
 +-----------------------------------------------+------------------------------+
 |            子网前缀（路由用，分层聚合）        |  可信设备标识符 AID（哈希后） |
 +-----------------------------------------------+------------------------------+
                                                  ^
                                    原为 EUI-64/MAC 派生的接口标识，可伪造
                                    现改为经认证的 AID，携带端设备信息
```

三项配套工作：

| 工作 | 内容 |
|---|---|
| 嵌入标识符的 IPv6 地址生成 | 设计嵌入 AID 的地址生成算法，兼顾多种 IPv6 地址分配机制与组网环境，把端设备信息携带在数据包中，实现端网协同 |
| 可信设备标识符 | AID 的认证、管理与溯源基础 |
| 设备追溯审计机制 | 构建 AID 的认证、管理、追溯与审计机制；地址标识采用**动态更新**机制，达到对终端设备或终端用户的身份动态标识与隐私保护 |

注意“动态更新”与“可追溯”的张力：地址随身份动态变化，隐私得到保护；但变化过程被审计机制记录，因此仍可回溯。这是隐私与追责之间的工程折衷——**不是让地址永久不变，而是让变化留痕**。

最终效果：在地址真实性基础上，通过在 IP 地址中嵌入可信设备标识符，实现端网协同的真实用户身份识别与溯源，赋予地址**防重放、防逆推、防 DDoS** 的特性。这里“防逆推”指不能由地址反推出设备原始标识（哈希的单向性），“防重放”指 AID 动态更新使旧地址失效。

### 6.8.2 数据包防篡改机制

**技术难点**：SAVA 保障了源地址的真实性，确保数据包源地址可追溯、可验证。然而数据包在域间传递的过程中，**数据内容仍存在被篡改的风险**。此外还有一个反向的难点——**源端无法判断正确标签**（源端不知道沿途各域会打什么标签，因此无法预先对“最终形态的包”做签名）。

**研究思路**：数据包完整性校验。实现方式是：利用 SAVA-X 标签证明源端身份，再增加数据包摘要信息，二者共同生成数据包签名。

```
   源端                                         中间节点
   ----                                         --------
   载荷 --哈希--> 摘要
   摘要 + SAVA-X标签 --签名算法--> 签名  ---->  转发（可校验，但无法重新签名）
                                                原因：中间节点没有源端的 SAVA-X 标签
```

安全性来自一个简单的不对称：**中间节点不具有源端 SAVA-X 标签，因而无法伪造数据包签名**。攻击者可以改内容，但改完签名就对不上；可以重放，但标签状态已推进。

该机制的特点被概括为：验证效率高、复杂度低、部署结构可扩展性强、防篡改能力突出。这四条正好回应了 6.3.3 里对传统签名方案的批评——传统方案要全网共享密钥或改协议栈，这里把“密钥”换成了体系结构里本来就有的标签。

### 6.9.3 局限：这套方案还差什么

把 PPT 全篇的信息收拢，SAVA 的局限可以归成五条，每条都能在原文里找到依据：

| 局限 | 具体表现 | 依据 |
|---|---|---|
| 覆盖不完备 | 只保证“已部署域”内的真实性；联盟外、未部署子网、静态配置主机仍是缺口 | 6.3.3“完备性不足”；FCFS 场景；联盟内外之分 |
| 增量部署的状态成本 | 部分部署时需处理边界互操作，绑定表与标签状态在多方案共存时须统一协调 | SAVA-MIX 的存在本身；6.5.3 失配问题 |
| 静态地址与无控制报文场景 | 无可监听的分配报文，只能退化为先来先服务式绑定，验证强度下降 | FCFS SAVI（RFC 6620）的定位 |
| 跨域信任的组织成本 | 区块链联盟需要成员互认、证书体系、状态机同步；联盟规模越大，协商与替换规则越复杂 | 6.7.3 主地址域、虚拟 AS 等机制均为复杂度代价 |
| 仍是“打补丁”而非重构 | 建立在现有体系结构之上，地址仍承担位置+身份双重角色；根本矛盾未消除，只是被层层校验包住 | 6.4.4 可演进原则“依附于现有体系结构实现” |

其中最后一条最值得记住。PPT 结尾的科学问题段落给出了完整的问题图谱——开放网络面临三重不可信：

| 不可信对象 | 后果 |
|---|---|
| IP 地址不可信 | 具有开放、易伪造特性的地址，严重破坏网络通信真实性 |
| 路由不可信 | 路由体系无法为用户提供可信通信渠道，可能造成严重信息泄露 |
| 用户及资源标识不可信 | 基础设施面临仿冒伪造，无法确保用户与服务的真实性 |

这三者共同指向一个科学问题：**开放网络的跨域可信访问**，以及**网络安全策略与行为一致性保证**。SAVA 解决的是第一条里的“地址”部分，另外两条仍在路上。PPT 用一句老话作结——“画虎画皮难画骨，知人知面不知心”：地址可以画得很像，皮相之下是谁，才是难点。

## 考点提示

- **最根本的缺陷是地址，不是路由也不是应用。** 依据：IP 地址同时承担位置与身份双重角色，且是上层协议识别对端的唯一凭据。
- **伪造源地址只需两步条件成立。** 一是首部源地址由发送方填写且无签名，二是网关不检查出流量源地址是否来自本网。缺一不可。
- **CAIDA 数据要记量级**：截至 2021 年 2 月，可被假冒的 IPv4 地址块约 21.1%，自治系统约 24%，即超过五分之一。
- **uRPF 的两条失效原因必考**：不能防同方向假冒；路由非对称导致假阳性。Ingress Filtering 的失效原因是配置过于复杂。
- **签名类方案（SPM/Passport/StackPi/Base）的共同死穴**：标签可被学习模仿，因为标签是包头里可写的字段，与密钥无关。
- **SAVA 三层与三粒度要能对上**：接入网—主机（地址）、域内—前缀、域间—地址域前缀。越靠近主机，有效性越高。
- **真实源地址三重含义**：经授权、唯一、可追溯。答题时三者并列写，不要只写“不能伪造”。
- **SAVA 三条设计原则**：可扩展（层次化 + 粒度可变）、可演进（协议兼容 / 部署共存 / 运营商各自实现）、安全（标识唯一可追溯 / 防篡改 / 无单点信任）。
- **SAVI 三步曲**：监听控制报文取合法地址 → 与链路层属性（绑定锚）绑定 → 逐包匹配验证。绑定锚比 IP 更难欺骗是关键理由。
- **三份 SAVI RFC 的分工**：RFC 7513（DHCP）、RFC 7219（SEND）、RFC 6620（FCFS，无状态）。RFC 7039 是 SAVI 框架本身，RFC 5210 是 SAVA 体系结构与测试床。
- **SAVA-MIX 要解决的问题**：多 SAVI 方法共存时互相拒绝对方建立的绑定，需统一绑定表并做冲突解决。
- **地址域的定义与意义**：同一机构所属全部 IP 地址中的可部分管理范围；解决 AS—前缀—主机三粒度与增量部署的失配，典型反例是未申请 ASN、不用 BGP 的校园网。
- **SAVA-X 的两个动作**：出方向做地址域级源前缀检查并打可验证标签；入方向校验标签，防前缀冒用。
- **防篡改为何成立**：中间节点没有源端 SAVA-X 标签，无法伪造签名；源端无法预判沿途标签，故用标签+摘要共同签名。
- **IPv6 可信标识的位置**：地址后 64 位设备标识符嵌入哈希后的 AID；动态更新兼顾隐私，审计机制保证可追溯。

## 易错点与自测

### 易混淆概念对比

| 概念 A | 概念 B | 区别 |
|---|---|---|
| Ingress Filtering | uRPF | 前者按“源地址是否属于本网”过滤，需精确前缀配置；后者按“源地址反查路由的出接口是否等于入接口”过滤，无需逐条配置但受路由对称性影响 |
| SAVA | SAVI | SAVA 是整体体系结构（三层）；SAVI 只是接入网那一层的技术，且是 IETF 工作组名 |
| 源地址真实性 | 数据包完整性 | 前者保证“包从声称的地方来”；后者保证“内容没被改”。SAVA 先做前者，防篡改机制再做后者 |
| 绑定锚 | 源 IP 地址 | 绑定锚是链路层属性（端口/MAC/VLAN 等），由本地设备掌握、远端难伪造；源 IP 由发送方填写，可任意伪造 |
| 自治域 AS | 地址域 | AS 是路由管理单元，需 ASN 与 BGP；地址域是“可部分管理”的地址范围，可与 AS 边界无关，支持嵌套与增量部署 |
| FCFS SAVI | SAVI-DHCP | 前者用于无状态分配，按先来先服务绑定，无权威分配记录；后者监听 DHCP 交互，绑定有权威依据 |

### 自测题

**题 1**：为什么说 IP 地址欺骗是“大量攻击成功的先决条件”，而不是一个独立的攻击类型？

**答**：因为 IP 地址是上层协议识别对端的唯一凭据。伪造源地址本身不直接造成破坏，但它使 DDoS 无法追溯、使基于地址的访问控制被绕过、使 TCP 连接身份可伪造，从而成为其他攻击的前置条件。PPT 的表述是：只要伪造了源地址，就相应地欺骗了使用该地址作标识的所有上层协议，攻击能力因此溢出网络层。

**题 2**：某运营商在边界部署了严格模式的 uRPF，为何仍可能被伪造源地址的攻击穿透？

**答**：严格 uRPF 只校验“源地址反查出的出接口是否等于报文入接口”，它防的是“从错误方向进来的伪造包”。若攻击者与被伪造者处于同一方向、同一接口进来（同方向假冒），校验通过。此外多宿主与流量工程造成的路由非对称会产生假阳性，运营商往往被迫放宽为松散模式，防护进一步减弱。

**题 3**：SAVI 为什么把绑定建立在“链路层属性”上，而不是直接给主机发证书？

**答**：因为要满足“对现有网络设备与主机协议栈透明”这一前提——不修改协议、不修改主机。发证书要求终端配合，难以在异构终端（安卓/iOS/嵌入式）上统一实现。链路层属性由接入设备本地掌握，主机无法从远端伪造，因此“可验证且比 IP 源地址更难欺骗”，同时部署成本只落在网络侧。代价是验证范围被限制在单域可控的接入网内。

**题 4**：早期 SAVA 按“自治域—前缀—主机”三粒度划分，为什么会失配？新方案怎么改？

**答**：因为增量部署使“部署边界”与“地址管理边界”不重合：一个 AS 内可能只有部分子网部署了验证；而很多校园网根本没有 ASN、不用 BGP，无法用 AS 作为管理单元。新方案引入“地址域”——同一机构所属全部 IP 地址中的可部分管理范围，可嵌套、可只覆盖一部分，于是三层变为“接入网—地址域内—地址域间”，实现松耦合、多重防御、支持增量部署。

**题 5**：SAVA-X 的标签为什么比 SPM 一类的包头标签更难被冒充？

**答**：SPM 一类方案的标签是包头里一个可写的固定格式字段，攻击者学会格式即可照样写一个，验证方无法区分签发与照抄。SAVA-X 的标签与联盟内的状态机（SMA）绑定，随状态推进而变化，并由密钥/证书体系与区块链共识维护；抄来的标签在下一个状态即失效，且伪造者不持有本域凭据，无法生成合法标签。这正对应设计原则中“即使被篡改也应被及时准确识别”的要求。
