# 第二章 网络接口层协议安全

网络接口层是协议栈里最贴近硬件的一层，它决定了"比特怎么上线、帧怎么划界、谁的身份被承认"。这一层的协议大多诞生于"彼此信任的邻接链路"这一假设之上：PPP 假设链路两端是可信的对等体，以太网假设同一广播域内的主机都守规矩，L2TP 只负责把帧运过去而不负责把它藏起来。所有这一层的攻击，本质上都是在利用这些"设计时未设防"的假设——伪造帧边界、冒充身份、塞满转发表、把单播变成广播。

本章依次讨论四条主线：网络接口层的功能划分与数据链路层的三大基本功（2.1）；承载拨号与串行链路的 PPP 协议族（2.2）；把 PPP 帧跨网络搬运的 L2TP 隧道（2.3）；构成局域网底座的以太网与交换机自学习机制（2.4）；把 PPP 塞进以太网的 PPPoE（2.5）；以及针对交换机转发表的 MAC 泛洪攻击（2.6）。

## 2.1 网络接口层功能与安全问题

### 2.1.1 分层模型中的网络接口层

同一个网络可以用三套分层模型描述，彼此的对应关系是理解本章的起点：OSI 有七层，TCP/IP 有四层，教学上常用的折中是五层。在 TCP/IP 四层模型中，最底下的**网络接口层**并不是"一层"，它把 OSI 的物理层与数据链路层合并成了一个整体——因为在工程实现上，网卡（适配器）与驱动程序本来就把"发比特"和"组帧"这两件事一起做了。

```text
   OSI 七层                  TCP/IP 四层            五层模型
+----------------+        +----------------+     +----------------+
| 应用层         |        |                |     | 应用层         |
| 表示层         |  --->  | 应用层         |     | 表示层/会话层  |
| 会话层         |        |                |     | 归入应用层     |
+----------------+        +----------------+     +----------------+
| 传输层         |  --->  | 传输层         |     | 传输层         |
+----------------+        +----------------+     +----------------+
| 网络层         |  --->  | 网际层         |     | 网络层         |
+----------------+        +----------------+     +----------------+
| 数据链路层     |  --->  | 网络接口层     |     | 数据链路层     |
+----------------+        | （合并两层）   |     +----------------+
| 物理层         |  --->  |                |     | 物理层         |
+----------------+        +----------------+     +----------------+
```

**物理层的定位**：它是 OSI 参考模型中的第一层、也是最底层，是唯一直接提供原始比特流传输的层，关注"如何在物理信道上传输各种数据的比特流"。它的功能有两条：一是提供在物理信道上接收和传送比特流的能力；二是**向上对数据链路层屏蔽掉因传输媒体多样性而产生的传输差异**。第二条常被忽略，但它解释了为什么链路层可以完全不管自己跑在双绞线、光纤还是同轴电缆上——介质差异已经在物理层被吸收了。

**数据链路层的定位**：OSI/RM 明确给出定义——数据链路层在物理层提供比特流服务的基础上，**建立相邻结点之间的数据链路**，通过差错控制提供数据帧在信道上的"透明"传输。关键词是"相邻结点"：链路层只管一跳（hop）之内的事，端到端的可靠性不归它负责。

两层的对比可以压成一张表，这张表也是考试的高频对照点：

| 对比项 | 物理层 | 数据链路层 |
|---|---|---|
| OSI 中的位置 | 第一层 | 第二层 |
| TCP/IP 中的归属 | 网络接口层 | 网络接口层 |
| 功能 | ① 比特流传输；② 屏蔽传输介质差异 | ① 封装成帧；② 透明传输；③ 差错控制 |
| 数据单位 | 比特（bit） | 帧（frame） |
| 典型安全问题 | 设备问题、意外故障、信息探测与窃听 | 身份认证、篡改 MAC 地址、网络嗅探 |

注意最后一行给了一个很有用的分类法：**物理层的威胁偏"被动与意外"（窃听、断线、设备故障），数据链路层的威胁偏"主动与伪造"（冒充、改地址）**。因为链路层开始出现"地址"和"身份"这两个概念，凡是有标识的地方就有伪造的空间。

### 2.1.2 数据链路层的信道类型

链路层使用的信道只有两大类，它们的差异直接决定了协议复杂度。

**点对点信道**：一对一的通信方式，通信双方共享一条专用的通信路径，没有其他通信实体可以访问这条信道。由于避免了网络中的多跳传输，延迟通常较低；信道可以是有线或无线的，取决于通信介质。PPP 就是为这种信道设计的——两端确定、顺序确定，因此不需要地址，也不需要介质访问控制。

**广播信道**：一对多的通信方式，过程复杂得多。广播信道上连接的主机很多，必须使用**专用的共享信道协议**来协调各主机的发送（以太网用的是 CSMA/CD）。安全问题在广播信道上也被放大：无线通信的信息传播过程中，信息会被第三方截获和窃听，容易出现信息泄密。PPT 给出的对策思路是**物理层安全技术**——利用通信系统物理层本身的特性，通过人工噪声、协作干扰等手段加强安全性。

> 补充：人工噪声的思路是发送方在信号零空间（或对合法接收者无影响的子空间）叠加干扰，使窃听者信噪比下降而合法端不受影响；协作干扰则由协作节点发干扰信号。二者都不依赖上层加密，属于"信息论安全"路线。

对比一下两种信道对协议的要求：

| 维度 | 点对点信道 | 广播信道 |
|---|---|---|
| 通信方式 | 一对一 | 一对多 |
| 是否需要地址 | 不需要（只有两端） | 需要（MAC 地址区分主机） |
| 是否需要介质访问控制 | 不需要 | 需要（CSMA/CD 等共享信道协议） |
| 典型协议 | PPP | 以太网（IEEE 802.3） |
| 主要安全风险 | 链路被劫持、认证被绕过 | 窃听、嗅探、地址伪造、泛洪 |

### 2.1.3 数据链路层协议的三大功能

链路层要为上层提供"看起来没有差错"的链路，靠的是三件基本功。

#### （1）封装成帧

封装成帧（framing）就是在一段数据的前后分别添加首部和尾部，构成一个帧，从而**确定帧的界限**。首部和尾部的一个重要作用就是进行帧定界。没有定界，接收方收到的只是一串连续的比特，无法判断哪里是一个完整的数据单元。

当数据是由可打印的 ASCII 码组成的文本文件时，帧定界可以使用特殊的帧定界符：控制字符 **SOH**（Start Of Header）放在一帧的最前面，表示帧的首部开始；另一个控制字符 **EOT**（End Of Transmission）表示帧的结束。

```text
        帧
+--------+----------------------------+--------+
|  SOH   |      装在帧中的数据部分      |  EOT   |
+--------+----------------------------+--------+
 帧开始符                                 帧结束符
                                发送在前 --->
```

#### （2）透明传输：帧定界带来的第一个副作用

透明传输是指不管所传数据是什么样的比特组合，都应当能够在链路上传送。问题在于：**当数据中的比特组合恰巧与某个控制信息完全一样时**，接收方就会误判。这也是帧定界方案的天生缺陷。

举例：如果数据部分某个字节的二进制代码恰好和 EOT 一样，接收方就会在这里"找到帧的边界"，把前半段当成一个完整的帧收下，把真正的后半段当成一个错误的新帧。结果是**一个帧被劈成两个，其中一个被判为无效帧而丢弃**。

```text
原始数据：  [SOH][ A ][ B ][EOT][ C ][ D ][EOT]
                              ^
                     数据里恰好出现 EOT 代码

接收端理解：[SOH][ A ][ B ][EOT]   <-- 误认为一帧结束
                          [ C ][ D ][EOT]  <-- 剩下的被当成另一帧/无效帧
```

解决办法是**字节填充（byte stuffing）**，也称字符填充（character stuffing），规则有三条：

1. 发送端的数据链路层在数据中出现控制字符 SOH 或 EOT 的前面插入一个转义字符 **ESC**（十六进制编码 1B）；
2. 接收端的数据链路层在将数据送往网络层之前，删除插入的转义字符；
3. 如果转义字符本身也出现在数据当中，则在转义字符前面再插入一个 ESC；接收端收到连续的两个转义字符时，删除其中前面那一个。

```text
原始数据：      SOH  ...  EOT  ...  ESC  ...  SOH  ...
                |          |          |          |
字节填充后：    SOH ESC..  EOT  ESC..  ESC  ESC..  SOH
                ^                ^      ^   ^
            帧开始符          数据内EOT 数据内ESC被转义成 ESC ESC
（首尾的 SOH/EOT 是真正的定界符，不加 ESC；数据内的才加）
```

这条机制的安全含义值得单独记一句：**转义字符的存在使"数据"与"控制"的边界由接收方的解析逻辑决定**，任何能影响解析逻辑的畸形输入（例如只发一个孤立 ESC 就断流）都可能造成解析器状态错乱，这是所有"带内信令"协议的共同弱点。

#### （3）差错控制：只检错，不纠错，也不重传

先说"不可靠"传输可能出现的问题，共四种：**比特差错、帧丢失、帧重复、帧失序**。为了保证数据传输的可靠性，在计算机网络传输数据时必须采用各种差错检测措施。

但关键结论是：**在现有网络实现中，数据链路层只提供比特差错检测**。它不负责丢帧重传、不负责去重、不负责排序——这些都留给上层（TCP）。链路层因此被设计成一个"尽力而为的检错器"，而不是一个可靠传输协议。

**比特差错**指传输过程中 1 可能变成 0、0 也可能变成 1，一旦发生很难自动恢复。衡量指标是**误码率（Bit Error Rate, BER）**：在一段时间内，传输错误的比特占所传输比特总数的比率。

检测方法是加冗余：在数据后面添加的冗余码称为**帧检验序列（Frame Check Sequence, FCS）**。FCS 可以用**循环冗余检验（CRC）**方法得出，也可以采用其他方法计算。目前常用的就是 CRC 差错检测技术，用以实现"无差错接受"——即凡是接收端接受的帧（不包括丢弃的帧），能以非常接近于 1 的概率认为这些帧在传输过程中没有产生差错。

| 概念 | 含义 | 容易混淆之处 |
|---|---|---|
| BER（误码率） | 出错比特数 / 传输比特总数 | 是信道质量指标，不是帧的指标 |
| FCS（帧检验序列） | 附加在帧尾的冗余码 | 是"冗余码"这个角色，可由多种算法算出 |
| CRC（循环冗余检验） | 计算 FCS 的一种具体方法 | 是算法，不是字段 |
| "无差错接受" | 接受下来的帧极大概率无差错 | 不等于"可靠传输"，被丢弃的帧无人重传 |

> 补充：CRC 的做法是把数据比特串视为一个多项式，乘以 x^n 后除以双方约定的生成多项式 G(x)，得到的余数即为 n 位 FCS。CRC 能检出所有单比特、双比特差错和所有长度不超过 n 的突发差错，但**它没有密钥**，因此只能对付随机误码，不能对付攻击者的主动篡改——攻击者改了数据后重算 CRC 即可通过校验。这也是"检错"与"认证"必须分开的原因。

## 2.2 PPP 协议

### 2.2.1 PPP 的设计目标与三个组成部分

点对点协议（Point-to-Point Protocol, PPP）制定于 1992 年，1994 年修订后成为互联网的正式标准。它最初的设计目的是**为对等节点之间的数据包传输提供封装功能**，目前是数据链路层使用最广泛的协议。PPP 封装来自网络层的 IP 数据报，并交付给物理层进行传输。

PPP 由三部分组成，这三条要背下来：

1. **将 IP 数据报封装到串行链路的方法**（帧格式本身）；
2. **链路控制协议（Link Control Protocol, LCP）**，用于建立、配置和测试 PPP 链路；
3. **网络控制协议（Network Control Protocol, NCP）**，用于建立和配置网络层协议。

NCP 不是一个单一协议，而是一族协议：如果传输的是 IP 数据，则 NCP 指 **IP 控制协议（IPCP）**；如果传输的是数字设备公司（DEC）推出的 DECnet 协议集合的数据，则 NCP 对应 DECnet 四阶段控制协议（DNCP）。在 PPP 链路上可以传输不同网络协议的数据，NCP 用于对这些网络协议相关的参数进行配置。

这个三分结构体现了一个清晰的分层思想：**链路层参数（LCP）与网络层参数（NCP）解耦**。同一条链路可以先跑 IP、再跑 IPX，链路本身不用重建。

### 2.2.2 PPP 架构：拨号上网场景

PPP 的经典应用是拨号上网。Internet 服务提供商（ISP）提供 **Modem 池**，用于接收来自不同用户的拨入请求；用户主机则需连接一个 Modem，以便通过电话网络拨入 ISP；在拨入成功之后，ISP 路由器 R 和用户主机之间通过 Modem 建立了一条点到点连接。

```text
 用户主机          电话网(PSDN)              ISP 机房
+--------+        +-----------+        +-------------+      +----------+
|  主机  |--+     |           |        |   Modem 池  |      |          |
+--------+  |     |  电话交换 |        |  +-------+  |      |  ISP     |
            +---->|   网络    |------->|  |Modem 1|--+----->|  路由器R |--> Internet
+--------+  |     |           |        |  +-------+  |      |          |
| Modem  |--+     +-----------+        |  +-------+  |      +----------+
+--------+                             |  |Modem n|  |
                                       |  +-------+  |
                                       +-------------+
        |<------------- 点到点连接（PPP 帧）----------->|
```

这张架构图要注意两点：一是"点到点"是**逻辑链路**层面的描述，物理上中间经过了整个电话网；二是链路的两个端点分别是用户主机与 ISP 路由器，PPP 的"对等体"就是这两个设备，后面的认证也是它们之间互相验证。

### 2.2.3 PPP 帧格式

PPP 帧共六个字段，其中信息字段与 FCS 是 PPT 明确给出数值的部分，其余字段的标准取值一并列在下表（PPT 该处以图呈现，无文字说明）：

| 字段 | 长度 | 作用 | 安全相关性 |
|---|---|---|---|
| 标志（Flag） | 1 字节，0x7E | 帧定界，标识一帧的开始与结束 | 帧边界可被伪造；数据内的 0x7E 需转义 |
| 地址（Address） | 1 字节，0xFF | 标准广播地址；点对点链路无寻址需求，取值固定 | 无鉴别能力，不能作为身份依据 |
| 控制（Control） | 1 字节，0x03 | 无编号帧（UI），无序号、无确认 | 无序列号 → 协议本身无重放检测 |
| 协议（Protocol） | 2 字节 | 标识信息字段承载的协议 | 决定多路分解，可被用于"类型混淆" |
| 信息（Information） | 可变，不超过 1500 字节 | 承载上层报文 | 常明文承载口令（PAP） |
| 帧校验序列（FCS） | 2 字节 | 检查 PPP 帧是否存在比特差错 | 无密钥，只能检错，不能抗篡改 |

"协议"字段的取值是本章最需要记的一张对照表，后续 LCP/PAP/CHAP/IPCP 的识别全靠它：

| 协议字段值 | 信息字段承载的内容 |
|---|---|
| 0xC021 | LCP 报文（链路控制） |
| 0xC023 | PAP 报文（口令认证） |
| 0xC223 | CHAP 报文（挑战握手认证） |
| 0x8021 | IPCP 报文（IP 层参数配置） |
| 0x0021 | IPv4 数据报 |

关于信息字段，PPT 特别说明：长度可变、不超过 1500 字节，其取值与"协议"类型相关，比如当"协议"类型为 0xC021 时，信息字段则为一个 LCP 报文。这个"不超过 1500"与以太网的 MTU 是同一个数量级，属于链路层对上层数据报大小的硬约束。

> 补充：PPP 帧前后各有一个 0x7E 标志字节，与 HDLC 类似；当信息字段中出现 0x7E、0x7D 或小于 0x20 的字符时，用 0x7D 做转义并异或 0x20，这套机制与 2.1.3 的字节填充是同一思路。

### 2.2.4 PPP 的工作流程：五个阶段

PPP 链路从"死"到"活"再到"死"，共五个阶段：

1. **链路不可用阶段**（物理连接尚未建立，链路处于静止）；
2. **链路建立阶段**（LCP 协商链路参数）；
3. **认证阶段**（PAP 或 CHAP）；
4. **网络层协议阶段**（NCP/IPCP 配置网络层参数，开始承载数据）；
5. **链路终止阶段**（LCP 终止链路，随后断开物理连接）。

由于 PPP 基于点对点链路建立通信，发起方和回应方在建立物理连接之后，动作顺序是：首先利用 LCP 配置和测试数据链路；然后利用密码认证协议 PAP 或询问握手认证协议 CHAP 验证通信实体的身份；接着通过 IPCP 协议配置 IP 层参数，双方开始通信；最后双方利用 LCP 断开 PPP 链路，之后断开物理连接。

```text
 链路不可用 --(物理连接建立)--> 链路建立 --(LCP 协商成功)--> 认证
                                                                 |
                                    (认证成功/无需认证)          v
 链路终止 <--(LCP 终止请求)--- 网络层协议阶段(NCP/IPCP) <--------+
     |
     v
 链路不可用（物理连接断开）
```

一次完整的报文交互可以展开成 8 步（这就是 PPP 建立到拆除的全过程，考试常要求按顺序写出）：

| 步 | 方向 | 报文 | 关键内容 |
|---|---|---|---|
| 1 | 发起方 → 回应方 | LCP 配置请求（Configure-Request） | 各项配置参数：使用的认证协议、最大接收单元（MRU）、压缩协议等 |
| 2 | 回应方 → 发起方 | LCP 配置确认（Configure-Ack） | 若同意各项配置参数则返回确认 |
| 3 | 发起方 → 回应方 | 认证请求（PAP）或对挑战的应答（CHAP） | 提供账号和口令，供回应方验证身份 |
| 4 | 回应方 → 发起方 | 认证确认 | 验证成功后返回确认 |
| 5 | 发起方 → 回应方 | IPCP 配置请求 | 请求协商 IP 地址等参数 |
| 6 | 回应方 → 发起方 | IPCP 配置确认 | 其中包含分配给发起方的 IP 地址 |
| 7 | 发起方 → 回应方 | LCP 终止链路请求（Terminate-Request） | 请求释放链路 |
| 8 | 回应方 → 发起方 | LCP 终止确认（Terminate-Ack） | 链路终止 |

```text
发起方                                          回应方
  |--- (1) LCP Configure-Request --------------->|
  |<-- (2) LCP Configure-Ack --------------------|
  |--- (3) 认证请求 / 挑战应答 ------------------>|
  |<-- (4) 认证确认 -----------------------------|
  |--- (5) IPCP Configure-Request -------------->|
  |<-- (6) IPCP Configure-Ack（含分配的 IP）-----|
  |============== 数据通信（PPP 帧双向）========|
  |--- (7) LCP Terminate-Request --------------->|
  |<-- (8) LCP Terminate-Ack --------------------|
  v                                             v
```

一个容易被追问的细节：**LCP 出现在最前和最后**。它既负责开链路，也负责关链路，中间还负责"测试"链路（通过 Echo-Request/Echo-Reply 保活）。所以 LCP 是 PPP 的"总控"，认证协议和 NCP 都是它的"乘客"。

### 2.2.5 LCP 协议

LCP 用于完成 PPP 链路的**配置、维护和终止**。当 LCP 数据报文被封装在 PPP 信息字段中时，PPP 的"协议"字段取值为十六进制 **0xC021**。

LCP 包格式四个字段：

| 字段 | 长度 | 作用 |
|---|---|---|
| 代码（Code） | 1 字节 | 标识 LCP 报文的类型（配置请求/确认/否认/拒绝、终止请求/确认等） |
| 标识符（Identifier） | 1 字节 | 用于匹配请求和响应数据包。通常一个配置请求的标识符从 0x01 开始逐步加 1；对方接收到该数据包后，响应包中的标识符一定与请求包一致 |
| 长度（Length） | 2 字节 | LCP 报文总长 |
| 数据（Data） | 可变长 | 根据 LCP 报文内容不同而不同；配置请求中承载一个或多个配置选项 |

"标识符"的设计是典型的**请求-响应配对**机制：它不提供安全性（可预测、可枚举），只解决"哪个响应对应哪个请求"的乱序问题。这一点常被拿来与 TCP 的序号对比——**标识符不是随机数，因此不能作为抗重放的手段**。

LCP 配置选项又由三个字段构成：**类型（Type）** 1 字节，用于配置选项的类型；**长度** 1 字节，指出该配置选项的长度；**数据** 可变长，包含配置选项的特殊详细信息。

| LCP 代码 | 报文类型 | 语义 |
|---|---|---|
| 1 | Configure-Request | 请求协商链路参数 |
| 2 | Configure-Ack | 全部接受 |
| 3 | Configure-Nak | 部分不接受，建议修改后重发 |
| 4 | Configure-Reject | 部分选项不认识，拒绝该选项 |
| 5 | Terminate-Request | 请求关闭链路 |
| 6 | Terminate-Ack | 同意关闭 |
| 7 | Code-Reject | 代码字段不认识 |
| 8 | Protocol-Reject | 协议字段不认识（上层协议不支持） |
| 9 | Echo-Request | 链路保活探测 |
| 10 | Echo-Reply | 保活应答 |
| 11 | Discard-Request | 用于测试，要求对方丢弃 |

> 补充：上表代码值属标准 LCP 定义；PPT 该处以"表2-1 LCP 功能与报文类型对应关系"呈现但未抽出文字，代码数值按 RFC 1661 补齐，考试若只要求"配置类 1~4、终止类 5~6"则记分类即可。注意 IPCP 只使用代码 1~7（见 2.2.8），这正是"IPCP 是 LCP 的子集"的由来。

### 2.2.6 PAP 协议：两次握手的明文认证

**密码认证协议（Password Authentication Protocol, PAP）** 是 PPP 协议集中的一种链路控制协议。在配置 PAP 认证时，需要在认证方建立**本地口令数据库**。该协议通过"两次握手"提供一种对等结点建立认证的简单方法。

流程只有三步：

1. 被认证方向认证方发送**明文形式**的认证请求，该请求包含用户名和密码；
2. 认证方核对被认证方发送的认证信息是否与数据库中存储的信息相符，相符则通过，否则拒绝；
3. 随后向被认证方发送适当的回复。

```text
被认证方                                      认证方
    |--- 认证请求（用户名 + 明文口令）--------->|
    |                                    查本地口令数据库
    |<-- 认证确认（代码=2，通过）---------------|
    |    或 认证未确认（代码=3，拒绝）----------|
```

PAP 数据包格式（协议字段 **0xC023**）：

| 字段 | 长度 | 作用 |
|---|---|---|
| 代码（Code） | 1 字节 | 1=认证请求，2=认证确认，3=认证未确认 |
| 标识符（Identifier） | 1 字节 | 匹配认证请求与认证回复，确保二者对应 |
| 长度（Length） | 2 字节 | PAP 数据包总长度，包括代码、标识符、长度和数据字段 |
| 数据（Data） | 可变长 | 认证所需数据，格式取决于代码字段的值 |

**PAP 的安全缺陷**（PPT 有明确结论）：PAP 虽然简单易用，但由于安全性较低，容易受到**中间人攻击**和**密码窃取攻击**，已逐渐被更安全的认证方式取代。缺陷的根因可以定位到设计本身的两条：

- **口令明文上线**：只要攻击者能在链路上嗅探（共享介质、被控交换机镜像口、ARP 欺骗后的中间人），口令就直接到手；
- **单次单向、无挑战值**：没有随机数参与，攻击者捕获到"代码+标识符+数据"的整个报文后可以**原样重放**，认证方无法区分这是新请求还是录播。

这两条正好对应后面 CHAP 要解决的两个问题——**不明文**、**不可重放**。

### 2.2.7 CHAP 协议：三次握手的挑战-响应

**询问握手认证协议（Challenge Handshake Authentication Protocol, CHAP）** 通过**挑战-响应机制**实现身份验证，采用"三次握手"：

| 步 | 方向 | 动作 | 关键点 |
|---|---|---|---|
| 1 | 认证方 → 被认证方 | 发送包含**随机值**的挑战消息 | 随机值长度取决于随机字节生成的方法 |
| 2 | 被认证方 → 认证方 | 提取随机值，用单向哈希函数计算"用户密码 + 随机值"，将计算结果作为**响应值**发回 | 口令本身不上线，上线的是哈希值 |
| 3 | 认证方 → 被认证方 | 根据用户名检索对应密码，用同样算法做哈希验证响应值；匹配则认证成功，否则终止连接 | 认证方本地也要保存明文口令（才能算出期望值） |
| 4 | 认证方 → 被认证方 | 在一定时间间隔后**发送新的挑战**，重复上述过程 | 周期性再认证，压缩重放窗口 |

```text
认证方                                          被认证方
   |  生成随机数 R                                 |
   |--- 挑战（Code=1, ID=n, R, 本端名字）-------->|
   |                                     H = Hash(口令 || R)
   |<-- 应答（Code=2, ID=n, 用户名, H）-----------|
   |  本端查库得口令，算 Hash(口令 || R) 比对       |
   |--- 成功（Code=3）或 失败（Code=4）---------->|
   |                                             |
   |    （间隔一段时间后，ID=n+1，新随机数 R'）    |
   |--- 挑战 ... -------------------------------->|
```

CHAP 相对于 PAP 的两处关键改进，正好补上 PAP 的两个洞：

| 缺陷 | PAP | CHAP |
|---|---|---|
| 口令是否上线 | 明文传输 | 只传哈希值，口令不出本机 |
| 能否重放 | 可原样重放 | 每次挑战随机数不同，旧响应值失效 |
| 握手次数 | 两次 | 三次（并可周期重复） |
| 认证方是否存明文 | 存 | 存（否则无法计算期望哈希，除非用不可逆存储） |

CHAP 包格式（协议字段 **0xC223**）：

| 字段 | 长度 | 作用 |
|---|---|---|
| 代码（Code） | 1 字节 | 1=挑战（发送查询值）；2=应答（提供散列计算结果和用户名）；3=成功（认证通过，允许访问）；4=失败（认证失败，拒绝访问） |
| 标识符（Identifier） | 1 字节 | 标识特定的认证交换；每个挑战和相应的应答使用相同的标识符 |
| 长度（Length） | 2 字节 | 整个 CHAP 数据报的长度，包括代码、标识符、长度字段本身以及后续的数据字段 |
| 数据（Data） | 可变长 | 挑战或应答的相关数据（随机值 / 用户名+哈希值） |

CHAP 仍不是"完整的安全方案"，剩下的弱点在于：**它只认证身份，不保护后续数据**。认证通过后 PPP 载荷仍是明文；哈希算法若为 MD5 且挑战值可预测、口令为弱口令，仍可离线爆破；此外它不防"认证方伪造"——被认证方无法验证对端真的是合法服务器。

### 2.2.8 IPCP 协议

IPCP 是 PPP 协议集的一个组成部分，负责在点对点链路两端**配置、启用和停用 IP 协议模块**。它采用与 LCP 相同的包交换机制，但**只在 PPP 达到网络层协议阶段后才开始交换 IPCP 包**；如果在此阶段之前收到 IPCP 包，它们将被丢弃。

这个"阶段门禁"很重要：它保证了认证先于参数协商——攻击者不能跳过认证直接要一个 IP 地址。

IPCP 的三个主要功能：

| 功能 | 说明 |
|---|---|
| 配置 IP 地址 | 可进行静态或动态 IP 地址协商。静态协商中通信双方各自告知对方的 IP 地址；动态协商中由服务器端分配 IP 地址给客户端 |
| 配置 DNS 服务器地址 | 协商链路节点的主 DNS 服务器地址和次 DNS 服务器地址 |
| 压缩 TCP/IP 头部 | 支持 Van Jacobson 压缩协议，减小 TCP/IP 头部大小，提高低带宽条件下的传输效率 |

IPCP 报文格式与 LCP 类似，但协议字段值不同：当 IPCP 数据报文被封装在 PPP 信息字段中时，"协议"字段取值为十六进制 **0x8021**。

| 字段 | 长度 | 说明 |
|---|---|---|
| 代码（Code） | 1 字节 | 仅使用 1~7 的包类型（即 LCP 表的前 7 行）；使用其他代码不被承认，并导致 Code-Rejects |
| 标识符（Identifier） | 1 字节 | 匹配请求和响应，确保正确处理 |
| 长度（Length） | 2 字节 | 整个 IPCP 数据报长度，包括代码、标识符、长度字段本身及后续数据字段 |
| 数据（Data） | 可变长 | IPCP 配置选项：IP 地址、DNS 服务器地址、IP 压缩协议等；每个选项有自己的格式（类型、长度、值） |

记住这条推论：**IPCP 只是 LCP 包类型的一个子集（1~7）**，所以"IPCP 能做什么"完全由 LCP 的六种配置/终止报文撑起来，它自己只增加了三类配置选项（地址、DNS、压缩）。

### 2.2.9 PPP 的安全问题与加固

把 2.2.1~2.2.8 的缺陷汇总，PPP 的攻击面是清楚的：

| 攻击 | 针对的机制 | 成因 | 加固 |
|---|---|---|---|
| 口令嗅探 | PAP | 口令明文上线，且链路可能是共享介质/被镜像 | 强制使用 CHAP；链路加密（IPsec/MPPE） |
| 认证重放 | PAP | 无随机挑战值，报文可原样重放 | 用 CHAP 的随机挑战 |
| 离线口令爆破 | CHAP | 哈希算法弱（MD5）+ 弱口令 + 挑战值可预测 | 强口令、更长随机数、用更强的哈希 |
| 链路参数降级 | LCP 配置协商 | 认证方式本身由 LCP 协商，可被诱导选择 PAP 或不认证 | 在两端强制 `ppp authentication chap`，禁用 PAP 回退 |
| 身份冒充（假服务器） | 单向认证 | 只认证被认证方，客户端不验证服务器 | 双向认证（双向 CHAP）、证书 |
| 数据窃听/篡改 | PPP 载荷 | PPP 本身不加密，FCS 无密钥 | 上层 TLS，或链路层加密（L2TP over IPsec） |

一句话总结：**PPP 的认证机制解决"你是谁"，不解决"别人看不见、改不了"**。前者靠 CHAP，后者要靠加密层，二者不可互相替代。

## 2.3 L2TP 协议

### 2.3.1 为什么需要隧道：PPP 的边界

计算机网络是将分布在不同地理位置的多台计算机及其外部设备通过通信线路连接起来、实现资源共享的计算机系统。尽管 PPP 非常适合用于直接连接（如通过电话线的拨号连接或串行链路），但它**并不直接支持在多接入网络环境中通过网络传输 PPP 帧**。

原因在 PPP 的设计假设里：PPP 帧没有跨网络寻址能力（地址字段固定 0xFF），它假定两端之间存在一条直接的、点对点的链路。一旦用户与服务器之间隔着一个 IP 骨干网，PPP 帧就无法被路由。

产业界的解决路径是逐层叠加的：

| 时间 | 技术 | 提出者 | 说明 |
|---|---|---|---|
| 1998 年 5 月 | 第二层转发（L2F） | 思科 | 让链路端点可以跨越多个网络 |
| 1999 年 7 月 | 点到点隧道协议（PPTP） | 微软、3Com 等 | 另一套隧道方案 |
| 1999 年 8 月 | 第二层隧道协议（L2TP） | IETF 起草，微软、Cisco、3COM 等参与 | 为避免 L2F 与 PPTP 两种隧道技术的不兼容性而制定 |

L2F 通常被认为是"L2TPv1"，1999 年 8 月推出的 L2TP 被认为是"L2TPv2"。这条演进线索的考点是**动机**：L2TP 不是从零发明的新协议，而是**两套互不兼容的隧道方案的合并标准**——它继承了 PPTP 的 PPP 承载方式和 L2F 的隧道思想。

### 2.3.2 隧道的本质：封装

"隧道"实质上是一种**封装**：将一种协议（协议 A）封装在另一个协议（协议 B）中传输。隧道协议的一般形式为：

```text
   （协议B（隧道头（协议A）））
```

用英法海底隧道的历史作类比（PPT 以此引入）：第一次尝试失败于 1802 年（军事问题），第二次 1834 年（政治问题），第三次 1872 年（地理问题），第四次 1955 年（成本问题）；第 N 次尝试在 1981 年，英国首相撒切尔和法国总统密特朗在伦敦举行首脑会晤，决定将英法海底隧道的建设和经营承包给私人部门，隧道终于在 1994 年 5 月 6 日举办通车典礼。类比的落点是：**隧道不改变两端是什么，只改变中间的运输方式**——火车进隧道前是火车，出隧道后还是火车，中间那段它"看不见"外界。

这句话在安全上有一个直接推论：**隧道提供的是"跨越"能力，不是"保护"能力**。是否加密，取决于隧道协议本身有没有密码学机制，而不取决于"叫不叫隧道"。

### 2.3.3 L2TP 架构：LAC 与 LNS

L2TP 的两个重要组件是 **L2TP 接入集中器（L2TP Access Concentrator, LAC）** 和 **L2TP 网络服务器（L2TP Network Server, LNS）**，它们是隧道的两个端点，互为对等体。在不同的网络中，二者通过协商建立隧道，用以转发 PPP 报文。

| 组件 | 位置 | 职责 |
|---|---|---|
| LAC | 靠近用户侧（ISP 接入设备） | 负责在 LNS 和远程系统之间转发 PPP 报文，并维护 LAC 与 LNS 之间的隧道（TUNNEL）和会话（SESSION）连接 |
| LNS | 靠近企业网侧 | 负责为远程系统提供对内部网的访问服务 |

```text
 远程用户        电话网/接入网          LAC                IP 骨干网              LNS        企业内网
+--------+      +----------+      +---------+          +-------------+      +---------+    +--------+
| 主机 + |----->|  接入    |----->|   LAC   |=========>|  隧道(Tunnel)|=====>|   LNS   |--->| 内部网 |
| Modem  |      |  网络    |      |         |  UDP1701 |  内含多个    |      |         |    |        |
+--------+      +----------+      +---------+          |  会话(Session)|     +---------+    +--------+
                                        |<---- PPP 帧被封装进 L2TP ---->|
```

隧道与会话是两个层级的概念：**一条隧道里可以复用多条会话**。LAC 和 LNS 通过协商隧道 ID 和会话 ID 来标识不同的隧道和会话，**隧道标识相同、会话标识不同的报文将被复用在一条隧道上**。这正是 L2TP 高效的地方——不必为每个用户建一条隧道。

### 2.3.4 协议层次：1701 端口与双通道

L2TP 是**端口号为 1701 的应用层协议**（运行在 UDP 之上）。它的层次结构包含两类消息，分走两条通道：

| 通道 | 承载 | 可靠性 |
|---|---|---|
| 数据通道 | 数据消息（用户 PPP 帧） | 无法保证可靠传输 |
| 控制通道 | L2TP 隧道和会话协商等控制消息 | 可以保证控制消息的可靠传输 |

```text
+---------------------------+
|        PPP 帧 / 数据       |
+---------------------------+
|        L2TP 报文头         |
+---------------------------+
|        UDP 头（1701）      |
+---------------------------+
|        IP 头（外层）       |
+---------------------------+
|        链路层帧            |
+---------------------------+
```

"控制可靠、数据不可靠"是刻意设计：控制消息涉及隧道/会话状态机的正确性，丢了就会状态错乱，所以用 Ns/Nr 序号做窗口与重传；数据消息则交给上层 TCP 去处理丢包，隧道层不重复做可靠性，避免"可靠 over 可靠"的性能损耗。

### 2.3.5 工作流程：五步

L2TP 的工作流程包括五步：**建立控制连接、建立会话、数据通信、终止会话、终止控制连接**。

**（1）建立控制连接 SCC（Start Control Connection）**：在此阶段，LAC 和 LNS 协商控制连接参数，并利用 **CHAP 的"三次握手"互相验证对方的身份**。注意这里是**双向**认证——比 PPP 里常见的单向 CHAP 更强。

**（2）建立会话**：对 LAC 而言，会话分呼入和呼出两个方向。当 LAC 检测到来自远程客户的呼叫时，应向 LNS 建立**呼入会话**；当收到来自 LNS 的请求时，则建立**呼出会话**。

**（3）数据通信**：双方互相传递 PPP 报文。LAC 将 PPP 帧封装在 L2TP 数据报文中，通过隧道发送给 LNS；LNS 拆分还原 PPP 帧，并发送到 PPP 链路上。

**（4）终止会话**：LAC 和 LNS 都可以提出终止会话。终止会话前，发起方发送**呼叫断连通告（Call-Disconnect Notify, CDN）**。

**（5）终止控制连接**：LAC 和 LNS 都可以提出终止控制连接。终止控制连接前，发起方向回应方发送 **StopCCN 报文**，该报文中指明需要终止的**隧道标识**和**终止原因**。

```text
时间轴
 |  (1) SCC：控制连接建立（CHAP 双向认证）        Tunnel ID 协商
 |  (2) 建立会话（呼入 / 呼出）                    Session ID 协商
 |  (3) 数据通信：PPP 帧 <-封装-> L2TP/UDP/IP
 |  (4) 终止会话：发送 CDN（呼叫断连通告）
 |  (5) 终止控制连接：发送 StopCCN（含隧道 ID + 原因）
 v
```

"先断会话、再断控制连接"的顺序不能颠倒：控制连接是所有会话的容器，容器先没了，里面的会话就没有通知通道可用。

### 2.3.6 L2TP 报文：三层包装与解封装

L2TP 连接的维护以及 PPP 数据的传送都是通过 L2TP 报文完成的。由于 L2TP 设计运行在 UDP 之上，需要在 L2TP 报文外再封装一个 UDP 报文头；为了在 IP 网络上路由该 UDP 数据包，需要为其再添加一个新的 IP 报头。**LAC 在收到 PPP 报文之后，先后为其封装 L2TP 报文头、UDP 报文头和新的 IP 头。**

PPT 用"快递"作类比，非常直观：

| 层 | 包装 | 类比 |
|---|---|---|
| 原始数据 | 用户的 IP 数据包（已被 PPP 包装好） | 货物本身 |
| 第一层：L2TP 头 | 收货人：LNS 的 Tunnel ID 和 Session ID | 写明"哪个仓库的哪个货位" |
| 第二层：UDP 头 | "使用 UDP 快递服务，送到 1701 号窗口" | 选快递公司 + 窗口号 |
| 第三层：外层 IP 头 | 填发货地址（LAC IP）和收货地址（LNS IP），并注明"内件为 UDP 快递"（协议号 17） | 面单上的收发地址 + 内件类型 |

**解封装**（LNS 侧）是严格逆序，每一步都在"看标签"：

1. IP 包被路由到达 LNS。LNS 剥掉外层 IP 头，看到是发给本机 UDP 1701 端口的；
2. 剥掉 UDP 头，看到是 L2TP 报文；
3. 根据 L2TP 头中的 Tunnel ID 和 Session ID，找到对应的**虚拟接口**；剥掉 L2TP 头，得到原始的 PPP 报文。

```text
封装（LAC 侧，自内向外）                    解封装（LNS 侧，自外向内）
+---------------------------+              +---------------------------+
| IP 头（外层，协议号 17）   |  (3) 最后加  | 1. 剥 IP 头 -> UDP 1701   |
+---------------------------+              +---------------------------+
| UDP 头（目的端口 1701）    |  (2)         | 2. 剥 UDP 头 -> L2TP      |
+---------------------------+              +---------------------------+
| L2TP 头(Tunnel ID/Session) |  (1) 最先加  | 3. 查 ID -> 虚拟接口      |
+---------------------------+              +---------------------------+
| PPP 帧（含用户 IP 数据）   |  原始数据    | 4. 剥 L2TP 头 -> PPP 帧   |
+---------------------------+              +---------------------------+
```

**L2TP 首部字段**逐项如下（前 6 项为标志/版本，位于首部第 1~2 字节）：

| 字段 | 长度 | 作用 |
|---|---|---|
| T（Type） | 1 bit | 类型标识：0=数据消息，1=控制消息 |
| L（Length） | 1 bit | 长度字段标识：1 表示首部包含"长度"字段；**控制消息必须置 1** |
| X（Reserved） | 3 bit | 保留位（预留未来扩展），通常置 0 |
| S（Sequence） | 1 bit | 序号字段标识：1 表示首部包含 Ns 和 Nr；**控制消息必须置 1** |
| O（Offset） | 1 bit | 偏移量字段标识：1 表示首部包含"偏移量"字段；**控制消息必须置 0** |
| P（Priority） | 1 bit | 优先级，只用于数据消息；置 1 表示报文具有较高优先级 |
| 版本（Ver） | 2 bit | 指明 L2TP 版本，例如 L2TPv2 取值为 2 |
| 长度（Length） | 2 字节 | 整个报文的总长度，单位为字节（L=1 时存在） |
| 隧道 ID（Tunnel ID） | 2 字节 | 发起方和回应方对同一隧道指定的标识不同；该字段指明**报文接收方**为隧道指定的标识 |
| 会话 ID（Session ID） | 2 字节 | 指明**接收方**指定的会话标识 |
| Ns | 2 字节 | 当前报文的序号（S=1 时存在） |
| Nr | 2 字节 | 确认序号，即发送方期望接收的下一个报文的序号 |
| 偏移量（Offset） | 2 字节 | 实体部分距首部起始点的偏移量（O=1 时存在） |
| 填充（Padding） | 可变 | 为保持首部 4 字节对齐而进行的填充 |

三个"必须"是最容易被出成判断题的点：**控制消息 L=1、S=1、O=0**。逻辑解释是——控制消息要长度（便于解析）、要序号（要可靠传输），但不需要偏移量（它不承载需要对齐的载荷）。

### 2.3.7 L2TP 的安全定位

PPT 给了非常明确的判断：**L2TP 不是严格意义上的安全协议**，因为它未提供基于密码学的机密性、完整性等保护，只是提供了对口令等敏感信息的加密，以及基于共享秘密的身份认证方法。

进一步说明安全性：原始的 L2TP（RFC 2661）本身不提供加密，**PPP 载荷是明文传输的**。因此在实际应用中，通常会结合 IPsec 对整个 L2TP/UDP 包进行加密和认证，形成 **L2TP over IPsec**，以保障数据传输的机密性和完整性。

| 安全属性 | 原始 L2TP | L2TP over IPsec |
|---|---|---|
| 身份认证 | 有（控制连接用 CHAP 双向认证） | 有（叠加 IPsec 的对等体认证） |
| 机密性 | 无（PPP 明文） | 有（ESP 加密整个 L2TP/UDP 包） |
| 完整性 | 弱（仅 CHAP 保护认证交换） | 有（ESP 的 ICV） |
| 抗重放 | 无（数据消息 Ns/Nr 只用于排序，不用于安全判定） | 有（IPsec 序列号 + 抗重放窗口） |

针对原始 L2TP 的典型攻击：

1. **嗅探**：在 LAC 与 LNS 之间的任意节点抓包，直接读出 PPP 载荷里的应用层数据（明文 HTTP、明文 FTP 口令）；
2. **注入/伪造**：由于数据消息没有密码学校验，攻击者可伪造 Tunnel ID / Session ID 注入伪造 PPP 帧；这两个 ID 都是 16 位、可枚举；
3. **中间人改写**：修改载荷后重算 UDP/IP 校验和即可，接收端无完整性校验；
4. **拒绝服务**：向 1701 端口灌控制消息（如伪造 SCCRQ/StopCCN）可打断隧道——因为控制消息解析开销大于数据消息。

对应的加固措施就是：**一律部署 L2TP over IPsec（或直接用 TLS 类 VPN）**；在防火墙上只放行来自已知对端 IP 的 1701/UDP；对控制消息做速率限制；不要把 L2TP 当作"加密方案"来宣传。

## 2.4 以太网协议

### 2.4.1 以太网的强势与标准演进

以太网之所以有强大生命力，PPT 总结了六条：

- **可扩展**：从 10 Mbit/s 到 100 Gbit/s；
- **简单性和灵活性**：支持多种传输媒体、全/半双工、共享/交换；
- **易于安装和维护**；
- **稳健性好**；
- **支持 TCP/IP，互联容易**；
- **善于借鉴**：4B/5B、8B/10B 等编码方案都吸收自其他技术。

标准演进的时间线要记清（DIX 与 IEEE 两条线）：

| 时间 | 事件 |
|---|---|
| 1980 年 9 月 | DEC、Intel、施乐（Xerox）联合发表 10 Mb/s 以太网规约第一版 **DIX V1** |
| 1982 年 | 修改为第二版 **DIX V2**（即以太网 V2 标准） |
| 1983 年 | IEEE **802.3** 公布第一个 IEEE 以太网标准 |

DIX V2 与 IEEE 802.3 只有很小的差别，因此常把 IEEE 802.3 局域网简称为"以太网"。

**LLC 与 MAC 两个子层**：为了使数据链路层能更好地适应多种局域网标准，IEEE 802 委员会把局域网的数据链路层拆成两个子层——**逻辑链路控制（Logical Link Control, LLC）子层**和**媒体接入控制（Media Access Control, MAC）子层**。与接入到传输媒体有关的内容都放在 MAC 子层，而 LLC 子层则与传输媒体无关；不管采用何种协议的局域网，对 LLC 子层来说都是透明的。很多厂商生产的适配器上就仅装有 MAC 协议而没有 LLC 协议。

```text
+--------------------------------------+
|            网络层（IP）               |
+--------------------------------------+
|  LLC 子层：与传输媒体无关（逻辑链路控制）|
+--------------------------------------+
|  MAC 子层：与接入传输媒体有关（寻址/接入）|
+--------------------------------------+
|            物理层                     |
+--------------------------------------+
```

这条"MAC 与介质相关、LLC 与介质无关"的划分，解释了今天的一个现实：**网卡只实现 MAC，LLC 基本被上层 IP 取代**。所以分析以太网安全时，关注点全部在 MAC 子层。

### 2.4.2 MAC 层的硬件地址

在局域网中，**MAC 地址 = 硬件地址 = 物理地址**，长度 6 个字节、48 位。

| 部分 | 长度 | 分配者 | 含义 |
|---|---|---|---|
| 前 3 字节（前 24 位） | 24 bit | IEEE 的注册管理机构 RA 分配给厂家 | 组织唯一标识符（OUI）。如 `00-00-0C` = CISCO SYSTEMS, INC.；`00-18-82` = Huawei Technologies Co. |
| 后 3 字节（后 24 位） | 24 bit | 厂家自行指派 | 扩展标识符（序列号），必须保证生产出的适配器没有重复地址 |

48 位地址空间极大，目前还没有出现地址枯竭的问题。书写上通常记为 12 个十六进制数，每 2 个之间用冒号或破折号隔开：`MM:MM:MM:SS:SS:SS`（M 代表制造商分配的唯一标识符，S 代表序列号）。例如 `08:00:20:0A:8C:6D` 中，`08:00:20` 是制造商编号，`0A:8C:6D` 是该制造商所制造的某个网络产品（如网络适配器）的系列号。

**I/G 位**（Individual / Group）：IEEE 规定地址字段**第一字节的最低位**为 I/G 位。

| I/G 位 | 含义 |
|---|---|
| 0 | 单站地址（单播，Individual） |
| 1 | 多播地址（Group），用来进行多播 |
| 48 位全 1 | 广播地址 `FF:FF:FF:FF:FF:FF`，**只能作为目的地址使用** |

```text
 第一字节
+---+---+---+---+---+---+---+---+
| b7| b6| b5| b4| b3| b2| b1| b0|   b0 = I/G 位
+---+---+---+---+---+---+---+---+
                              ^
                    0 = 单播（Individual）
                    1 = 组播（Group）
       例：01:00:5E:... 首字节 0x01，最低位为 1 -> 组播
           00:1A:2B:... 首字节 0x00，最低位为 0 -> 单播
```

MAC 地址的固化方式：生产网络适配器时，6 字节 MAC 地址已被固化在适配器的 ROM 中，因此也叫硬件地址或物理地址；当一台计算机启动时，MAC 地址从 ROM 拷贝到 RAM。

这里埋着本章最重要的安全前提：**"固化在 ROM"只是出厂行为，操作系统发送帧时用的是 RAM 里那份**。所以 MAC 地址在软件层可以被任意改写——"物理地址"这个名字给了它不应有的可信度。

### 2.4.3 MAC 帧格式（以太网 V2）

以太网 V2 的 MAC 帧包含六个字段（另加帧前 8 字节的前导码）：

| 序号 | 字段 | 长度 | 作用 | 安全相关性 |
|---|---|---|---|---|
| — | 前同步码 + 帧开始定界符 | 8 字节（硬件生成） | 实现比特同步：前 7 字节为 1/0 交替码；第 8 字节取值 10101011，是帧开始定界符，表示后面的信息就是 MAC 帧 | 决定"帧从哪开始"，是帧同步的基础 |
| （1） | 目的地址（DA） | 6 字节 | 目的主机的 MAC 地址 | 可被伪造（伪造网关 MAC 做中间人） |
| （2） | 源地址（SA） | 6 字节 | 发送方的 MAC 地址。**该字段只能是单播地址，不能是广播或多播地址** | 交换机据此学习端口映射 → 泛洪攻击的入口 |
| （3） | 类型（Type） | 2 字节 | 标识上一层采用的协议，以便把数据交付给上层对应协议。0x0800 = IPv4；0x0806 = ARP | 可被用于协议混淆/绕过过滤 |
| （4） | 数据（Data） | 46~1500 字节 | 存储被封装的上层数据 | 承载明文载荷；不足 46 字节需填充 |
| （5） | 帧校验序列（FCS） | 4 字节 | 包含 CRC 数据校验计算的结果 | 无密钥，抗随机误码、不抗篡改 |
| （6） | — | — | 帧长度取值范围：**64 ~ 1518 字节** | — |

```text
+----------+--------+--------+--------+------------------+--------+
| 前导码8B | 目的6B | 源6B   | 类型2B | 数据 46~1500B     | FCS 4B |
| 7B同步码 |        |        |        | (不足46B则填充)   |        |
| 1B SFD   |        |        |        |                  |        |
+----------+--------+--------+--------+------------------+--------+
            |<------------- 64 ~ 1518 字节 ------------->|
            |<-- 不计前导码，这就是"帧长"的定义范围 -->|
```

**为什么有效帧长度 ≥ 64 字节？** 这是 CSMA/CD 的要求：最短帧发送时间必须大于等于争用时隙 2τ。以太网（802.3）规定，在 10 Mbps 局域网中时隙 2τ = 51.2 微秒，于是最短帧长度 = 10 Mbps × 2τ / 8 = **64 Byte**。

这个数字的物理含义是：发送方必须"占住"信道足够久，才能在自己发完之前收到最远端可能发生的冲突信号。如果帧太短，发送方会在冲突信号返回之前就发完并释放信道，于是它**误以为发送成功**——这就是"漏检冲突"。所以 64 字节不是随意规定的，它是**冲突检测窗口的时间投影**。

**为什么有效帧长度 ≤ 1518 字节？** 工作站在处理接收到的帧时需要内存，而上世纪七八十年代内存昂贵，故规定有效帧长度 ≤ 1518 字节。

**MTU 与分片**：链路层规定了传输的最大数据单元（MTU）。不同类型的网络在传输数据时大多有一个上限。如果 IP 层交付下来的数据比数据链路层的 MTU 值还大，那么 IP 层就需要进行分片，将数据报分成长度小于 MTU 的若干分片后再传输。

**填充**：如果数据报小于 46 字节，则需要在该数据字段后面填充一定的字段，以保证以太网帧长不小于 64 字节。

```text
数据 40 字节（如 TCP ACK 的裸 IP 包）
+--------+--------+--------+----------------+--------+------+
| 目的 6 | 源 6   | 类型 2 | 数据 40 + 填充 | FCS 4  |      |
+--------+--------+--------+----------------+--------+------+
                            共 46 字节（填充 6 字节）
 帧长 = 6+6+2+46+4 = 64 字节  -> 恰好达到下限
```

> 补充：填了填充字节后，"数据字段里到底有多少是真实数据"由上层协议的长度字段（IP 总长度）决定，接收方会按 IP 首部的总长度截断，所以填充不会污染上层数据。

### 2.4.4 IEEE 802.3 与以太网 V2 的差别

两者格式相似，区别集中在第三个字段：

1. IEEE 802.3 规定 MAC 帧的第三个字段为**"长度/类型"**。当这个字段值**大于 0x0600**（十进制 1536）时，就表示"类型"，这样的帧和以太网 V2 MAC 帧完全一样；当字段值**小于 0x0600** 时才表示"长度"。
2. 当"长度/类型"字段值小于 0x0600 时，数据字段必须装入 LLC 子层的 LLC 帧。

现在市场上流行的都是以太网 V2 的 MAC 帧，但大家也常常把它称为 IEEE 802.3 标准的 MAC 帧。

| 判据 | 结论 |
|---|---|
| 字段值 > 0x0600（1536） | 按"类型"解释 → 与 V2 相同 |
| 字段值 < 0x0600 | 按"长度"解释 → 数据字段里是 LLC 帧 |
| 阈值为什么是 1536 | 因为最大数据字段是 1500，长度值不可能超过 1500，故 1536 以上必是类型码 |

### 2.4.5 拓扑与设备演进：从总线到交换机

**拓扑**是用拓扑学方法抽象的网络结构，研究计算机网络中"点"和"线"构成的几何图形。种类有总线型、星型、环型、树型、网状型等。

| 拓扑 | 结构 | 优点 | 缺点 |
|---|---|---|---|
| 总线型 | 所有结点连接到一条共享总线上 | 电缆长度短，布线容易 | 故障扩散性强，故障定位排除困难 |
| 星型 | 由中央节点和通过点到点链路连接到中央节点的各节点组成 | 便于集中管理、单点故障易隔离 | 依赖中央节点 |

**总线型以太网**：传统以太网最初使用粗同轴电缆，后来演进到较便宜的细同轴电缆。接入方式是通过 T 形头穿透同轴电缆的保护层，使一根针接触到里面的铜线，与计算机网卡相连。它采用 **CSMA/CD 协议**，在具有广播特性的总线上实现一对一的通信：B 向 D 发送数据时，总线上所有站都能收到信号，但只有 D 接受，A、C、E 都不接受。总线两端还有**匹配电阻**，用来吸收总线上传播的信号（防止反射）。

```text
 匹配电阻                                                          匹配电阻
 --[=]--+--------+--------+--------+--------+--------+--------+--[=]--
        |        |        |        |        |        |        |
        A        B        C        D        E      (T形头接入)
                 |                 |
              发送数据           接受数据
        （B -> D：只有 D 接受，其余站点不接受）
```

**使用集线器的以太网**：采用双绞线，构建基于星形拓扑的以太网，在星形中心增加了可靠性非常高的设备**集线器（hub）**。10BASE-T（10 Mbit/s 无屏蔽双绞线星形网）的出现既降低了成本又提高了可靠性，性价比很高，是局域网发展史上一个非常重要的里程碑，为以太网在局域网中的统治地位奠定了牢固基础——以太网的拓扑从此由总线形变为更方便的星形。

**集线器的关键特点**（安全上极其重要）：

- 集线器用电子器件模拟实际电缆线的工作，很像一个**多接口的转发器，工作在物理层**；
- 使用集线器的以太网**在逻辑上仍是总线网**，各工作站使用的还是 CSMA/CD 协议，并**共享逻辑上的总线**。

推论：**集线器上的每一个端口都能看到所有帧**。这就是"接在 hub 上的任何一台机器都能嗅探全网"的根本原因。

**以太网交换机**：网桥工作在数据链路层，根据 MAC 帧的目的地址对收到的帧进行转发和过滤；收到一个帧时，先检查目的 MAC 地址，再确定将该帧转发到哪一个接口，或把它丢弃。1990 年问世的交换式集线器可明显提高以太网性能，常称为以太网交换机（**多接口的网桥**），工作在数据链路层。

交换机的特点：

- 接口有存储器，能在输出端口繁忙时把到来的帧进行**缓存**；
- 是一种**即插即用**设备，其内部的帧交换表（又称**地址表**）通过**自学习算法**自动逐渐建立；
- 使用专用交换结构芯片，**硬件转发**，速率比软件转发的网桥快很多；
- 是以太网发展史上的另一个里程碑。

| 设备 | 工作层次 | 转发依据 | 广播域 | 冲突域 | 能否被嗅探 |
|---|---|---|---|---|---|
| 集线器（hub） | 物理层 | 无（信号再生后向所有端口复制） | 一个 | 一个 | 全部端口互相可见 |
| 交换机（switch） | 数据链路层 | MAC 地址表 | 一个（不划分 VLAN 时） | 每端口一个 | 默认仅本端口，除非表被污染或做端口镜像 |
| 路由器 | 网络层 | 路由表（IP） | 每接口一个 | 每接口一个 | 仅本网段 |

### 2.4.6 交换机自学习算法

自学习算法指交换机通过学习和维护 MAC 地址表，实现在局域网内部转发数据帧的过程，包括三步：**初始化、自学习过程、自动更新过程**。运行时交换机通过检测接收帧的**源 MAC 地址**，动态学习 MAC 与端口的映射关系，并存入 MAC 地址表。

**初始化**：开始时，交换机里面的交换表是空的。

**第一个帧（A → B，从接口 1 进入）**：

1. 交换机收到帧后查找交换表，该表为空；
2. 交换机把该帧的**源地址 A 和接口 1** 写入交换表，"有效时间"确保过期的项目自动被删除；
3. 向除接口 1 以外的所有接口**广播**这个帧；C 和 D 丢弃该帧，只有 B 收下这个目的地址正确的帧。

**第二个帧（B → A，从接口 3 进入）**：

1. 交换表新增项目（B, 3），表明如有发送给 B 的帧，就应当从接口 3 转发出去；
2. 查找发现交换表中已有 A 的记录，则从**接口 1 直接转发**（单播，不再广播）。

```text
初始：交换表 = 空

 A ---1---[ 交换机 ]---2--- C
              | 3
              B

① A->B（入口 1）：表空 -> 学得 (A,1)，其余端口广播
② B->A（入口 3）：学得 (B,3)；查表命中 A -> 仅从 1 转发

最终交换表：
+--------+--------+----------+
| MAC    | 接口   | 有效时间 |
+--------+--------+----------+
|   A    |   1    |   TTL    |
|   B    |   3    |   TTL    |
+--------+--------+----------+
```

**转发帧的规则可以压成一张判定表（考试高频）**：

| 情况 | 处理 |
|---|---|
| 收到帧，源地址不在表中 | 增加项目（源地址、进入的接口、有效时间） |
| 收到帧，源地址已在表中 | 更新原有项目（进入的接口或有效时间） |
| 目的地址不在表中 | 向所有其他接口（进入接口除外）转发 —— **泛洪** |
| 目的地址在表中且接口 = 进入接口 | **丢弃**（目的地与本端口同侧，无需转发） |
| 目的地址在表中且接口 ≠ 进入接口 | 按表中接口**转发** |

这套算法让交换机"即插即用，不必人工配置"，非常方便；学习算法通过自动学习和动态更新机制有效管理内部 MAC 地址表，确保数据帧快速准确到达目的地。

但它有三个结构性弱点，全部是后续攻击的入口：

1. **只信源地址、不做验证**——谁能发出一个帧，谁就能"声明"自己占据某个端口；
2. **表容量有限**——地址表是硬件 CAM，条目数固定；
3. **未知目的地址就泛洪**——"学不到"的代价是"广播出去"。

第 3 条是理解 MAC 泛洪攻击的关键：**泛洪不是异常行为，而是算法的正常兜底逻辑**。攻击者要做的事只是让"查不到"成为常态。

## 2.5 PPPoE 协议

### 2.5.1 为什么需要 PPPoE

**PPPoE（PPP over Ethernet）** 通过将 PPP 协议封装在以太网帧内，在广播式以太网上建立**逻辑点对点隧道**，成功将 PPP 的认证、计费等管理能力无缝扩展至宽带接入场景，兼顾了网络效率与管理需求。

它是将 PPP 封装在以太网框架中的一种网络隧道协议，允许在以太网广播域中的两个以太网接口间创建点对点隧道。优势在于结合了**以太网的经济性**和**PPP 协议的可管理控制性**，较好解决了用户管理和上网收费等实际问题，为宽带接入提供了一种有效的解决方案，得到运营商认可并被广泛采用。PPPoE 还继承了传统的拨号上网方式，使用户能用熟悉的硬件和软件接入互联网，同时简化了客户端配置。

把动机讲透，其实是一句话：**以太网便宜但没有"用户"概念，PPP 有认证和计费但没有跨网能力，PPPoE 把两者的优点接起来。**

| 需求 | 以太网能否满足 | PPP 能否满足 | PPPoE 的答案 |
|---|---|---|---|
| 低成本、大规模部署 | 能 | 不能（需专线/拨号） | 用以太网做承载 |
| 用户身份认证 | 不能（无认证机制） | 能（PAP/CHAP） | 把 PPP 会话跑在以太网上 |
| 按用户计费/限速 | 不能 | 能（会话级） | 每个用户一个 PPP 会话 |
| 每用户独立 IP | 不能 | 能（IPCP 动态分配） | IPCP 协商地址 |

### 2.5.2 两个阶段

PPPoE 协议包括两个阶段：**PPPoE 发现阶段**和 **PPPoE 会话阶段**。

**发现阶段**：客户端通过在广播网络上发送发现报文来寻找可用的 PPPoE 服务器，建立一个唯一的 **PPPoE 会话 ID（SESSION_ID）**。客户端发现合适的服务器后，会与服务器进行初始化通信，以建立后续的 PPPoE 会话。

**会话阶段**：一旦客户端与服务器选择建立 PPPoE 连接，在会话阶段中实际建立起点对点连接，并通过交换认证信息和建立会话参数，确保双方能够安全地通信。会话建立后，双方之间就可以传输数据。

会话阶段的核心特征是：**所有以太网帧均为单播传输**，并严格沿用发现阶段确定的 MAC 地址与 SESSION_ID，确保通信的唯一性与安全性。

| 对比 | 发现阶段 | 会话阶段 |
|---|---|---|
| 以太网类型字段 | 0x8863 | 0x8864 |
| 传输方式 | 广播（PADI 起）+ 单播 | 全部单播 |
| 是否有 SESSION_ID | 尚未分配（为 0） | 已分配，全程沿用 |
| 目的 | 找到服务器、确定会话 ID | 承载 PPP（含认证与数据） |

```text
客户端                                              服务器（BRAS）
  |--- PADI（广播：谁提供 PPPoE 服务？）------------>|
  |<-- PADO（单播：我可以，我的能力是...）-----------|
  |--- PADR（单播：就选你，请分配会话 ID）---------->|
  |<-- PADS（单播：会话 ID = X，会话开始）-----------|
  |=========== 会话阶段：PPP LCP/认证/IPCP =========|
  |<=========== 数据（全部单播，沿用 X）============|
```

> 补充：发现阶段的四个报文缩写为 PADI（Active Discovery Initiation）、PADO（Offer）、PADR（Request）、PADS（Session-confirmation），结束时还可能用 PADT（Terminate）通知会话结束。PPT 只给出代码 0x07 = PADO 这一例，上述缩写属标准背景。

### 2.5.3 PPPoE 帧格式

PPPoE 数据包由四部分串联而成：**以太网头（14 字节）+ PPPoE 头（6 字节）+ PPP 帧（承载 IP 数据）+ FCS 校验序列（4 字节）**。PPPoE 数据包封装在以太网帧的数据字段中。

| 以太网类型字段 | 含义 |
|---|---|
| 0x8863 | PPPoE **发现阶段**数据报的数据包 |
| 0x8864 | PPPoE **会话阶段**数据报的数据包 |

PPPoE 头部的六个字段：

| 字段 | 长度 | 说明 |
|---|---|---|
| 版本（Version） | 4 bit | PPPoE 版本号，协议规定值为 0x01 |
| 类型（Type） | 4 bit | PPPoE 类型，协议规定值为 0x01 |
| 代码（Code） | 1 字节 | 区分 PPPoE 报文类型。如代码 0x00 表示会话数据；0x07 表示 PPPoE 主动发现提议包 PADO（PPPoE Active Discovery Offer）等 |
| 会话 ID（SESSION_ID） | 2 字节 | 会话阶段用于标识特定的 PPPoE 会话 |
| 长度（Length） | 2 字节 | 表示 PPPoE 数据的长度，**不包括首部** |
| 数据（Data） | 可变长 | 发现阶段包含用于在客户端和接入集中器之间交换必要信息的标记；会话阶段携带 PPP 协议的数据 |

注意"版本 4 位 + 类型 4 位 = 1 字节"，这是说"头部只有 6 字节"的原因：版本与类型共用一个字节。PPT 的评价是——PPPoE 头部短小精悍，仅 6 字节，最大限度减少协议开销；设计兼顾了会话识别的唯一性与报文类型的灵活性，是实现高效宽带接入的关键。

```text
+-------------+------------------+---------------------------+--------+
| 以太网头 14B| PPPoE 头 6B      | PPP 帧（含 PPP 头 + IP）   | FCS 4B |
| 目的6 源6   | Ver4|Type4 = 1B  |                           |        |
| 类型2       | Code 1B          |                           |        |
| (8863/8864) | SESSION_ID 2B    |                           |        |
|             | Length 2B        |                           |        |
+-------------+------------------+---------------------------+--------+
                              |<-- Length 只算这一段 -->|
```

### 2.5.4 PPPoE 的安全问题

PPPoE 把 PPP 的认证搬到了以太网广播域里，于是**两层的弱点叠加**：

| 攻击 | 手法 | 成因 |
|---|---|---|
| PADI 洪泛 / 会话耗尽 | 伪造大量源 MAC 发送 PADI，耗尽服务器会话资源 | 发现阶段依赖广播，服务器必须响应未知客户端 |
| 假冒 PPPoE 服务器 | 抢先应答 PADO，把客户端引到攻击者主机，再代理转发 | 客户端无法验证 PADO 的真伪（发现阶段无认证） |
| 中间人窃听 | 假冒服务器后，用 PAP 获取明文口令，或转发中截获数据 | PPP 认证在会话阶段才做，且 PAP 明文 |
| 会话 ID 猜测/注入 | SESSION_ID 仅 16 位，可枚举后注入伪造帧 | 会话标识无密码学保护 |
| 强制断线 | 伪造 PADT 报文 | PADT 无认证 |

防御要点：客户端与服务器侧启用 CHAP 而非 PAP；在接入设备上限制单位时间的 PADI 速率与最大会话数；用端口隔离（PVLAN/端口保护）阻止用户间二层互通；对 PADT 做源 MAC 与 SESSION_ID 一致性校验。

## 2.6 MAC 泛洪攻击

### 2.6.1 攻击原理：把"有限"变成"失效"

MAC 泛洪攻击指攻击者通过**伪造大量的 MAC 地址**来淹没网络交换机的地址表，导致正常的 MAC 帧无法转发。它影响网络性能，并存在"敏感信息泄露"的安全风险。

核心在于：**MAC 地址表的大小是有限的**。交换机正常运行时通过检测接收帧的源 MAC 地址动态学习 MAC 与端口的映射关系并存入 MAC 地址表；当攻击者不断发送大量含有随机源 MAC 地址的帧时，交换机会尝试学习这些地址并添加到地址表中。当 MAC 地址表超出容量时，交换机无法再学习新的地址。一旦发生这种情况，**交换机将退化为集线器模式，广播所有传入的帧到所有端口**。这样不仅影响网络效率，还可能泄露敏感数据。

```text
正常状态                         泛洪之后
+--------+--------+              +--------+--------+
| MAC    | 端口   |              | MAC    | 端口   |
+--------+--------+              +--------+--------+
| A      | 1      |              | 随机1  | 24     |
| B      | 3      |              | 随机2  | 24     |
| 网关   | 24     |              | 随机3  | 24     |
| ...    | ...    |              |  ...   | ...    |
+--------+--------+              | 随机N  | 24     |  <- 表满
  命中即单播                      +--------+--------+
                                  查不到 -> 泛洪所有端口
```

这个"退化"用 2.4.6 的转发规则解释得一清二楚：表满之后，**新学不到，老的还会被老化掉**，于是绝大多数目的地址都"查不到"，按规则就要"向所有其他接口转发"。**交换机的安全模型依赖地址表的准确性，表一旦失真，它就变回了一个 hub。**

### 2.6.2 攻击步骤与后果

以"服务器为客户端提供 FTP 文件传输服务"的场景为例（PPT 的例子）：

| 步 | 攻击者动作 | 交换机反应 | 目的 |
|---|---|---|---|
| 1 | 生成大量随机源 MAC 的帧（源地址不断变化） | 逐条学习，写入 MAC 地址表 | 尽快填满表 |
| 2 | 持续发送，直到表项达到容量上限 | 新地址无法学习；老表项被老化挤掉 | 使表长期处于"满/错"状态 |
| 3 | 正常主机（如客户端）发起到服务器的 FTP 连接 | 目的 MAC 查不到 → 向所有端口泛洪 | 帧被送到攻击者端口 |
| 4 | 攻击者在自己的端口抓包 | — | 获得会话内容、用户名、口令 |
| 5 | 观察现象 | 登录延迟或登录失败（泛洪导致拥塞与丢帧） | 拒绝服务 |

两类后果要分开记：

- **可用性**：MAC 地址表满后无法学习新地址，交换机只能广播，导致登录延迟或登录失败；大量泛洪帧本身也挤占带宽与 CPU。
- **机密性**：由于广播，用户名和密码等敏感信息存在泄露风险。原始 MAC 泛洪只造成"能看到"，配合 ARP 欺骗即可升级为"能改写"（中间人）。

> 补充：MAC 泛洪通常与 ARP 欺骗配合使用——泛洪让交换机变成 hub（被动嗅探），ARP 欺骗则主动把网关 IP 映射到攻击者 MAC（主动中间人）。二者成因不同：前者打的是 CAM 表容量，后者打的是 ARP 无认证。

### 2.6.3 防御：端口安全与配套机制

PPT 给出的多层次防御机制有三条：

1. **启用端口安全机制**，限制连接到交换机端口的设备数量，防止过多连接导致网络拥塞；
2. **采用动态 ARP 检测（Dynamic ARP Inspection, DAI）技术**，防范伪造的 ARP 请求，确保网络设备的 MAC 地址信息真实；
3. **通过静态 MAC 地址绑定**，将端口与特定 MAC 地址关联，限制未授权设备的连接。

最核心的手段是 **Port Security（端口安全）**。它是交换机的一种安全特性：配置了端口安全功能的交换机对网络管理员定义的**合法用户**的数据进行正常转发，对**非法用户**的数据执行丢弃或直接关闭接口，以阻止非安全用户数据经过本交换机传输。为了防止 MAC 泛洪攻击，可以在交换机端口上实施端口安全性策略，**通过限制有效 MAC 地址的数量**来增强网络安全。

Port Security 提供三种管理 MAC 地址的方法：

| 类型 | 产生方式 | 是否写入配置文件 | 重启后 | 适用场景 |
|---|---|---|---|---|
| 静态安全 MAC 地址 | 手动设置，如 `switchport port-security mac-address 1111.1111.1111` | 是 | 仍被识别并保持有效 | 固定设备（服务器、打印机、上行口） |
| 动态安全 MAC 地址 | 交换机自动学习 | 否 | 需重新学习 | 临时/流动终端 |
| 粘滞安全 MAC 地址 | 可手动指定或自动学习 | 是（可保存到配置文件与 CAM 表） | 无需重新学习，自动恢复 | 办公区接入端口（最常用） |

关于 CAM：**内容可寻址存储器（Content Addressable Memory, CAM）** 通常称为 MAC 地址表 / CAM 表。粘滞（sticky）地址保存到配置文件后，交换机重启无需重新学习即可自动恢复。

配置思路（按 PPT 的例子）：**限制每个端口只能学习 10 个 MAC 地址**；一旦学习的地址数量达到限定值，任何超出此数量的新 MAC 地址将会被自动丢弃。这样即使攻击者继续发随机源 MAC，这些帧也进不了地址表，表不会被挤满，交换机保持"按表转发"的正常状态。

```text
配置要点（示意，命令按厂商语法）
 interface Fa0/1
   switchport mode access
   switchport port-security                     <- 启用端口安全
   switchport port-security maximum 10          <- 最多 10 个 MAC
   switchport port-security mac-address sticky  <- 学习并固化合法 MAC
   switchport port-security violation shutdown  <- 超限则关闭端口（或 protect/restrict）

效果对照
 未配置：随机 MAC 源源不断入表 -> 表满 -> 泛洪（等价 hub）
 已配置：第 11 个 MAC 被拒 -> 表保持稳定 -> 继续单播转发
```

### 2.6.4 防御的局限与延伸

端口安全并非"配了就没事"，需要注意它的边界：

| 风险点 | 说明 | 缓解 |
|---|---|---|
| 误伤 | 接在端口后的 hub/小交换机（多个设备）会触发超限，导致整口 shutdown | 接入端口限制 downstream 设备，或改用 restrict 模式 |
| 端口耗尽式 DoS | 攻击者故意触发 violation 使端口关闭，属于"用防御机制打 DoS" | 设置自动恢复（errdisable recovery） |
| 只保护接入端口 | 上行口/级联口若也开端口安全，容易误封合法流量 | 上行口只做静态绑定，不做粘滞学习 |
| 不防 ARP 欺骗 | 泛洪被挡住了，但 ARP 缓存投毒仍可做中间人 | 配合 DAI + DHCP Snooping |
| 不防 VLAN 跳跃 | 双标签（QinQ）攻击可越 VLAN | 接入端口强制 `switchport mode access`，关闭 DTP，未用端口 shutdown |
| CAM 老化时间 | 表项老化后又会短暂"查不到"而泛洪 | 缩短泛洪窗口、开启未知单播抑制 |

DAI 的作用要理解清楚：它依赖 **DHCP Snooping 建立的 IP-MAC-端口绑定表**，逐帧校验 ARP 报文中的 IP 与 MAC 是否与绑定表一致，不一致就丢弃。所以**没有 DHCP Snooping 就没有可信的绑定表，DAI 无从判定**——这是一条常被忽略的依赖关系。

## 考点提示

- **网络接口层 = 物理层 + 数据链路层**，在 TCP/IP 四层模型中合并为一层；数据单位分别是比特与帧。
- 物理层的两条功能必须成对记：传比特流 + 屏蔽介质差异；链路层的三条功能必须成组记：封装成帧、透明传输、差错控制。
- 帧定界的控制字符是 **SOH / EOT**，转义字符是 **ESC（0x1B）**；遇 ESC 本身要再插一个 ESC，收端收到连续两个 ESC 时删前一个。
- **数据链路层只提供比特差错检测**，不负责重传、去重、排序；"无差错接受" ≠ "可靠传输"。
- FCS 是冗余码的角色，CRC 是算出 FCS 的一种算法；BER 是信道指标，三者不可混用。
- PPP 三组成：封装方法 + LCP + NCP；协议字段与承载内容的对应：**0xC021 LCP、0xC023 PAP、0xC223 CHAP、0x8021 IPCP**。
- PPP 五阶段顺序：链路不可用 → 链路建立（LCP）→ 认证（PAP/CHAP）→ 网络层协议（NCP/IPCP）→ 链路终止（LCP）。
- **PAP 两次握手、明文、可重放；CHAP 三次握手、哈希、随机挑战、可周期性再认证**。判断"哪个更安全"必须从"是否明文"和"能否重放"两条说。
- LCP 的标识符只做请求-响应配对，是递增而非随机，因此**不提供抗重放能力**。
- IPCP 只使用 LCP 的代码 1~7；它在**网络层协议阶段之后**才交换，之前收到的 IPCP 包一律丢弃。
- 隧道的一般形式：**协议B（隧道头（协议A））**；LAC 与 LNS 互为对等体，**一条隧道可复用多条会话**（隧道 ID 相同、会话 ID 不同）。
- L2TP 跑在 **UDP 1701**；控制通道可靠、数据通道不可靠；**控制消息必须 L=1、S=1、O=0**。
- **L2TP 不是严格意义上的安全协议**（无密码学机密性与完整性），实际部署用 **L2TP over IPsec**。
- MAC 地址 48 位，前 24 位 OUI 由 IEEE 分配、后 24 位厂家指派；**第一字节最低位是 I/G 位**，0 单播、1 组播、全 1 广播（只能作目的地址）。
- MAC 帧长 **64~1518 字节**；64 字节来自 CSMA/CD 的 2τ=51.2 μs（10 Mbps×2τ/8）；1518 来自当年内存成本；数据字段 46~1500。
- 以太网 V2 与 802.3 的区分点是第三字段：**>0x0600 为类型，<0x0600 为长度**。
- 交换机**按源地址学习、按目的地址转发**；查不到就泛洪，同口则丢弃。
- MAC 泛洪的本质是**打满有限的 CAM 表 → 交换机退化为集线器 → 泛洪导致嗅探与 DoS**；防御核心是 Port Security 限 MAC 数量，辅以静态绑定与 DAI。

## 易错点与自测

### 易错概念对比

| 对比项 | 概念 A | 概念 B | 区分要点 |
|---|---|---|---|
| 差错控制 vs 可靠传输 | 链路层差错控制：只检测比特差错 | 可靠传输：确认、重传、去重、排序 | 链路层只做前者，后者由 TCP 承担 |
| FCS vs CRC | FCS：附加的冗余码（字段/角色） | CRC：计算冗余码的算法 | 一个是"东西"，一个是"做法" |
| PAP vs CHAP | 两次握手、明文口令、可重放 | 三次握手、哈希响应、随机挑战、周期再认证 | 记"手数 + 是否明文 + 能否重放"三点 |
| LCP vs IPCP | 链路层参数（认证方式、MRU、压缩） | 网络层参数（IP 地址、DNS、VJ 压缩） | LCP 是总控，IPCP 是"乘客"，且代码只用 1~7 |
| 隧道 vs 加密 | 隧道解决"跨网搬运" | 加密解决"看不见、改不了" | L2TP 有隧道无加密，必须套 IPsec |
| 集线器 vs 交换机 | 物理层、共享总线、全端口可见 | 链路层、按 MAC 表转发、端口隔离 | 泛洪后交换机"表现像"集线器，但层次没变 |
| MAC 泛洪 vs ARP 欺骗 | 打 CAM 表容量，造成被动嗅探/DoS | 打 ARP 无认证，造成主动中间人 | 一个灌表，一个投毒；常配合使用 |

### 自测题

**1. 一条 PPP 链路上，若把 PAP 换成 CHAP，攻击者"抓到包就能登录"的问题为什么消失？请从机制上说明。**

**答**：PAP 的认证请求里就是"用户名 + 明文口令"，抓包即得口令，且报文无随机因素，可原样重放。CHAP 是挑战-响应：认证方先发随机值 R，被认证方回的是 Hash(口令‖R)，口令从不上线；由于每次 R 都不同，旧的响应值对新的挑战无效，重放失败。因此"抓包即登录"在 CHAP 下不再成立（但仍需防范弱口令下的离线爆破）。

**2. 以太网最短帧长为什么是 64 字节？如果帧可以只有 20 字节，会发生什么？**

**答**：CSMA/CD 要求"最短帧发送时间 ≥ 争用时隙 2τ"。10 Mbps 以太网的 2τ = 51.2 μs，对应 10 Mbps × 51.2 μs / 8 = 64 字节。若帧短于 64 字节，发送方会在最远端的冲突信号返回之前就发送完毕并释放信道，从而**误判发送成功**（漏检冲突），CSMA/CD 的冲突检测机制失效。

**3. 交换机收到一个帧，源地址在表中已存在但记录的接口与本次进入的接口不同，交换机会怎么做？为什么这一行为可被攻击？**

**答**：交换机会**更新**该表项为"新进入的接口"（同时刷新有效时间），然后用更新后的表转发。因为学习只信源地址、不做任何认证，攻击者只要伪造源 MAC 持续发帧，就能把"网关 MAC → 上行口"改写成"网关 MAC → 攻击者端口"，后续发往网关的帧全被引到攻击者处（MAC 欺骗/中间人），而合法主机的表项会被覆盖，还可能出现来回翻动导致的转发不稳。

**4. 判断：L2TP 使用 CHAP 做隧道端点认证，因此 L2TP 提供了机密性保护。**

**答**：错。CHAP 只解决"对端是谁"，且只保护认证交换本身。原始 L2TP（RFC 2661）不提供基于密码学的机密性与完整性，PPP 载荷明文传输。要获得机密性与完整性，必须叠加 IPsec，形成 L2TP over IPsec。

**5. MAC 泛洪攻击为什么会让交换机"退化为集线器"？端口安全是怎么阻断这条链路的？**

**答**：交换机按源地址学习并写入容量有限的 CAM 表。攻击者用大量随机源 MAC 的帧把表灌满后，新地址无法学习、旧表项又被老化挤出，于是绝大多数目的地址"查不到"，按转发规则只能向除入口外的所有端口泛洪——行为上等价于集线器。端口安全通过限制端口可学习/可绑定的 MAC 数量（如最多 10 个），使超限的新 MAC 直接被丢弃或触发端口关闭，CAM 表不再被污染，交换机保持按表单播转发。
