# 第五章 应用层协议安全

前四章解决的是"数据怎么可靠地、正确地送到对面"——链路、网络、传输层关心的是可达性、有序性和完整性。本章换一个视角：数据送到了，**对面那个人是不是它声称的那个人、这段内容有没有被别人看过或改过、这个应用本身会不会被滥用**。这三件事全部由应用层协议决定，而应用层协议恰恰是历史上最晚才考虑安全的一层。

本章的展开方式是"逐协议解剖"：先看协议为什么这样设计（报文格式、交互流程），再看设计上留下的哪一条缝隙被攻击者利用，最后看工程上如何补。六个协议——DNS、HTTP、邮件（SMTP/POP3/IMAP）、DHCP、FTP、SSH——覆盖了"名字解析、内容获取、消息投递、地址配置、文件搬运、远程登录"这六类最基本的网络动作，它们的缺陷模式高度重复，最后 5.7 节把这种重复归纳成三条共性根因。

## 5.1 应用层协议概述

### 5.1.1 定义：应用层协议是"应用程序之间的约定"

应用层协议是一种**面向应用程序**的通信协议，负责在网络中的不同应用程序之间传输数据。这句话里有两个关键词需要拆开：

- **面向应用程序**：它不关心比特怎么调制、包怎么路由，它只规定"两个进程之间用什么格式说话"。所以应用层协议本质是一份**语义契约**——字段叫什么、取值什么含义、谁先开口、出错怎么回。
- **不同应用程序之间**：通信的两端不是主机，而是主机上的进程。同一个 80 端口上跑的可能是 Apache 也可能是 Nginx，但对 HTTP 而言它们是同一个角色，因为协议约束的是行为而不是实现。

由此可推出本章的一条主线：**应用层协议的安全性，绝大部分不取决于实现质量，而取决于协议文本本身有没有规定安全机制**。一个严格按 RFC 实现的 HTTP/1.0 服务器，仍然是明文、仍然无状态，这不是 bug，是规格。

### 5.1.2 分类：按协议族与按开放程度

按功能，课程给出的应用层协议清单如下（端口号是考点，必须记牢）：

| 中文名 | 应用层协议 | 端口号 | 用途 |
|---|---|---|---|
| 域名系统 | DNS | 53 | 将域名转换为 IP 地址，是互联网域名解析的基础服务 |
| 超文本传输协议 | HTTP | 80 | 用于从服务器传输超文本到本地浏览器的标准协议 |
| 简单邮件传输协议 | SMTP | 25 | 用于发送电子邮件 |
| 邮件读取协议 | POP3 | 110 | 用于从邮件服务器上接收邮件 |
| 邮件读取协议 | IMAP | 143 | 用于从邮件服务器上接收、读取和管理电子邮件 |
| 动态主机配置协议 | DHCP | 67（服务器）、68（客户端） | 自动分配 IP 地址给网络中的设备 |
| 文件传输协议 | FTP | 20（数据连接）、21（控制连接） | 用于在网络上进行文件传输 |

按**开放程度**，应用层协议分为两类，这个划分直接决定了安全分析的边界：

| 类别 | 定义方式 | 典型例子 | 安全含义 |
|---|---|---|---|
| 公用协议 | 由 RFC 文档定义，位于公共领域，任何人可自由实现 | HTTP（RFC 2616） | 协议文本公开，攻击者与防御者掌握同样的细节，"隐蔽"不能作为安全手段 |
| 专用协议 | 不能随意应用于公共领域，实现细节不公开 | P2P 文件共享系统所用协议 | 细节不公开只提高分析成本，不构成真正的安全边界；一旦逆向即失效 |

> 补充：端口号只是"默认约定"，服务端完全可以改到非标准端口。因此端口过滤只能提高扫描成本，不能作为访问控制手段；真正的控制要靠认证与网络边界策略。

### 5.1.3 重要性：应用层是"距离数据和用户最近的一层"

课程从两个层面说明其重要性：

1. **对个体**：应用层协议直接承载用户隐私——浏览了什么、给谁发了信、传了什么文件。下层协议加密只能保护"管道"，如果应用层自己把口令明文写在报文里，管道再安全也无意义。
2. **对组织**：应用层协议是不同系统之间数据交流的桥梁，其安全性关系到整个系统和组织的稳定运行，以及在遭受恶意攻击时的抵御能力。

课程把应用层协议安全涵盖的范围明确列为一组安全属性：**认证、授权、数据完整性、机密性、抗否认**。这五个词可以当作分析任何一个应用层协议的检查表——拿到一个新协议，逐条问"它有没有做到"，缺失的那几条就是它的攻击面。

| 安全属性 | 含义 | 缺失后的典型后果 |
|---|---|---|
| 认证（Authentication） | 确认通信对端身份真实 | 仿冒服务器、仿冒客户端 |
| 授权（Authorization） | 确认该身份能做什么 | 越权访问、权限重叠导致泄漏 |
| 完整性（Integrity） | 数据未被篡改 | 报文内容被改写、缓存被投毒 |
| 机密性（Confidentiality） | 数据不被未授权者读取 | 嗅探获取口令、邮件、文件 |
| 抗否认（Non-repudiation） | 行为发生后不可抵赖 | 邮件伪造、交易抵赖 |

### 5.1.4 三类根因：设计缺陷、缺乏认证、缺乏加密

课程把应用层安全威胁归纳为三条，这三条几乎能解释后面所有具体攻击：

| 根因 | 具体表现 | 本章对应实例 |
|---|---|---|
| 设计缺陷 | 早期协议在设计时未考虑安全，默认网络环境可信 | DNS 无认证的响应匹配、HTTP 无状态、FTP 明文口令 |
| 缺乏认证 | 无法验证对方身份，任何主机都能声称自己是某角色 | DHCP 仿冒服务器、DNS 缓存投毒、SMTP 任意伪造发件人 |
| 缺乏加密 | 数据明文传输，易被窃听与篡改 | FTP/SMTP/POP3 明文、HTTP 明文 Cookie |

理解这三条之后，后面每一节的"防御"其实都只是在补其中一条：加认证（DNSSEC、PKI、DHCP Snooping 绑定表）、加密（TLS/DoT/DoH/FTPS/STARTTLS）、改设计（HTTP/2 多路复用、FTP 被动模式、DNS 去中心化）。

## 5.2 DNS 协议安全

### 5.2.1 为什么需要 DNS：两套命名体系的矛盾

网络空间存在**两套命名体系**：一套是用于路由寻址的 **IP 地址**，机器友好但人不可记；另一套是便于人类记忆的**域名（Domain Name）**。域名系统（DNS）的功能就是实现二者之间的转换。

没有 DNS，用户很难正常使用互联网——这句话不是修辞。IP 地址会随服务迁移、负载均衡、容灾切换而变化，而域名可以保持稳定。也就是说，**DNS 把"身份"从"位置"中解耦出来**：用户记住的是名字，网络实际使用的是地址，中间那层映射由 DNS 动态维护。

这个解耦带来了一个结构性风险：**映射结果本身成了攻击目标**。攻击者不需要攻破目标服务器，只要让"名字→地址"这一步返回错误答案，用户就会自愿地、带着全部凭据走进攻击者的机器。所以 DNS 被称为"互联网的单点信任基础"。

### 5.2.2 基本要素与域名结构

DNS 的基本要素有三个：

- **域**：由地理位置或业务类型联系在一起的计算机或网络资源集合。
- **域名**：由字符、数字组成的名称。
- **域名服务器**：将域名映射为 IP 地址的主机。

域名结构的规则（考点密集）：

| 规则 | 具体数值/说明 |
|---|---|
| 字符集 | 由英文字母和数字构成 |
| 单个子域名长度 | 不超过 63 个字符；为便于记忆建议不超过 12 个字符 |
| 排列方向 | 从左至右，级别由低到高，标号之间用点号（.）分隔 |
| 最右侧 | 最高级别的顶级域名 |
| 整个域名总长度 | 不得超过 255 个字符 |
| 管理归属 | 各级域名由其上级域名管理机构负责；顶级域名由 ICANN 统一管理 |

以 `www.baidu.com` 为例，自右向左读：

```
        www      .    baidu      .    com
         |              |             |
      三级域名        二级域名    顶级域名(TLD)
      (主机名)        (SLD)        级别最高
   <---------- 级别由低到高 <----------
```

域名空间采用**层次化树形结构**：树形最顶层为根（Root），进一步划分顶级域（TLD），顶级域管理机构再授权给二级域名（SLD）。课程特别指出：**层次化授权行为最多可迭代 127 次**。这个数字是协议栈对递归深度设的上限，防止解析过程中出现无限循环。

顶级域分三类：

| 类型 | 含义 | 举例 |
|---|---|---|
| 国家顶级域名 nTLD | 按国家/地区划分 | .cn 中国、.us 美国、.uk 英国、.ch 智利、.au 澳大利亚、.ca 加拿大 |
| 通用顶级域名 gTLD | 按行业/性质划分 | .com 公司和企业、.net 网络服务机构、.org 非赢利性组织、.edu 美国专用教育机构、.gov 美国专用政府部门、.mil 美国专用军事部门、.int 国际组织 |
| 基础结构域名 | 只有 arpa 一个，美国军方保留域名，用于反向域名解析，故又称反向域名 | arpa |

以"某高校服务器主机的完整标识 `www.example.edu.cn`"为例，其层级为：根（.）→ cn（国家顶级域）→ edu（教育类二级域）→ example（学校）→ www（主机）。

> 补充：域名解析是"右向左收敛"的过程，因此越靠右的层级越少变化，越靠左的层级越常变化。DNS 缓存 TTL 的设置正是在"变更速度"和"查询开销"之间取平衡。

### 5.2.3 四类域名服务器与主辅备份

域名服务器是互联网中的核心组件，负责把易于记忆的域名转换为计算机能识别的 IP 地址。按其功能分为四类：

| 类型 | 位置 | 职责 | 安全相关性 |
|---|---|---|---|
| 根域名服务器 | 域名系统最高层级 | 存储所有顶级域名服务器的域名和 IP 地址；本地域名服务器遇到无法直接解析的情况，首先向根发起查询 | 被攻击或遭劫持将影响全局解析，是 DDoS 的首选目标 |
| 顶级域名服务器 | 根之下 | 专门管理注册在其下的二级域名；响应可能是最终 IP，也可能是指引下一步应联系的服务器 IP | 返回"指引"而非答案，故其响应可被用于把查询引向恶意 NS |
| 权限域名服务器 | 具体域内 | 存储特定域名的 DNS 记录并提供官方认证信息，回答与该域相关的详细查询 | 是"权威答案"的来源，被攻陷即等于该域被完全劫持 |
| 本地域名服务器 | 用户/组织网络内部 | 通常由 ISP 或企业网管配置，为本网络用户提供解析，并作为其首选 DNS 服务器 | 缓存所在地，是缓存投毒的直接受害者；也是用户唯一的信任出口 |

根服务器的数量与分布（常考细节）：

- **IPv4 时代**：共有 **13 个不同 IP 地址**的根域名服务器。其中 1 台主根服务器由美国运营；12 台辅根服务器中，9 台由美国运营，英国、瑞典、日本各 1 台。
- **IPv6 时代**：全球在 16 个国家共部署了 **25 台** IPv6 根服务器。通过国际合作的"雪人计划"，中国部署了 1 台主根服务器和 3 台辅根服务器。

> 注意"13 个 IP 地址"与"13 台物理服务器"不是一回事：这 13 个地址通过任播（anycast）在大量物理节点上同时宣告，这正是根区能抵御大规模 DDoS 的结构性原因。

为保证解析服务的稳定性，DNS 把数据在多个服务器上备份，形成主辅结构：

- **主域名服务器**：存储和管理原始的 DNS 记录，是唯一可写入的节点。
- **辅助域名服务器**：用于数据备份；主服务器故障时可接管服务，保证解析连续性。
- **同步方向单一**：主服务器定期把更新后的记录同步到辅助服务器，**所有数据的修改和更新只能在主服务器上执行**，以此确保数据的准确性和一致性。

这条"单写多读"的规则有明确的安全含义：**攻击者若能伪装成辅助服务器向主服务器发起"区域传送"，就能一次性拿走整个域的记录**。因此区域传送必须按 IP 或 TSIG 密钥做授权。

### 5.2.4 解析过程：递归查询与迭代查询

因特网的域名解析过程由两种查询方式组合而成。课程用一句口诀区分：

- **递归查询**＝"委托任务，静候佳音"——我托你办，你负责给我最终结果，中间过程我不管。
- **迭代查询**＝"执行任务，按图索骥"——我问你，你告诉我下一步该问谁，我再自己去问。

为什么实际部署采用混合模式？课程的答案很直接：**递归查询对于被查询的域名服务器负担太大**。如果根服务器对每个查询都做递归，它就要替全世界跑完全部解析，既不可扩展，也把全部压力集中到顶层。

所以实际采用：

```
从请求主机 → 本地域名服务器：递归查询（用户只发一次请求，等最终答案）
从本地域名服务器 → 其余各级服务器：迭代查询（LDNS 自己一站一站问）
```

完整交互（以 `www.bank.com` 为例）：

```
 主机            LDNS            根服务器        .com TLD        bank.com 权威NS
  |               |                |               |                 |
  |--(1)递归查询->|                |               |                 |
  |               |--(2)迭代问根-->|               |                 |
  |               |<--指.com TLD---|               |                 |
  |               |--(3)问.com TLD--------------->|                 |
  |               |<--指bank.com的权威NS-----------|                 |
  |               |--(4)问权威NS------------------------------------->|
  |               |<--www.bank.com = 8.8.8.8 ------------------------|
  |<--(5)返回IP---|                |               |                 |
```

**DNS 高速缓存（Cache）**是整条链路上最重要的性能与安全装置：

- 作用：临时存储查询过的"域名—IP 地址"对应关系，减少重复查询，提升查询速度。
- 举例：假设已经有用户查询过 `www.bank.com` 的 IP，则本地域名服务器的高速缓存中应该已有该记录，之后再有人问，直接把缓存中的上次查询结果告诉用户即可。

**实际请求流程**（课程强调："并不是每一次域名解析都完成整个查询流程"）：

```
1. 客户端：查询本机缓存及 hosts 文件
2. 向 LDNS 发送请求
3. LDNS 查找缓存，有结果就直接返回
4-6. LDNS 依次查找根服务器、顶级域、权威服务器，获取结果
7. 本机获取 IP 地址
```

从浏览器视角看，这 7 步表现为 6 个动作：浏览器输入域名 → 请求到达 DNS 解析程序 → 查询获得 IP → 返回 IP 至 Web 浏览器 → 访问该 IP → 浏览器显示页面。

**这里埋下了本章最大的隐患**：第 3 步"LDNS 有缓存就直接返回"意味着——**缓存里的内容一旦是错的，错误会被无差别地发给该 LDNS 服务的所有用户，并持续到 TTL 到期**。缓存本是性能优化，却把单次欺骗放大成群体性欺骗。

### 5.2.5 DNS 报文格式

DNS 报文是 DNS 协议中传输数据的基本单元，分为**查询报文**和**响应报文**两类。结构上分两段：

- **前六个字段（首部）**：通过"标志"字段中的**第一位**区分类型——取值为 0 表示查询报文，否则表示响应报文。
- **后四个字段（数据）**：问题区是查询报文**必须**包含的部分，而后三个区域则根据查询类型和响应需求而存在差异。

```
+---------------------------------------------------+
|            首部（6 个字段，12 字节）               |
|  标识ID | 标志 | 问题数 | 回答数 | 授权数 | 附加数 |
+---------------------------------------------------+
|            问题区 Question Section                 |  ← 查询报文必须有
+---------------------------------------------------+
|            答案区 Answer Section                   |  ← 对查询问题的直接回答
+---------------------------------------------------+
|            权威区 Authority Section                |  ← 相关顶级(权限)域名服务器信息
+---------------------------------------------------+
|            附加区 Additional Section               |  ← 与问题直接相关的额外信息
+---------------------------------------------------+
```

| 字段/区域 | 长度 | 作用 | 安全相关性 |
|---|---|---|---|
| 标识 ID | 16 位 | 匹配请求与响应，客户端据此判断响应是否属于自己的查询 | **唯一的响应合法性依据**，可被猜测/暴力枚举，是 DNS 欺骗的突破口 |
| 标志 | 16 位 | 首位区分查询/响应；其余位表示递归期望、权威、截断等 | 可被伪造以干扰客户端的解析行为 |
| 问题数/回答数/授权数/附加数 | 各 16 位 | 声明各区域条目数量 | 数量异常可作为检测特征（如附加区过大是放大攻击的典型形态） |
| 问题区 | 变长 | 查询域名 + 查询类型 + 查询类 | 攻击者可构造超长或不存在的域名，触发后续恶意响应 |
| 答案区 | 变长 | 对查询问题的直接回答 | 直接决定用户最终访问的 IP |
| 权威区 | 变长 | 提供与查询域相关的顶级（权限）域名服务器信息 | Kaminsky 攻击正是往这里塞入伪造的 NS 记录 |
| 附加区 | 变长 | 提供与问题直接相关的额外信息（通常是 NS 对应的 A 记录） | 与权威区配合，让伪造的 NS "自带地址"，无需再查 |

> 补充：上述字段位宽依 RFC 1035，首部固定 12 字节；PPT 未列出全部位宽，记忆时以"6 字段定长 12 字节 + 4 个变长区"为骨架即可。

**问题区的三个基本元素**（由查询者提供）：

| 元素 | 含义 | 示例 |
|---|---|---|
| 查询域名 | 需要查询的域名 | www.bank.com |
| 查询类型 | 指定查询的资源类型 | A 表示 IPv4 查询，AAAA 表示 IPv6 查询 |
| 查询类 | 指定查询所属的网络协议 | 通常为 IN，代表 Internet |

互联网查询类型表（数值—简写—功能）：

| 值 | 简写 | 功能 |
|---|---|---|
| 1 | A | IPv4 的 IP 地址 |
| 2 | NS | 名称服务器 |
| 5 | CNAME | 符合规定的名称（域名的别名） |
| 6 | SOA | 验证的开始；包含关于域的信息 |
| 11 | WKS | 众所周知的服务 |
| 12 | PTR | 逆向查询（IP 地址到名称） |
| 13 | HINFO | 主机信息，主机的描述 |
| 15 | MX | 邮件交换 |
| 28 | AAAA | IPv6 的 IP 地址 |
| 252 | XFER | 区域转换请求 |
| 255 | ANY | 所有记录请求 |

域名解析应答中，每个数据条目称为一个**资源记录（Resource Record, RR）**，其数据格式为标准五元组：

| 五元组分量 | 作用 |
|---|---|
| 域名 | 该记录属于哪个名字 |
| 类别 | 通常为 IN |
| 类型 | A / AAAA / NS / CNAME / MX 等 |
| 生存时间（TTL） | 可被缓存多久；TTL 越长，投毒收益越大 |
| 数据 | 记录的实际值（如 IP、主机名） |

常见资源记录类型及含义：

| 类型 | 含义 |
|---|---|
| A | 域名对应主机的 IPv4 地址 |
| AAAA | 域名对应主机的 IPv6 地址 |
| MX | 域名对应邮件服务器地址 |
| NS | 域名对应权威服务器名称 |
| CNAME | 域名指向的别名记录 |

### 5.2.6 迭代查询的报文实例（三段 dig 输出）

课程用 `dig` 的三次输出，把"迭代"这个抽象概念落到了具体报文上。注意每一次请求里**问题区不变，变化的是被询问的服务器**。

**第 2-3 步**：LDNS 发送 `dig @a.root-servers.net www.www.bank.com`。根服务器**不直接给答案**，而是在授权区提供 .com 顶级域名服务器的名称，并把它们的地址放在附加区：

```
;; QUESTION SECTION:
;www.bank.com.            IN  A

;; AUTHORITY SECTION:
com.            172800  IN  NS  h.gtld-servers.net.
com.            172800  IN  NS  f.gtld-servers.net.
com.            172800  IN  NS  b.gtld-servers.net.

;; ADDITIONAL SECTION:
h.gtld-servers.net.  172800  IN  A  192.54.112.30
f.gtld-servers.net.  172800  IN  A  192.35.51.30
b.gtld-servers.net.  172800  IN  A  192.33.14.30
```

读法：`ANSWER SECTION` 为空——根服务器没答；`AUTHORITY` 说"这事归 .com 的这几台机器管"；`ADDITIONAL` 顺手给出它们各自的 IP，省掉一轮额外查询。

**第 4-5 步**：LDNS 改问 `dig @f.gtld-servers.net www.www.bank.com`，得到 `www.bank.com` 区域的权限域名服务器及其地址：

```
;; AUTHORITY SECTION:
www.bank.com.   172800  IN  NS  dns2.hichina.com.
www.bank.com.   172800  IN  NS  dns1.hichina.com.

;; ADDITIONAL SECTION:
dns2.hichina.com.  172800  IN  A  106.11.141.114
dns1.hichina.com.  172800  IN  A  106.11.141.113
```

**第 6-7 步**：LDNS 改问 `dig @dns1.hichina.com www.www.bank.com`，这次才拿到最终答案：

```
;; ANSWER SECTION:
www.www.bank.com.   600  IN  A  8.8.8.8
```

三点值得记住：

1. **授权区的 TTL（172800）远大于最终答案的 TTL（600）**。NS 记录稳定，A 记录易变；这符合"越靠右越少变化"的层级规律。
2. **"指路"与"给答案"是两种不同的响应**。凡是只指路不给答案的响应，都携带"请去问某某"的指令——这条指令若被伪造，解析权就被移交给了攻击者。
3. **整个过程无签名、无认证，仅凭 ID 匹配**。LDNS 判断"这个响应是不是我要的"，靠的是源地址、源端口和 16 位 ID 三个可猜测的量。

### 5.2.7 案例分析：Kaminsky 缓存污染（2008 年）

**定义**：攻击者通过非法手段添加 DNS 服务器的缓存记录，诱使用户访问到恶意的服务器。

**为什么这个攻击特别危险**：它污染的不是某一次会话，而是**缓存**。一台被投毒的 LDNS 会在 TTL 有效期内，把所有查询该域名的用户全部导向恶意服务器。

**攻击步骤**：

| 步骤 | 动作 | 目的 |
|---|---|---|
| 1 | 主动访问一个**不存在的域名**，触发本地域名服务器向上发送 DNS 请求 | 制造一个"正在等待响应"的合法查询，攻击者知道该查询的 ID 与端口范围 |
| 2 | 在正常响应报文返回之前，**抢先**发送大量伪造的响应报文，往权威区、附加区塞入恶意记录 | 赢得与真实响应的赛跑（race condition） |
| 3 | 本地域名服务器接受伪造响应，**污染缓存**；此后所有用户都被导向恶意地址 | 把单次欺骗放大为群体性、持续性的劫持 |

**伪造报文的构造要点**（课程给出的报文骨架）：

```
;; QUESTION SECTION:
;www.bank.com.    IN  A

;; ANSWER SECTION:                ← 故意留空，因为攻击者"答不上来"
                                  （真实的 A 记录它并不知道）
;; AUTHORITY SECTION:
example.com    NS   www.example.com      ← 关键：把某域的权威服务器
                                          指向攻击者控制的主机

;; ADDITIONAL SECTION:
www.example.com   A   3.3.3.3           ← 给这个冒牌 NS 配上地址
```

**成因分析（必须能说清"缺陷在哪一条"）**：

- **没有源认证**：DNS 响应没有任何密码学签名，服务器无法验证"这个响应确实来自权威服务器"。
- **匹配依据太弱**：仅靠 源 IP + 目的端口 + 16 位 ID。ID 只有 65536 种取值，在攻击者能高速发包时可暴力枚举。
- **接受"额外记录"**：LDNS 会接受响应中与问题无直接关系的权威区/附加区记录并缓存——这就是"名字连锁攻击"的入口。攻击者问 A 域，却顺手教会了服务器 B 域的权威是谁。
- **缓存是信任的放大器**：一次成功即长期有效（受 TTL 约束）。

Kaminsky 的修补思路（课程未展开，属标准背景）：随机化查询源端口、在问题名中引入随机大小写、限制对无关记录的接受。**注意这些都是"提高熵"的缓解手段，不是根治**——根治要等 DNSSEC。

### 5.2.8 DNS 面临的安全威胁（协议层面的六条）

| 威胁 | 机制 | 后果 |
|---|---|---|
| 数据窃听和篡改 | DNS 协议不加密，数据容易被截获和修改 | 明文可见、可改，中间人可任意改写应答 |
| ID 猜测和请求预测 | 攻击者通过预测技术构造假冒的响应（ID 字段的猜测） | 无需破解即可"抢答"成功 |
| 名字连锁攻击 | 构造恶意资源记录（如 CNAME、NS），插入响应的权威区或附加信息区，使查询者缓存被错误信息充斥 | 查询被误导至攻击者控制的域名，进而钓鱼、分发恶意软件 |
| 信任服务器背叛 | DNS 服务器配置常由 ISP 提供；若该服务器故障或被攻击者掌控，攻击者利用信任关系漏洞提供非法响应 | 用户对唯一出口的信任被滥用 |
| 否认域名的存在 | 操纵响应，使客户端认为所查询的域名不存在 | 服务不可达（拒绝服务），或诱导用户改用其他途径 |
| 通配符滥用 | DNS 支持 `*` 通配符，简化多子域名管理、可统一指向邮件流量，但会隐藏邮件真实来源、使验证复杂 | 增加邮件欺诈与钓鱼风险 |

"名字连锁攻击"值得单独强调，因为它是理解 Kaminsky 的关键：**它的本质是"越权教学"**——我问你 A，你却告诉我 B 的权威服务器是谁，而我还信了。凡是一个协议允许响应携带"未被请求的信息"，就存在这类连锁信任问题。

### 5.2.9 常见 DNS 攻击（五类对比）

| 攻击方式 | 攻击原理 | 攻击后果 |
|---|---|---|
| DNS 欺骗 | 修改 DNS 缓存、劫持 DNS 请求 | 网络钓鱼、信息窃取 |
| DNS 隐蔽信道 | 利用 DNS 数据包封装信息 | 发送恶意指令，窃取隐私信息 |
| DNS DDoS 攻击 | 直接耗尽服务器带宽资源 | 丧失网络服务能力 |
| DNS 反射放大攻击 | 间接耗尽服务器带宽资源 | 丧失网络服务能力 |
| 恶意 DGA 域名 | 使用 DGA 生成大量恶意域名 | 存在大量恶意域名，破坏安全性 |

**（1）DNS 欺骗（也叫域名劫持）**

定义：通过篡改用户请求的域名对应的 IP 地址，将用户引导到一个伪造的、恶意的网站。它有两种主要实施方式：

| 方式 | 是否修改缓存 | 机制 | 关键差异 |
|---|---|---|---|
| DNS 缓存中毒 | 是 | 篡改 DNS 服务器的缓存记录，把合法域名本应指向的 IP 改为恶意 IP | 影响面大、持续到 TTL 过期；所有使用该 LDNS 的用户都受害 |
| DNS 信息劫持 | 否 | 不修改缓存，而是在 DNS 服务器向用户发送响应**之前**，伪造更快的假响应，指向恶意 IP | 只影响被抢答的那一次查询；本质是与真响应赛跑 |

可以用一句话记住二者区别：**缓存中毒改"账本"，信息劫持改"传话"**。

**（2）DNS DDoS 攻击**

- 攻击者向 DNS 服务器发送海量查询请求，耗尽服务器 CPU、内存、带宽。
- 课程实例：**2016 年 Dyn 攻击**，Twitter、Netflix 等大面积瘫痪。其影响之所以巨大，是因为 Dyn 是托管 DNS 服务商——打掉一家，等于打掉它背后成千上万个域名。

**（3）DNS 反射放大攻击**

```
  攻击者                   开放DNS服务器                受害者
     |  伪造源IP=受害者地址      |                          |
     |---小请求(40~60字节)------>|                          |
     |                          |---大响应(4000~6000字节)-->|
     |                          |        （放大近100倍）    |
```

- 第一步：伪造源 IP（受害者地址）→ 向开放 DNS 服务器发送**小请求**（40-60 字节）。
- 第二步：DNS 服务器返回**大响应**（4000-6000 字节），放大近 100 倍。
- 结果：攻击者以极小计算代价，产生超大攻击流量。

它与 DDoS 的区别就在"直接/间接"：DDoS 用自己的机器打；反射放大用**别人的服务器**打，且流量被放大两个数量级。因此防御重点不是"抗流量"，而是**关闭开放递归**（不让非授权网段使用你的解析器）与**源地址校验**（BCP38，防伪造源 IP）。

**（4）DNS 隐蔽信道**

通过在 DNS 数据包中隐藏信息实现数据传输。它的可行性来自一个现实约束：**由于 DNS 主要功能非数据传输，常被忽视其可能用于恶意通信或数据泄露；防火墙和入侵检测系统通常允许 DNS 流量通过，以免干扰正常连接**。这种开放性使 DNS 隐蔽信道成为攻击者理想的**命令与控制（C&C）通道**，用于秘密收发指令和数据。

防御要点在"形状"而非"内容"：正常 DNS 查询的域名短、熵低、重复率高；隧道流量表现为域名超长、标签随机、请求频次规律、TXT/NULL 记录异常增多。

**（5）恶意 DGA 域名**

DGA（Domain Generation Algorithm，域名生成算法）：通过**周期性生成大量域名**并结合**快速变化的 IP 地址**，增加隐蔽性和不可预测性，使传统黑名单过滤失效，给恶意软件检测带来重大挑战。

其对抗逻辑是"以量取胜"：恶意软件每天生成几千个候选域名，攻击者只需注册其中几个即可保持通信；防御方要预先黑名单全部候选，成本不可承受。因此检测思路转向**算法识别**（字符分布、长度分布、n-gram 特征）而不是逐个封堵。

### 5.2.10 DNS 安全防护

课程把防护分为三条主线：**去中心化、加密认证、解析限制**。

**（1）DNS 去中心化**

| 方案 | 做法 | 优点 | 局限 |
|---|---|---|---|
| 基于 P2P 网络的 DNS | 设计基于 P2P 的解析系统，利用分布式特性和负载均衡，所有节点地位平等，资源和服务分散 | 避免单点故障，增强对 DDoS 的抵御能力 | 节点可信度难保证，一致性维护复杂 |
| 基于区块链的 DNS | 利用去中心化和不可篡改特性 | 增强抗 DDoS 能力和记录安全性 | 面临兼容性问题与"51% 攻击"风险 |
| 基于根联盟的根去中心化 | 把解析权限分散到多个子根服务器 | 减轻对特定域名的攻击风险 | 仍依赖 IANA，未完全消除权力滥用风险 |

**（2）DNS 加密认证**

问题的根源是：**传统开放式 DNS 解析缺乏数据真实性和完整性保护，易受欺骗攻击**。课程给出三条技术路线：DNSSEC、DoT、DoH。

**DNSSEC：用非对称加密验证身份**

DNSSEC 不加密内容，只解决"这条记录是不是权威服务器签发的、有没有被改过"。

签名过程：

1. 域名服务器用散列函数计算回复 DNS 报文内容的散列值，即"内容摘要"；
2. 使用**私钥**对该摘要加密（即签名）；
3. 加密后的信息附加到 DNS 报文上发出。

验证过程：

1. 本地 DNS 服务器收到 DNSSEC 报文，用同样方法计算报文的"内容摘要"；
2. 利用**公钥**解密收到的加密摘要；
3. 对比两个摘要内容，一致则报文真实且完整。

```
签名端（权威服务器）                      验证端（LDNS）
报文内容 --散列--> 摘要A               报文内容 --散列--> 摘要B
摘要A --私钥加密--> 签名                签名 --公钥解密--> 摘要A'
签名附加到报文 ------------------------>  比较 摘要A' == 摘要B ？
                                          一致 → 接受；不一致 → 丢弃
```

要点：**私钥签名、公钥验证；散列保证完整性，非对称加密保证来源真实**。这也解释了为什么 DNSSEC 不能防窃听——报文内容仍是明文。

**DoT（DNS-over-TLS）**

- 背景：在 DNSSEC 被广泛接受之前（全球顶级域 DNSSEC 部署已超过 93%），需要找到其他方案有效阻止 DNS 攻击造成破坏。
- 做法：**直接使用传输层安全协议对数据执行加密操作**，保证域名协议交互中信息的完整性与机密性。
- 与 DNSSEC 的差别（三个对比维度）：

| 维度 | DNSSEC | DoT |
|---|---|---|
| 信任链 | 用 DNS 区域层次结构提供信任链 | 依赖公钥基础设施（PKI），包括证书授权中心（CA） |
| 数据封装 | 不改传输方式，仅在记录上附加签名 | 把整个 DNS 报文放进 TLS 记录中加密 |
| 可部署性 | 需逐域逐级签名，全球推进缓慢 | 只需客户端与解析器支持，部署门槛低 |

**DoH（DNS-over-HTTPS）**

- 与现有域名系统**不兼容**，采用 HTTPS 信道传输域名协议数据。
- 传输路径：`客户端 → DoH 服务器 → DNS 服务器 → DoH 服务器 → 客户端`。
- 特点：**通用性**——部分浏览器或操作系统直接支持 DoH，无需改动网络设备。

**DoT 与 DoH 的区别**，可以按"像不像 DNS"来记：

| 对比项 | DoT | DoH |
|---|---|---|
| 承载协议 | TLS（专用端口） | HTTPS（与网页流量同端口） |
| 是否兼容传统 DNS | 传输层封装，语义不变 | 与现有 DNS 体系不兼容，需专门服务器 |
| 可识别性 | 端口固定，网络管理员可识别并放行/限制 | 与普通 HTTPS 流量混同，难区分，便于穿透管控 |
| 典型部署 | 操作系统级、解析器级 | 浏览器级、应用级 |

> 补充：DoH 的"不可区分性"是双刃剑——它保护用户隐私，也让企业网络失去对 DNS 的可见性，因此企业侧常配合基于证书或 IP 的出口策略使用。

**（3）DNS 解析限制**

| 措施 | 做法 | 抵御的攻击 |
|---|---|---|
| 设置开放服务器查询权限 | 限制只有合法和可信的来源才能向服务器发送请求 | 减少恶意 DNS 请求数量；抑制反射放大（不给任意源地址当"放大器"） |
| 设置权威服务器响应速率 | 权威域名服务器设置响应速率阈值，限制同一来源的 DNS 查询频率 | DDoS、DNS 反射放大，增强服务器防护能力 |

### 5.2.11 横向视角：一次远程访问中"每一步都可能出事"

课程最后用一个"局域网中的 Client 远程访问 Server"的场景，把 DNS 放回协议栈，说明**消息在协议栈中横向传递时，每一跳都有对应的攻击**。这对理解"为什么单点加固不够"很关键。

```
Client                            局域网            Internet            Server
  |                                 |                  |                  |
  |--(1) DNS请求与解析 ------------>| DNS基础设施      |                  |
  |--(2) ARP请求与应答 ------------>|                  |                  |
  |--(3) 帧转发 ------------------->|                  |                  |
  |--(4) 分组转发 ------------------------------------>|                  |
  |--(5) TCP连接建立/数据响应 ------------------------->|                  |
```

| 步骤 | 处理环节 | 对应风险 |
|---|---|---|
| 1 | DNS 请求与解析 | DNS 劫持 |
| 2 | ARP 请求与应答 | ARP 污染 |
| 3 | 帧转发 | 嗅探监听 |
| 4 | 分组转发 | 地址伪造、路由劫持 |
| 5 | 连接建立/数据响应 | TCP 连接劫持、DoS 攻击 |

这张表的教学价值在于：**用户以为"我访问的是正确的网站"，这个判断依赖五个环节全部正确**。任一环节被攻破，最终看到的页面都可能是假的。所以应用层的加密（HTTPS）才如此重要——它是唯一能跨越全部中间环节、由端点自行验证的机制。

**本讲小结（DNS）**：

| 常见攻击 | 防御策略 |
|---|---|
| DNS 欺骗（缓存中毒 / 信息劫持） | DNSSEC |
| DNS DDoS 攻击 | DNS 加密认证（DoT/DoH） |
| DNS 反射放大攻击 | DNS 去中心化 |
| DNS 隐蔽信道 & 恶意 DGA 域名 | 解析限制与源认证 |

## 5.3 HTTP 协议安全

### 5.3.1 万维网的五大要素与工作过程

WWW 的问世动机很具体：**为了使欧洲各国的核物理学家能通过计算机网络，共享分布在各地物理实验室、研究所的最新信息、数据、图像资料**。需求是"跨机构共享文档"，所以设计重心从一开始就是"文档的命名、定位与传输"，而不是"身份与权限"。

Web 技术的五大要素，各自解决一个问题：

| 要素 | 全称 | 解决的问题 |
|---|---|---|
| URL | Uniform Resource Locator | 文档的命名和寻址识别 |
| HTTP | HyperText Transfer Protocol | 浏览器与服务器应用层之间的交流 |
| HTML | HyperText Markup Language | 超文本文档的表示格式 |
| Web 浏览器 | — | 向服务器发起请求，并解析收到的文档 |
| Web 服务器 | — | 保存文档，并响应来自浏览器的请求 |

工作过程可以概括为"三段式"：

```
浏览器程序                                          服务器程序
   |  (1) 解析 URL，得到主机名 www.tsinghua.edu.cn      |
   |  (2) DNS 解析得到 IP，建立 TCP 连接（HTTP 使用此连接）|
   |------------- HTTP 请求 --------------------------->|
   |<------------ HTTP 响应（HTML 文档）-----------------|
   |  (3) 解析 HTML，遇到超链(URL)则重复上述过程          |
```

关键点：**HTTP 只负责"要一个资源、给一个资源"，它不负责找服务器（DNS 负责）、不负责可靠传输（TCP 负责）、不负责记住你是谁（Cookie 负责）**。这种"只做一件事"的设计带来了极简的实现，也带来了后面所有的安全缺口。

### 5.3.2 版本演进：每一版都在解决上一版的结构性瓶颈

| 版本 | 时间 | 关键特性 | 遗留问题 |
|---|---|---|---|
| HTTP/0.9 | 1991 | 只支持 GET；响应为 HTML 格式文本；**没有请求头和响应头**；只能传静态文本文件，无动态内容 | 被设计为简单的文件传输协议，无法表达元数据 |
| HTTP/1.0 | 1996 | 支持多种请求方法（GET、POST、PUT、DELETE 等），更灵活；引入请求头和响应头，可携带内容长度、缓存控制等 | 每个请求都要新建 TCP 连接，网络开销大；无并发请求机制，浏览器必须等前一个请求完成才能发下一个 |
| HTTP/1.1 | 1997 | 通过 header 引入 `Connection: keep-alive` 支持持久连接，多个请求响应可在同一 TCP 连接中进行；支持管道化（pipelining），可同时发送多个请求不必等响应 | **队头堵塞（HOL blocking）**：所有数据通信按次序完成，服务器处理完一个才处理下一个，前面的请求慢就拖住后面全部 |
| HTTP/2.0 | 2015 | 多路复用：单一连接可并发多个请求-响应消息，不必顺序一一对应；数据流最小单位是**帧**，帧组成消息，消息组成流 | 仍基于 TCP，TCP 层丢包仍会造成整体停顿 |
| HTTP/3.0 | 2022 | 采用 **QUIC**（基于 UDP 的新型协议），减少连接建立延迟和丢包率；支持**连接迁移**，客户端切换网络可无缝继续 | 部署与中间设备兼容性挑战 |

两个细节值得单独记：

**（1）HTTP/2 的层次**：帧（frame）→ 消息（message）→ 流（stream）。一个 TCP 连接里可并发许多流，每个流有自己的 ID，因此响应可以乱序返回、按流 ID 重组。这就从机制上消灭了 HTTP/1.1 的队头堵塞——不是"排队更快"，而是"不用排队"。

**（2）HTTP/3 为什么要换掉 TCP**：TCP 的连接由四元组标识，切换网络（如 Wi-Fi 换 4G）后源 IP 变了，连接必须重建；QUIC 用**连接 ID**标识连接，与地址解耦，因此可以迁移。课程的原话是"TCP 在切换网络的时候要不断的重连，无法做到那么丝滑"。

> 从安全角度看这条演进线：**HTTP/1.1 到 HTTP/2 一直在优化"效率"，而"明文与无状态"这两个安全问题始终没在协议内部解决**，靠的是外挂 TLS（HTTPS）与 Cookie 之上的应用层机制。这是理解 HTTP 安全的关键前提。

### 5.3.3 HTTP 报文结构

HTTP 的请求报文和响应报文均由**三个主要部分**组成，二者的区别主要体现在**开始行**：

```
请求报文                          响应报文
+----------------------+          +----------------------+
| 请求行               |          | 状态行               |   ← 开始行（区别在此）
| GET /x HTTP/1.1      |          | HTTP/1.1 404 Not Found|
+----------------------+          +----------------------+
| 首部行（0~n 行）     |          | 首部行（0~n 行）     |
| Name: Value          |          | Name: Value          |
+----------------------+          +----------------------+
| 空行（CRLF）         |          | 空行（CRLF）         |   ← 首部与主体的分隔
+----------------------+          +----------------------+
| 实体主体             |          | 实体主体             |   ← 请求中通常不用
+----------------------+          +----------------------+
```

**开始行**：两种报文的开始行都由三个字段组成，不同字段之间用空格分隔，行尾使用**回车（CR）和换行（LF）**作为结束。

- 请求行 = 请求方法 + 请求资源 URL + HTTP 版本
- 状态行 = HTTP 版本 + 状态码 + 解释状态码的简单短语

**方法**：HTTP 方法定义了要对资源执行的操作：

| 方法 | 意义 |
|---|---|
| OPTION | 请求一些选项的信息 |
| GET | 请求读取由 URL 所标志的信息 |
| HEAD | 请求读取由 URL 所标志的信息的首部 |
| POST | 给服务器添加信息（例如，注释） |
| PUT | 在指明的 URL 下存储一个文档 |
| DELETE | 删除指明的 URL 所标志的资源 |
| TRACE | 用来进行环回测试的请求报文 |
| CONNECT | 用于代理服务器 |

> 安全视角：GET 的参数在 URL 里，会进浏览器历史、代理日志、Referer 头；POST 的参数在主体里，相对不易外泄。而 PUT/DELETE 一旦被服务器误开，等于把文件系统的写权限暴露给全网——这是"方法越权"的经典来源。

**状态码**：用三位数字表示对请求的处理结果。

| 类别 | 含义 |
|---|---|
| 1xx 信息性 | 请求已接收，继续处理中 |
| 2xx 成功 | 请求正常处理完毕 |
| 3xx 重定向 | 需要进一步操作以完成请求 |
| 4xx 客户端错误 | 请求包含错误或无法被服务器理解 |
| 5xx 服务器错误 | 服务器在尝试处理请求时遇到错误 |

两个必记实例：

- **404**：客户端请求了不存在的资源，服务器无法找到请求的文件或页面。
- **500**：服务器内部错误，遇到未知的无法解决的问题。

> 安全视角：4xx/5xx 的详细错误页常泄露路径、框架版本、SQL 片段；3xx 的 Location 若可被用户输入控制，就是开放重定向（钓鱼跳板的常用手法）。

**首部行**：包含浏览器、服务器或报文主体属性等信息。首部行可以有多行，也可以没有；每行含字段名和字段值，行尾用 CR LF 分隔。**首部行结束后，用空行（只包含 CR LF）作为首部行与实体主体之间的分隔**。请求与回应的首部格式相同，首部是可选的，每行格式为：

```
Header Name：<SP>Header Value
```

> 注意 HTTP 头部的解析细节：冒号后的空格是格式的一部分，但很多服务器会容错。**这种"容错"正是请求走私（request smuggling）与头部注入的温床**——前后端对同一段字节的理解不一致，就会出现夹带。

**实体主体**：在请求报文中通常不使用，但在响应报文中可能包含，如返回的 HTML 页面、图片数据等。

**一个真实的请求报文**：

```
GET /apache_pb.gif HTTP/1.1          ← 请求行：方法 资源 版本
Keep-Alive：300                      ← 一般头部：管理保持激活的连接
Connection：keep-alive               ← 一般头部：确定连接的类型
                                     ← 空行
（无主体）
```

**一个真实的响应报文**：

```
HTTP/1.1 404 Not Found               ← 状态行
Date：Sat，28 Oct 2006 16:01:55 GMT  ← 一般头部
Keep-Alive：timeout = 15，max=97     ← 一般头部
Connection：keep-alive               ← 一般头部
Server：Apache/1.3.33(Unix)          ← 回应头部（泄露服务器软件与版本）
Content-type：text/html；charset = iso-8859-1   ← 实体头部
                                     ← 空白行
HTML Document                        ← 实体主体
```

这四类头部（一般头部、请求/回应头部、实体头部）的分类值得记：**一般头部**对报文整体起作用（连接、时间），**请求/回应头部**描述请求方或应答方（Server、User-Agent、Cookie），**实体头部**描述主体本身（Content-Type、Content-Length）。

### 5.3.4 无状态与 Cookie/Session：为什么 HTTP 需要一个"外挂记忆"

课程把这条因果链讲得很清楚：

- 早期的万维网应用非常简单，仅仅是用户查看存放在不同服务器上的各种静态文档。因此 **HTTP 被设计为一种无状态的协议，这样可以简化服务器的设计**。
- 但用户后来通过万维网进行网上购物、电子商务等复杂应用，**这些应用往往需要服务器能够识别用户**。
- **Cookie 提供了一种机制使得服务器能够"记住"用户，而无需用户主动提供标识信息**——也就是说，Cookie 是一种对无状态的 HTTP 进行**状态化**的技术。

补上 Cookie 与 Session 的分工：

| 技术 | 存储位置 | 内容 | 安全相关性 |
|---|---|---|---|
| Cookie | 客户端 | 随请求自动发送的小段数据，常含 Session ID | 可被窃取、被固定、被 XSS 读取；自动随请求发送是便利也是风险 |
| Session | 服务器端 | 真正的会话状态与信息，以唯一 Session ID 索引 | Session ID 是"临时身份证"，泄露即等于身份被接管 |

**一句话总结攻击面**：HTTP 本身不认人，认人的是 Session ID；而 Session ID 在每个请求里都被明文携带（默认情况下），所以**拿到 Session ID 就等于拿到这个人**。

### 5.3.5 攻击一：会话劫持（Session Hijacking）

定义：通过窃取目标用户的 Session ID，冒充目标用户，非法访问其账户或执行其他恶意操作。

四个步骤：

| 步骤 | 动作 | 关键点 |
|---|---|---|
| 1 | 目标用户登录网站 | 攻击者只需等待或诱导，不需参与 |
| 2 | 登录成功后，用户获得网站颁发的 Session ID，通常存储在 Cookie 中 | Session ID 是唯一凭证 |
| 3 | 攻击者利用**网络嗅探**、**跨站脚本攻击（XSS）** 等手段捕获该 Session ID | 明文传输 → 嗅探可行；页面可注入脚本 → XSS 可行 |
| 4 | 攻击者使用捕获的 Session ID 访问网站，冒充目标用户获得合法会话 | 服务器无法区分"本人"与"持票人" |

**成因**：这是"凭证与身份可分离"的必然结果。协议层没有把 Session ID 与信道或设备绑定，任何持有者都被视为本人。

### 5.3.6 攻击二：会话固定（Session Fixation）

定义：攻击者诱导受害者使用**预先设定**的 Session ID 创建会话。三个阶段：

| 阶段 | 动作 | 目的 |
|---|---|---|
| （1）会话建立 | 攻击者在目标服务器上创建一个"陷阱会话"，并采取措施保持其活跃状态，防止超时 | 让这个 Session ID 在服务器端真实存在且有效 |
| （2）会话固定 | 攻击者把陷阱会话的 Session ID 传递给目标用户，使其浏览器接受并使用该 ID | 让受害者的浏览器"代言"攻击者的会话 |
| （3）会话进入 | 攻击者利用已被固定的 Session ID，等待或诱导用户使用该 ID 登录网站，从而获得目标用户会话的访问权限 | 用户登录的动作把权限"注入"到了攻击者已知的会话里 |

**与劫持的本质区别**（高频考点）：

- 会话**劫持**：先有受害者的会话，攻击者**事后偷走** ID。
- 会话**固定**：先有攻击者的会话，攻击者**事前安排**受害者用这个 ID 登录。

前者需要"窃取成功"，后者只需要"诱导成功"——后者不需要嗅探，因此在全站 HTTPS 环境下依然可能成立。

### 5.3.7 HTTP 协议的防御措施

**针对会话劫持**：

| 措施 | 作用 |
|---|---|
| 引入 Token 验证机制 | 在客户端和服务器之间增加一个 Token 验证步骤，检查请求的合法性（ID 之外再加一道不可预测的凭据） |
| 使用安全的传输层协议 | 通过 HTTPS 加密客户端与服务器之间的通信，防止 Session ID 在传输过程中被截获 |
| 限制 Session 生命周期 | 为 Session 设置合理的过期时间，减少 Session ID 被滥用的机会 |

**针对会话固定**，按攻击三阶段分别设防：

| 阶段 | 防御措施 | 机制 |
|---|---|---|
| 建立过程 | 服务器控制会话标识生成 | 确保服务器是会话标识的唯一生成者，不使用用户输入或可预测的值 |
| 建立过程 | 加强会话标识的保密性 | 通过加密传输和使用强随机数生成器，创建难以预测的会话标识 |
| 建立过程 | 绑定会话标识与用户 IP | 将 Session ID 与用户 IP 地址绑定，减少被滥用风险 |
| 固定过程 | **登录后更新会话标识** | 用户登录成功后服务器生成新的 Session ID，使攻击者的旧 ID 失效（最核心的一条） |
| 固定过程 | 及时销毁会话 | 用户退出或会话超时时，服务器端彻底删除会话信息 |
| 固定过程 | 修复 Web 应用漏洞 | 定期检查并修复 XSS、文件上传漏洞等，减少被利用进行会话固定的机会 |
| 进入过程 | 设置会话超时限制 | 防止攻击者长时间维持非法会话 |
| 进入过程 | 监控会话一致性 | 检查附加信息（如源 IP、User Agent）的一致性，异常立即结束会话 |
| 进入过程 | 会话监控和警报 | 对异常行为进行警报和响应 |

一句话贯穿：**会话安全的本质是"让凭证不可预测、不可复用、不可转移"**。登录后换 ID 解决"不可复用"，绑定 IP/UA 解决"不可转移"，强随机数解决"不可预测"，HTTPS 解决"不被看到"。

## 5.4 邮件传输协议安全

### 5.4.1 邮件系统的组成与收发流程

历史线索：1971 年，雷·汤姆林森博士奉命寻找一种电子邮箱地址的表现格式，他编写了可以把一封信从一台主机发送到另一台主机的小程序，于是第一封电子邮件诞生，他被称为"E-Mail"之父。1987 年 9 月 20 日，钱天白发出我国第一封电子邮件。

发送电子邮件通常涉及三个主要组件：**用户代理、发送方邮件客户端、接收方邮件服务器**。发送过程至少涉及两种类型的邮件协议：

| 用途 | 协议 | 端口 |
|---|---|---|
| 发送邮件 | SMTP | 25 |
| 读取邮件 | POP3 | 110 |
| 读取邮件 | IMAP | 143 |

```
发件人                发件方邮件服务器              收件方邮件服务器           收件人
  |                        |                            |                     |
  |--SMTP(提交)----------->|                            |                     |
  |                        |--SMTP(中转/relay)--------->|                     |
  |                        |                            |--POP3/IMAP-------->|
```

**注意"两段 SMTP"**：发件人→自己服务器是"提交"，服务器→对方服务器是"中转"。中间可能经过多个 MTA（邮件传输代理）逐跳转发，这也是"邮件在传输过程中经过多个服务器，增加被截获风险"的结构原因——**每多一跳，就多一个可读明文的位置**。

### 5.4.2 邮件报文格式（RFC 822 → RFC 5322）

电子邮件的信息格式在 **RFC 822** 中单独定义，该文档已在 **2008 年更新为 RFC 5322**。一个电子邮件有**信封**和**内容**两部分，而内容又由**首部**和**主体**两部分构成。

| 部分 | 说明 |
|---|---|
| 信封 | 传输时使用（类似快递面单），由 SMTP 的 MAIL FROM / RCPT TO 命令给出，收件人看不到 |
| 首部（Header） | 邮件元数据，提供邮件路由和呈现所需的信息；由多行组成，每行格式为"关键字：内容" |
| 主体（Body） | 邮件主要内容，由用户撰写，可含纯文本或格式化文本（如 HTML）；通常在首部之后 |
| 分隔 | 首部与主体之间用**一个空行（即两个连续的 CRLF）**分隔，表明首部字段结束、主体开始 |

常见首部字段：

| 字段 | 含义 | 安全相关性 |
|---|---|---|
| From | 邮件发送者的地址 | **可任意伪造**，是最典型的欺骗点 |
| To | 邮件接收者的地址 | 与实际投递对象（信封 RCPT TO）可以不一致 |
| Cc | 抄送地址，其他接收者也应收到副本 | 泄露收件人列表 |
| Bcc | 密送地址，与 Cc 类似，但其他收件人无法看到 Bcc 收件人 | 若处理不当会整批泄露 |
| Subject | 邮件主题，提供内容的简短描述 | 钓鱼标题的主要载体 |
| Date | 邮件发送的日期和时间 | 可伪造，影响时间线取证 |
| Message-ID | 邮件的唯一标识符 | 可用于追踪与去重 |

课程给出的实例（一封完整邮件报文的骨架）：

```
From：teacher@example.edu.cn
To：课程教学团队的邮箱
Cc：学院管理部门的邮箱
Subject：新冠肺炎疫情期间网上教学计划

课程教学团队的各位老师：
    大家好！
    根据学校《关于切实做好……的通知》，"停课不停教不停学"的要求，
    将于 2 月 24 日开始进行网上授课……
```

**记住这条因果**：首部字段是"写信人自己写的"，没有任何机制校验其真实性。SMTP 时代没有发件人认证，所以 From 可以是任何人——这就是今天需要用 SPF/DKIM/DMARC 补救的原因（课程未展开，属标准背景）。

### 5.4.3 SMTP：一个"人机对话式"的文本协议

SMTP（简单邮件传输协议）的关键属性：

| 属性 | 内容 |
|---|---|
| 位置 | 运行在 TCP 之上的应用层协议，用于发送和中转电子邮件 |
| 规范 | 工作方式由 RFC 2821 定义 |
| 模型 | 客户端/服务器模型，服务器默认监听 TCP 25 端口 |
| 会话阶段 | 完整会话包括三个阶段：建立连接、邮件传输、断开连接 |
| 编码 | 通信基于文本，命令和响应以文本形式交换，以 CRLF（`\r\n`）作为行结束符 |

**命令格式**：`COMMAND<SP><Parameter><CRLF>`。命令**不区分大小写**，但**参数通常区分大小写**。

**响应信息**：通常只有一行，以三位数响应代码开头，后跟简短文本说明，用于告知客户端命令执行情况。课程补充：SMTP 定义了 **14 条命令**和 **21 种应答信息**；每条命令用 **4 个字母**组成；每种应答一般只有一行，由一个 **3 位数字**的代码开始，后面附上（也可不附）很简单的文字说明。

应答码三位数字的含义：

| 位 | 含义 |
|---|---|
| 第一位 | 表示命令是成功了还是失败了 |
| 第二位 | 指出代码类型 |
| 第三位 | 指出特定代码 |

一条真实应答：

```
220 163.com Anti-spam GT for Coremail System(163com[20141201])
```

`220` 表示"服务就绪"，后面的文字是服务器自报家门（顺带泄露了邮件系统与反垃圾网关的型号、版本与日期——这本身就是信息泄露）。

**完整会话流程**（课程用"服务器周期性扫描邮件缓存（如每 30 分钟），发现有邮件就主动推送"这一场景串起来）：

| 序号 | 一方 | 动作 | 对方应答 |
|---|---|---|---|
| 1 | 服务器 | 主动推送"服务就绪"应答（220） | — |
| 2 | 客户端 | 向服务器说明身份，告知自己的域名（HELO/EHLO） | 若身份有效，发回 250 |
| 3 | 客户端 | 告知服务器邮件来自何方（MAIL FROM） | 若合理，发回 250 |
| 4 | 客户端 | 告知服务器邮件去往何地（RCPT TO） | 若该邮箱存在，发回 250 |
| 5 | 客户端 | 告知服务器自己准备发送邮件内容（DATA） | 若准备好接收，发回 354 |
| 6 | 客户端 | 发送邮件内容 | — |
| 7 | 客户端 | 发送结束符（单独一行 `.`） | 若收件成功，发回 250 |
| 8 | 客户端 | 请求断开 TCP 连接（QUIT） | 发回 221 并主动断开连接 |

```
   SMTP客户端                                  SMTP服务器(25)
       |                                            |
       |<------------------ 220 服务就绪 ------------|  (1)
       |------------------- HELO 我的域名 ---------->|  (2)
       |<------------------ 250 OK ------------------|
       |------------------- MAIL FROM:<a@x> ------->|  (3)
       |<------------------ 250 OK ------------------|
       |------------------- RCPT TO:<b@y> ---------->|  (4)
       |<------------------ 250 OK ------------------|
       |------------------- DATA ------------------->|  (5)
       |<------------------ 354 开始发送 ------------|
       |------------------- 邮件内容 --------------->|  (6)
       |------------------- . (结束符) ------------->|  (7)
       |<------------------ 250 已接收 --------------|
       |------------------- QUIT ------------------->|  (8)
       |<------------------ 221 Bye -----------------|
```

**注意这条流程里没有任何一步验证"你是不是 a@x 的主人"**。第 3 步的 MAIL FROM 只是一个字符串，服务器最多检查域名是否合法。这解释了为什么邮件伪造如此容易——**协议把"声称"当成了"事实"**。

### 5.4.4 POP3 与 IMAP：读信的两种哲学

POP3（Post Office Protocol，邮局协议）和 IMAP4（Internet Message Access Protocol，因特网邮件访问协议）**都采用基于 TCP 连接的客户/服务器方式**，端口分别为 **110** 和 **143**。

| 对比项 | POP3 | IMAP4 |
|---|---|---|
| 端口 | 110 | 143 |
| 基本模型 | 下载到本地，本地管理 | 邮件保留在服务器，在线管理 |
| 多设备 | 早期下载后删除，多设备无法保留副本 | 天然支持多端同步 |
| 状态 | 简单但过时 | 更适合现代需求 |

课程对 POP3 的评价集中在"机制即缺陷"这一点上：**离线访问安全性——邮件下载到本地后无需身份验证即可阅读，可能泄露敏感信息；邮件同步问题——早期 POP3 下载后通常从服务器删除，导致多设备用户无法保留邮件副本；现代 POP3 虽可保留邮件，但单向工作模式不适合多设备同步需求。**

也就是说，POP3 的设计假设是"一台机器、一个用户、拨号上网"，这个假设在移动多端时代已不成立。

### 5.4.5 MIME：让 SMTP 能送"非 ASCII 的东西"

SMTP 的能力边界很硬：**只能传送 ASCII 码文本数据，不能传送可执行文件或其他二进制对象**。因此：

- 不能满足传送多媒体邮件（如带图片、音频、视频）的需要；
- 许多非英语国家的文字（中文、俄文，甚至带重音符号的法文或德文）也无法用 SMTP 传送。

**MIME（多用途互联网邮件扩展）**的作用：定义了一套**编码规则**，用于处理非 ASCII 数据，扩展电子邮件功能。课程强调 MIME **不仅用于电子邮件，还广泛应用于万维网的 HTTP 协议**——今天 HTTP 响应头里的 `Content-Type: text/html` 就是 MIME 类型。

MIME 定义了 **7 个基本内容类型**和 **15 种子类型**：

| 内容类型 | 子类型举例 | 说明 |
|---|---|---|
| text（文本） | plain, html, xml, css | 不同格式的文本 |
| image（图像） | gif, jpeg, tiff | 不同格式的静止图像 |
| audio（音频） | basic, mpeg, mp4 | 可听见的声音 |
| video（视频） | mpeg, mp4, quicktime | 不同格式的影片 |
| model（模型） | vrml | 3D 模型 |
| application（应用） | octet-stream, pdf, javascript, zip | 不同应用程序产生的数据 |
| message（报文） | http, rfc822 | 封装的报文 |
| multipart（多部分） | mixed, alternative, parallel, digest | 多种类型的组合 |

（表中 multipart 是复合类型的组织方式，7 个"基本类型"指 text/image/audio/video/model/application/message，multipart 用于把多个部分装进一封邮件。）

MIME 的两个关键机制：

1. **Content-Type 必须含两个标识符**：内容类型（type）和子类型（subtype），中间用 `/` 分开，如 `text/plain`（纯文本）、`image/jpeg`（JPEG 图片）。
2. **multipart 类型**：用于创建包含多个部分的复合邮件，通过 `boundary` 参数区分各部分。
3. **Content-Transfer-Encoding**：定义邮件内容的传输编码方式，确保多种类型数据的无缝传输（把二进制转成可打印字符，如 Base64）。

```
MIME-Version: 1.0
Content-Type: multipart/mixed; boundary="----=_Part_1"
------=_Part_1
Content-Type: text/plain; charset="utf-8"
Content-Transfer-Encoding: base64

（正文的 base64 编码）
------=_Part_1
Content-Type: application/octet-stream; name="a.exe"
Content-Transfer-Encoding: base64

（附件的 base64 编码）
------=_Part_1--
```

> 安全视角：MIME 让"一封邮件里同时有正文和附件"成为常态，也让**附件成为恶意代码的主要投递方式**；而 `multipart` 的嵌套解析歧义，是邮件网关与客户端理解不一致（导致绕过过滤）的常见根源。

### 5.4.6 邮件协议的安全风险与 TLS/STARTTLS

**SMTP 的安全风险**：

| 风险 | 机制 |
|---|---|
| 缺乏数据加密 | 传统 SMTP 协议不加密，容易被第三方监听和截获邮件内容 |
| 多跳转发 | 邮件在传输过程中经过多个服务器，每一跳都增加被截获的风险 |
| 内容可恢复 | 攻击者可通过截获数据包恢复邮件内容，导致用户隐私和敏感数据泄露 |

**防范策略**：使用 TLS 对 SMTP 会话进行加密，防止数据被截获和篡改；具体有两种落地方式——**隐式 TLS**（直接以 TLS 建连，通常用 465 端口）与 **STARTTLS**（明文连上后再升级）。

**TLS 的主要工作过程**（四步）：

| 步骤 | 内容 |
|---|---|
| 连接建立 | 客户端与服务器建立 TCP 连接，告知支持的加密套件和 TLS 版本 |
| 证书和公钥交换 | 服务器提供 TLS/SSL 证书和公钥，客户端验证证书确认服务器身份 |
| 密钥交换 | 客户端使用服务器公钥加密共享密钥并发送给服务器 |
| 加密通信 | 双方使用共享密钥加密和解密邮件数据，确保传输安全 |

**STARTTLS 的工作过程**（五步，注意第一步是明文的）：

```
(1) 初始连接：建立普通 TCP 连接，此时通信尚未加密        ← 风险窗口
(2) 发送 STARTTLS 请求：请求服务器升级连接为加密通信
(3) 服务器响应：若支持，返回响应表明可以开始 TLS 握手
(4) 加密升级：TLS 握手（证书验证、密钥交换），把连接升级为 TLS 会话
(5) 加密通信：握手完成后，所有后续通信都被加密
```

**STARTTLS 的固有弱点**（由第 1 步决定）：既然前几步是明文，中间人就可以**剥离（strip）STARTTLS 命令**，让双方退回明文而彼此不察觉（降级攻击）。这是"机会式加密"的通行问题，防御要靠客户端策略"要求必须加密，否则不发送"（MTA-STS 等，属标准背景）。

### 5.4.7 POP3 的安全缺陷与改进

| 缺陷 | 说明 |
|---|---|
| 明文传输 | 初始设计未加密传输内容，攻击者可截获明文数据（**包括用户名和密码**），存在严重安全风险 |
| 离线访问安全性 | 邮件下载到本地后无需身份验证即可阅读，可能泄露敏感信息 |
| 邮件同步问题 | 早期下载后从服务器删除，多设备无法保留副本；现代虽可保留，但单向模式不适合多设备同步 |

**提高 POP3 安全性和适应性的措施**：

| 措施 | 说明 |
|---|---|
| 使用加密连接 | 通过 TLS/SSL 或 STARTTLS 加密 POP3 会话（POP3S 常用 995 端口） |
| 改进客户端设计 | 客户端应本地加密存储邮件，并支持多设备间安全同步 |
| 多端同步解决方案 | 考虑使用支持多端同步的协议（如 IMAP）以满足现代需求 |

### 5.4.8 常见的电子邮件防范策略

课程给出三条主线：**加密和验证、过滤机制、电子邮件取证**。

**（1）加密和验证——PGP**

PGP（Pretty Good Privacy）解决的是"端到端"的机密性与身份真实性，其原理是**混合加密**：

```
发送方                                          接收方
 |  1. 生成随机对称会话密钥 K                     |
 |  2. 用 K 加密邮件正文（快）  --> 密文 C        |
 |  3. 用接收方公钥加密 K       --> 加密的 K'     |
 |  4. 用自己私钥对正文摘要签名 --> 签名 S        |
 |--- C + K' + S ------------------------------>|
 |                              5. 用自己私钥解 K' 得 K
 |                              6. 用 K 解 C 得正文
 |                              7. 用发送方公钥验 S
```

要点：**对称加密保证效率（正文大），非对称加密保证密钥分发（K 小），签名保证完整性与抗否认**。这与 DNSSEC 只做签名、TLS 做双向密钥交换形成对照，可以放在一起比较记忆。

**（2）过滤机制**

电子邮件过滤器一般配置在电子邮件服务器**之前**，是接收电子邮件的第一个 **MTA（Message Transfer Agent，邮件传输代理）**。

```
互联网 --> 电子邮件过滤器(第一个MTA) --> MTA(未修改) --> 邮件服务器 --> 用户
                |            |
             追加头部      写 Log
```

三个动作值得注意：

- **拦截**：按规则拒收或隔离（病毒附件、垃圾邮件特征）。
- **追加头部**：在报文首部加注扫描结果（如"已检毒""垃圾邮件评分"），供下游判断——这也是**为什么邮件首部会越来越长**。
- **写 Log**：留痕，用于事后追查与取证。

**（3）电子邮件取证**

课程用一个 eBay 钓鱼邮件实例说明取证要看什么：

| 观察点 | 实例中的表现 | 取证意义 |
|---|---|---|
| 图片引用 | `<img src="http://pics.ebaystatic.com/aw/pics/navbar/eBayLogoTM.gif" width="150" height="70">` | 图片由 Web 网站复制并出现在邮件中，证明"看起来像官方"不等于"来自官方" |
| 商标使用 | eBay 商标包含在电子邮件中 | 品牌被冒用，是社工话术的一部分 |
| 链接指向 | `Href="http://linux.netzero.idv.tw/~ming/.change.index.php?..."`，目标 `_blank`，文字为 "Click here to Change Your Password" | 显示文字与真实 URL 不一致；域名与 eBay 无关，指向 Phishing Site |
| 话术 | "multiple password failures were present before the logons"，"If this is not completed by September 15, 2006, we will be forced to suspend your account" | 制造紧迫感，诱导点击 |

**取证的核心方法**：不看渲染后的显示文本，只看**原始首部与真实链接**（Received 链、Return-Path、Message-ID、URL 的实际域名）。这与"看源码而不是看页面"是同一条原则。

## 5.5 DHCP 协议安全

### 5.5.1 为什么需要 DHCP

一台主机要接入网络，需要配置四项参数：

| 参数 | 作用 |
|---|---|
| IP 地址 | 主机在网络中的唯一标识 |
| 子网掩码 | 划分网络号与主机号，决定"谁是本地" |
| 默认路由器的 IP 地址 | 出网的第一跳网关 |
| 域名服务器的 IP 地址 | 解析域名时的查询对象 |

这些信息通常存储在配置文件中，计算机在引导过程中可以对这个文件进行存取。**手工配置的问题**是：工作量大且容易出错——尤其在主机数量多、变动频繁的网络里，手工维护 IP 与 MAC 的对应关系几乎必然出错（地址冲突、网关写错、DNS 漏配）。

DHCP（动态主机配置协议）的解决办法是：开机启动 DHCP，让主机自动获取网络配置参数。举例，DHCP 可为局域网中各主机配置如下参数：

```
IP 地址：      192.168.0.1 ~ 192.168.0.251
子网掩码：     255.255.255.0
默认网关：     192.168.0.254
DNS 服务器：   192.168.0.253
```

这样计算机就能"**即插即联网**"（Plug-and-Play Networking）。DHCP 目前是因特网草案标准（RFC 2131、RFC 2132），由 IETF 基于这两个标准开发设计，采用客户机-服务器模式运行，**在传输层使用 UDP 通信：服务器监听 67 号端口，客户端监听 68 号端口**。

### 5.5.2 三种分配方式与四个阶段

| 分配方式 | 特点 | 适用场景 |
|---|---|---|
| 自动分配 | **永久性**分配，客户端获取 IP 地址后可以长期保留使用 | 固定工作站 |
| 手动分配 | 管理员为特定客户端分配**固定的** IP 地址 | 服务器、打印机 |
| 动态分配 | **临时性**分配，IP 在特定时间内有效，使用后需释放回地址池 | 移动设备、访客网络 |

**动态分配的工作过程包括四个阶段**（DISCOVER → OFFER → REQUEST → ACK，常称 DORA）：

| 阶段 | 报文 | 发送方式 | 内容 |
|---|---|---|---|
| 发现 | DHCP Discover | 客户端**广播** | 查找网络中的 DHCP 服务器，并表达获取 IP 地址的需求 |
| 提供 | DHCP Offer | 服务器**单播** | 服务器收到 Discover 后准备一个 IP 地址提议并发出 |
| 请求 | DHCP Request | 客户端广播 | 客户端从收到的多个 Offer 中选择一个，向对应服务器接受该提议 |
| 确认 | DHCP Ack / DHCP Nak | 服务器 | 确认分配成功，客户端可使用该 IP；**无法分配则发 DHCP Nak，客户端需重新进入发现阶段** |

```
 客户端(68)                                     DHCP服务器(67)
    |                                                |
    |---- DHCP Discover（广播：谁是DHCP服务器？）---->|  发现
    |<--- DHCP Offer（单播：这个IP给你用）------------|  提供
    |---- DHCP Request（广播：我要这个IP了）--------->|  请求
    |<--- DHCP Ack（确认，可使用）--------------------|  确认
```

**为什么 Discover 必须广播**：客户端此时还没有 IP（源地址 0.0.0.0），也不知道服务器在哪，只能"朝所有人喊"。**为什么 Request 也广播**：让所有发过 Offer 的服务器都知道自己没被选中，从而收回提议——这是一个优雅的资源回收设计。

### 5.5.3 报文格式与中继代理

DHCP 报文共**八种类型**：DHCP Discover、DHCP Offer、DHCP Request、DHCP Ack、DHCP Nak、DHCP Release、DHCP Decline、DHCP Inform。**DHCP 报文的封装格式基于早期的 BOOTP 报文格式**。

报文格式中与安全最相关的两个字段：

| 字段 | 长度/说明 | 安全相关性 |
|---|---|---|
| 跳数（Hops） | 报文经过的中继的数目 | 可判断报文是否跨网段、是否被异常转发 |
| Chaddr（客户端硬件地址） | 以太网的硬件地址长度为 **6 个字节** | **饥饿攻击伪造的就是这个字段**；Snooping 校验的也是这个字段 |
| Yiaddr（分配给客户端的 IP） | 在提供阶段和确认阶段，该字段会被填充为服务器分配的 IP 地址 | 仿冒服务器可填任意地址，把客户端引入错误网络 |

**中继代理（DHCP Relay Agent）**的存在原因：并不是每个网络上都有 DHCP 服务器，否则 DHCP 服务器的数量太多。现在是**每一个网络至少有一个 DHCP 中继代理**，它配置了 DHCP 服务器的 IP 地址信息。

工作方式：

1. 中继代理收到主机发送的**发现报文**；
2. 以**单播**方式向 DHCP 服务器转发此报文，并等待回答；
3. 收到 DHCP 服务器的**提供报文**后，再把它发回给主机。

```
   主机 ----广播 DISCOVER----> DHCP中继代理 ----单播----> DHCP服务器（其他网络）
   主机 <---OFFER------------  DHCP中继代理 <---单播----  DHCP服务器
```

注意课程的一句提醒：**DHCP 报文只是 UDP 用户数据报中的数据**。这句话有两层意思：其一，DHCP 没有自己的传输层保障，靠 UDP 的尽力而为加应用层重传；其二，**DHCP 报文没有任何完整性保护**，任何能构造 UDP 包的主机都能伪造。

### 5.5.4 完整租约过程（含 T1/T2 计时器）

获得地址只是开始，租约需要持续维护。课程给出的完整时序：

| 序号 | 报文 | 方向 | 说明 |
|---|---|---|---|
| 1 | DHCP Discover | 客户 68 → 服务器 67 | 广播查找服务器，表达地址需求 |
| 2 | DHCP Offer | 服务器 → 客户 | 凡收到 Discover 的服务器都发出提供报文，**客户可能收到多个 Offer** |
| 3 | DHCP Request | 客户 → 所选服务器 | 从几个服务器中选一个，向它发送请求报文 |
| 4 | DHCP Ack | 服务器 → 客户 | 进入**已绑定**状态，可开始使用临时 IP |
| 5 | DHCP Request（续租） | 客户 → 服务器 | **T1 时间到（租用期的一半）**，请求更新租用期 |
| 6 | DHCP Ack | 服务器 → 客户 | 同意则发回确认，客户得到新租用期，**重新设置计时器** |
| 7 | DHCP Nak | 服务器 → 客户 | 不同意则发回否认，客户必须**立即停止使用原 IP**，重新申请（回到步骤 1） |
| 8 | DHCP Request（重发） | 客户 → 服务器 | 若服务器不响应步骤 5，则在**租用期过了 87.5%** 时，客户必须重新发送请求 |
| 9 | DHCP Release | 客户 → 服务器 | 客户可随时提前终止租用期，只需发送释放报文 |

计时器规则（考点）：

| 计时器 | 触发点 | 含义 |
|---|---|---|
| T1 | 0.5T | 租用期过一半，开始**续租**（向原服务器请求） |
| T2 | 0.875T | 租用期过 87.5%，原服务器仍未响应，**重新广播请求**（可接受其他服务器） |
| T | 到期 | 必须停止使用该地址 |

```
|<--------------------- 租用期 T --------------------->|
0                  0.5T(T1)          0.875T(T2)        T
|--------------------|------------------|-------------|
     正常使用         请求续租          重新广播        必须放弃
                      (单播)           (广播)
```

**报文寻址方式的变化**（课程给出的抓包对照表，重点看源 IP 的演化）：

| 数据包 | 以太网目标 | 以太网源 | 目标 IP | 源 IP | 目的端口 | 源端口 | 类型 |
|---|---|---|---|---|---|---|---|
| 1 | 广播 | 客户端 | 广播 | 0.0.0.0 | 67 | 68 | 发现 |
| 2 | 客户端 | 服务器1 | 广播 | 服务器1 | 68 | 67 | 提供 |
| 3 | 客户端 | 服务器2 | 广播 | 服务器2 | 68 | 67 | 提供 |
| 4 | 服务器1 | 客户端 | 服务器1 | 0.0.0.0 | 67 | 68 | 请求 |
| 5 | 客户端 | 服务器1 | 广播 | 服务器1 | 68 | 67 | 确认 |
| 6 | 服务器1 | 客户端 | 服务器1 | 客户端 | 67 | 68 | 请求 |
| 7 | 客户端 | 服务器1 | 广播 | 服务器1 | 68 | 67 | 确认 |
| 10 | 客户端 | 服务器1 | 广播 | 服务器1 | 68 | 67 | 否认 |
| 11 | 广播 | 客户端 | 广播 | 0.0.0.0 | 67 | 68 | 发现 |

读这张表要注意三点：

1. **第 1 行的源 IP 是 0.0.0.0**——客户端还没有地址，这是 DHCP 的"身份真空期"，也是攻击窗口。
2. **服务器发往客户端的报文，目标 IP 常是广播**（因为客户端此时可能还不能接收单播）。
3. **第 4、6 行的源 IP 仍是 0.0.0.0 或旧地址**——续租时客户端用的是"正在用的地址"，而不是"已确认的地址"。

### 5.5.5 DHCP 的攻击与防御

**协议层面的两个根因**（先记住这个，再看具体攻击）：

| 根因 | 说明 |
|---|---|
| 运行在不可靠的 UDP 之上 | 攻击者比较容易伪造虚假的 DHCP 报文，增加网络攻击风险 |
| 缺乏认证机制 | 攻击者可冒充合法服务器，向客户端分发错误的 IP 地址或网络配置信息，可能导致客户端无法接入网络或引发数据泄露 |

**（1）DHCP 饥饿攻击（Starvation）**

- **定义**：攻击者通过不断地向 DHCP 服务器发起大量 IP 地址请求报文，目的是迅速耗尽服务器的 IP 地址池，导致服务器无法为合法客户端提供可用的 IP 地址。
- **关键手法**：**频繁更改 DHCP 请求中的客户端硬件地址（Chaddr）字段的值**——服务器按 MAC 分配地址，伪造不同 MAC 就能不断申请新地址。
- **后果**：地址池耗尽，合法用户无法获得有效 IP（一种针对"配置层"的拒绝服务）。

**防御**：在网络交换机上启用 **DHCP Snooping** 功能，对 DHCP 请求报文中的 Chaddr 字段与数据帧的源 MAC 地址进行**比对验证**：

```
客户端发送 DHCP 请求
        |
        v
  +---------------------------+
  | 交换机 DHCP Snooping      |
  |  比较 Chaddr 与 帧源MAC   |
  +---------------------------+
     | 一致                | 不一致
     v                     v
   允许通过              丢弃报文
```

原理：真实主机的 Chaddr 必须等于它自己的网卡 MAC，二者天然一致；攻击者要伪造大量 Chaddr，就无法同时伪造等量的真实帧源 MAC（受限于物理网卡与链路）。因此一条规则同时封死了"批量伪造"。

**（2）DHCP Server 仿冒者攻击（Rogue DHCP）**

- **定义**：攻击者在网络环境中设置伪造的 DHCP Server，模仿合法 DHCP Server 的功能，致使 DHCP Client **无法连接到预期的网络**，或者可能被**诱导至攻击者控制的网络环境**中。
- **危害升级路径**：伪造服务器通常把自己设为默认网关和 DNS 服务器——于是客户端的全部流量都经过攻击者，从"配错地址"升级为"全面中间人"。

**防御**：在 DHCP Snooping 技术中，交换机端口被划分为两种类型——**信任端口**和**非信任端口**：

| 端口类型 | 连接对象 | 行为 |
|---|---|---|
| 信任端口（Trusted） | 合法 DHCP Server | 允许从这些端口接收的 DHCP 报文正常转发 |
| 非信任端口（Untrusted） | 普通终端 | **自动丢弃**从这些端口接收到的所有 DHCP 报文 |

因为终端只应该"发请求"而不应该"发应答"，所以按"谁能说服务器的话"来划分端口，就从根本上排除了仿冒服务器。

**（3）DHCP 中间人攻击（MITM）**

- **定义**：攻击者使用 **ARP 欺骗**技术，操纵 DHCP 客户端和服务器之间的通信，截获或篡改双方传输的数据包。
- **注意攻击的复合性**：这里的主角不是 DHCP 而是 ARP。DHCP 只提供"初始配置"，ARP 提供"运行期地址解析"，攻击者用后者污染前者建立的信任。

**防御**：启用交换机上的 **ARP 与 DHCP Snooping 联动**功能：

1. 交换机通过收集 DHCP 报文中的 Chaddr 字段确定客户端 MAC，并通过 DHCP 服务器分配的 IP 来识别客户端；
2. 建立并维护**动态的 DHCP Snooping 绑定表**，记录 DHCP 客户端与服务器间的通信信息（IP—MAC—端口—VLAN）；
3. 当检测到 ARP 报文时，交换机验证报文中的**源 IP 和源 MAC 是否与绑定表记录匹配**；
4. 不一致则拒绝该报文。

**这三条防御的共同逻辑**：**"配置阶段的事实"要固化成"运行阶段的规则"**。DHCP Snooping 绑定表就是这样一个"事实快照"——地址是服务器正式分配的，那么后续任何声称拥有该地址的报文都必须与这张表相符。这与 DNS 的 DNSSEC（把权威签名固化）、会话的绑定 IP（把登录时的事实固化）是同一个思路。

## 5.6 FTP 与 SSH 协议安全

### 5.6.1 FTP 的定位与演进

将某台计算机中的文件通过网络传送到可能相距很远的另一台计算机中，是一项基本的网络应用，即**文件传送**。FTP（File Transfer Protocol，文件传送协议）是因特网上使用得最广泛的文件传送协议。

FTP 的三个特性：

| 特性 | 含义 |
|---|---|
| 交互式访问 | 允许客户指明文件的类型与格式（如指明是否使用 ASCII 码） |
| 存取权限控制 | 允许文件具有存取权限，访问文件的用户必须经过授权并输入有效口令 |
| 屏蔽系统差异 | 屏蔽各计算机系统的细节，适合在异构网络中任意计算机之间传送文件 |

**历史地位**：在因特网发展的早期阶段，用 FTP 传送文件约占整个因特网通信量的三分之一，而由电子邮件和域名系统所产生的通信量还要小于 FTP；只是到了 **1995 年，万维网 WWW 的通信量才首次超过 FTP**。

**技术定位**：FTP 是用于网络文件传输的标准协议，工作在 OSI 模型的应用层和 TCP/IP 模型的第四层，**依赖 TCP 实现可靠、面向连接的传输，连接建立前需经过三次握手**。

**演进线索**（课程强调"核心驱动：从满足基础连通性到适应复杂网络环境，再到全面保障数据安全"）：

| 里程碑 | 内容 | 解决的问题 |
|---|---|---|
| RFC 114 | FTP 正式发布，在 ARPANET 上基于 NCP（Network Control Program/Protocol）实现最早的跨主机文件交换 | 互联网文件共享的雏形 |
| RFC 1579 | 引入**被动模式** | 解决客户端位于防火墙或 NAT 网关后无法建立数据连接的难题 |

**典型部署形态**：多个 FTP 客户通过因特网（或经交换机在局域网内）访问同一台 FTP 服务器。根据应用需求不同，FTP 服务器可能需要一台高性能和高可靠性的服务器计算机，也可能只需一台普通个人计算机。

**常见用途**：

1. 在计算机之间传输文件，尤其是**批量传输**文件；
2. 让网站设计者把构成网站内容的大量文件**批量上传**到 Web 服务器。

### 5.6.2 双连接设计：控制连接与数据连接

FTP 基于 C/S 架构，最核心的设计精髓在于**分离的"控制连接"与"数据连接"**。两条连接各司其职，确保指令的稳定传达与数据的高效传输。

| 对比项 | 控制连接 | 数据连接 |
|---|---|---|
| 定位 | "指挥中枢" | "搬运通道" |
| 端口 | 服务器端默认监听 **21**，是建立会话的基础 | 主动模式下服务器端使用 **20**，被动模式下动态分配 |
| 作用 | 传递操作指令及服务器的状态响应 | 传输实际的文件数据等二进制信息 |
| 生命周期 | 一旦建立，在整个 FTP 会话期间**始终保持连接** | **按需临时建立**，数据传输完成后立即断开 |
| 持久性 | 持续存在 | 临时连接 |

```
        FTP 客户端                              FTP 服务器
            |                                        |
            |<======= 控制连接（TCP 21，全程保持）=====>|
            |         USER / PASS / LIST / RETR        |
            |                                        |
            |<------- 数据连接（TCP 20 或临时端口）---->|   传输文件时临时建立
            |         文件内容（传输完即关闭）          |
```

**为什么要这样设计**？课程给出的解释分两层：

**(1) 半双工限制**：单连接上难以同时进行"发数据"和"收命令"，而 FTP 恰恰需要**传输中随时响应控制指令**。这种"信令与数据分离"的设计，解决了单连接模型中**指令易被大数据量淹没**的问题，保证了协议的高交互性和稳定性，是早期网络协议设计的经典智慧体现。

**(2) 历史条件**：FTP 的分离设计是在**缺乏多路复用机制的年代**，用"**物理双连接**"实现逻辑解耦的经典方案。

这个对比非常适合出简答题：**今天的 HTTP/2 用"流"在一条连接上做逻辑复用，而 1970 年代的 FTP 只能用两条 TCP 连接做物理分离**——同样是"控制与数据解耦"的需求，不同年代的实现手段不同。

### 5.6.3 主动模式与被动模式

| 模式 | 客户端命令 | 谁发起数据连接 | 服务器端口 | 适用场景 |
|---|---|---|---|---|
| 主动模式（PORT/Active） | 客户端发送 **PORT** 命令，告知自己的 IP 和端口 | **服务器**从 TCP 20 端口主动连接到客户端指定端口 | 20 | 客户端无防火墙时 |
| 被动模式（PASV/Passive） | 客户端发送 **PASV** 命令 | 服务器打开临时端口，**客户端**主动连接到该端口 | 临时端口 | 客户端位于防火墙/NAT 后 |

**为什么被动模式是现代默认选择**：

- 主动模式下，服务器主动连回客户端，被客户端防火墙视为"**外部主动入站**"而拦截；
- 被动模式下，客户端主动连出，符合防火墙通常"**放内出、阻外入**"的策略，故被动模式适用于客户端位于防火墙内的情况，避免防火墙阻止外部连接（主动模式的数据连接常被防火墙拦截）。

```
主动模式 (PORT)                          被动模式 (PASV)
客户端              服务器                客户端              服务器
  |                  |                     |                  |
  |--控制连接 21---->|                     |--控制连接 21---->|
  |--PORT 192,168,1,2,19,137-->|          |--PASV----------->|
  |                  |                     |<--227 进入被动模式(IP,端口)--|
  |<--服务器从20端口主动连客户端端口--|     |--连接服务器临时端口---------->|
  |<==数据==>        |                     |<==数据==>        |
```

**PORT 命令的参数怎么算**（课程给的实例，属于易考细节）：

```
PORT 192,168,1,2,19,137
     └──┬───┘ └──┬──┘ └┬┘
      客户端IP   高字节 低字节
端口号 = 256 * 19 + 137 = 5001
```

即：**前 4 个参数是客户端 IP 地址（用逗号分隔），最后两个参数用来计算客户端所侦听的端口号，算法是 高字节×256 + 低字节**。

> 安全视角：PORT 命令让客户端能指定"服务器来连我的哪个端口"，这是一个天然的**端口扫描/反弹跳板**原语（FTP bounce 攻击）。因此现代 FTP 服务器会校验 PORT 命令中的 IP 必须与发起控制连接的 IP 一致。

### 5.6.4 一次完整的 FTP 会话（含应答码）

课程用一段真实交互说明"命令—应答"的节奏。注意每条服务器应答都是三位数字开头，这一点与 SMTP 同源。

| 步骤 | 客户端发送 | 服务器应答 | 含义 |
|---|---|---|---|
| 1 | `ftp spock.dougj.net`（建立控制连接） | `220 spock.dougj.net FTP server (version 6.00LS) ready` | 服务器用 220 和一段文本响应，客户端显示该消息 |
| 2 | `User: cpre530` → `USER cpre530` | `331 password required for cpre 530` | 331 表示需要输入密码 |
| 3 | `PASS password` | `230 User cpre530 logged in.` | 登录成功用 230；**失败则返回 530** |
| 4 | `ls` | `200 PORT command successful` | 请求目录列表，需要先打开数据连接，通过 PORT 命令表示 |
| 5 | `PORT 192,168,1,2,19,137` | `200 PORT command successful` | 告知服务器客户端的 IP 与数据端口 |
| 6 | （数据连接建立后）`LIST` | 文件列表经数据连接返回 | 控制连接与数据连接并行的时刻 |

**这条流程里最扎眼的是第 3 步**：`PASS password` —— **密码在网络上明文传输**。任何能嗅探控制连接的人都能直接拿到账号密码。这不是实现疏忽，是 1971 年设计时的规格。

### 5.6.5 匿名 FTP

**FTP 身份验证**：用户需通过用户名和密码验证后才能上传或下载文件（需要两组连接：控制连接和数据连接）。

**匿名 FTP 服务**：提供 "anonymous" 账号，允许用户**无需注册即可下载文件**。登录时用户名为 `anonymous`，密码可为任意字符串（如邮箱地址）。

**安全限制**：

- 匿名 FTP 服务**限制用户访问范围**，仅开放特定目录供公众下载文件；
- 其他系统目录保持隐藏，保护服务器数据安全和隐私。

> 安全视角："匿名 + 只读 + 目录受限"才是安全形态。一旦匿名账号被授予写权限，服务器立刻变成恶意文件的公共投放点；而"目录受限"若靠路径过滤实现而非内核级 chroot，就可能被 `../` 穿越绕过。

### 5.6.6 FTP 的安全风险与防御

| 风险 | 具体表现 |
|---|---|
| 用户名和密码的明文传输 | FTP 在传输用户凭据时不会对其进行加密或其他形式的加密处理，用户名和密码以明文方式传输，容易被拦截并窃取 |
| 传输数据的不安全性 | FTP 传输的数据本质不加密，任何人都可以窥视正在传输的数据内容；传输过程中还可能存在中间人攻击，导致数据被篡改或窃取 |
| 权限管理不完善 | FTP 服务器通常提供多个权限级别，但不同级别的用户之间的文件权限可能存在重叠或冲突，导致数据泄漏或错误 |

**防范策略**：

| 措施 | 说明 |
|---|---|
| 改用加密协议 | FTP 明文传输账号密码和数据，安全性差，**公网场景应改用 FTPS（FTP over TLS）或 SFTP（SSH 文件传输协议）** |
| 使用加密和身份验证 | 确保 FTP 服务器仅接受加密连接，要求用户使用合法凭据（用户名/密码、证书、令牌等）访问 |
| 限制用户权限 | 通过访问控制列表（ACL）和强制访问控制（MAC）等机制，严格控制用户文件操作权限，限制访问范围 |
| 监控服务器活动 | 监控 FTP 服务器的登录、文件操作记录，检测异常活动 |
| 使用防火墙 | 通过防火墙限制未经授权的网络访问，提供额外安全保护 |

**FTPS 与 SFTP 的区别**（容易被混为一谈）：

| 对比项 | FTPS | SFTP |
|---|---|---|
| 全称 | FTP over TLS | SSH File Transfer Protocol |
| 加密层 | 在 FTP 之上加 TLS | 在 SSH 连接内传输文件 |
| 连接数 | 仍然是控制连接 + 数据连接（两条） | 单条 SSH 连接内多路复用 |
| 端口 | 990（隐式）/ 21（显式） | 22 |
| 协议关系 | FTP 的加密版 | **与 FTP 无继承关系**，是 SSH 的子系统 |

### 5.6.7 SSH：安全远程访问的事实标准

SSH（Secure Shell）是**支持机器验证和流量加密的开源协议**，已经成为事实上的安全远程访问标准。

**设计目的**（必背的一句话）：提供公共密钥和对称密钥，其中**公共密钥加密用于验证 SSH 服务器**，**对称密钥用于加密数据传输**。

这个分工很经济：非对称运算慢，只用于"验明正身"和"协商出对称密钥"；对称运算快，用于之后全部的数据加密。

**SSH 协议交换的五个阶段**：

```
SSH客户端                                             SSH服务器
    |                                                    |
    |  1. 版本协商：服务器通知其版本，客户端响应           |
    |<-------------------------------------------------->|
    |  2. 功能协商：双方交换功能和参数选择                 |
    |<-------------------------------------------------->|
    |  3. 会话密钥协商：基于密钥交换参数选择会话密钥       |
    |     （用于加密客户端与服务器之间的流量交换）          |
    |<-------------------------------------------------->|
    |  4. 用户验证：协商会话密钥后，进行用户身份验证        |
    |<-------------------------------------------------->|
    |  5. 加密数据交换                                    |
    |<==================================================>|
```

| 阶段 | 内容 | 安全作用 |
|---|---|---|
| 版本协商 | 服务器通知其版本，客户端响应 | 确定双方可用的协议版本与算法集 |
| 功能协商 | 双方交换功能和参数选择 | 决定压缩、认证方式等能力 |
| 会话密钥协商 | 协商基于密钥交换参数选择的会话密钥 | 生成后续加密使用的对称密钥（**前向保密的关键环节**） |
| 用户验证 | 协商会话密钥**之后**才进行 | 身份信息在加密信道内传递，不会被嗅探 |
| 加密数据交换 | 全部后续数据加密 | 机密性与完整性 |

**注意顺序上的安全含义**：SSH 先建立加密信道、再验证用户；而 FTP 与 SMTP 是先后传口令、后传数据。**先加密后认证**是 SSH 比前两者安全的根本原因——不仅数据安全，连认证过程本身也不暴露。

> 补充：SSH 的密钥交换（如 Diffie-Hellman）提供前向保密：即使服务器私钥日后泄露，攻击者也无法解密此前录下的会话流量。这也是"会话密钥"与"主机密钥"必须分开的原因。

## 5.7 应用安全攻击的共性特征与基本防御原理

前面六节讲的协议各不相同，但攻击手法高度相似。本节回答一个问题：**导致应用安全问题的根本原因是什么？**

### 5.7.1 共性特征一：资源有限 → DDoS

DDoS（Distributed Denial of Service，分布式拒绝服务）：通过大量合法的请求占用大量网络资源，以达到使网络瘫痪的目的。

**分类**（按干扰目标）：

| 类型 | 表现 |
|---|---|
| 网络过载 | 通过使网络过载来干扰甚至阻断正常的网络通讯 |
| 服务器超负荷 | 通过向服务器提交大量请求，使服务器超负荷 |
| 个体阻断 | 阻断某一用户访问服务器 |
| 通信阻断 | 阻断某服务与特定系统或个人的通讯 |

**占用的资源类型**：网络带宽、磁盘读写、CPU 计算等。**Web、CDN、物联网、云计算都面临对应的安全风险**。

**为什么这是"共性"**：因为任何服务都在有限的资源上运行，而"合法请求"与"攻击请求"在语法上无法区分——这正是 5.2 的 DNS 反射放大（用别人的服务器放大流量）、5.5 的 DHCP 饥饿（耗尽地址池）属于同一族的原因：**都是把"资源有限"这一物理事实当作攻击面**。

### 5.7.2 共性特征二：资源共享 → 越权与推理

攻击者可以合法、或者非法地获取应用数据，进而**推理构造出目标数据**。课程分两种情况：

| 类型 | 机制 | 典型场景 |
|---|---|---|
| 合法的越权访问 | 一些网络应用的数据是相互共享的，所有用户都可以合法使用；但这些数据往往由于隐私保护存在缺陷（**差分隐私、互补隐私**等） | Web 应用和社交网络中最常见 |
| 非法的访问资源 | 逻辑上相互独立的用户数据存放在**相同的一片物理区域**，攻击者利用漏洞非法访问其他用户的数据，造成一定程度的数据泄露 | 主要存在于云计算中 |

课程点名的技术：

- **差分隐私攻击**：通过多次查询的统计结果之差，反推出个体信息。
- **侧信道攻击**：通过时间、功耗、缓存等间接信息推断数据内容（课程中与"资源有限/共享"并列讨论，属于"共享即泄露"的典型）。
- **RangeAmp**：课程在"系统漏洞"一节提到"RangeAmp 两种攻击形式"，属于通过 HTTP Range 请求放大攻击的形态。

**核心逻辑**：**共享是效率的来源，也是泄露的通道**。多租户的物理共用、统计接口的多次查询、缓存的时间差异——三者同源。

### 5.7.3 共性特征三：系统漏洞

课程给出的推理链很干脆：

1. 现有计算机体系结构复杂、应用丰富；
2. 不能确保多变、异构的应用硬件和软件的实现万无一失；
3. **完全没有任何漏洞是不可能的**；
4. **漏洞的及时修复也存在问题**（补丁要评估兼容性、要停机、要覆盖所有实例）。

第 4 点常被忽略但很关键：**"有漏洞"是工程现实，"修不上"是运维现实**。所以防御设计必须假设"某些漏洞永远存在"，这就是纵深防御的前提。

### 5.7.4 基本防御原理：三条主线

针对上述本质与共性原因，课程给出三条防御主线：

| 防御主线 | 对应根因 | 具体手段 |
|---|---|---|
| 身份认证与信任管理 | 缺认证、资源共享导致的越权 | 身份认证系统、对称/非对称加密系统、PKI |
| 隐私保护 | 资源共享导致的推理泄露 | K 匿名、差分隐私、隐私计算 |
| 应用安全监控防御 | 系统漏洞无法避免 | 异常流量监测、安全软件、快速识别与恢复 |

**（1）身份认证与访问控制**

- 身份认证是保证信息安全的**第一道门户**：用户在被确认身份之后，在信息系统中根据身份所具有的权限享受相应的信息服务。
- 常用的身份认证方式：**用户名/口令**、**生物/物理特征**（如面部识别）、**图灵测试**。
- 对于网络中的大型实体应用，一般会利用**公钥基础设施（PKI）**来进行身份的管理和认证。

| 认证方式 | 依据 | 强度 | 弱点 |
|---|---|---|---|
| 用户名/口令 | 你知道什么 | 弱 | 可猜测、可撞库、可嗅探 |
| 生物/物理特征 | 你是什么 | 较强 | 不可更换，泄露即永久 |
| 图灵测试 | 你是不是人 | 用于区分人机 | 只能防自动化，不防定向攻击 |

**（2）隐私保护**

- 隐私数据的泄露会引起严重的危险后果；通过**身份认证和信任管理可以一定程度保护隐私，但是无法从数据本身保护**——这是关键判断：身份管住了"谁能进门"，但管不住"进门后看到的东西如何被使用"。
- 因此需要利用隐私保护算法或技术对隐私数据本身进行保护，常有算法：**K 匿名、差分隐私、隐私计算**等。
- 法律法规层面：美国的 HIPPA、PCI DSS、FACT，欧盟的 GDPR，以及中国的《网络安全法》等。

**（3）应用安全监控防御**

- 前提：一定网络应用系统的漏洞是无法避免的。
- 作用：在网络发生被攻击、破坏的情况下，可以通过监控检测，**快速识别、恢复网络应用的服务，减少损失**。
- 布局原则：在网络系统各个点上部署安全防御措施，**避免出现安全的木桶效应**——短板决定整体强度，所以不能只在边界防护。
- 手段：异常流量监测、安全软件。

```
        身份认证与访问控制          隐私保护            监控与恢复
        （谁能进来）              （进来能看什么）      （出事怎么办）
              |                       |                    |
   -----------+-----------------------+--------------------+---------->
   预防（Prevention）            保护（Protection）      检测响应（Detection & Response）
```

这三条主线与本章各节的防御措施可以一一对应：

| 主线 | DNS | HTTP | 邮件 | DHCP | FTP/SSH |
|---|---|---|---|---|---|
| 认证 | DNSSEC | Token、绑定 IP/UA | PGP 签名、TLS 证书 | DHCP Snooping 信任端口 | SSH 主机公钥 |
| 加密 | DoT/DoH | HTTPS | TLS/STARTTLS | （本身无，靠上层） | FTPS/SFTP |
| 监控 | 解析限制、速率阈值 | 会话监控与告警 | 邮件过滤、取证 | 绑定表校验 | 登录与操作日志 |

## 考点提示

- **DNS 的两种查询分工**：主机→LDNS 是递归，其余是迭代；原因是递归对服务器负担太大，必须靠迭代保证分布式可扩展。
- **13 个根服务器 IP 与 25 台 IPv6 根**要分清；IPv4 时代 1 主 12 辅，其中美国运营 1 主 9 辅。
- **域名长度三条硬指标**：单标号 ≤63 字符、总长 ≤255 字符、层次化授权最多迭代 127 次。
- **DNS 报文四区**：问题区必有；权威区与附加区是 Kaminsky 攻击的注入点；类型 0 表示查询、非 0 表示响应（由标志字段第一位区分）。
- **Kaminsky 三步**：查不存在域名 → 抢在真响应前伪造响应 → 污染缓存；根因是"无源认证 + ID 可猜 + 接受额外记录 + 缓存放大"。
- **DNS 欺骗两分法**：缓存中毒改缓存（影响大、持续），信息劫持不改缓存（抢答、仅影响当次）。
- **反射放大公式**：小请求 40-60 字节 ↔ 大响应 4000-6000 字节，放大近 100 倍；防御靠关闭开放递归 + 源地址校验。
- **DNSSEC 只签名不加密**：私钥签名、公钥验证、散列保完整性；DoT/DoH 才解决机密性。
- **DoT vs DoH**：DoT 用 TLS+专用端口、可信链靠 PKI；DoH 走 HTTPS、与现有 DNS 不兼容但通用性好。
- **HTTP 五版一句话**：0.9 只有 GET 无头部；1.0 多方法+头部但每请求一连接；1.1 持久连接+管道化但队头堵塞；2.0 帧/消息/流多路复用；3.0 用 QUIC（UDP）+连接迁移。
- **HTTP 三部分**：开始行（请求行/状态行）＋首部行＋空行＋实体主体；请求与响应只差开始行。
- **会话劫持 vs 会话固定**：劫持是"事后偷 ID"，固定是"事前给 ID"；固定不需要嗅探，全站 HTTPS 也防不住，关键是登录后换 ID。
- **SMTP 会话三阶段**：建立连接、邮件传输、断开连接；14 条命令、21 种应答、命令不区分大小写而参数区分。
- **四个邮件端口**：SMTP 25、POP3 110、IMAP 143；POP3S 995、SMTP over TLS 465（补充项）。
- **MIME 解决的是字符集与二进制**：7 个基本类型、15 种子类型；Content-Type 必须 "type/subtype"，multipart 用 boundary 分段。
- **STARTTLS 的软肋**：前几步明文，可被中间人剥离降级；因此必须配置"强制加密"策略。
- **DHCP 四阶段 DORA**：Discover（广播）→ Offer（单播）→ Request（广播）→ Ack/Nak；8 种报文，基于 BOOTP 格式。
- **租约计时器**：T1=0.5T 续租、T2=0.875T 重发、到期必须放弃；客户端可用 DHCP Release 提前终止。
- **三种 DHCP 攻击对应三种防御**：饥饿→Chaddr 与帧源 MAC 比对；仿冒→信任/非信任端口；中间人→ARP 与 Snooping 绑定表联动。
- **FTP 双连接**：控制连接 21 全程保持，数据连接 20 或临时端口按需建立；分设计初衷是解决半双工下"指令被数据淹没"。
- **PORT 端口计算**：256×19+137=5001；主动模式服务器主动连客户端（易被防火墙拦），被动模式客户端主动连服务器（易穿透）。
- **SSH 五阶段**：版本协商→功能协商→会话密钥协商→用户验证→加密数据交换；公钥验服务器、对称密钥加密数据。
- **三条共性根因**：资源有限、资源共享、系统漏洞；三条防御主线：认证与访问控制、隐私保护、监控与恢复。

## 易错点与自测

### 易错点对比表

| 易混概念 | 正确区分 | 常见错误 |
|---|---|---|
| 递归查询 / 迭代查询 | 递归＝你替我问到底；迭代＝你告诉我下一步问谁。主机→LDNS 递归，LDNS→其余迭代 | 误以为"根服务器做递归"，或误以为全程都是递归 |
| 缓存中毒 / 信息劫持 | 前者改服务器缓存（持久、影响全量用户），后者只伪造更快响应（当次、不改缓存） | 把二者都说成"篡改缓存" |
| DNSSEC / DoT / DoH | DNSSEC 只签名（真实性与完整性），不加密；DoT/DoH 加密（机密性）；DoH 与现有 DNS 不兼容 | 认为"部署 DNSSEC 后内容就不会被看到" |
| 会话劫持 / 会话固定 | 劫持＝先有受害者会话再偷 ID；固定＝先造陷阱会话再让受害者用该 ID 登录 | 认为"上了 HTTPS 就不会被会话固定" |
| HTTP/1.1 管道化 / HTTP/2 多路复用 | 管道化仍是顺序处理，故有队头堵塞；多路复用按流并发、可乱序重组 | 认为"管道化解决了队头堵塞" |
| POP3 / IMAP | POP3 下载到本地、单向、早期删信；IMAP 服务器端管理、多端同步 | 把 IMAP 说成"加密版 POP3"（二者与加密无关） |
| SMTP / POP3 方向 | SMTP 只发（25），POP3/IMAP 只收（110/143）；认证与加密是另外叠加的 | 认为"SMTP 既能发也能收" |
| 主动 FTP / 被动 FTP | 主动＝服务器连客户端（PORT，服务器 20）；被动＝客户端连服务器（PASV，临时端口） | 记反"谁主动连谁"，从而记反防火墙行为 |
| 饥饿攻击 / 仿冒服务器 | 饥饿耗尽地址池（DoS）；仿冒提供错误配置（可升级为中间人） | 把饥饿说成"偷 IP 地址" |
| FTPS / SFTP | FTPS＝FTP+TLS，仍两条连接；SFTP＝SSH 子系统，一条连接、与 FTP 无继承关系 | 认为 SFTP 是"安全版 FTP 协议"（协议族完全不同） |

### 自测题

**1. 为什么实际互联网采用"主机到本地域名服务器递归、其余迭代"的混合模式？**

**答**：因为递归查询对被查询服务器的负担太大。若让根服务器对每个查询递归到底，全部解析压力会集中到顶层，既不可扩展也无法承载全球查询量。混合模式让 LDNS 承担"跑腿"（迭代），主机只享受"一次委托"（递归），既保证用户便捷，又保持系统分布式与可扩展性。

**2. Kaminsky 缓存污染攻击中，攻击者为什么先查询一个"不存在的域名"？伪造响应为何要在权威区和附加区写记录？**

**答**：查不存在的域名是为了**制造一个正在等待响应的合法查询**，从而知道 LDNS 当前使用的查询 ID 与端口范围，便于抢答；同时该域名不存在，真实响应必然为"无此记录"，攻击者的伪造响应不会与真实答案冲突。在权威区写入伪造的 NS、在附加区写入该 NS 的 A 记录，是为了让 LDNS 把"某域的权威服务器是攻击者主机"这条**与问题无直接关系的记录**一并缓存（名字连锁攻击），从而一次性劫持整片域名空间，而不只是那一个不存在的主机名。

**3. HTTPS 已经全站启用，为什么仍可能遭到会话固定攻击？应如何防御？**

**答**：因为会话固定不依赖窃听。攻击者先在服务器上建立陷阱会话并保持活跃，再把该 Session ID 设法让受害者浏览器使用；受害者用自己的账号密码登录后，服务器把这个会话"升级"为已认证会话，而该 ID 攻击者早已知道，于是直接获得权限。全程没有明文泄露，HTTPS 无法阻止。核心防御是**登录成功后由服务器生成全新的 Session ID**（使旧 ID 失效），并配合"服务器独占生成会话标识、使用强随机数、登录/退出时销毁会话、绑定 IP 与 UA、设置超时"。

**4. 说明 DNS 反射放大攻击的三方角色与放大倍数的来源，并给出两条最有效的防御措施。**

**答**：三方是攻击者、被滥用的开放 DNS 服务器（反射器）、受害者。攻击者伪造源 IP 为受害者地址，向开放递归服务器发送 40-60 字节的小查询；服务器把 4000-6000 字节的大响应发往受害者，放大近 100 倍。倍数来源是"请求小、响应大"的不对称性，加上 UDP 无连接、无需握手即可放大。最有效的两条防御：①**关闭开放递归**，只允许授权网段使用解析服务，使攻击者找不到反射器；②**源地址校验（入口过滤）**，阻止伪造源 IP 的报文出网；辅以权威服务器响应速率限制。

**5. DHCP 饥饿攻击与 DHCP 仿冒服务器攻击的成因、后果、防御有何不同？**

**答**：成因上，饥饿攻击利用"服务器按 Chaddr 分配地址"这一点，通过频繁伪造不同 Chaddr 大量申请，迅速耗尽地址池，后果是合法客户端拿不到 IP（拒绝服务）；仿冒服务器攻击利用"DHCP 缺乏认证"，攻击者架设假服务器抢先应答，后果是客户端获得错误网关/DNS，无法接入预期网络甚至被引入攻击者网络（可升级为中间人）。防御上，前者靠 DHCP Snooping 比对 Chaddr 与数据帧源 MAC 是否一致，不一致即丢弃；后者靠端口信任划分，只允许信任端口（连合法服务器）转发 DHCP 应答，非信任端口上来的 DHCP 报文一律丢弃。

**6. FTP 为什么设计成两条连接？这种设计在防火墙上带来什么问题，如何解决？**

**答**：因为单条 TCP 连接在半双工条件下难以同时"发数据"和"收命令"，而 FTP 需要在传输过程中随时响应控制指令；在缺乏多路复用机制的年代，只能用两条物理连接实现"信令与数据"的逻辑解耦，避免指令被大数据量淹没。问题在于数据连接的方向不固定：主动模式下服务器从 20 端口主动连回客户端，被客户端防火墙视为外部主动入站而拦截；解决方案是改用被动模式（PASV），由客户端主动连出到服务器临时端口，符合防火墙"放内出、阻外入"的策略。彻底的安全方案则是改用 FTPS 或 SFTP。
