# 第4章 传输层协议安全

传输层是"用户功能的最低层、通信功能的最高层"。它把网络层"尽力而为"的逐跳分组搬运，变成进程与进程之间可用的端到端信道。也正因为传输层直接面向应用进程、又承载着连接状态与序列号这两种可被利用的"软状态"，针对它的攻击往往比网络层攻击更省力：攻击者不需要瘫痪链路，只要让协议状态机走偏、让资源分配失衡、让序号被猜中，就能造成连接不可用或数据被注入。本章按 TCP → UDP → SSL/TLS 的顺序展开：先讲清报文格式与连接机制（原理），再讲这些机制如何被反向利用（攻击），最后给出检测与加固手段（防御）。

## 4.1 传输层概述

### 4.1.1 传输层的定义与作用

在典型的五层体系结构（物理层、链路层、网络层、传输层、应用层）中，传输层向上为应用层提供通信服务，它既是"面向通信部分"的最高层，也是"用户功能"中的最低层。这个位置决定了它的双重身份：向下，它要屏蔽网络层"尽力而为"带来的丢失、乱序、重复；向上，它要为一台主机上同时运行的多个应用进程分别提供独立的通信能力。

传输层的核心功能是为**不同主机上的应用进程之间提供端到端的逻辑通信**。所谓"逻辑通信"，是指两个进程看起来像有一条直通的管道，而实际上数据要经过多个路由器逐跳转发；这条管道由两端主机的协议栈共同"虚拟"出来，中间设备（路由器）只处理到网络层，不感知传输层连接。具体动作有两条：

1. 发送端把应用程序交下来的长消息切分成若干**报文段（segment）**，加上传输层首部后向下交给网络层；
2. 接收端把收到的报文段按序重组为原消息，去掉首部后向上交付给应用层。

理解这一点要区分三种"作用范围"：IP 协议的作用范围是主机到主机（主机 A 到主机 B，中间跨越 LAN1、WAN、LAN2 和两台路由器）；TCP/UDP 的作用范围是两端主机内部**应用进程到应用进程**（AP1↔AP4）；而链路只负责相邻节点之间的一跳。因此"端到端"与"点到点"不是修辞差别：网络层只保证把分组送到目的**主机**，究竟交给主机上的哪个进程，是传输层用端口号完成的。

传输层还承担**复用（multiplexing）与分用（demultiplexing）**：发送端把多个应用进程的数据统一封装进网络层（复用），接收端依据首部中的端口号把数据分发回正确的进程（分用）。复用与分用的实现手段就是端口号——这也解释了为什么后文的注入类攻击（RST 注入、会话劫持）都必须先"端口一致"。

### 4.1.2 端口号：进程的网络标识

本机上运行的进程本来是用**进程标识符（PID）**标识的。但 Internet 上的主机运行着不同操作系统（Windows、Linux、macOS），各系统的 PID 格式与分配策略互不相同，跨主机通信时无法作为通用标识。于是 TCP/IP 体系在传输层引入了统一的进程标识——**端口号（port number）**。

端口号长度 **16 比特**，在报文上占 **2 字节**，取值范围 **0~65535**。它与 IP 地址组合成"IP:端口"二元组，唯一确定一台主机上的一个应用进程端点。

按用途与分配方式，端口号分为三类：

| 类别 | 分配者 | 特征 | 典型例子 |
|---|---|---|---|
| 熟知端口（系统端口） | IANA 分配并管理，保证全网设备统一识别 | 保留给常用、知名的应用层协议 | FTP 21/20、SMTP 25、DNS 53、DHCP 67/68、HTTP 80、HTTPS 443 |
| 登记端口 | IANA 为用户空间应用分配 | 供相对知名的应用或服务使用，需要注册 | MySQL 3306、SQL Server 1433、RDP 3389、Redis 6379、Oracle 1524 |
| 短暂端口（动态端口） | 操作系统动态分配 | 客户端发起连接时临时使用，通信结束即释放，不需注册 | 客户端访问服务器时的源端口 |

> 补充：三类端口的标准数值分界为 0–1023（熟知端口）、1024–49151（登记端口）、49152–65535（短暂端口）；PPT 只给出了类别名称与实例，未给边界。

端口号有三个必须在考试中写准的性质：

- **只具有本地意义**。端口号只用于标识"本机协议栈应用层中的各个进程"，它是一个本地索引，不是全局地址。同一端口号在不同主机上毫无关系，互不影响。
- **TCP 与 UDP 的端口空间相互独立**。TCP 的 53 端口与 UDP 的 53 端口是两个不同的端点，可以分别被不同进程占用（DNS 正是同时使用两者）。
- **端口不是物理端口**。它看不见摸不着，纯粹是区分应用进程的标识符；一台主机可以同时有成千上万个端口在用，而物理网卡只有一个。

结合五层栈看：数据自上而下逐层封装，每层加上本层首部；端口号被写进传输层首部，接收端逐层解封装时在传输层依据它完成分用。这就形成了"IP 定位主机、端口定位进程"的分工。

### 4.1.3 TCP 与 UDP：两种传输层服务

因特网的传输层为应用层提供两种协议：面向连接的 **TCP（传输控制协议，Transmission Control Protocol）** 和无连接的 **UDP（用户数据报协议，User Datagram Protocol）**。二者的差异不是"新旧"而是"取舍"。

TCP 为其上层提供面向连接的、可靠的数据传输服务。使用 TCP 通信的双方在传送数据之前必须先建立 TCP 连接，数据传输结束后必须释放连接。为了实现可靠传输，TCP 必须叠加大量机制：连接管理、确认机制、超时重传、流量控制等。代价是实现复杂、首部较大（固定 20 字节）、占用处理机资源较多。

UDP 为其上层提供无连接的、不可靠的数据传输服务。通信双方在传送数据前不需建立连接；因为不承诺可靠交付，也就不需要确认与重传等机制。收益是实现简单、首部小（仅 8 字节）、转发开销低、时延抖动小。

| 对比项 | TCP | UDP |
|---|---|---|
| 连接性 | 面向连接，先握手后传输 | 无连接，知道地址即可发送 |
| 可靠性 | 可靠：确认、重传、排序、去重 | 不可靠：尽最大努力交付 |
| 数据单位 | 面向字节流（字节编号） | 面向报文（一次一个完整报文） |
| 首部开销 | 20 字节固定 + 最多 40 字节选项 | 8 字节 |
| 流量/拥塞控制 | 有（滑动窗口、慢启动等） | 无 |
| 典型应用 | HTTP/HTTPS、FTP、SMTP、SSH | DNS、DHCP、RTP、QUIC、视频直播 |
| 主要安全弱点 | 状态资源可被打爆、序号可被预测 | 源地址可伪造、无状态难溯源、易被反射放大 |

> 关键认识：TCP 的安全问题几乎都长在它的"优点"上——因为它维护连接状态，才会有半连接耗尽；因为它用序号保证有序，序号才成为伪造的门槛与目标。UDP 的安全问题则长在它的"省略"上——因为不握手、不验证源地址，才使伪造源 IP 的反射放大成为可能。

## 4.2 TCP 协议及其安全

### 4.2.1 TCP 报文段格式

一个 TCP 报文段分为**首部**和**数据**两部分，TCP 的全部功能都体现在首部各字段中。首部固定部分 20 字节，加上最多 40 字节选项，最大 60 字节。

| 字段 | 长度 | 作用 | 安全相关性 |
|---|---|---|---|
| 源端口 | 2 字节 | 源进程端口号 | 复用入口；注入报文必须与真实流一致 |
| 目的端口 | 2 字节 | 目的进程端口号 | 分用入口；端口开放情况是扫描与反射的起点 |
| 序号 seq | 4 字节 | 本报文段数据第一个字节在字节流中的编号 | 会话劫持、RST 注入、SYN Flood 的核心猜测量 |
| 确认号 ack | 4 字节 | 期望收到的下一个字节序号；ack=N 表示 N-1 及之前全部正确收到 | 伪造可制造"已确认"假象；SYN Cookie 把它当作校验位 |
| 数据偏移 | 4 位 | 数据起始处距报文段起始处的距离，即首部长度；以 4 字节为单位 | 可被用于构造畸形首部（长度与实际不符） |
| 保留 | 6 位 | 保留将来使用，目前置 0 | 异常非零值可作为畸形包检测特征 |
| 标志位 | 6 位 | URG/ACK/PSH/RST/SYN/FIN | 攻击者最直接的"操作杆"：SYN 建连、RST 断链、FIN 释放 |
| 窗口 | 2 字节 | 接收方通告的接收窗口大小（0~2^16-1），作为发送方设置发送窗口的依据 | 注入报文必须"落在接收窗口内"才被接受 |
| 校验和 | 2 字节 | 校验首部+数据，计算时前置 12 字节伪首部 | 伪首部含源/目的 IP，可发现地址被篡改 |
| 紧急指针 | 2 字节 | 仅在 URG=1 时有意义，指出紧急数据的字节数 | 带外数据通道，可被滥用传递隐藏指令 |
| 选项 | 0~40 字节 | 如 MSS、窗口扩大、时间戳、SACK 等 | 选项字段是协议扩展面，也是历史漏洞高发区 |

关于**数据偏移**的换算必须会算：4 位二进制最大表示 15，以 4 字节为单位，故首部最大长度 = 15×4 = **60 字节**；固定部分 20 字节，因此选项长度只能在 **0~40 字节**之间。当没有选项时首部就是 20 字节。

六个标志位的语义如下，做题时经常要求"给一个场景判断该置哪个位"：

| 标志位 | 置 1 的含义 |
|---|---|
| URG（紧急） | 紧急指针字段有效，报文段含紧急数据，应尽快传送；紧急数据在数据字段中的位置由紧急指针给出 |
| ACK（确认） | 确认号字段有效 |
| PSH（推送） | 发送方即使受发送窗口限制也要立即发送；接收方收到后不必在接收缓冲区排队，尽快交付应用进程 |
| RST（复位） | 连接出现严重差错（如主机崩溃），必须释放连接后重建 |
| SYN（同步） | 这是一个连接请求或连接接受报文 |
| FIN（终止） | 发送方数据已发送完毕，要求释放连接 |

> 三条容易被忽略的规则，是后面所有攻击分析的前提：①**SYN=1 的报文段不能携带数据，但要消耗一个序号**；②**FIN=1 的报文段即使不携带数据，也要消耗一个序号**；③序号是**按字节**编号的，不是按报文段编号，所以下一个报文段的 seq = 上一个报文段的 seq + 其数据字节数（+1 若带 SYN/FIN）。

### 4.2.2 TCP 连接：三次握手

TCP 连接由两个端点（两个套接字）确定：

```
socket = (IP 地址 : 端口号)
TCP 连接 ::= {socket1, socket2} = {(IP1:Port1), (IP2:Port2)}
```

也就是说，一条 TCP 连接由**四元组**唯一标识。这一定义直接决定了两件事：一是同一对主机之间可以并存多条连接（端口不同）；二是只要四元组不变，中间设备就可以把后续报文归入同一会话——这既是 NAT/防火墙的工作基础，也是 QUIC 后来改用连接 ID 的动机。

网络层 IP 采用"尽力而为"的分组传输，可能存在丢失、乱序。为在不重复、不遗漏、不乱序的前提下交付，TCP 使用**累计确认**：在指定时间内，对按序到达的最后一个分组发送确认报文，表示"该字节及之前的所有字节都已收到"。累计确认把"逐包确认"压缩为"按序最高位确认"，代价是丢一个包可能触发重复传输后续数据。

三次握手的完整过程与状态迁移：

```
   TCP 客户                                             TCP 服务器
   CLOSED                                               CLOSED
                                                        LISTEN（监听）
      |                                                     |
      |  ① SYN=1, seq=x                                     |
      |---------------------------------------------------->|
  SYN-SENT                                            SYN-RCVD
  （同步已发送）                                    （同步已接收）
      |                                                     |
      |  ② SYN=1, ACK=1, seq=y, ack=x+1                     |
      |<----------------------------------------------------|
      |                                                     |
      |  ③ ACK=1, seq=x+1, ack=y+1                          |
      |---------------------------------------------------->|
  ESTABLISHED                                        ESTABLISHED
  （连接已建立）                                     （连接已建立）
```

| 步骤 | 报文 | 关键字段 | 状态变化 | 目的 |
|---|---|---|---|---|
| ① | TCP 连接请求报文段 | SYN=1，seq=x（客户选择的初始序号 ISN） | 客户 CLOSED→SYN-SENT | 告诉服务器"我想建连，我的起始字节是 x" |
| ② | TCP 连接请求确认报文段 | SYN=1、ACK=1，seq=y，ack=x+1 | 服务器 LISTEN→SYN-RCVD | 既确认客户的 x，又同步自己的 y（两个方向各一次同步，合并在一个报文里） |
| ③ | 普通 TCP 确认报文段 | ACK=1，seq=x+1，ack=y+1 | 客户 SYN-SENT→ESTABLISHED；服务器收到后 SYN-RCVD→ESTABLISHED | 确认服务器的 y，双向序号同步完成 |

字段取值的因果关系要能自己推：第①步 seq=x 且 SYN 消耗一个序号，所以客户下一次发送的第一个数据字节序号是 **x+1**；第②步 ack=x+1 正是"我已收到 x，期待 x+1"；第③步 seq=x+1（沿用上一条推得的下一序号）、ack=y+1（对服务器 y 的确认）。服务器侧同理，第二条报文占用了 y，故 y+1 是服务器下一字节。

**为什么不能是两次握手？** 两个缺陷都源于"服务器在收到第三次 ACK 之前无法确认客户端真的收到了自己的 SYN+ACK"：

- 缺陷一：无法确认客户端的接收能力。若服务器发出的 SYN+ACK 丢失，客户端认为连接失败（未进入 ESTABLISHED），服务器却已认为连接建立并分配资源等待数据，资源被白白占用。
- 缺陷二：无法处理延迟的历史连接请求。一个延迟很久的旧 SYN 到达服务器，服务器会直接建立一条无效连接。攻击者正是利用这一点发起 **SYN 泛洪**：只要不断发送源地址伪造的 SYN，就能让服务器堆积大量"已建立但无对端"的连接。

三次握手解决这两点的机制是：服务器收到 SYN 后**不立即确认连接**，而是回 SYN+ACK 并进入 SYN-RCVD，等待第三次 ACK。若收到的是延迟旧 SYN，客户端收到 SYN+ACK 后会用 **RST** 回应，告知服务器这是无效连接，从而避免资源被无效占用。换句话说，第三次 ACK 的作用是"让服务器获得'客户端确实在线且收到了我的序号'这一证据"。

**为什么不需要四次握手？** 服务端的 SYN（同步自己的序号）与 ACK（确认对方的序号）是两个相互独立的操作，但它们可以高效地合并在同一个报文中一次发出，完全没有必要拆成两趟。结论：**三次握手是"可靠性"与"通信效率"之间的最佳平衡点**——少一次不可靠，多一次纯属浪费。

### 4.2.3 TCP 连接释放：四次挥手

TCP 是全双工，两个方向的数据流独立关闭，因此释放需要四次交互（每一方向各一次 FIN + 一次 ACK）。客户主动关闭的完整过程：

```
   TCP 客户                                             TCP 服务器
  ESTABLISHED                                         ESTABLISHED
      |                                                     |
      |  ① FIN=1, ACK=1, seq=u, ack=v                        |
      |---------------------------------------------------->|
  FIN-WAIT-1                                          CLOSE-WAIT
  （终止等待1）                                       （关闭等待）
      |                                                     |
      |  ② ACK=1, seq=v, ack=u+1                            |
      |<----------------------------------------------------|
  FIN-WAIT-2                                          （半关闭：服务器仍可发数据）
  （终止等待2）                                              |
      |                                                     |
      |  ③ FIN=1, ACK=1, seq=w, ack=u+1                     |
      |<----------------------------------------------------|
      |                                               LAST-ACK（最后确认）
      |  ④ ACK=1, seq=u+1, ack=w+1                          |
      |---------------------------------------------------->|
  TIME-WAIT                                           CLOSED（撤销 TCB）
  （时间等待，2MSL 后）                                     |
  CLOSED（撤销 TCB）                                        |
```

| 步骤 | 报文 | 关键字段 | 状态变化 | 说明 |
|---|---|---|---|---|
| ① | TCP 连接释放报文段 | FIN=1、ACK=1，seq=u（= 客户已传送数据最后字节序号+1），ack=v | 客户→FIN-WAIT-1 | 表示"我没数据要发了"，同时确认之前收到的数据 |
| ② | 普通确认报文段 | ACK=1，seq=v，ack=u+1 | 服务器→CLOSE-WAIT；客户→FIN-WAIT-2 | 确认客户的 FIN；此时进入**半关闭** |
| ③ | TCP 连接释放报文段 | FIN=1、ACK=1，seq=w，ack=u+1 | 服务器→LAST-ACK | 服务器数据也发完了；seq=w 说明半关闭期间可能又发了数据 |
| ④ | 普通确认报文段 | ACK=1，seq=u+1，ack=w+1 | 客户→TIME-WAIT；服务器收到后→CLOSED 并撤销 TCB | 客户在 2MSL 后撤销 TCB 进入 CLOSED |

两个概念必须讲透。

**半关闭（half-close）**：第②步之后，客户已无数据要发，但服务器若还有数据要发，客户仍须接收——从服务器到客户这个方向的连接并未关闭。因此"客户发 FIN"只释放了客户→服务器一个方向。这也是 FIN 与 RST 的本质区别：FIN 是"我这一半说完了"，RST 是"整条连接立即作废"。半关闭状态可能持续一段时间，这正是第③步 seq 要用 w 而不是 v+1 的原因。

**TIME-WAIT 与 2MSL**：MSL 是最长报文段寿命（Maximum Segment Lifetime），建议为 2 分钟。客户进入 TIME-WAIT 后还要经过 4 分钟（2×MSL）才进入 CLOSED，这是从工程上考虑的；对现在的网络，MSL 取 2 分钟可能太长，因此 TCP 允许不同实现根据具体情况使用更小的 MSL 值。

> 补充：TIME-WAIT 等 2MSL 有两个目的——① 保证最后一个 ACK 能到达服务器（若 ACK 丢失，服务器会重传 FIN，客户仍在 TIME-WAIT 才能重发 ACK）；② 让本连接产生的旧报文段在网络中全部消逝，避免它们被后续使用相同四元组的新连接误收。

从攻击视角看，这段机制提供了两个抓手：**FIN 可被伪造**（伪造 FIN 让对端半关闭，业务单向失效）；**TIME-WAIT 状态可被消耗**（大量短连接让端口/TCB 堆积）。同时它也提供了防御线索：出现大量 FIN-WAIT-2 或异常 FIN 报文，往往意味着扫描或半关闭攻击。

### 4.2.4 TCP SYN 泛洪攻击（SYN Flood）

**成因**：TCP 三次握手的第二步之后，服务器就为这条连接**开辟传输控制块（TCB）并存储连接的全部状态信息**，然后等待第三次 ACK。在收到 ACK 之前，这条连接处于**半连接（Half-Open）**状态。协议设计上"先分配资源、后验证对端"，这是效率优先的必然选择，也正是可被榨取的地方。

**攻击步骤**：

| 步骤 | 动作 | 目的 |
|---|---|---|
| 1 | 伪造大量**不同的源 IP 地址**，向目标端口发送大量 SYN 连接请求 | 让每个请求看起来来自不同客户，绕过基于单源 IP 的限速 |
| 2 | 服务器为每个 SYN 回 SYN+ACK，并**分配 TCB、缓存等资源**，连接进入半连接队列 | 消耗内存与队列槽位 |
| 3 | 攻击主机对 SYN+ACK **不作任何响应**（源地址本就是伪造的，报文发给了不存在的或无关的主机） | 半连接无法转正，只能等超时 |
| 4 | 服务器超时重传 SYN+ACK，等待 SYN Timeout 后丢弃该连接 | 每个半连接占用资源的时间被拉长到秒级 |
| 5 | 半连接数量超过系统允许上限，服务器**不再接受任何新的 TCP 连接请求** | 正常客户无法建立连接，服务不可用 |

关键点在于"放大比"：攻击者只需极小的上行带宽（一个 40~60 字节的 SYN），就能让服务器维持一个占用数百字节 TCB 的半连接数秒。防御因此不能靠"识别恶意 IP"（地址是伪造的、每包都不同），只能靠**改变资源分配时机**或**验证源的真实性**。

**防御一：SYN 缓存（SYN Cache）**。服务器收到 SYN 时**不立即分配完整的 TCB**，只记录最小化的状态信息；同时生成一个随机的"秘密位"（基于客户端 IP、端口号等信息经哈希函数生成，攻击者无法伪造），把它嵌入 SYN+ACK 报文中。只有当客户端返回的 ACK 携带正确的秘密位时，服务器才分配完整 TCB 并建立连接。要点：把"完整资源分配"推迟到"源已被验证"之后，半连接队列的单项成本从"一个 TCB"降到"几十字节"。

**防御二：同步 Cookie（SYN Cookie）**。收到 SYN 时按源/目的 IP、端口、时间等报头信息计算 Cookie，并**把该 Cookie 直接作为 SYN+ACK 的初始序列号**发出——服务器此时完全不保存状态。客户端返回 ACK 时，服务器重新按报头信息计算 Cookie，与 ACK 中的确认序列号比对，一致则判定连接合法，此时才分配资源、建立连接。要点：**用序号字段承载状态**，从而做到"零状态建连"；代价是无法在 SYN 阶段协商选项（如窗口扩大），部分信息要延后处理。

**防御三：源认证（Anti-DDoS 系统的源认证）**。思路是先判断请求是否来自真实源，分两级：

| 类型 | 服务器响应 | 真实客户端行为 | 虚假源行为 |
|---|---|---|---|
| 基本源认证 | 回**带有错误确认序号**的 SYN+ACK | 发现确认号不对，回 **RST** 要求重新建连 | 无任何响应（收不到或不管） |
| 高级源认证 | 回**带有正确确认序号**的 SYN+ACK | 回 **ACK**，正常继续 | 无任何响应 |

两级认证的差别是"逼出什么反应"：基本认证利用真实协议栈对错误 ack 的纠错行为（RST），高级认证则要求真实客户端完成正常握手。凡是"没反应"的源，就判定为虚假源并丢弃/加入黑名单。这比 SYN Cookie 更强的地方在于它在**防护设备**上完成，不改造服务器协议栈。

### 4.2.5 TCP RST 攻击

**RST 的语义**：RST 用来强制、立即终止一个 TCP 连接。当一端收到无法处理的报文（端口未开放、连接超时、应用层异常关闭等）时，会发送 RST 断开连接，而且**不需要 ACK 来确认**。发出或收到置 RST 的包后，相应的内存、端口等连接资源都会被立即释放。

正因为"立即释放、无需确认"，RST 成了最经济的断链工具：一个几十字节的报文就能让一条已建立的连接作废，且不需要任何应用层凭据。

**攻击条件**：TCP 的实现引入了 **32 位随机的序列号和确认号**以及 **16 位随机的源端口号**，攻击者要把恶意报文注入目标 TCP 流，必须正确预测这些值。具体到 RST 伪造，需要同时满足：

1. **端口一致**：源/目的端口与真实流相反且完全一致（四元组匹配）；
2. **序列号落在接收窗口之内**：否则接收方会把它当作过期/异常报文丢弃（或回 ACK 纠正）；
3. **获知 A 的 IP、端口以及 A 与 B 的 TCP 序列号**。

**获取这些信息的两条路径**：

| 位置 | 手段 | 说明 |
|---|---|---|
| 与受害者位于同一内网 | 欺骗或嗅探 | 二层可达即可抓包拿到四元组与当前序号；配合 ARP 欺骗可中转流量 |
| 处于不同网络 | 伪造大量 RST，随机猜测端口和序列号 | 盲打；成功率取决于窗口大小与序号随机性，靠数量取胜 |

**攻击效果**：C 伪造的 RST 使 B 认为"来自 A 的连接有错误"，B 将**丢弃与 A 连接缓冲区上的所有数据**，并强制关闭连接。这不仅能断链，还会造成数据丢失——缓冲区中未被应用读取的数据随 TCB 一起被销毁。

**防御**（Anti-DDoS 对恶意 RST 报文的处理）：原则是"**不能信任所有 RST 包**"，落地为三条：

- **速率限制**：对单位时间内到达的 RST 数量设阈值，异常突增即限流（正常网络中 RST 是低频事件）；
- **会话校验**：RST 必须命中一条已存在的会话表项，且其四元组、方向与表项一致；对不存在的会话直接丢弃；
- **序列号验证**：严格校验 RST 的序列号是否精确落在当前接收窗口内（而非宽松接受），并可要求 RST 的 ack 与当前发送序号匹配。

### 4.2.6 TCP 会话劫持

**定义**：TCP 会话劫持（TCP Session Hijacking）是指劫持通信双方**已建立**的 TCP 会话连接，假冒其中一方与另一方通信，以达到控制会话的目的。

**成因**：使用 TCP 通信需要维护两段序列号（两个方向各一段），TCP 用它们确保连接同步与安全通信。在通信过程中双方序列号是**相互依赖**的——收到对方的 ack 就能推出对方期待的序号，发包后自己的序号递增。因此**会话劫持的关键是预测正确的序列号**：一旦序列号可被预测，攻击者就能在不打断连接的情况下插入自己的报文，双方都察觉不到第三方存在。

**攻击步骤**：

| 步骤 | 动作 | 说明 |
|---|---|---|
| 1 | 嗅探/截获客户端与服务器之间的 TCP 报文 | 拿到四元组、当前 seq/ack、窗口大小 |
| 2 | 依据截获报文推算下一个合法序列号 | 序列号的相互依赖性使推算可行 |
| 3 | 伪造源地址为客户端的 TCP 报文发给服务器 | 携带落在接收窗口内的正确序号 |
| 4 | 服务器先收到伪造报文 → 接受并更新会话状态 | 服务器认为这就是客户端，指令被执行 |
| 5 | 攻击者凭从服务器获得的连接信息，与被攻击客户端建立连接 | 完成双向劫持，通信双方毫无察觉 |
| 6 | 后续数据经由第三方攻击者中转 | 形成"合法两端 + 中间人"的隐蔽通道 |

与 RST 攻击的差别要分清：RST 攻击的目标是**破坏**（让连接死掉），会话劫持的目标是**接管**（让连接活着但由攻击者说话）。前者只需序列号"落窗"，后者需要序列号"精确接续"并持续保持同步，技术门槛更高，危害也更大——可以冒充已登录用户执行操作，绕过所有基于"连接已认证"的信任。

**防御**（PPT 给出四条，覆盖加密、检测、底层协议三个层次）：

| 措施 | 做法 | 针对的环节 |
|---|---|---|
| 对 TCP 会话加密 | 使用 SSH 代替 Telnet、使用 SSL 代替 HTTP，或使用 IPsec/VPN | 使攻击者即使截获也无法读出内容、无法推出可用序号 |
| 检测非同步状态 | 若不断收到在接收窗口之外的数据或确认报文，即可确认遭到 TCP 劫持 | 劫持必然造成"预期的 seq"与"实际收到的 seq"错位 |
| 防范 ARP 欺骗 | ARP 欺骗是 TCP 会话劫持中典型的获取序列号的网络嗅探技术 | 切断同网段嗅探与中间人这一前置条件 |
| 监听网络流量中的 ACK 包 | 若网络中出现大量 ACK 包，可能已遭遇会话劫持 | 劫持者为保持同步需不断发 ACK，形成异常统计特征 |

> 防御的逻辑顺序值得记住：加密是根本（让预测失去意义），检测是补救（发现已发生的劫持），防 ARP 欺骗是清场（去掉最省力的嗅探路径），统计 ACK 是工程化的告警手段。

### 4.2.7 序列号可预测性的历史成因

TCP 的许多攻击之所以成立，根子在 1970 年代的**设计假设**：

- 1974 年，Vint Cerf 和 Bob Kahn 提出 TCP；
- 1980~1990 年代发现：TCP 初始序列号（ISN）可被预测；
- 早期网络环境是学术/军事内部网，参与者彼此信任，默认**无恶意**存在；
- 设计哲学是**可靠性优先，安全性后置**。

于是 ISN 生成算法长期使用"时间计数器 + 固定增量"这类可推算的方式，攻击者只要采样几个连接的 ISN 就能外推下一个值，从而伪造 SYN、伪造 RST、注入数据。后续的演进方向就是 **ISN 生成从"可预测"到"不可预测"**：引入密码学随机源（并混入四元组、时间等熵）生成 32 位 ISN，使预测难度从"解方程"变成"猜 2^32"。这也解释了为什么今天的 RST 攻击与盲劫持多要靠"海量尝试"而非"精确计算"。

## 4.3 UDP 协议及其安全

### 4.3.1 UDP 的报文结构

UDP 是一种无连接的、简单的传输层协议，三个特征互为因果：

- **无连接**：发送数据前不需要建立连接，只要知道对方地址信息就可以直接发送；
- **不可靠**：使用尽最大努力交付，不保证可靠交付，因为没有确认机制和重传机制；
- **面向报文的**：应用层给 UDP 多长的报文，UDP 就照样发送，一次发一个完整报文。

"面向报文"的后果是应用必须自己选报文大小。接收方 UDP 对 IP 层交上来的用户数据报，去掉首部后原封不动地交付上层，**一次交付一个完整报文**，既不合也不拆。因此：

- 报文太长：交给 IP 层后可能被**分片**，降低 IP 层效率，且任一分片丢失就整包作废；
- 报文太短：IP 数据报首部的相对长度太大（8 字节 UDP 首部 + 20 字节 IP 首部 vs 极少数据），同样降低效率。

UDP 首部只有 4 个字段，共 **8 字节**：

| 字段 | 长度 | 作用 | 安全相关性 |
|---|---|---|---|
| 源端口 | 2 字节 | 发送方使用的端口号；**可选项**，需要对方回信时选用，不需要时可置 0 | 置 0 时更难溯源，为反射攻击提供了便利 |
| 目的端口 | 2 字节 | 接收方使用的端口号，终点交付时必须用到；分用找不到对应进程则丢弃该报，并回 ICMP"端口不可达" | 开放的高危 UDP 端口（如 11211）是反射攻击的入口 |
| 长度 | 2 字节 | UDP 报文的整个长度（首部+数据），**不含伪首部**；最小 8，最大 65535，限制一个完整 UDP 报文不超过 64K | 长度与实际不符是构造畸形包、绕过检测的常见手法 |
| 校验和 | 2 字节 | 对"伪首部"+UDP 首部+数据做二进制反码求和，检验传输是否出错，有错则丢弃 | 唯一（且很弱）的完整性手段；可被直接算好伪造 |

**伪首部（pseudo header）** 是理解 UDP 校验和的关键：它**不是** UDP 用户数据报真正的首部，只是在计算校验和时**临时**添加在 UDP 用户数据报前面，拼成一个临时的 UDP 用户数据报参与运算。它共 12 字节：

| 伪首部字段 | 长度 | 取值 |
|---|---|---|
| 源 IP 地址 | 4 字节 | 取自 IP 首部 |
| 目的 IP 地址 | 4 字节 | 取自 IP 首部 |
| 全 0 | 1 字节 | 固定为 0 |
| 协议号 | 1 字节 | 固定为 17（表示 IP 首部协议字段为 17，即承载 UDP） |
| UDP 长度 | 2 字节 | UDP 首部+数据的长度 |

引入伪首部的意义在于**扩大校验范围**：IP 数据报只检查自己的首部，UDP 校验和检查 UDP 首部+数据，而通过伪首部又额外把 IP 首部的源/目的 IP 地址纳入校验。这样若地址在传输中被篡改，校验和会失配。计算方法与结果判定：

1. 发送方在 UDP 用户数据报前临时加上 12 字节伪首部；
2. 把整个临时报文按 16 位分组，做**二进制反码求和**；
3. 把结果取反码填入校验和字段（若结果为 0 则填全 1），然后去掉伪首部发出；
4. 接收方重新加上同样的伪首部，再按二进制反码求和：**无差错时结果为全 1**，否则说明有差错，丢弃该报。

该方法的评价要背下来：**简单、处理速度高，但检错能力不强**。它只能发现随机比特错误，无法抵御有意的伪造——攻击者可以自行算好校验和填入，因此 UDP 校验和不构成任何安全边界。

### 4.3.2 实时传输协议 RTP

**实时传输协议（Real-time Transport Protocol, RTP）** 为 IP 上的语音、图像等需要实时传输的多媒体数据提供端到端的传输服务和流同步，配合**实时传输控制协议（Real-time Transport Control Protocol, RTCP）** 一起使用。RTP 与 RTCP 位于传输层，通常基于 UDP，也支持 TCP。

RTP 报文由**报头**和**有效载荷**两部分组成，与安全/同步直接相关的字段有四个：

| 字段 | 作用 | 安全/工程意义 |
|---|---|---|
| 有效载荷类型 | 说明有效载荷的类型，如 GSM 音频、JPEG 图像等 | 明文可读，可被用于流量识别与指纹匹配 |
| 时间戳 | 反映该 RTP 报文第一个八位组的采样时刻，是 RTP 实现音视频同步的**核心字段**；接收方据此决定何时播放 | 时间戳被篡改会造成播放抖动或错序，且难以被应用层察觉 |
| 同步源标识符 SSRC | 标识产生媒体流的源（如一个麦克风或摄像头），同一 RTP 会话中 SSRC 唯一 | 伪造 SSRC 可冒充媒体源，注入伪造音视频 |
| 参与源标识符 CSRC | 当报文由混合器把多个源的流混合而成时（如音频会议把多人语音混成一路），CSRC 列表标识所有贡献此包的原始源 SSRC | 混合场景下溯源依赖 CSRC，被伪造则无法定位真实发言者 |

RTP 本身不提供加密与完整性保护，这是它"轻量"的代价：报文头与载荷默认明文，任何中间人都能读取甚至替换媒体内容。工程上需由 SRTP 等扩展补上，这一思路与后文"用 SSL/TLS 给 TCP 应用加安全层"完全一致——传输层协议只负责搬，安全由叠加层负责。

### 4.3.3 快速 UDP 互联网连接协议 QUIC

先看现实动因：2026 年前 2 个月，我国移动互联网累计流量达 **666.7 亿 GB**，其中短视频、直播等实时应用占据主要份额。这些应用的传输层大量采用基于 UDP 的优化方案（如 QUIC、WebRTC）。原因很直接：

- 这类应用**可以容忍偶尔丢包**（画面小卡顿），但**无法容忍高时延**（画面卡死）；
- UDP 的轻量化设计契合时效性需求——没有队头阻塞、没有握手等待、重传策略由应用自己决定。

由此得到一条工程哲学：**没有最好的协议，只有最合适的方案**，实事求是、因地制宜。

**QUIC（Quick UDP Internet Connection）** 是 Google 在 2013 年推出的传输协议，它整合了 TCP 的可靠性与 UDP 的速度和效率。按 OSI 视角定义其功能：**在无连接的传输层（UDP）之上，提供可靠、加密、低时延的数据传输服务**。具体地，QUIC 把 TCP 的可靠性（丢失恢复、拥塞控制）、TLS 的安全性（内置加密）与 UDP 的速度结合，通过单一连接 ID 实现连接迁移，并支持 0-RTT 握手。

| 能力 | TCP + TLS（HTTPS） | QUIC |
|---|---|---|
| 建连时延 | 一次完全握手需 **3 个 RTT**（TCP 三次握手 + TLS 握手） | 在 UDP 上增加加密握手，实现 **0-RTT** 安全握手（会话恢复场景） |
| 加密范围 | TCP 首部无任何加密与认证，需与 SSL/TLS 结合才有保密性 | 几乎所有报文都经过认证和加密，任何修改都能被接收端察觉 |
| 连接标识 | 由 IP+端口四元组表示，四元组任一元素变化就需重建连接 | 由 **64 位随机数连接 ID** 标识，ID 不变则连接维持，上层业务感知不到变化，不会中断、不需重连（**连接迁移**） |
| 拥塞控制 | 实现在内核，算法演进受操作系统发布周期约束 | 拥塞控制转移到**应用程序与用户空间**，协议可快速演进；通过 UDP 实现丢失恢复、支持多路复用连接 |

三点对比要能讲出因果：0-RTT 之所以可能，是因为 QUIC 把传输握手与加密握手合并（TCP 的建连与 TLS 建连是串行的两趟）；连接迁移之所以可能，是因为它把"连接身份"从"地址四元组"解耦为"连接 ID"；演进快之所以可能，是因为它跑在用户态。反过来，QUIC 的代价是对 UDP 的依赖——凡封禁 UDP 的网络，QUIC 只能回落到 TCP，且 UDP 反射放大攻击的治理手段（限流 UDP）也会误伤 QUIC。

### 4.3.4 UDP 泛洪攻击与防御

**UDP 泛洪（UDP Flood）** 是拒绝服务（Denial of Service, DoS）攻击中最普遍的**流量型**攻击。它利用 UDP 协议无状态的特性，向目标主机和网络发送大量 UDP 数据包。为在短时间内打出大流量，UDP 泛洪一般采用**分布式拒绝服务（Distributed Denial of Service, DDoS）** 方式，即通过僵尸网络发起。

**成因**：UDP 无连接、无握手、无确认，服务器收到报文后必须"先查端口再决定"，且无法用"三次握手"这类成本门槛筛掉伪造源。同时 UDP 报文可以任意伪造源 IP，使攻击流量不可溯源、不可反向阻断。

**两种打法**：

| 类型 | 手法 | 危害机理 |
|---|---|---|
| 小包攻击 | 使用以太网最小数据包，即 **64 字节**的数据包 | 相同流量下包越小、包数量越多；设备按"包/秒"处理的能力先被打满（PPS 瓶颈），CPU 花在查表与中断上 |
| 大包攻击 | 使用超过以太网最大传输单元（MTU）的数据包 | 目标服务器收到大包后需**分片与重组**，消耗设备性能并造成网络拥堵；重组缓冲区被打满后正常分片也被丢弃 |

实际攻击中，攻击者通过僵尸网络向目标设备发送大量伪造的 UDP 报文，这种报文一般为**大包且速率非常快**，通常造成链路拥塞甚至网络瘫痪。注意"小包打 PPS、大包打带宽与重组"这一分工，是判断攻击类型与选择清洗策略的依据。

**防御**：

| 手段 | 做法 | 说明 |
|---|---|---|
| 按 IP 限流 | 以某个 IP 地址为统计对象，对到达该 IP 的 UDP 流量统计并限流，超过部分丢弃 | 保护单个目标不被单点打爆 |
| 按会话限流 | 以 UDP 会话（五元组）为统计对象，若某会话 UDP 报文速率达到告警阈值，则锁定该会话，后续命中该会话的报文全部丢弃 | 精细到流，误杀面小 |
| 指纹学习 | 利用攻击报文**高度相似**的特性，收集相同特征的字符串来检测；对有规律的 UDP 攻击报文负载特征自动提取指纹，作为过滤条件自动应用 | 同一工具生成的攻击包载荷往往重复，指纹命中率高、误杀率低 |

指纹学习的机制值得展开：如果相同的特征频繁出现，就会被学习成指纹；后续命中该指纹的报文被判定为攻击报文，并作为攻击特征进行过滤。它与限流的差别是——限流按"量"下手，指纹按"形"下手，前者对变异攻击无效，后者对随机填充载荷无效，实战需组合使用。

### 4.3.5 UDP 反射放大攻击与防御

**反射攻击**是指利用路由器、服务器等设施（称为**反射器**）对请求产生应答，从而反射攻击流量、并隐藏攻击源的 DDoS 方法。**放大攻击**的实质是利用反射器对请求数据量进行放大：一些网络服务协议存在请求与响应数据量**不对称**的情况，通常响应数据量远大于请求数据量——即"小请求、大响应"。例如 HTTP 请求可能只有几百字节，而响应可以是几 KB 到几 GB；DNS 请求很小，响应可能包含多条记录。

两个条件叠加，攻击者就获得了三重收益：**流量放大**（一份上行换几十上百份下行）、**源地址隐藏**（受害者只看到反射器的 IP）、**反射器代劳**（攻击者无需自身带宽）。

```
攻击者(伪造源IP=受害者)        反射器(如 Memcached:11211)          受害者
        |                                 |                          |
        |  ① 小请求(几十~几百字节)         |                          |
        |-------------------------------->|                          |
        |                                 |  ② 大响应(放大数万倍)      |
        |                                 |------------------------->|
        |                                 |                          |
        |  ③ 受害者只看到反射器的地址，无法回溯到攻击者              |
```

**以 Memcached 为例的完整链条**：Memcached 是一款开源的高性能分布式内存对象缓存系统，用于动态 Web 应用以减轻数据库负载；它**支持 UDP 协议的访问请求，默认 UDP 端口 11211**。攻击者通过端口扫描即可收集到开放 UDP 11211 的 Memcached 服务器，并利用它们发起攻击：

1. 向 Memcached 服务器的 UDP 11211 端口发送**伪造源 IP** 的小字节请求（源 IP 填受害者地址）；
2. Memcached 服务器收到后产生**数万倍大小**的响应，发回"伪造源 IP 地址"，即被攻击目标；
3. 规模化时采用 DDoS 方式：控制大量僵尸主机、冒充攻击目标，向大量 Memcached 服务器发起请求，返回受害者的响应数据包呈**指数级上升**。

**防御**（限速要"多种搭配组合"，因为单一维度总有绕过路径）：

| 限速维度 | 作用 |
|---|---|
| 目标 IP + 源端口 | 用于控制反射性攻击，且可预防未知的反射协议（同一目标、同一源端口的大量响应是反射的典型形状） |
| 源 IP | 对单个请求源 IP 做整体控制 |
| 目标 IP | 对单个攻击目标 IP 做整体可用性控制（保业务不断） |
| 源 IP + 源端口 | 降低部分大客户源 IP 在访问请求时的副作用影响（避免误伤大客户） |
| 目标 IP + 目标端口 | 适用于目标 IP 端口开放范围较大时，提高业务端口可用率、降低目标整体影响 |

另有三种非限流手段：

- **指纹学习**：检查 UDP 报文负载内容，自动提取攻击指纹特征，基于特征自动丢弃或限速；
- **白名单**：对已知的 UDP 反射协议，把 DNS 服务器等可信反射器的 IP 加入白名单，封禁其余源 IP 的 53 号端口请求包——只允许"合法反射器"发来的响应，堵住伪造反射；
- **地理位置过滤器**：遭遇反射攻击时，优先从**用户量最少**的地理位置的源 IP 开始封禁阻断，逐步扩大到异常地理位置全部封禁，使流量降至可控范围。选"用户最少"的地方先动手，是为了把业务损失压到最低。

> 补充：反射放大的通用治理前提是"关闭不必要的 UDP 服务 + 禁止网络允许伪造源地址的包外出"（入口/出口过滤），PPT 只讲了防护设备侧的限速与指纹，未展开源头治理。

## 4.4 传输层的安全策略：SSL

### 4.4.1 SSL 的定位与三个安全目标

传输层本身不提供任何安全能力：TCP 首部明文、无认证、无加密；UDP 更是连状态都没有。**安全套接字层（Secure Socket Layer, SSL）** 通过引入数据加密和认证机制，为用户的隐私和数据完整性提供保护。版本演进如下：

| 时间 | 事件 |
|---|---|
| 1994 | 网景公司（Netscape）设计 SSL 1.0 版，但未发布 |
| 1995 | Netscape 发布 SSL 2.0 版，很快发现严重漏洞 |
| 之后 | SSL 3.0 成熟；IETF 在 SSL 3.0 基础上标准化设计了 TLS 协议 |
| 2006 | TLS 1.1 |
| 2008 | TLS 1.2 |
| 2018 | TLS 1.3（目前的新版本） |

传输层安全机制的优点是提供了基于**进程对进程**（而不是主机对主机）的安全服务和加密传输信道，利用公钥体系进行身份认证，安全强度高，并支持用户选择加密算法。它包含三项功能：

| 功能 | 内容 | 是否必备 |
|---|---|---|
| 服务器鉴别 | 支持 SSL 的客户端通过验证来自服务器的证书，鉴别服务器的真实身份，并获得服务器的公钥 | 必备 |
| 客户鉴别 | 用于服务器证实客户的身份 | **可选**安全服务 |
| 加密会话 | 加密客户与服务器之间传送的所有报文，并检测报文是否被篡改 | 必备 |

**位置**：从 TCP/IP 协议栈层次关系看，SSL 位于**应用层和传输层之间**。应用层的数据在传输之前首先封装在 SSL 报文中，然后把 SSL 报文封装在 TCP 报文中再传输。这个位置决定了它的通用性——应用无需改动即可获得加密信道，且安全边界精确到进程（同一主机的其他进程不受影响），比 IPsec 的主机对主机模式更细。

### 4.4.2 SSL 体系结构与四个子协议

SSL 的整体思路分两段：**先用非对称密码学解决"信任与密钥"问题，再用对称密码学解决"速度"问题**。客户端和服务器基于非对称加密算法相互鉴别，协商加密算法和基于对称加密算法的会话密钥；此后在记录协议中使用这个会话密钥来加密双方通信。这一"握手协商 → 记录加密"的分层，是理解 SSL/TLS 全部流程的主线。

SSL 由四个子协议组成，分工明确：

| 子协议 | 职责 | 关键点 |
|---|---|---|
| 握手协议（Handshake） | 客户端与服务器通过请求/应答方式统一 SSL 连接中的参数；通过数字证书鉴别对方身份合法性；鉴别通过后进入密钥协商阶段；双方都产生会话对称密钥后，通过发送 Finished 消息结束握手 | 建立安全能力 + 握手完成 |
| 更改密码规范协议（Change Cipher Spec） | 在握手过程中安全参数协商好之后、Finished 消息之前发送；双方都可发送，通知对方启用协商好的安全参数 | 实现"从明文切换到加密""从旧加密状态切换到新加密状态"的状态跃迁 |
| 警告协议（Alert） | 将警告消息及其严重程度传递给 SSL 会话中的主体 | 双重功能：报错机制（发现问题即通告对等端）+ 安全断连机制（以可认证方式关闭连接；若警告是致命级别，双方应立即关闭连接） |
| 记录协议（Record） | SSL 的数据承载协议，规定报文格式与处理过程：把上层数据分块压缩，尾部加 MAC 保证完整性，最后用握手协商好的保密参数加密 | 握手报文与应用数据都要封装成"记录"的形式投递 |

**记录协议的五个处理步骤**（顺序不能错，考试常考）：

1. 把来自上层协议的数据进行**分组**（分块）；
2. 对每个分组进行**压缩**；
3. 计算压缩数据的 **MAC 值**，放置在尾部；
4. **加密**压缩数据和 MAC 值；
5. 在密文上增加 **SSL 头**。

注意"MAC 在内、加密在外"的顺序含义：先算 MAC 再整体加密（MAC-then-Encrypt），使 MAC 覆盖明文、密文覆盖 MAC，接收方先解密再验 MAC。这一设计后来被发现存在填充预言等隐患，TLS 1.3 改为只保留 AEAD 类算法，不再使用这种组合方式。

### 4.4.3 SSL 连接与会话

SSL 区分两个层次的概念，这是本章最容易混淆的一对：

- **SSL 连接（connection）**：能够提供合适服务类型的传输。连接是**点对点**关系，每个 SSL 连接在特定的通信过程中存在，并且每个连接都与会话相关。
- **SSL 会话（session）**：客户机与服务器之间的 SSL 协议对等实体之间的关联。会话由握手协议创建，握手协议定义了一组密码安全参数，这些参数**可以被多个连接公用**。

一句话总结：**连接是为了在客户端和服务器之间建立安全的传输；会话是为了提高效率，通过定义一组可被多个连接共享的密码安全参数，减少重复的安全协商过程**。理解方式：一个会话可以派生多条连接（例如浏览器对同一站点并发多个 TCP 连接），握手只做一次，密钥材料复用。

**连接状态参数**（每条连接独有，随连接结束而消失）：

| 参数名 | 说明 |
|---|---|
| 随机字 | 每个连接中服务器和客户机选择的字节序列 |
| 服务器写 MAC 密钥 | 服务器发送数据时用于计算 MAC 的密钥 |
| 客户机写 MAC 密钥 | 客户机发送数据时用于计算 MAC 的密钥 |
| 服务器写密钥 | 服务器对数据加密、客户端对数据解密时使用的对称密钥 |
| 客户机写密钥 | 客户机对数据加密、服务器对数据解密时使用的对称密钥 |
| 初始化向量 | 被握手协议初始化后，每个记录集密文块作为下一个记录的初始化向量 |
| 序列号 | 为连接的传输和接收报文生成单独的序列号 |

注意"写密钥/MAC 密钥"是按**发送方**命名的：服务器写密钥用于服务器加密，客户端用它解密。因为 SSL 为两个方向各配一套密钥，所以一共四把（两把加密 + 两把 MAC），这是"双向独立密钥"的典型设计，可防止反射式重放。

**会话状态参数**（可被多条连接共享，也是"恢复会话"的依据）：

| 参数名 | 说明 |
|---|---|
| 会话标识符 | 由服务器产生的、用来确定活动或可恢复会话状态的随机字节序列 |
| 对等实体证书 | 对等实体的 X.509v3 证书，该状态元素可为空（如客户端不认证时） |
| 压缩方法 | 加密前用于压缩数据的算法 |
| 加密规格 | 指定批量数据加密算法和用于 MAC 计算的哈希算法，指定密码属性 |
| 主控密钥 | 由客户机和服务器共享的 48 字节密码 |
| 是否可恢复 | 用来确定会话是否可用于初始化新连接的标志 |

> 提示：主控密钥的长度应为 **48 字节**（PPT 会话参数表中写作"48 位"，与 4.5.2 中 TLS 的"48 字节"表述不一致，以 48 字节为准）。

### 4.4.4 SSL 协议流程

典型的 SSL 通信过程完成三件事，正好对应三个子协议：

1. **建立 SSL 连接**：实现身份鉴别，协商加密算法以及密钥（握手协议、更改密码协议）；
2. **传输数据**：利用协商好的算法和密钥处理数据（记录协议）；
3. **断开连接**：数据传输完成后，通过**可认证的方式**断开（警告协议）。

以 HTTPS 为例（HTTPS 的 TCP 端口号为 **443**）的完整交互：

| 阶段 | 动作 | 关键点 |
|---|---|---|
| 1 | 客户端发起 TCP 连接（三次握手）到 443 端口 | 先有可靠信道，才有安全信道 |
| 2 | 客户端发送 ClientHello：SSL/TLS 版本、支持的加密套件列表、客户端随机数 | 明文，宣告能力 |
| 3 | 服务器回 ServerHello（选定加密套件、服务器随机数）+ 服务器证书 | 证书是身份与公钥的载体 |
| 4 | 客户端**使用该证书的认证中心 CA 公开发布的公钥验证该证书** | 校验签名、有效期、域名、吊销状态；通过则获得服务器公钥 |
| 5 | 客户端生成预主密钥，用服务器公钥加密后发送（可选：同时做客户端证书鉴别） | 非对称加密只用来传密钥，不用来传数据 |
| 6 | 双方以**预主密钥和随机数作为输入，在本地计算所需的会话密钥** | 相同的输入 + 相同的算法 = 相同的密钥，密钥从不在网上明文传输 |
| 7 | 双方发送 ChangeCipherSpec 切换加密状态，随后互发 Finished 校验握手完整性 | Finished 内含握手表摘，可发现协商过程被篡改 |
| 8 | 应用数据经记录协议分块、压缩、加 MAC、加密、加 SSL 头后传输 | 此后全部密文 |
| 9 | 传输结束，用警告协议（close_notify）以可认证方式关闭连接 | 防止截断攻击 |

两个细节要能解释"为什么安全"：

- **为什么要随机数？** 若只用预主密钥派生会话密钥，同一对端每次连接都会得到相同密钥，重放即可解密历史流量。客户端随机数与服务器随机数保证每次连接的密钥材料都不同（前向差异）。
- **为什么用 CA 公钥验签？** 非对称加密只能保证"用某公钥能解开"，不能保证"这个公钥属于谁"。证书把公钥与身份绑定，CA 的签名把这种绑定传递成可验证的信任链；客户端本地预置 CA 根证书，因此无需在线信任第三方。

## 4.5 TLS

### 4.5.1 TLS 与 SSL、DTLS 的关系

IETF 在 SSL v3.0 的基础上制定了 TLS 1.0 规范，目前已演进到 TLS 1.3 版本。TLS 在结构上与 SSL 协议相同（同样分层、同样四个子协议），差异在于细节：密钥计算方式、告警类型、MAC 计算与填充方式、密码套件命名（TLS 用 TLS_ 前缀）等。

TLS 基于传输层面向连接的可靠 TCP 协议为上层应用提供安全保护；针对传输层无连接的、尽力而为的 UDP 协议，TLS 经过适配也可以在 UDP 上运行，被称为**数据包传输层安全性协议（Datagram Transport Layer Security, DTLS）**。适配要解决的核心问题是 UDP 会丢包、乱序、重复——TLS 的握手机制假设报文可靠有序，DTLS 因此为握手报文加上显式序号与重传定时器，并允许接收窗口内的乱序到达。

传输层安全实例的部署形态很直观：SSL/TLS 作用于 TCP/IP 体系结构的应用层与传输层之间，在应用层中使用 SSL/TLS 最多的协议是 HTTP。两端各自的协议栈自上而下是"应用层（基于 HTTP 的安全应用）→ SSL/TLS → 传输层（基于 TCP 连接的可靠传输）→ 网际层（基于 IP 的无连接不可靠传输）→ 网络接口层"，中间经因特网传输。效果是在 TCP 连接上建立起一个安全通道：中间任何一跳只能看到密文与流量特征，看不到请求内容。

### 4.5.2 TLS 协议结构

TLS 逻辑上划分为两层：

| 层 | 作用 |
|---|---|
| TLS 记录协议（Record Protocol） | 通过握手协议建立的密钥保护高层协议数据；**承载的业务不同，加密密钥不同** |
| TLS 握手协议（Handshake Protocol，广义） | 用于通信双方相互认证、协商加密模式和参数、以及建立预主密钥 |

握手层内部包括四个协议：**TLS 更改密码规范协议、TLS 警告协议、TLS 握手协议（狭义）、TLS 应用数据协议**。其中应用数据协议是"安全通道上的业务搬运工"——它本身不做任何密码运算，只是把应用字节流交给记录协议加密后发出。

"承载的业务不同，加密密钥不同"这句话常被考到：TLS 允许在同一连接上为不同高层协议使用不同密钥（早期为多协议复用设计），而 SSL 只有一套。这也是 TLS 比 SSL 更适合"一条连接跑多种业务"的原因。

### 4.5.3 TLS 连接与会话参数

TLS 在安全参数与状态元素之间做区分，SSL 不做这种区分——这是两者在规范层面的主要结构差异之一。

**TLS 连接的安全参数（静态——"用什么保护"）**：

| 参数名 | 说明 |
|---|---|
| 连接端（connection end） | 包括"客户端"和"服务器端"的信息 |
| 批量加密算法（bulk encryption algorithm） | 包括其密钥大小、是块密码还是流密码等 |
| MAC 算法（MAC algorithm） | 用于消息认证的算法 |
| 压缩算法（compression algorithm） | 数据压缩算法 |
| 主控密钥（master secret） | 在客户端和服务器之间共享的 48 字节密钥 |
| 客户端随机（client random） | 客户端提供的 32 字节值 |
| 服务器随机（server random） | 服务器提供的 32 字节值 |

**TLS 连接的状态参数（动态——"当前进行到哪"）**：

| 参数名 | 说明 |
|---|---|
| 压缩状态（compression state） | 压缩算法的当前状态 |
| 加密状态（cipher state） | 加密算法的当前状态 |
| MAC 密钥（MAC secret） | 连接的 MAC 密钥 |
| 序列号（sequence number） | 在特定连接状态下传输的记录的 **64 位**序列号 |

区分"参数"与"状态"的价值在于：参数在握手结束时确定、整条连接不变；状态随每条记录推进（序列号递增、加密状态含 IV 与剩余块）。TLS 把二者分开建模，使"参数协商"与"记录处理"可以独立实现；SSL 混在一起，实现时容易把可变状态写进共享结构，带来并发与恢复上的隐患。注意 TLS 的记录序列号是 64 位，且**每条记录递增、不随重传重置**——这正是抗重放的基础。

### 4.5.4 TLS PRF

SSL 与 TLS 的另一处主要区别在于**实际生成所需密钥材料的方式**：TLS 使用一种通常称为 **TLS PRF（TLS Pseudo Random Function，TLS 伪随机函数）** 的结构。

它要解决的问题很具体：安全散列函数（Hash Function）的输出长度有限（MD5 为 128 位、SHA-1 为 160 位），而 TLS 一次握手往往需要派生出远超这个长度的密钥材料（主密钥、四把会话密钥、IV、Finished 校验值等）。不能简单地"哈希一次取结果"，必须能把短种子**扩展**成任意长度、且输出在计算上不可预测的比特流。PRF 就是这样一个"密钥扩展器"。

TLS 1.0/1.1 的 PRF 构造分三步：

1. **密钥被分为两半**，S1 和 S2；
2. S1 与 seed 的级联被输入到 P_MD5，S2 与 seed 的级联被输入到 P_SHA-1；
3. 两个输出值经过**逐位加法模 2（XOR）**合并。

```
                 secret
                   |
        +----------+----------+
        |                     |
       S1                    S2
        |                     |
  P_MD5(S1, label+seed)   P_SHA1(S2, label+seed)
        |                     |
        +----------XOR--------+
                   |
              伪随机输出（可截取任意长度）
```

公式写作：

```
PRF(secret, label, seed) = P_MD5(S1, label + seed) XOR P_SHA(S2, label + seed)
```

三个设计要点：

- **双哈希并行**：只要 MD5 与 SHA-1 中有一个未被攻破，PRF 的输出就仍然安全。这是典型的"不把鸡蛋放一个篮子"（防御性设计），在 2004 年后 MD5 被破、SHA-1 出现理论攻击的时代背景下显得很有远见。
- **label 参与运算**：label 是固定字符串（如 "master secret"、"key expansion"、"client finished"），把用途绑定进密钥派生。同样的 secret 与 seed 派生出不同用途的密钥，防止跨用途复用。
- **哈希函数随版本更换**：TLS PRF 组合 MD5 与 SHA-1 仅针对 TLS 1.0 和 TLS 1.1；TLS 1.2 与 TLS 1.3 使用的哈希函数是 **SHA-256**（TLS 1.3 起改用基于 HKDF 的密钥派生，不再使用这种双哈希异或结构）。

## 考点提示

- **传输层的双重定位**：面向通信部分的最高层、用户功能中的最低层；提供的是"应用进程间"的端到端逻辑通信，不是主机到主机。依据：五层体系结构与"逻辑通信"定义。
- **端口号三性质**：16 位/2 字节/0~65535；只有本地意义；TCP 与 UDP 端口空间互不相关。判断"同一端口能否被两进程同时使用"时先看协议与四元组。
- **首部长度换算**：数据偏移 4 位 × 4 字节 = 最大 60 字节首部；减去 20 字节固定部分，选项为 0~40 字节。
- **序号消耗规则**：SYN=1 与 FIN=1 的报文段即使不带数据也消耗一个序号；数据报文按字节消耗。据此可推任何一步的 seq/ack。
- **三次握手不可减为两次**：SYN+ACK 丢失会使服务器单方面认定连接建立（资源浪费）；延迟旧 SYN 会造成无效连接（SYN Flood 的入口）。第三次 ACK 的作用是向服务器证明"客户端在线且收到了我的序号"。
- **三次握手不需增至四次**：服务端的 SYN 与 ACK 相互独立但可合并在一个报文，多一次只增时延不增可靠性——三次是可靠性与效率的平衡点。
- **四次挥手与半关闭**：FIN 只关闭一个方向；第③步 seq=w 而非 v+1，说明半关闭期间服务器可能又发了数据。
- **TIME-WAIT = 2MSL**：MSL 建议 2 分钟 → 等待 4 分钟；目的是保证最后 ACK 可达 + 让旧报文消逝。
- **SYN Flood 的根因**：收到 SYN 即分配 TCB 并进入半连接。防御的共同思路是"推迟资源分配"（SYN 缓存）或"用序号承载状态"（SYN Cookie）或"先验证源"（源认证）。
- **SYN Cookie 与 SYN 缓存的区别**：缓存"少存"，Cookie"不存"（把状态编码进 ISN）。
- **RST 攻击两条件**：四元组一致 + 序列号落在接收窗口内；效果是丢弃缓冲区全部数据并强制断链。
- **RST 攻击 vs 会话劫持**：前者求"破坏连接"（落窗即可），后者求"接管连接"（需精确接续并保持同步）。
- **会话劫持四防御**：会话加密（SSH 代 Telnet、SSL 代 HTTP、IPsec/VPN）、检测非同步状态、防范 ARP 欺骗、监听异常 ACK 流量。
- **UDP 校验和范围**：伪首部 + UDP 首部 + 数据；伪首部 12 字节，第三字段全 0、第四字段为 17；无差错时反码求和结果为全 1；检错能力不强。
- **QUIC 三个卖点**：0-RTT（对比 HTTPS 的 3 RTT）、连接迁移（64 位连接 ID 取代四元组）、全程加密与用户态拥塞控制。
- **UDP 泛洪两类打法**：小包（64 字节）打 PPS，大包（超 MTU）打带宽与分片重组能力。
- **反射放大的两条件**：可伪造源地址 + 请求/响应不对称；Memcached 默认 UDP 11211，是放大倍数最高的入口之一。
- **SSL 四子协议与顺序**：握手 → 更改密码规范 →（应用数据经记录协议）→ 警告；记录协议五步为分组、压缩、加 MAC、加密、加 SSL 头。
- **SSL 连接 vs 会话**：连接是点对点的一次传输；会话是可被多条连接共享的参数集合（含 48 字节主控密钥），用于减少重复协商。
- **TLS 相对 SSL 的三处差异**：区分安全参数与状态元素；用 TLS PRF 生成密钥材料；哈希函数从 MD5+SHA-1 换为 SHA-256（1.2 起）。
- **SSL/TLS 位置结论**：SSL/TLS 位于应用层与传输层之间，安全性基于"进程对进程"，比网络层的"主机对主机"更细。

## 易错点与自测

### 易错概念对比

| 易混概念 | 区别要点 | 记忆钩子 |
|---|---|---|
| 端口号 vs 进程标识符 PID | PID 是本机操作系统内部的进程编号，格式随系统而异；端口号是 TCP/IP 体系统一规定的 16 位进程标识，跨主机可识别 | "PID 只能本地认，端口才能全球认" |
| 熟知端口 vs 短暂端口 | 熟知端口由 IANA 固定分配给知名服务（80/443/53）；短暂端口由操作系统动态分配、通信结束即释放 | "服务器用固定、客户端用临时" |
| 半连接 vs 半关闭 | 半连接指三次握手未完成、服务器已分配 TCB 的 SYN-RCVD 状态（攻击面）；半关闭指四次挥手中一方已发 FIN、另一方向仍可传数据（正常状态） | "半连接没握手完，半关闭只关一半" |
| SYN 缓存 vs SYN Cookie | 缓存只保存最小状态、延迟分配完整 TCB；Cookie 完全不保存状态，把状态编码进 SYN+ACK 的初始序列号 | "缓存少存，Cookie 不存" |
| RST 攻击 vs 会话劫持 | RST 只需序列号落在窗口内即可断链；劫持要求序列号精确接续并能持续同步，目的是冒充身份执行操作 | "RST 杀人，劫持替身" |
| 小包攻击 vs 大包攻击 | 小包（64 字节）以数量打满设备的包处理能力（PPS）；大包（超 MTU）以体积与分片重组消耗带宽和内存 | "小包打包数，大包打带宽" |
| UDP 泛洪 vs 反射放大 | 泛洪是直接向目标灌流量（可用伪造源但无需第三方应答）；反射放大必须借助反射器，且依赖请求/响应不对称获得放大倍数 | "泛洪自己打，放大借刀打" |
| SSL 连接 vs SSL 会话 | 连接是点对点的一次传输，状态参数随连接消失；会话是可恢复、可被多连接共享的参数集合 | "会话是模板，连接是实例" |
| SSL vs TLS | 结构相同（四子协议）；TLS 在 SSL 3.0 基础上标准化，区分参数与状态，改用 TLS PRF，1.2 起用 SHA-256 | "同架构、不同算法细节" |
| TCP 首部固定 20 字节 vs 最大 60 字节 | 20 字节是无选项时的长度；60 字节是数据偏移 4 位上限（15×4）推出的最大值 | "20 起步，60 封顶，中间是选项" |

### 自测题

**1. 三次握手中，客户端发送的第一个 SYN 报文段 seq=x 且不携带数据。第二个报文段的 seq 应是多少？为什么？**
**答**：seq=x+1。TCP 规定 SYN=1 的报文段不能携带数据，但要消耗一个序号，因此客户下一次发送的第一个数据字节序号为 x+1。这也解释了服务器回送 ack=x+1 的含义——"已收到 x，期待 x+1"。

**2. 若把三次握手改成两次（服务器发出 SYN+ACK 后即认为连接建立），会带来哪两类问题？**
**答**：① 无法确认客户端接收能力：SYN+ACK 丢失时客户端认为失败、服务器却占用资源等待数据；② 无法处理延迟的历史 SYN：旧请求到达后服务器直接建立无效连接，攻击者可据此发起 SYN 泛洪。

**3. 服务器遭受 SYN 泛洪时 CPU 与内存都不算紧张，但新连接一律失败。用本章机制解释原因，并给出两种不改客户端的缓解方案。**
**答**：服务器每收到一个 SYN 就分配 TCB 并置为半连接，伪造源地址的客户端永不回第三次 ACK，半连接超时才释放；当半连接数达到系统上限，服务器不再接受任何连接请求。缓解方案：SYN 缓存（只存最小状态，收到正确秘密位才分配完整 TCB）与 SYN Cookie（把状态编码为 SYN+ACK 的初始序列号，零状态建连），或由 Anti-DDoS 设备做源认证。

**4. 攻击者与目标服务器不在同一网段，仍想伪造 RST 断掉一条连接。他必须凑齐哪些条件？成功率受什么限制？**
**答**：必须凑齐四元组（源/目的 IP 与端口与真实流一致）、RST 标志位置 1、且序列号落在接收方当前接收窗口之内。跨网段无法嗅探，只能伪造大量 RST 随机猜测端口与序列号，成功率受 32 位序号随机性与窗口大小的比值限制，只能靠数量取胜；对应的防御是速率限制 + 会话校验 + 序列号验证。

**5. HTTPS 一次完全握手为什么需要 3 个 RTT，而 QUIC 能实现 0-RTT？**
**答**：HTTPS 需先完成 TCP 三次握手（1.5~2 个 RTT 量级）再串行执行 TLS 握手（另外的往返），二者串行叠加约 3 个 RTT；QUIC 直接在 UDP 上把传输参数协商与加密握手合并，并在会话恢复场景复用先前密钥材料，从而实现 0-RTT 发送应用数据。代价是 0-RTT 数据缺乏前向安全性且可被重放，故一般只用于幂等请求。

**6. 某 DNS 服务器被用于反射放大攻击，受害者看到海量来自该 DNS 的响应。请说明攻击链，并给出两条针对性防御。**
**答**：攻击者伪造受害者源 IP，向开放递归的 DNS 服务器发送小体积查询（如 ANY 类型），服务器把数倍于请求的响应发往受害者；规模化时用僵尸网络放大。针对性防御：① 对"目标 IP + 源端口"限速，压制反射流量且可覆盖未知反射协议；② 对已知反射协议加白名单（仅允许可信 DNS 服务器 IP 的 53 端口响应），并配合指纹学习识别同源攻击载荷。

**7. SSL 记录协议为什么先算 MAC 再加密，而不是先加密再算 MAC？**
**答**：MAC 覆盖明文、密文覆盖 MAC，接收方可先解密再验 MAC，从而同时保证完整性与保密性；若先加密再算 MAC，MAC 只保护密文，接收方在验证完整性前就必须解密，容易暴露于填充预言类攻击。这一"MAC-then-Encrypt"组合后来被证明存在隐患，TLS 1.3 因此只保留 AEAD 算法。
